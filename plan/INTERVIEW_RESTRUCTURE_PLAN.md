# 面经知识库改造计划（docs/interview）

> 本文是可执行的改造规格。目标：任何一个 Agent 拿到本文，都能做出与原作者几乎一致的结果。
> 适用范围：`docs/interview/` 全部内容，重点是 `agent/`。基线版本：commit `0a538a9`。
> 本文不进站点（不在 `docs/` 下），不随站点构建。

## 0. 怎么使用本文

1. 先读第 1～3 节，理解为什么改、改成什么样。
2. 动手前先看第 17 节「待确认决策」。状态为「待确认」的项，必须先问用户，不能自行默认。
3. 每改一篇，严格按第 13 节「单篇改造 SOP」走，提交前过第 14 节「自检清单」。
4. 写作时以第 6 节模板、第 7 节写作规范、第 8 节排版规范为准；有冲突时优先级：用户最新指示 > 第 17 节已确认决策 > 本文其他章节 > 现有文档写法。
5. 拿不准某个知识点放哪篇，查第 9 节「知识点唯一归属表」。
6. 每个阶段完成后，在第 18 节「进度记录」里登记。

术语约定：

- 「旧 01·5」指改造前 `agent/01-agent-runtime-architecture.md` 的第 5 题。
- 「新 01-5」指改造后 `agent/01-runtime-harness.md` 的第 5 题。
- 真题编号：`X01`～`X31` 是真题合集里的小红书样本，`N01`～`N35` 是牛客样本（按合集里的序号）。来源文件：`agent/2026-autumn-agent-interview-collection.md`。`X02-12` 表示 X02 这篇帖子的第 12 题。写进站点「真题：」行时只写帖子编号和简称（如 `X02 字节 Agent 一面`），不写题序。

### 1.2 核心诊断：题目和真题脱节

真题合集里的题目，按形态分有四类：

| 形态 | 例子 | 真题占比 | 现有文档 |
| --- | --- | --- | --- |
| 项目下钻 | 「记忆系统为何用 Redis」「为什么选择该阈值」「自研项目为何选 Agent 而不是普通工作流」 | 最高 | 几乎没有通用写法，只在 08/09、Skill·3、MCP·9 有项目稿 |
| 带约束的场景题 | 「工具执行 100 秒而 Agent 只能容忍 50 秒」「用户长期不输入，Graph 状态如何变化」 | 高 | 很少 |
| 选型对比 | 「MCP / FC / A2A 区别」「Workflow 和 Agent 怎么选」 | 中 | 有，但重复 |
| 概念定义 | 「什么是 RAG」「Skill 是什么」 | 低 | 占绝大多数 |

结论：现有文档的主体是概念题，而真题的主体是项目下钻和场景题。改造的主线就是把题目换成真题问法，并补上场景题和项目篇。

### 1.3 为什么 vue.md 质量更高

vue.md 是用户认可的标杆，它做对了五件事，新文档全部照做：

1. 题目就是面试官原话，例如「computed 为什么有缓存？它和 watch 有什么区别？」。
2. H2 按主题分组，H3 题目带序号，组内序号从 1 开始。
3. 每题开头一行 `**核心结论：**`，读一句就知道答案方向。
4. 讲解只讲一遍，讲解之后是 `#### 高频追问`（可选），最后是 `> **面试回答：**` 加列表。
5. 面试回答是列表，每条一个意思，先结论后原因，会主动澄清常见误解。

## 2. 改造目标与验收标准

### 2.1 目标

1. 真题对齐：每道题都能对应到至少一条真题，或者属于真题明显缺失的必要基础。
2. 一处讲透：每个知识点只在一个地方完整讲解，其他地方只用一行加链接引用。
3. 格式统一：全站使用同一套页面模板和单题模板（第 6 节）。
4. 复习友好：导读页有高频 Top 30，每篇末尾有速记表，考前 10 分钟能过完一篇。
5. 项目可讲：项目篇能直接支撑「介绍一下你的 Agent 项目」及其后的下钻追问。

### 2.2 可量化验收标准

| 指标 | 标准 |
| --- | --- |
| 单题「面试回答」长度 | agent 篇：5～8 条列表，总字数 450～900 字（约 2～3 分钟口述）；前端篇沿用 vue.md 的 4～6 条 |
| 「面试回答」思考层次 | 每题必须覆盖第 7.3 节「五层答法」中至少四层，且至少一条是取舍或边界判断 |
| `**核心结论：**` | 每题必有，不超过 80 字 |
| 「考察点」 | agent 篇每题必有一行，说明面试官想听什么、真正区分候选人的是什么 |
| 题目长度 | 不超过 35 字，最多两个问号 |
| 每篇题量 | 6～16 题（RAG 上限 16，其他上限 13） |
| 全局重复 | 第 9 节表中的知识点，只在归属篇有完整讲解 |
| 免责句 | 正文不出现第 7.4 节列出的套话 |
| 代码块 | 全站 0 处 ` ```latex ` |
| 构建 | `npm run check` 与 `npm run build` 全部通过 |
| agent 通用章节总行数 | 约 4,500 行（基线约 7,600 行），项目篇约 800 行 |

## 3. 设计原则

这些是做所有取舍时的依据。遇到本文没写到的情况，按这几条判断。

1. **按面试官的问法组织，不按知识体系组织。** 题目先找真题原话，没有原话就写成面试官会说出口的句子。
2. **先能答，再讲透，最后讲出自己的判断。** 每题第一行就给结论；讲解服务于「把结论讲清楚、扛住追问」；面试回答必须体现候选人的取舍和思考过程，而不是复述定义。和这三个目标无关的知识点删掉。
   - 用户明确要求（改造中途补充）：agent 篇的题目要写细，面试回答要有深度，能凸显个人思考。这一条优先于「少即是多」：可以删重复和冷门知识点，但不能把回答压成只剩结论。
3. **一个知识点只有一个家。** 重复的内容合并到归属篇，其他篇写一行结论加链接。宁可多一次跳转，也不要三处不一致。
4. **通用知识和项目证据分开。** 通用题回答「一般怎么做」，项目篇回答「我具体怎么做的、数据是多少」。通用题最多留一行「项目落点」。
5. **为复习设计，不为完整设计。** 真题里低频、只出现过一次的冷门细节，放追问或附录，不单独成题。
6. **少即是多。** 讲解只选一种主形式（表格、流程图、代码三选一，最多再加一种辅助），不用同一份信息画三遍。
7. **讲真话、不夸张。** 不写「亮点」「加分项」「最关键」；示例数字明确标成示例；不确定的地方写清楚边界，但只写一次。

## 5. 同步脚本与侧栏

现状：`scripts/sync-interview.mjs` 从 `../../interview` 覆盖式同步 agent/、frontend/、coding/，同时生成 `_sidebar.json`。本机没有源仓库；agent 00～06、真题合集和 frontend 多篇不在 CURATED 名单里，一旦跑同步就会被覆盖。

推荐方案（决策 D1，待确认）：本仓库作为唯一源。

1. 删除 `scripts/sync-interview.mjs` 和 package.json 里的 `sync:interview`。
2. `_sidebar.json` 改为手写维护，`rspress.config.ts` 的读取逻辑不变，只把注释改成「面经侧栏手写维护」。
3. index.md 的「维护说明」整节删除，改成一句：「本目录在本仓库直接维护。」
4. 新增或改名文件时，同步修改 `_sidebar.json`、index.md 入口、真题索引。

备选方案：保留脚本，把所有站点侧文件加进 CURATED，并按新目录改 SECTIONS、TITLES、FRONTEND_GROUPS。代价是两边长期不同步，不推荐。

在 D1 确认之前，不要运行 `npm run sync:interview`。

## 6. 模板

### 6.1 页面模板（agent 通用章节）

````markdown

整体知识链：

**信息产生 → 写入筛选 → 分层存储 → 按需召回 → 分区拼接 → 超窗裁剪与压缩 → 评估有没有丢。**

---

## 记忆分层

### 1. 题目……

（单题内容，见 6.2）

### 2. 题目……

---

## Context 拼接

### 1. 题目……

---

## 速记

| 题 | 一句话 |
| --- | --- |
| 记忆为什么要分层 | 生命周期、更新频率、召回方式不同；短期保过程，长期存事实 |
| …… | …… |
````

页面级规则：

1. frontmatter 只写 `title`，和 H1 一致。
2. 头部引用块固定两段：「范围」一行，「必会 + 相关」一行。不写「定位」「边界」「读法」「依据」这类元信息。
3. 「整体知识链」一行，用加粗的箭头链表达本篇主线；概念散、没有主线的篇（如 13 模型基础）可以省略。
4. H2 分组 2～5 个，分组之间用 `---` 分隔。每组 2～6 题，组内 H3 序号从 1 开始（与 vue.md 一致）。
5. 篇末固定是 `## 速记` 表，一行一题，「题」列写题目的短说法（不超过 15 字），「一句话」列和该题的核心结论保持一致（可以缩短，不能换说法）。
6. 页面里不写「和其他篇的分工」「本篇不讲什么」这类章节。归属关系由第 9 节保证，读者需要的跳转在题目内用链接给。

题号引用写法：同篇写「本篇〈Context 拼接〉第 1 题」；跨篇写 `[Memory 与 Context 第 3 题](./02-memory-context)`。这里的题号指页面内 H2 分组下的序号，引用时带上分组名，避免歧义。

### 6.2 单题模板（agent 篇）

agent 篇比 vue.md 多两行：「真题」和「考察点」。因为 agent 题开放度高，同一题不同面试官想听的东西不一样，先把考察点写清楚，回答才能打在点上。

````markdown
### 3. 第十一轮对话该给模型哪些上下文？按什么顺序拼？

真题：N06 抖音电商 Agent 全栈 · X12 阿里千问二面（「短中长期记忆如何拼接、顺序是什么」）

**考察点：** 是否把上下文当成「每轮重建的分区」而不是「不断追加的聊天记录」；能不能说出预算不够时先砍谁、为什么。

**核心结论：** 不是把前十轮原样重发，而是按分区重建：规则 → 相关长期事实 → 任务状态 → 摘要 → 近几轮原文 → 本轮工具结果，并给每个分区定预算。

讲解正文（只选一种主形式：表 / 流程图 / 代码，最多再加一种辅助）

```text
1. System 规则         静态、版本化、永远保留
2. 长期记忆 top-k       本轮相关才出现，没有就不放
...
```

#### 高频追问

- **预算不够先砍谁？** 旧工具原文 → RAG 片段 → 长期记忆条数 → 摘要粒度；State 和用户刚说的话最后动，因为丢了它们会直接做错事，而不是只是答得差一点。
- **关键信息放中间会被忽略吗？** 有位置效应的研究，但不同模型表现不一致；我的做法是把当前目标和硬约束放在模型稳定关注的位置，再用评测验证，而不是背「中间最差」。

> **面试回答：**
>
> - 结论：第十一轮不是重发历史，而是每轮按分区重新组装上下文，每个分区有自己的生命周期和 token 预算。
> - 拼接顺序我会这样排：System 规则、和本轮相关的长期事实、当前任务 State（目标、槽位、未完成项）、前面轮次的摘要、最近两三轮原文、本轮截断后的工具结果，最后给输出留空间。
> - 为什么要显式放 State：多轮跑偏的根因往往不是记忆丢了，而是模型只看到对话原文，看不到「现在要干什么、还缺什么」。State 是防跑偏的锚。
> - 取舍：分区的真正价值在预算打穿的时候。我会先砍第 2 轮那份 20k 的工具 JSON，再缩 RAG，最后才动 State 和用户刚说的话，因为前者丢了是答得差一点，后者丢了是直接做错。
> - 边界：顺序不是铁律，位置效应因模型而异，所以我把它当成可调参数，用同一批多轮评测用例对比任务完成率和重复提问率来定。
> - 项目里：〔填：分区预算各多少、压缩前后 token 从 x 降到 y、重复提问率变化〕。
````

单题结构固定为下面的顺序，不能调换：

1. `### N. 题目`
2. `真题：`一行（只列编号和简称，最多 3 条；属于基础必需、没有直接真题的写 `真题：基础题`）
3. `**考察点：**` 一行（20～60 字）
4. `**核心结论：**` 一行（不超过 80 字）

## 7. 写作规范

### 7.1 题目怎么写

1. 先在真题合集里找原话。原话能用就用，只做三种修改：去掉口语噪音、补全省略的主语、把一题多问压到最多两问。
2. 没有原话时，想象面试官坐在对面会怎么问，写成第二人称或无人称问句：「你会怎么……」「为什么……」「……有什么区别？」。
3. 场景题必须保留约束条件。约束才是这道题的考点，例如「工具执行 100 秒、Agent 只能等 50 秒」不能改成「工具超时怎么办」。
4. 不在标题里写标签（【P0】）、项目名、文件名。
5. 不写作者视角标题：「基础篇要掌握什么」「怎么理解 X」「X 详解」「关于 X」。

| 不要这样写 | 改成 |
| --- | --- |
| Context 与状态管理：基础篇要掌握什么？ | （删除，内容并入 Memory 篇） |
| State、Context、Memory、Checkpoint 分别是什么？Session、Sandbox 怎么放？ | Agent 的 State、运行内存和 Checkpoint 有什么区别？ |
| Agent Loop 的最小核心实现 | 手写一个最小 Agent Loop；除了最大轮数，还靠什么让它停下来？ |
| Agent 的组成部分是什么？Harness 又是什么 | 你怎么理解 Harness？它和模型之间传什么？ |
| 【P0】客户只说"东西有问题，想退"，从这句话到退款真正执行…… | 涉及资金的 Agent，哪些环节不能交给模型决定？ |
| 如何防止死循环、Token 爆炸与任务挂死 | 复杂长任务怎么避免 Agent 无限循环和任务挂死？ |

### 7.2 「考察点」怎么写

考察点回答一个问题：同样答出了定义的两个候选人，面试官靠什么分出高下。写法：

- 「是否……」开头，写一到两个判断标准。
- 指向一个具体能力：取舍、边界、工程落地、验证方法、失败处理。
- 不写「考察对 X 的理解」这种空话。

例子：

- Workflow vs Agent：是否能用「路径能否枚举、错误代价、延迟容忍」做判断，而不是说 Agent 更先进；能否说出混合架构的具体切分。
- Tool Call 谁执行：是否清楚模型只有提议权；能否说出执行链上程序必须掌握的校验、权限、幂等、审计。
- 记忆冲突：是否区分「可裁决冲突」和「完全冲突」；完全冲突时是否知道不能把两条都塞给模型。

### 7.3 面试回答怎么写：五层答法

用户的要求是「面试版回答要深入，能凸显我的思考」。深入不等于长，而是每一层都有判断。agent 篇的面试回答按下面五层组织，每题至少覆盖四层，顺序可以按题目微调，但结论永远在第一条：

| 层 | 回答什么 | 典型句式 | 失败写法 |
| --- | --- | --- | --- |
| ① 结论 | 一句话给出立场或答案 | 「结论：……」「我的判断是……」 | 先铺背景，三句之后才进正题 |
| ② 机制 | 它是怎么工作的，关键链路或关键数据结构 | 「具体是：……」「链路是 A → B → C」 | 罗列名词，不说清它们怎么连 |
| ③ 取舍 | 为什么这样做而不是另一种做法，代价是什么 | 「我选 A 不选 B，因为……；代价是……」 | 只说优点，不说代价 |
| ④ 边界 | 什么情况下这个结论不成立、会失败，怎么兜底 | 「它不解决……」「当……时我会改成……」 | 讲成万能方案 |
| ⑤ 验证 / 落地 | 怎么证明有效，项目里怎么做的，数字多少 | 「我会看……指标」「项目里：〔填：…〕」 | 「效果提升明显」 |

体现个人思考的四种手段，每题至少用一种：

1. **主动纠正一个常见说法。** 例：「我先纠正一个常见说法：单 Agent 并不是只能串行，同一轮里独立的工具调用可以并行。」
2. **说出自己的默认立场和理由。** 例：「我的默认立场是能不拆就不拆，因为 Multi-Agent 的通信损耗和调试成本是确定的，收益是不确定的。」
3. **给出判断标准，而不是答案。** 例：「判断标准就一条：这条约束如果被违反，能不能回滚。不能回滚的必须在执行前由程序拦住。」
4. **讲一个反例或失败经历。** 例：「我踩过的坑是压缩后模型重复问已经确认过的槽位，原因是摘要没保留槽位状态。」

长度：agent 篇 5～8 条，450～900 字。每条 40～150 字，一条只讲一个意思。超过 900 字说明在复述讲解正文，砍掉讲解里已经有、口述时不必说的细节。

口吻：

- 用第一人称，但第一人称要带判断：「我会先看路径能不能枚举」可以，「我理解 Agent 是……」不要。
- 句子要能直接说出口：短句，主谓宾完整，不用括号嵌套，不用「/」并列三个以上的词。
- 术语第一次出现时可以带一句白话解释，但不要每条都解释。

前端篇的面试回答沿用 vue.md 的写法（4～6 条，每条先结论后原因，主动澄清误解），不强制五层，但至少要有一条「为什么」。

### 7.4 禁用表达

改完每篇都用 grep 扫一遍下面的词，命中就改写或删除。

| 类别 | 禁用 | 原因 / 替代 |
| --- | --- | --- |
| 元评论 | 加分项、亮点、面试亮点、最关键的加分点、这是本篇最容易答混的地方、必须背熟 | 让内容自己说明重要性；要强调就写进「考察点」 |
| 免责套话 | 这只是……不是绝对规则、不是学术上唯一的严格定义、参考排法不是唯一标准、不是铁律、不是定律 | 全站在 index.md 声明一次；正文只有当「保留意见」本身就是答案的一部分时才写，且一题最多一次 |
| 空洞开头 | 我理解……、我认为……（后面没有判断）、首先我们来看、综上所述、总的来说 | 直接给结论 |
| 夸张 | 大幅、飙升、完全不同、彻底解决、最好、非常关键 | 给具体对比或数字 |
| 凑数编号 | 三件套、四件套、五层手段、六个必看维度 | 直接列出；数量和列表条数必须一致 |
| 目录引用 | 见《00》、见《Memory 与 Context 工程》 | 用 Markdown 链接 |
| 中英混搭伪术语 | 「做 fail-fast 标 failed」这类拼接 | 中文写清楚，英文术语只用业界通用的 |

允许并鼓励的表达：「我的判断是」「我会先……再……」「代价是」「它不解决」「判断标准是」「我踩过的坑」「我会用……验证」。

### 7.5 讲解正文怎么写

1. 第一段就讲最核心的机制，不写背景铺垫。
2. 主形式三选一：对比用表格；链路用 `text` 流程图；实现用 TypeScript 代码（≤ 30 行，必须有注释说明关键行）。最多再加一种辅助形式。
3. 讲解里出现的每个结论，面试回答里要么复述，要么有意省略；面试回答里出现的结论，讲解里必须能找到依据。两者不能矛盾（基线里旧 00·1 正文说「没有工具的 Agent 也存在」，回答却说「能用工具」是 Agent 的特征，这类矛盾必须消除）。
4. 「项目落点」最多一行，格式：`- 项目落点：……，详见 [售后退款 Agent](../project/refund-agent)。`
5. 示例数字统一用 〔填：…〕 占位（全角六角括号，方便 grep），不写编造的具体值。确属公开基准的数字（如论文结果）可以写，但要写出处。

### 7.6 「高频追问」怎么写

1. 2～5 条，每条格式：`- **问题？** 回答。`
2. 回答 1～3 句，只写增量信息，不重复面试回答里的话。
3. 追问优先取真题合集里的连续追问；其次取讲解中最容易被追问的边界。
4. 追问是面试官「下钻」的方向，问题要能接在面试回答后面问出来。

### 7.7 标杆示例一：概念 / 选型题

改造前（旧 00·1 面试版回答，约 400 字散文，节选）：

> 我认为 Agent 是以大模型为决策核心，能自主完成"感知、决策、行动"闭环的系统……它有四个特征——LLM 做决策、能用工具、自主循环、对结果负责。和 LLM 的区别是「能力」和「系统」……两者的工程量差别很大，多出来的部分基本都是系统侧的活……

问题：散文难背；「四个特征」和正文矛盾；没有取舍，没有边界，听不出候选人自己的判断。

改造后：

````markdown
### 1. Agent 和直接调大模型、Chatbot 有什么区别？

真题：X22 淘天 · X23 蔚来（「Agent 和 AI 有什么区别」）· X30 字节前端（「Chatbot 与 Agent 的差异」）

**考察点：** 是否能把差异落到「控制流在谁手里」和「系统要多承担什么」，而不是背「感知-决策-行动」；能否说清有工具调用不等于 Agent。

**核心结论：** Agent 是围绕目标循环「决策 → 执行 → 看反馈」的系统，下一步做什么由模型参与决定；大模型只是其中的决策能力，Chatbot 通常没有任务目标和多步闭环。

（讲解：四角色表 + 执行闭环流程图，略）

> **面试回答：**
>
> - 结论：我区分它们看两件事，控制流在谁手里，以及系统要不要对任务结果负责。Agent 是围绕目标循环「决策、执行、看反馈」的系统，下一步做什么由模型参与决定。
> - 和直接调大模型的区别是「能力」和「系统」：模型无状态、不能产生副作用，两次调用之间什么都不记得；Agent 要在模型外面补上工具执行、状态、上下文组装和终止条件，工程量主要在这一圈。
> - 和 Chatbot 的区别是有没有任务闭环：Chatbot 一问一答就结束；Agent 有目标，会多步执行，最后要能判断「做完了没有」。
> - 我会主动纠正一个常见说法：有工具调用不等于 Agent。「模型选一个工具、执行、返回结果」这种一次性调用，本质还是函数调用链；关键是模型有没有根据执行结果决定后续路径。
> - 和 Workflow 的区别只有一条：Workflow 的控制流写死在代码里，Agent 把一部分控制流交给模型。代价是成本、延迟和可评测性，所以生产上我更常用混合：外层 Workflow 管阶段，开放环节交给 Agent。
> - 项目落点：〔填：你的项目里哪一段是 Agent、哪一段是 Workflow，为什么这样切〕。
````

这一版的特点：第一条就是判断标准；第四条主动纠错体现思考；第五条带出代价和混合架构，自然引向下一题「什么时候用 Agent」；最后留项目落点。

### 7.8 标杆示例二：场景题（新写的题）

````markdown
### 3. 一个工具要执行 100 秒，但 Agent 单轮只能等 50 秒，你怎么设计？

真题：N07 抖音电商后端（「工具执行 100 秒而 Agent 只能容忍 50 秒时，CLI/MCP 交互如何设计进度、心跳和等待」）

**考察点：** 是否意识到问题不在「把超时调大」，而在把同步调用改成可挂起、可查询、可恢复的异步任务；能否讲清重复提交和结果丢失两个风险。

**核心结论：** 把长工具从「同步等结果」改成「提交任务拿 task_id → 挂起 Run → 进度回传 → 完成后恢复」，等待超时和任务失败分开处理，提交带幂等键。

#### 链路

```text
模型决策 call slow_tool(args)
  → Runtime 生成幂等键，提交任务，立刻拿到 task_id（几百毫秒内返回）
  → 写 Checkpoint：pending_task = task_id，Run 状态改为 waiting_tool
  → 工具侧通过进度通知回传进度（MCP 可用 progressToken + notifications/progress）
  → 前端订阅进度；Agent 不占用模型轮次
  → 任务完成：回调或轮询拿到结果 → 结果作为 ToolMessage 回灌 → Run 恢复
  → 任务失败或超过业务上限：结果标 failed，回灌错误让模型决定重试 / 降级 / 告知用户
```

#### 高频追问

- **为什么不直接把超时改成 120 秒？** 治标不治本：模型网关、HTTP 连接、用户耐心都有上限，而且下次工具变成 300 秒还要再改；同步等待期间进程一挂，结果就丢了。
- **等待期间用户又发了一句话怎么办？** Run 处于 waiting_tool，新消息可以排队，或者允许模型只做「回答进度」这类只读动作，但不能再次提交同一个任务。
- **Agent 宕机后任务还在跑，恢复时怎么办？** 从 Checkpoint 读出 pending_task，用 task_id 去查状态，已完成就直接回灌结果，不重新提交。

> **面试回答：**
>
> - 结论：我不会去调大超时，而是把这个工具改成异步任务。同步等 100 秒有两个问题，一是总会碰到网关、连接或用户耐心的上限，二是等待期间进程一挂，结果和状态都丢了。
> - 具体是：模型发起调用后，Runtime 先生成幂等键提交任务，几百毫秒内拿到 task_id，就把这个 pending 任务写进 Checkpoint，Run 状态改成 waiting_tool，不占用模型轮次。
> - 进度通过通知回传，比如 MCP 的 progressToken 加 progress 通知，前端订阅后展示「正在生成报表 60%」。任务完成后通过回调或轮询拿结果，作为 ToolMessage 回灌，Run 从断点继续。
> - 这里我会特别区分两种「超时」：等待超时是正常现象，不代表失败；只有任务本身失败或超过业务上限，才把错误回灌给模型，让它决定重试、降级还是告诉用户。混在一起的话，模型会对一个还在跑的任务发起重试。
> - 最大的风险是重复提交。幂等键由 Runtime 生成，不交给模型，粒度是「一次业务意图加一次工具调用」；恢复时先用 task_id 查状态，查到已完成就直接回灌，不重新提交。
> - 边界：如果这个工具本身能拆成分页或流式返回，我会优先拆，因为异步任务要多维护一套任务表和回调。只有确实拆不开的长任务才走这套机制。
> - 项目落点：〔填：哪个工具耗时多久、改造后用户等待体验或失败率的变化〕。
````

这一版的特点：开头直接否定直觉方案并说明原因；中间讲链路；第四条区分两种超时，是这题真正的区分点；第五条讲风险；第六条给边界，说明这套方案什么时候不该用。

- 核心结论：State 是本次任务的运行数据，Context 是本轮实际交给模型的 token，Memory 是窗口外以后还要用的信息；企业知识库不是用户 Memory，它有版本、权限和生效期，走 RAG。
- 讲解要点：三概念表；「Memory 是 Context 的一个来源，反过来不成立」；Skill references / RAG / Memory 三条检索链分开、注入时分区放。Checkpoint 只写一句并链接 01。
- 追问：Skill 怎么使用 Memory 和第三方知识？（N08-9）；把 Checkpoint 当 Memory 有什么问题？
- 思考点：纠正「重启能续跑 = 记得用户」；纠正「RAG 结果写进用户档案」。

**3. 记忆存在哪？为什么用 Redis？关系库和向量库怎么分工？**

- 来源：旧 Memory·5 后半；真题 X03-3、X27-4、X31-7（双引擎存储）
- 考察点：是否按访问模式选型；能否说出 Redis 的优点和不能当长期事实唯一真源的原因。
- 核心结论：按访问模式选：热会话 State 用 Redis（TTL、按 session 快速重建、多实例共享），结构化事实用关系库（按 key 更新和作废），语义召回用向量库（只存 embedding + 引用 id），大结果进对象存储。
- 讲解要点：存储表；Redis 适合与不适合各三条；「向量库只是召回手段，不等于长期记忆」。
- 追问：Redis 挂了记忆会丢吗？（热数据可从 Checkpoint 重建，长期事实不应只在 Redis）；业务线之间记忆怎么复用？（按 tenant / user / bizLine 分 namespace）
- 思考点：说出「双引擎」的合理性（关系库保正确性、向量库保召回）和一致性代价（写入要有主从顺序，以关系库为真源）。

**1. 长期记忆写什么、怎么写？筛选靠模型判断还是规则触发？用户偏好怎么异步提取？**

- 来源：旧 Memory·6；真题 X17-5、X11-6、X10-7、X20-4（阈值或次数怎么定）
- 考察点：是否有「规则挡 + 模型出候选 + 校验入库」的链路；为什么异步；阈值怎么定。
- 核心结论：只写稳定事实、明确偏好和可验证的任务结论；规则先挡（敏感信息、临时状态、未确认内容），模型只产出候选，校验通过才入库；提取放在异步任务里，不阻塞用户回复。
- 讲解要点：写入链路（text）；记忆条目结构（key / value / type / source / confidence / validFrom / expiresAt）；异步提取的触发时机（会话结束、N 轮一次、出现显式偏好表达）。
- 追问：为什么选这个阈值或次数？（X20-4：用离线回放比较不同 N 的召回有用率和写入噪声率，〔填：…〕）；用户说「以后都用英文回复」要不要立即生效？（显式指令走同步写入，推断类偏好走异步候选）
- 思考点：「模型适合抽取，不适合决定写不写」；阈值必须用数据定，不能拍脑袋。

**2. 记忆如何按需读取？什么上下文可以丢，什么必须保留？**

- 来源：旧 Memory·5 前半；真题 X03-6、X05-二面6、X14-4/5、N10-3
- 考察点：是否知道 JIT（指针 + 回读）；可丢 / 必留是否有可执行的标准；召回「看似相关但没帮助」怎么优化。
- 核心结论：默认按需：用当前 query 和任务 State 检索 top-k，Context 里只放 id、一句话和时间，需要细节再回读；可丢的是已完成步骤的原文和重复内容，必留的是目标、约束、未完成项、明确偏好、数字实体和指针。
- 讲解要点：读取流程（text）；可丢 / 必留对照表；隔离要求一句（召回前按租户和用户过滤，链接 09）。
- 追问：召回结果看似相关但对回答没帮助怎么办？（X14-5：加 Rerank 或模型二次判定相关性、按任务类型过滤记忆类型、用「被引用率」监控）；上一轮结果怎么传，哪些不该直接塞进上下文？（N10-3：大工具结果、敏感字段、中间推理）
- 思考点：「压缩和裁剪都允许丢正文，但不允许找不到」：指针是可丢的前提。

**3. 记忆冲突、完全冲突、过期淘汰怎么处理？比如用户搬家了。**

- 来源：旧 Memory·7；真题 X07-5、X13-5、N08-10、X17-5
- 考察点：是否区分可裁决冲突和完全冲突；完全冲突时是否知道不能两条都给模型。
- 核心结论：同 key 新值覆盖旧值并保留历史；能按时间和来源可信度裁决的自动裁决；两条都可信、裁不了的属于完全冲突，向用户澄清一次并写回结果；过期按有效期弱化或淘汰。
- 讲解要点：冲突分类表（类型 / 例子 / 处理）；新闻类时效信息的处理（带 validFrom / expiresAt，过期降权）。
- 追问：为什么不能把两条都注入让模型挑？（模型可能编出折中答案）；过期记忆删除还是降权？（偏好降权，事实按有效期作废，审计需要保留历史）
- 思考点：「冲突检测发生在写入时，不是在读取时」：写入时发现同 key 就处理，读取时只拿当前有效值。

**4. 压缩什么时候触发？定时还是同步？怎么减少用户等待？跨天任务怎么接上？**

#### 分组「Prompt 与输出」

**1. System Prompt 的作用是什么？为什么要和用户消息分开？生产级 System Prompt 包含哪些部分？**

- 来源：新写；真题 X17-4、X03-8
- 考察点：是否知道角色分离的原因（优先级、注入防护、缓存）；生产级结构是否完整且可版本化。
- 核心结论：System Prompt 定义角色、硬规则、工具使用规范和输出约定，和用户消息分开是为了区分指令优先级、降低注入影响、并让静态部分能被缓存和版本化；生产级一般包含角色与目标、边界与禁止事项、工具使用规则、输出格式、终止与澄清规则、少量示例。
- 讲解要点：结构模板（text，每部分一行说明）；「静态在前、动态在后」以利用前缀缓存一句。
- 追问：System Prompt 越长越好吗？（不是，规则互相冲突、注意力稀释；硬约束放 Runtime）；不同模型要不要不同 Prompt？（同一份逻辑，按模型做小幅适配并分别评测）

**2. 怎么确保模型生成的 JSON 键名、嵌套层级和格式可靠？**

- 来源：新写；真题 X07-3、N02-1、N02-5
- 考察点：是否知道约束解码 / 结构化输出 API；校验 + 修复重试；Schema 设计本身对可靠性的影响。
- 核心结论：分三层：生成时用模型的结构化输出或 JSON Schema 约束（能约束解码就不靠 Prompt）；生成后用 Schema 校验并把错误回灌重试，有限次后降级；Schema 设计上减少嵌套、用枚举、字段名语义化。
- 讲解要点：三层表；一段 TypeScript（zod 或类似库校验 + 重试 ≤ 20 行）；简历评分类结构化输出的维度设计一句（N02-1）。
- 追问：约束解码之后还要校验吗？（要，格式对不等于业务值合法）；模型偶尔输出多余文字怎么办？（结构化输出模式或提取第一个合法 JSON 块）
- 思考点：「先用机制约束，再用校验兜底，最后才是 Prompt 措辞」的优先级。

**3. 工具参数通过了 JSON Schema，为什么还不能直接执行？中间还要过哪些校验？**

- 来源：旧 09·3 去项目化；真题 X13-6
- 考察点：Schema 只管形状；是否能说出归属、状态前置、授权、防线、对账各层及各自失败处理。
- 核心结论：Schema 只保证形状对，不保证这件事现在合法；执行前还要过归属校验、状态前置条件、授权或审批、幂等等防线，执行后还要对账。
- 讲解要点：保留旧 09·3 的五层表，例子用「退款」通用描述。
- 追问：每层失败为什么处理方式不同？（回灌、拒绝、审批、去重）

**4. 涉及资金的 Agent，哪些环节不能交给模型决定？**

- 考察点：是否能把链路切成澄清、查证、判定、授权、执行、沟通，并说清哪三环不能交给模型；检索结果为什么不能当授权。

**5. 意图识别用模型还是规则？需不需要单独做一个意图分类器或路由器？**

- 来源：旧 09·8；真题 X05-一面5、X12-2
- 考察点：规则 / 小模型 / 大模型的分工；什么时候值得单独做路由器；意图模型和工程流怎么衔接多个模型（X12-2）。
- 核心结论：头部高频、表达稳定的意图用规则或小分类器，便宜且可测；长尾和多意图交给大模型；当意图种类多、下游处理链路差异大、或者要分流到不同模型时，才值得单独做路由器，并给路由器单独评测。
- 讲解要点：三种方案对比表（准确率来源 / 成本 / 维护 / 适用）；路由器输出结构（intent、confidence、slots）和低置信度走澄清。

- 思考点：「路由器是一个需要独立评测的模型，不是一个 if」。

**7. Prompt 多次调试仍然没效果，你怎么定位问题？怎么避免再犯？**

**8. 怎么判断一次 Prompt 修改真的有效？Prompt 怎么做版本管理和 A/B 测试？**

- 来源：旧 09·7；真题 X22-5、X14-12、X06-7、N11-9

**10. Text-to-SQL 怎么让模型理解对应的表？业务黑话和语义相近的字段怎么处理？生成的 SQL 怎么校验？**

## 13. 单篇改造 SOP

每改一篇都按这个顺序走：

1. **读旧文**：完整读一遍旧文，以及第 4.2 节映射里列出的所有来源题。
2. **查归属**：对照第 9 节，标出本篇要讲透的知识点和只写一行的知识点。
3. **对真题**：在真题合集里搜本篇主题关键词，确认第 10 节规格里的真题编号，并补充遗漏的连续追问。
4. **搭骨架**：先写页头、知识链、全部 H2 / H3 标题和每题的「真题 / 考察点 / 核心结论」三行，不写正文。自查题目是否都符合 7.1 节。
5. **写讲解**：按规格的「讲解要点」写，选定主形式；旧文里质量好的表格、代码、流程图直接复用并按第 8 节修格式。
6. **写追问**：按 7.6 节。
7. **写面试回答**：最后写。按 7.3 节五层答法，覆盖规格「思考点」；写完朗读一遍（或估算字数），超过 900 字就砍。
8. **写速记**：每题一行。
9. **扫禁用词**：用第 19 节的 grep 命令扫一遍。
10. **改链接**：本篇引用的其他篇、其他篇引用本篇的地方，都改成新路径；更新 `_sidebar.json` 和 index.md。
11. **验证**：`npm run check`、`npm run build`。
12. **自检**：过第 14 节清单。
13. **提交**：按第 16 节。

改造期间旧文件和新文件并存时，以新文件为准；旧文件在该篇改完、链接全部切换后用 `git mv` 或删除处理，不要留两份。
