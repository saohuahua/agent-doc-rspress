# 02 一条消息的旅程

以 **Pi v0.84.3 (+20, `8fa7eebd`)** 源码为基准。本章所有 `file:line` 经 `pnpm check:refs` 校验，代码块里的中文注释为本文补充。

消息与上下文的基本概念在 [Learn 04](/learn/04-message-and-context) 讲过：一次请求带的是 system prompt + 全量 messages。本章要看的是 Pi 在这条链路上加了多少道闸、每道闸拦的是什么。

:::tip 一句话版本

用户输入 → TUI 先吃掉一批命令 → 产品层拦八次、展开一次 → 循环层转三次格式 → 模型层再改两次 → HTTP 请求体。中间任何一道拦下来，模型就什么都收不到。

:::

## 0. 本章回答哪些面试问题

- **#1 AI Coding 整体的实现思路是什么** —— 用户输入到 provider 请求体的完整链路，以及每一段谁负责
- **#2 怎么保证执行过程中的准确性和可靠性** —— 校验为什么放在这些位置、fail fast 的三个点在哪

编号见交接文档 §12。

## 一、问题：这行字为什么不能直接发出去

场景很具体。你在 pi 里敲下这一行，回车：

```text
/review src/api.ts 重点看鉴权
```

模型最终收到的东西可能是下面四种之一，取决于 `/review` 是什么：

| `/review` 是什么 | 模型收到什么 |
|---|---|
| 某个扩展注册的命令 | **什么都没有**，扩展自己处理完就结束了 |
| `~/.pi/agent/prompts/review.md` | 一大段模板文本，`$1` 被替换成 `src/api.ts` |
| 一个 skill（写成 `/skill:review`） | 一个 `<skill>` 标签包住的完整 SKILL.md |
| 三者都不是 | 原样的 `/review src/api.ts 重点看鉴权` |

同一串字符，四种结局。而且这还只是"文本变成什么"这一层——它变成消息之后，还要经过压缩检查、认证解析、上下文转换、provider 载荷改写。

面试里被问"用户输入之后发生了什么"，答"拼进 messages 发出去"是不及格的。真实的链路上，**用户输入在被当成用户输入之前，先被五个不同的东西抢着处理过一遍**。

## 二、全景：四层链路

```text
  ┌──────────────────────────────────────────────────────────────────────┐
  │  ① TUI 层           interactive-mode.ts  onSubmit                     │
  │     命令、shell、排队都在这层被吃掉，不进 session                        │
  └───────────────────────────────┬──────────────────────────────────────┘
                                  │ session.prompt(text)
  ┌───────────────────────────────▼──────────────────────────────────────┐
  │  ② 产品层           AgentSession.prompt()                             │
  │     八道闸：扩展命令 · 压缩互斥 · 扩展 input · 展开                      │
  │             流式分流 · 模型认证 · 压缩检查 · 组装消息                    │
  └───────────────────────────────┬──────────────────────────────────────┘
                                  │ agent.prompt(messages)
  ┌───────────────────────────────▼──────────────────────────────────────┐
  │  ③ 循环层           agent.ts → agent-loop.ts                          │
  │     状态快照 → transformContext → convertToLlm → llmContext           │
  │     → getApiKey（每次请求重新解析）                                     │
  └───────────────────────────────┬──────────────────────────────────────┘
                                  │ streamFn(model, llmContext, options)
  ┌───────────────────────────────▼──────────────────────────────────────┐
  │  ④ 模型层           model-runtime.ts → ai/api/*.ts                    │
  │     prepareRequest（auth + headers）→ buildParams → onPayload         │
  │     → HTTP / SSE                                                     │
  └──────────────────────────────────────────────────────────────────────┘
```

### 十四道闸速查

前两层一共十四道闸。这张表是本章最该记住的东西：

| # | 层 | 这道闸在判断什么 | 不通过会怎样 |
|---|---|---|---|
| ① | TUI | 是不是空串 | 直接丢弃 |
| ② | TUI | 是不是 26 条内置斜杠命令 | 本地处理，**不产生任何消息** |
| ③ | TUI | 是不是 `!` / `!!` 开头 | 直接跑 shell，记成 `bashExecution` 消息 |
| ④ | TUI | 压缩是不是正在跑 | 进 TUI 本地队列，压缩完再发 |
| ⑤ | TUI | agent 是不是正在跑 | 转成 steer 排队 |
| ⑥ | TUI | 以上都不是 | 交给 `AgentSession.prompt()` |
| ⑦ | 产品层 | `/xxx` 是不是扩展注册的命令 | 立即执行并返回，**不产生任何消息** |
| ⑧ | 产品层 | 压缩是不是正在跑 | `throw`（唯一一处并发保护） |
| ⑨ | 产品层 | 扩展的 `input` 要不要拦 | `handled` 直接返回；`transform` 改写文本 |
| ⑩ | 产品层 | 是 skill 还是 prompt 模板 | 替换成完整文本；都不匹配就原样通过 |
| ⑪ | 产品层 | agent 是不是正在跑 | steer 插队 / followUp 排队，然后返回 |
| ⑫ | 产品层 | 有没有模型、有没有凭据 | `throw`（fail fast） |
| ⑬ | 产品层 | 上一条 assistant 是否溢出或超阈值 | 先压缩再继续 |
| ⑭ | 产品层 | 扩展的 `before_agent_start` 要不要加料 | 追加 custom 消息、可整体替换 system prompt |

十四道闸里，**真正在改"用户那句话"的只有 ⑨ 和 ⑩**，其余十二道都在决定"这句话要不要发、发之前还要做什么"。

## 三、四层各自在干什么

### TUI 层：先被界面自己吃掉一批

26 条内置斜杠命令、`!` 开头的 shell、压缩期间的排队、流式期间的插队，全都在 `onSubmit` 的 if 链里就地解决。只有全都不匹配的文本，才会通过 `getUserInput()` 交给主循环、进入产品层。

这一层的取舍：命令的**声明**在 `core` 里（供补全 UI 用），**行为**在 TUI 里。好处是 `core` 不需要知道 `/model` 会打开一个选择器，代价是加一条命令要动两个文件。

→ 详见 [02.1 十四道闸](./gates)

### 产品层：`AgentSession.prompt()` 的八道闸

这是全仓最值得读的一个方法。它把"用户意图"翻译成"循环层参数"的所有脏活都摆在明面上：查扩展命令、拒绝并发压缩、给扩展改写文本的机会、展开 skill 与模板、流式期间分流到两个队列、校验模型与凭据、按上一条回执判断要不要压缩、最后组装消息并让扩展加料。

八道闸里只有一道在改文本，其余七道都是"要不要发"和"发之前做什么"。

→ 详见 [02.1 十四道闸](./gates)

### 循环层：三次格式转换

`Agent.prompt()` 先拍一张状态快照（`messages` 和 `tools` 都 `slice()` 一份），再组一份回调配置，然后进 `agent-loop`。每次真正发请求之前做三件事：

1. `transformContext` —— 扩展的 `context` 事件，还在 AgentMessage 这一层
2. `convertToLlm` —— 把 Pi 特有的消息类型压平成 provider 认识的三种
3. 拼成 `llmContext`，同时**重新解析一次 API Key**（OAuth token 会在长工具执行期间过期）

→ 详见 [02.2 从上下文到请求体](./assembly)

### 模型层：最后两次改写机会

`prepareRequest` 解析认证并合并 headers，这里连着扩展的 `before_provider_headers`；然后每家 provider 按自己的协议 `buildParams`，在真正发出去之前调一次 `onPayload`，对应扩展的 `before_provider_request`。

`onPayload` 拿到的已经不是 Pi 的抽象消息，而是 **provider 专属的请求体**——这是链路上抽象泄漏最严重的一处。

→ 详见 [02.2 从上下文到请求体](./assembly)

## 四、这个顺序为什么是这个顺序

链路上有四组顺序是刻意的，换一下就出问题。

**扩展 `input` 在展开之前。** 扩展要审计的是用户敲的字，不是模板作者写的字。放到展开之后，一条 `/deploy-prod` 展开成三千字的部署指令，扩展再想拦已经失去了语义。

**认证校验在消息组装之前。** 认证失败会 `throw`，而 `throw` 之前一条消息都还没进 `messages` 数组。如果反过来，失败的会话里会留下一条孤立的用户消息，下次 resume 时最后一条是 user，`agent.continue()` 会直接把它当成待回复的提问重新发一遍。

**压缩检查在组装之前、发送之前。** 循环层看到的 `messages` 就是要发的全部内容（第 01 章），压缩没有别的地方可插。

**`before_agent_start` 在最后。** 它要看到最终文本才能决定加什么上下文，所以必须排在展开之后；它又要能改 system prompt，所以必须排在进循环之前。前后都被卡死，位置是唯一的。

## 五、边界：这条链路解决不了什么

**命名冲突没有仲裁。** 内置命令 / 扩展命令 / skill / 模板四类共用 `/` 前缀，先到先得，冲突时无提示。想知道 `/review` 到底会触发谁，只能自己按顺序推一遍。

**展开失败静默。** 名字打错、SKILL.md 读不出来，都退回原文继续发。模型收到一条像命令但不是命令的字符串，行为不可预测。读文件失败会通过扩展 runner 发一个 error 事件，但普通的"名字不存在"连事件都没有。

**`input` 事件不是安全边界。** 它只能改文本。模型能不能读 `.env`，跟用户在输入框里敲了什么没关系——那是工具层的事（第 04 章、[第 09 章](../09-extension-system)）。

**压缩判断依赖上一条回执。** 会话刚 resume、还没有任何 assistant 消息时，这一轮跳过压缩检查。极端情况下（导入一个巨大的历史会话后第一条消息）可能直接撞上溢出，靠的是发出去之后的溢出恢复兜底，而不是发之前拦住。

**`onPayload` 泄漏 provider 细节。** 想跨厂商用它，得自己写 if。`compat` 收敛了协议差异（第 08 章），但这个钩子的位置在收敛之后。

## 六、未验证与推断

- ✅ 十四道闸的顺序、每处的判断条件、三次转换的位置，均读源码得出并经 `check:refs` 校验
- ✅ 23 条内置命令声明 + 26 条实际处理，靠 `BUILTIN_SLASH_COMMANDS` 数组与 `onSubmit` 里的 `text === "/xxx"` 分支计数
- ⚠️ "内置命令 → 扩展命令 → skill → 模板"的冲突优先级是从代码顺序推出的，未构造同名冲突实测
- ⚠️ 认证校验可能触发网络请求，未抓包确认哪些 provider 会真的发请求
- ❌ 未实跑打点验证一条消息在各关卡的耗时分布

## 七、本章小结

- 用户输入在成为"用户消息"之前，被 TUI、扩展命令、扩展 `input`、skill、模板五个东西抢着处理过
- TUI 层吃掉 26 条内置命令（不产生任何消息）和 `!` 开头的 shell 执行（记成 `bashExecution` 消息，但不走 Agent Loop）
- `AgentSession.prompt()` 的八道闸里，只有一道在改文本，其余七道在决定"要不要发、发之前做什么"
- 三处 fail fast：压缩互斥、无模型、无凭据。全部在消息进数组之前，失败不留残骸
- 压缩检查看的是**上一条 assistant 的 usage**，因为循环层没有"发之前问额度"的能力
- 进循环后还有三次转换：`transformContext`（扩展）→ `convertToLlm`（类型压平）→ `llmContext`（协议形状）
- Pi 自有的消息类型全部降级成 user 消息，语义靠前后缀标记
- 最后两个改写点在模型层：`before_provider_headers` 和 `onPayload`，后者已经是 provider 专属结构
