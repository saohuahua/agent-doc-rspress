# 哈希基础：把反复寻找变成直接查询

假设页面有一千个用户，每次收到用户编号后都用 `users.find` 找对应信息。单次不难，但查询一千次就可能反复查看同一批数据。一个自然的改善是提前建立“编号 → 用户”的表。算法中的哈希结构经常也在做这件事：**用一些空间保存可复用的信息，减少重复寻找。**

本章重点是查询目标、存储内容、记录的有效范围及其操作成本。

## 下标 数值 键与值的含义

数组 `[8, 5, 8]` 的下标是 `0`、`1`、`2`，数值是 `8`、`5`、`8`。数组通过连续的下标访问元素；查询表允许通过指定的键寻找值。

在“数值 → 最后出现位置”的表里，键是 `8`，值可能是下标 `2`。在“数值 → 出现次数”的表里，同样的键 `8`，值却是次数 `2`。两张表长得相似，含义不同。实现前需要明确键和值的语义，更新操作才有确定依据。

哈希表内部通过哈希函数把键映射到存储位置。不同键可能映射到相同位置，称为碰撞，需要由底层结构处理。它不是把键当作普通数组下标，因此可以接受负数和字符串。实际语言容器有具体实现差异，算法题通常按查询和更新平均 O(1) 估算，不能理解成任何情况下都只执行一个机器指令。

## Map 与 Set 的选择依据

| 需要回答的问题 | 保存的信息 | TS 容器 |
| --- | --- | --- |
| 某个数出现过吗 | 数值本身 | Set&lt;number&gt; |
| 某个数在哪里出现过 | 数值到下标 | Map&lt;number, number&gt; |
| 某个字符出现几次 | 字符到次数 | Map&lt;string, number&gt; |
| 哪些字符串属于同一组 | 分组标识到字符串数组 | Map&lt;string, string[]&gt; |

`Set` 只关心成员身份。`Map` 额外保存每个键对应的信息。存在性查询适合 `Set`，次数查询则需要关联计数；仅使用集合会丢失重复次数。

常用操作包括 `has` 查询是否存在、`get` 取关联值、`set` 写入关联值、`delete` 删除、`size` 查看键的数量。重复写入同一个键会覆盖旧值，不会创建第二个同名键。保存多个位置时，需要让值本身成为数组。

## 计数记录的建立过程

从左到右读 `[8, 5, 8]`，建立出现次数表。

| 本次读到 | 更新前次数 | 更新后次数 | 原因 |
| --- | --- | --- | --- |
| 8 | 不存在 | 1 | 首次看见 |
| 5 | 不存在 | 1 | 首次看见 |
| 8 | 1 | 2 | 原来一次再增加一次 |

读取不存在的键时，`Map.get` 返回 `undefined`。计数通常用 `get(key) ?? 0` 取得旧次数。下标也可能为零，所以不能把 `get` 的返回值直接当布尔值判断存在。若业务确实允许保存 `undefined`，应使用 `has` 区分“键不存在”和“值就是 undefined”。

对象作为 `Map` 或 `Set` 的键时按引用身份判断。两个内容同为 `{ id: 1 }` 的新对象不是同一个键。需要按业务编号去重就使用编号，需要按字符组成分组就先构造一致的分组标识。**相等关系由问题定义，容器按所提供的键执行比较。**

## 查询表的适用条件

先找到朴素方法里反复进行的查询。例如找补数、检查出现情况、累计次数、按某种特征归组。再问查询的答案能不能在扫描过程中增量维护：加入一个元素，只修改少量记录，而不用重新检查整个历史。

不是所有慢循环都能靠加一张表解决。若需要随时知道“所有值中最小的是谁”，普通 `Map` 不会自动把键按数值排序；若需要查询区间内所有数的和，单个值的计数表也不能直接给出答案。应明确目标操作，再选择数据结构。

建立含 `n` 项的表需要 O(n) 次写入，也需要相应空间。只查询一次时，建立整张表未必比扫描一次更划算。这里的收益主要来自消除重复扫描，或者在一次遍历中快速回答多次历史查询。
