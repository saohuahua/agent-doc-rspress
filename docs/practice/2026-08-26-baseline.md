## 3. 第一份真实数据：写 `pi/guide/` 这次会话

指标不是估的，是用 `scripts/session-stats.mjs` 从会话 JSONL 里算出来的。

```bash
node scripts/session-stats.mjs --latest --cwd "D:/project/agent-doc-rspress"
```

**任务**：从 Pi 官方英文文档出发，写出 20 篇中文使用指南（约 5600 行），并接入 rspress 站点、修侧边栏、跑通构建。

| 指标 | 值 |
|---|---|
| 时间跨度 | 2 小时 18 分 |
| 会话条目 | 283 |
| user 消息 | **4 条** |
| assistant 消息 | 129 条 |
| toolResult | 142 条 |
| 工具调用 | 143 次：`bash` 74 / `read` 30 / `write` 25 / `edit` 14 |
| 工具报错 | 4 次 |
| stopReason | `toolUse` 127 / `stop` 2 |
| 压缩 | **0 次** |
| 分支摘要 | 0 次 |
| 换模型 | 1 次（会话中途从 `glm-5.3` 换到 `claude-opus-5`） |
| 换 thinking level | 5 次 |
| token | input 258 / output 152,779 |
| 缓存 | cacheRead **23,780,399** / cacheWrite 1,156,941 |
| 成本 | $0.0000 ← **不可用，见坑 2** |

### 从这组数字里能读出什么

**① 4 条用户消息驱动 129 轮助手回合。**
平均一条指令换来 32 轮自主工作。这是 Coding Agent 与普通 Chat 最直观的差距，也是回答面试问题 #1 时可以直接引用的实测比例。

**② input 258，cacheRead 2378 万。**
差了五个数量级。说明几乎**全部上下文都命中了 prompt 缓存**，真正当作新 input 计费的只有 258 token。这解释了长会话为什么没有想象中那么贵，也说明"token 总量"这个指标单独看没有意义——**必须区分 input / cacheRead / cacheWrite**。

**③ 整场 0 次压缩。**
2 小时、143 次工具调用、写了 5600 行，居然一次都没触发压缩。结合 ② 可以推断上下文始终没超过 `contextWindow - reserveTokens`（默认预留 16384）。
→ 这意味着我**还没有观察到压缩的真实行为**，[上下文压缩](/pi/guide/getting-started/compaction) 那一页目前完全是读文档写的，属于**未实跑验证**。

**④ 143 次工具调用里 `bash` 占 74 次。**
一半以上是 shell。其中很大一部分是 `grep`/`ls` 这类查找——因为 `grep`、`find`、`ls` 三个内置只读工具默认没启用，模型只能用 `bash` 绕。
→ 下次试试把 `defaultTools` 加上 `grep`/`find`/`ls`，看 `bash` 占比是否下降、是否更快。这是一个**具体可做的对照实验**。

**⑤ 4 次工具报错，没有中断整体任务。**
对应 [Learn 03](/learn/03-tool-basics) 讲的"错误回填给模型，模型自己决定下一步"——实测确实如此。

**⑥ 中途换了 1 次模型、5 次 thinking level。**
这两个动作在会话文件里是**显式条目**（`model_change`、`thinking_level_change`），所以事后可复盘。如果某段输出质量突然变差，可以定位到是哪次切换之后。

:::warning 坑 2：自定义 provider 拿不到成本

成本统计显示 `$0.0000`，**不是免费，是没有价格表**。

`models.json` 里自建的 provider 不带定价信息，所以底栏和会话里的 cost 恒为 0。

**直接后果**：面试问题 #11「效率提升」如果想用"省了多少钱"来答，**在当前配置下拿不到数据**。要么改用官方 provider 跑对照实验，要么只用时间和 token 作为指标。这一条必须在写 `interview/` 之前解决。

:::

**② 交接文档 §2 / §8 的 `agent-loop.ts` 行号指向的是调用点不是定义**

| 符号 | 交接文档 | 实际定义 |
|---|---|---|
