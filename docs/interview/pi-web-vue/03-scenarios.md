# 03 场景与综合

> 前两篇讲「这个项目是什么」和「为什么这么设计」，本篇讲「出问题时怎么办」。十四道题按难度分四层：单点故障 → 并发与一致性 → 边界与可信 → 系统与演进。
>
> 每道题都给出：考察点、回答主线、项目对照（哪些做了、哪些没做）、边界与追问。**项目没做的地方会明确标注**——面试里把没做的说成做了，是最容易被拆穿的一类失分。

## 第一层：单点故障

### 1. 工具调用已经展示出来，但结果一直没回来，界面该显示什么？

**考察点**：能否意识到「没有结果」有三种成因，而把其中两种显示成「完成」等于把未知说成成功。

**回答**

先拆成两问：怎么关联、该显示什么。第二问才是重点。

**关联**：工具调用在助手消息的 `content` 块里，结果是一条独立的 `toolResult` 消息，唯一标识是 `toolCallId`。这个关联做成派生值而不是独立状态——独立状态要手动同步，结果更新时容易漏；派生值自动跟着消息列表重建。

**状态判断**不能用「消息还在不在流式」。助手消息在工具开始执行之前就已经定稿了，定稿后流式标记是 false，而工具才刚开始跑。所以另有一个 `activeTools` 映射，`tool_execution_start` 写入、`tool_execution_end` 删除。

三种情况都会导致「没有结果」：

| 情况 | 当前显示 | 应该显示 |
| --- | --- | --- |
| 工具还在跑 | 执行中 | 执行中 |
| 结果事件丢了 | **完成** | 未确认 |
| 工具根本没启动 | **完成** | 未确认 |

后两种把未知说成了成功，用户看到「完成」就会以为可以进下一步。

**正确的状态机**应该是四态：执行中（在 `activeTools` 里）、完成（拿到成功结果）、失败（拿到错误结果）、**未确认**（两样都没有）。

- **项目对照**：没有未确认态。这是纯前端改动、成本几乎为零，但消除的是主动误导。
- **抽象原则**：用证据驱动状态，不要用「没消息就是好消息」推断。有成功信号才算成功，有失败信号才算失败，都没有就显示「无法确认」。适用于所有「发起操作 + 异步等结果」的界面——支付、构建、部署。
- **其他异常输入**：`toolCallId` 缺失时归一化给空串，多个缺标识的工具会互相串；结果找不到对应调用时渲染成不显示的空节点，**用户看不到「有个结果没配上」**，问题被静默了。

### 2. SSE 断线重连后，内容重复或缺失，怎么恢复？

**考察点**：能否区分「重连」和「补发」。答「浏览器会自动重连」的人，没意识到重连不解决数据缺口。

**回答**

先排除一个误解：重连后内容重复**不是**因为快照重复发送——快照是整体替换，不是追加。重复和缺失是两个不同原因。

**重复**有三个来源：

| 来源 | 说明 | 严重程度 |
| --- | --- | --- |
| 快照去重失效 | 缓冲事件用**引用相等**判断「是否已包含在快照里」，SDK 若每次克隆就形同虚设 | 待核实 |
| 增量事件无去重 | 同一条 `_delta` 重复到达会被追加两次 | 中 |
| 消息层无去重 | 用户消息有去重，助手消息没有 | 中 |

后两个不致命，因为每次任务结束都会重新拉一次权威数据整体替换，会把重复修掉——**前提是那次拉取成功**。

**缺失是必然的，而且更严重**。断线期间服务端还在推事件，但前端没有连接，这些事件没有缓冲、没有序号、没有游标，永久丢失。重连后只能拿到两样：当前流式消息的快照、已落盘的权威历史。中间过程信息，比如某个工具的实时进度，**找不回来**。

**关键区分**：连接重连 ≠ 事件补发。

| | 能力 | 谁提供 |
| --- | --- | --- |
| 重连 | 重建传输通道、区分可重试错误 | 浏览器 + 项目封装 |
| 补发 | 断线期间丢失的事件 | **需要协议层设计** |

**真正的解法**：服务端给事件编号并保留一段 ring buffer；客户端记录最后收到的序号；重连时带 `Last-Event-ID` 让服务端从那里补发；缓冲已被覆盖时返回一个重置信号，前端做全量拉取。这正是 SSE 标准的 `Last-Event-ID` 机制，项目**没有用**。

- **项目对照**：有重连，没有游标和补发。判断一个流式系统可不可靠，就看它有没有「游标 + 补发」这一对机制。
- **判断标准**：能接受的缺口是「过程丢、终态对」，不能接受的是「终态也可能错」。

### 3. 工具调用迟迟不返回，超时、重试、幂等怎么设计？

**考察点**：能否把「超时」和「没执行」分开，以及重试策略的第一步是判断可重复性而不是次数。

**回答**

关键判断：**超时只说明等待超过阈值，不代表操作已终止，更不代表没有产生副作用**。把「超时了」当成「没执行」，是这类设计里最常见的误判。

**第一问不是「重试几次」，而是「重复执行会怎样」**：

| 操作类型 | 可重试性 | 处理 |
| --- | --- | --- |
| 只读（`read` / `grep` / `ls`） | 安全 | 可直接重试 |
| 幂等写（整文件 `write`） | 安全 | 可直接重试 |
| 非幂等写（追加、`git commit`、发消息） | 危险 | 转人工确认，不自动重试 |

**超时分层**：单工具超时、整轮任务超时、空闲超时，三层语义不同。单工具超时的处理有个讲究——把它作为**结果**返回给模型，而不是抛错终止任务。模型需要知道这个工具超时了，才能决定换方法还是报失败。

但必须补一句：**把超时信息交给模型不等于系统安全了**。模型收到之后仍可能决定再调一次。执行层要有自己的保障，能回答「有没有副作用」「重复调用后果是什么」「要不要人工确认」。

**一个「重试」按钮在没有幂等保证时是危险的**——它只是把用户的一次误判变成两次副作用。

- **项目对照**：工具级超时、任务级超时、重试、幂等键**都没有**。代码里有个 3 秒兜底定时器，但那是为了让界面不永久停在运行中，与中断超时工具是两回事。这一点必须主动说，否则被追问「超时后怎么保证不重复执行」会答不上来。
- **迁移原则**：任何「调用外部系统 + 用户能看到状态」的地方都适用，不只是 Agent 工具。

## 第二层：并发与一致性

### 4. 用户快速切换会话，旧请求才返回，怎么防止状态污染？

**考察点**：能否说出「为什么不用取消请求」和「三层判据各挡什么」。只答会话 ID 的人会被「切走再切回」追问到卡住。

**回答**

根本问题是：**异步操作完成时，发起它的上下文可能已经不存在了**。

先说一条判断：**不要用取消请求来解决**。取消能省带宽，但**不能保证回调不执行**——已缓冲的数据仍可能触发回调。所以在**写入点校验**：数据真正写进状态之前，判断它还算不算数。

三层是逐步加出来的，每层被一个具体场景逼出来：

| 层 | 判据 | 挡住的场景 |
| --- | --- | --- |
| 1 | `sessionId` | 响应回来时已经切到别的会话 |
| 2 | `sessionGeneration` | 从 A 切到 B 再切回 A，第一层放行，但响应属于**上一轮**生命周期 |
| 3 | `reloadSequence` | 同一会话内两次对账乱序返回，旧数据晚于新数据到达，界面「倒退」 |

代次在每次关闭会话时递增；序号在每次查询前递增。最严格的写法是三个条件同时成立才写入。

整个 store 有十几处校验点，原则是**每个 `await` 之后都要重新确认**——await 期间用户可能切了会话。

- **抽象规则**：异步结果写入状态前，同时确认**归属**（属于哪个实体）和**代次**（是不是最新一次操作）。两者缺一不可：只有归属会漏「同一实体被重复操作」，只有代次会漏「实体已经换了」。
- **同源问题**：队列状态有两个写入源（SSE 推送 + HTTP 拉取），拉取飞行期间推送落地，返回的快照就过期了，直接覆盖会让排队数量倒退。做法是版本号 + 条件写入，与数据库乐观锁同一思路。判断要不要加守卫看的是**有没有第二个写入源**，不是「这个状态重不重要」。
- **项目对照**：三层都实现了。已知缺口一处——`workspaceStore.syncFromSessionCwd()` 没有 sessionId 守卫，影响范围限于工作区选择器显示。
- **迁移场景**：搜索联想、表单异步校验、切换详情页、并发保存。

### 5. Agent 执行到一半用户改主意，怎么保证行为符合预期？

**考察点**：能否把「改主意」拆成追加、停止、撤回三种操作，并指出「停止」的真实语义与用户预期相反。

**回答**

「改主意」在系统里是三个不同操作，时序约束完全不同。

**① 追加指令——判断放服务端，不放前端。**
「这条指令插到当前轮，还是等当前轮跑完」需要知道服务端此刻的执行状态，前端手里那份是可能过期的副本。前端自己猜，猜错就变成「用户以为插进去了，其实开了新一轮」。所以判断放在接纳的那一刻。

**② 停止——必须先撤回队列，再中止。**
这里有个不直观的地方：**中止只中断当前执行，队列里剩下的指令还会继续跑**。用户点了停止、界面显示停了，实际上还有指令在排队等着执行，与用户预期相反。

所以改成**先撤回队列、再中止**。而且撤回失败就**不执行中止**——这时队列状态未知，贸然中止会让未知数量的指令继续执行，且没有恢复手段。宁可保持运行态、告诉用户「队列没确认」，也不要造出一个「看起来停了其实没停」的状态。

**③ 撤回——必须等接纳链结束。**
命令从发出到真正进队列是异步的。撤回抢在前面会拿到空队列，让前端以为清干净了，紧接着那条命令才被接纳进去。

**④ 兜底**：中止的响应和最终落定事件可能乱序甚至丢失，所以设一个几秒的兜底定时器，超时就强制落定并对账。

- **通用原则**：**取消长任务时，先处理排队中的动作，再处理正在执行的动作**。很多系统的取消语义只管后者。
- **项目对照**：三点都实现了（`clear_queue` 再 `abort`，兜底 3 秒）。
- **追问**：**如果写权限受限、撤回请求本身失败了怎么办？** 不用链式写法——中止被跳过、保留运行态，同时把失败原因透出给用户，可以重试撤回。宁可「没停干净」，也不要「以为停了」。

### 6. 用户想从第 3 轮改起，怎么保证分支语义正确？

**考察点**：能否从「历史只追加」推出「编辑的落点是父节点」。这是全场唯一一个必须靠推导、不能靠记忆的结论。

**回答**

先纠正一个直觉：**编辑历史不是「修改那条消息」**。

会话历史是**只追加**的结构——entry 一旦写入不可变，删改不了。既然不可变，「修改第 3 轮」只能表达成「从第 3 轮之前分叉出一条新路径」。所以编辑的落点不是那条消息本身，而是它的**父 entry**。

这个结论同时解释了为什么**发送前必须先导航**：导航到消息本身，新消息会挂成它的子节点，那就变成「在它后面继续对话」，编辑退化成追加。只有导航到父节点，新消息才会成为原消息的**兄弟**。

值得说明的是这不是独创——CLI 的树导航也是同一语义：选中一条用户消息，位置移到父节点，文本放回编辑器。这是「只追加 + 树索引」这种数据结构的自然结果。

**第二个设计点是先预览再导航。** 导航是唯一有副作用的操作，执行就改变服务端位置；预览是只读的，能提前发现非法目标和断链。把校验放在副作用之前，避免「已经跳过去了但目标是坏的」这种必须回滚的局面。

**第三是失败处理的区别**：

| 失败位置 | 服务端状态 | 处理 |
| --- | --- | --- |
| 预览阶段失败 | 理论上没动过 | 不需要回退 |
| 导航之后失败 | **不能假定「没发生」** | 超时可能是「已执行但响应丢了」，先重读真实状态，确认偏离才反向导航 |
| 回退也失败 | 位置未知 | 置「位置未知」，锁死发送/编辑/导航，要求重新加载 |

最后一种状态的含义是「不知道服务端现在在哪」，继续操作只会把消息挂到错误分支上。

- **边界**：项目**没有实现分叉和克隆**，它们是「创建新会话文件」的语义；这里的导航是在同一个文件里移动指针。这是产品选择，不是能力缺口——说清楚这一点否则会被当成没实现。
- **追问**：**为什么不复制一份历史做新分支？** 会话文件是 append-only + entry 树，复制会导致两份文件各自演进、无法合流；树索引本身已经能表达分叉，复制的成本远高于收益。

### 7. 多个工具并行执行，怎么处理依赖和部分失败？

**考察点**：能否看出难点不是「怎么同时跑」而是「部分失败怎么汇总」。答并发框架的人没答到点上。

**回答**

核心不是怎么并发，而是**部分失败的语义**。

**① 并行模型：默认独立并行。**
模型在一轮里发起的多个工具调用，通常是它判断可以同时做的事。做成「一个失败全部失败」，一个无关工具的失败会拖垮整个任务，模型也失去了「用部分结果继续」的机会。只有工具之间确实有依赖时才用全或无。

**② 汇总：每条结果带结构化成败标记。**
只给内容是不够的——只有一段输出，模型会从自然语言里猜「测试失败」是不是「测试成功」。

而且必须区分两种情况：

| 情况 | 含义 | 模型该做什么 |
| --- | --- | --- |
| 工具失败 | 进程崩了、参数非法、超时 | 换方法或报告 |
| 业务结果为负 | 执行成功但退出码非 0，测试没通过 | **视为有效结果**，继续分析 |

这个区分必须在汇总时保留，否则模型会误以为工具坏了，去重试一个其实正常工作、只是返回了失败结果的工具。

**③ 取消：显式设计。**
立即中断所有正在跑的工具（响应快，但可能留下半完成状态），还是等当前跑完（状态干净，但用户等待久）。更好的做法是标记取消、让工具自己响应，但这需要工具支持协作式取消。

- **项目对照**：**没有实现显式的并行编排**，工具执行由 SDK 内部处理，前端不参与调度。前端能做的是展示：`activeTools` 是映射结构，可以同时容纳多个，状态条会全部展示。所以多工具并行时界面不会串，但这是**展示层的正确性，不是调度能力**。这条边界要说清楚。
- **追问**：**并行的工具里有一个要写文件、另一个要读同一个文件，怎么办？** 这一层不做依赖分析——工具级依赖由模型自己在发起顺序上表达；如果模型发起了冲突调用，属于模型判断失误，不是编排层该兜的。要兜的话得引入文件级锁，复杂度远高于收益。

## 第三层：边界与可信

### 8. Agent 声称完成但结果没验证，怎么判断真的做完了？

**考察点**：能否承认这是一个产品缺口，并说出「模型结论」和「工具证据」是两份独立证据。

**回答**

关键是**把两件事分开**：系统能提供「执行过程」，不能提供「结果的可信度」。

用户能看到 Agent 读了哪些文件、跑了什么命令、输出是什么、工具有没有报错。但界面**不会替用户判断「Bug 是否真的修好了」**——这个结论来自模型的自然语言，不是经过验证的事实。如果任务实际失败但模型说成功了，界面会照着模型的话显示。

**项目没有做验证层，这是最真实的产品缺口**，而且它比缺几个功能更值得说，因为它涉及「Agent 系统该不该相信模型自己的话」这个根本问题。

如果要补，按成本排序：

| 步骤 | 做法 | 成本 |
| --- | --- | --- |
| 1 | **把确定性工具的退出码提升成结构化状态**，界面渲染成显著的通过/失败标记 | 极低，数据本来就在 |
| 2 | **区分「模型声称完成」和「验证通过」**——前者是自然语言，后者要工具证据 | 中 |
| 3 | 保留可回滚的修改记录 | 高 |

- **抽象原则**：模型的结论和工具的结果是两份独立证据，不能互相替代。能自动验证的任务，让确定性工具当裁判——跑测试、跑类型检查，用工具结果说话；不能自动验证的任务，明确显示「未验证」，而不是默认成功。
- **更高一层的判断**：**面对不确定的状态，应该展示不确定性，而不是假装成功**。这条比任何具体实现都重要，也是第一层第 1 题「未确认态」的同一条原则。

**追问**

- **让模型自检行不行？** 不行，这是同一个模型给自己打分。有效的是外部可判定信号：测试结果、退出码、diff 是否能编译。自检只能提高概率，不能给出保证。
- **如果任务本身无法自动验证呢？** 那就把「未验证」当成一等状态显式展示，并保留操作记录供人工复核。假装成功比显示不确定更糟。

### 9. 上下文越来越长，什么时候压缩、保留什么？

**考察点**：能否看出难点在「保留什么」而不是「怎么压」，以及压缩 ≠ 截断。

**回答**

难点不在压缩算法，在保留策略——压掉哪些内容直接决定后续任务能不能继续。

先澄清一个概念：**压缩不等于截断**。截断是直接丢，压缩是用摘要换空间。混淆的话会把「做了压缩」当成「已处理约束保留」。

**上下文分类**：

| 内容 | 处理 |
| --- | --- |
| 系统提示、工具定义 | 不能压 |
| 用户明确说过的约束（「不要改数据库」「必须用 TypeScript」） | **必须保留** |
| 任务目标、已完成工作、未完成待办 | **必须保留** |
| 工具调用与结果 | 体积最大，优先压缩 |
| 久远的对话 | 参考价值递减，可摘要化 |

判断依据是「哪些信息丢了会导致后续出错」。关键矛盾在于：这些关键信息通常在**早期对话**里，而压缩最容易压掉的恰恰是早期内容。

两个容易忽略的点：

- **摘要本身可能把推测当事实**。摘要由模型生成，可能把早期的猜测写成确定结论，后续就基于这个被固化的结论继续。所以摘要要可追溯——能点开看到被压掉的原消息。
- **压缩后占用会跳变**。摘要本身也占空间，压缩前的用量已不对应当前内容，这时界面应显示「不确定」而不是一个误导的数字。

- **项目对照**：**压缩算法是 SDK 的**，项目做事件对接和状态展示，「保留什么」的策略项目不参与。这是必须主动划清的边界——否则被问「你的保留策略怎么设计的」会露馅。
- **SDK 的实际判据**：`contextTokens > contextWindow - reserveTokens`，默认 `reserveTokens = 16384`、`keepRecentTokens = 20000`。是 token 差额不是百分比阈值，所以 200k 窗口约 91.8% 触发、32k 窗口约 48.8% 触发，界面上的 80% 只是警戒色。

### 10. Agent 能读写文件和执行命令，权限边界怎么划？

**考察点**：能否指出「注入本身不可怕，可怕的是注入后有足够权限造成伤害」，从而把问题定位到授权而不是过滤。

**回答**

先纠正一个误区：**恶意指令不只来自用户输入**。文件内容、工具输出、检索结果都可以是载体——读到一个含指令的 README，模型就可能照着做。所以这不是输入校验问题，是**执行层权限问题**。

两个相关但不同的问题：

| | 含义 | 关系 |
| --- | --- | --- |
| 提示注入 | 模型读到了不该听的内容 | 不可完全防住 |
| 过度授权 | 工具能做的事太多 | 可控 |

**注入本身不可怕，可怕的是注入成功后有足够权限造成伤害**。所以核心思路是限制权限，不是过滤内容——过滤做不到完全，授权可以做到最小。

**分层**：

| 层 | 内容 |
| --- | --- |
| 路径校验 | 词法归一化 + 真实路径双重校验，防 `../` 与符号链接逃逸 |
| 工具权限 | 只开必要工具，写操作单独授权 |
| 高风险确认 | `bash`、删除、`git push` 之类需人工确认 |
| 执行隔离 | 容器或受限用户兜底 |

**必须主动强调的一条判断**：**文件接口的路径校验不等于命令执行被沙箱隔离**。前者只保护「通过接口读文件」，后者保护「通过命令行做任何事」。很多人把前者当成后者的证明，这是错的——`bash` 一旦可用，路径校验就形同虚设。

项目里还有一处体现同源原则：图片上传做前端限制加服务端再验，代码注释写的是「前端压缩只是体验优化，不是安全边界」——客户端代码可被绕过，安全限制必须在服务端独立验证。

- **项目对照**：**只做了路径校验这一层**（双重校验 + SVG 预览的 CSP）。工具权限、高风险确认、执行隔离、审计日志都没有，接口也没有鉴权。项目定位就是本机使用，文档里明确写了「接口无鉴权，Agent 可执行任意命令，仅限本机使用」。要开放给多人，这几层都得补。
- **审计**：必须有，而且要脱敏，否则等于把风险换个地方存一遍。

## 第四层：系统与演进

### 11. 用户反馈「任务卡住了」，怎么分层定位？

**考察点**：能否用排除法把范围砍下来，以及能否区分「间接证据」和「直接结论」。

**回答**

先建分层模型，再用排除法，不要凭现象猜。

一条事件从产生到渲染经过：执行产生 → 封装层广播 → 流写入 → 网络传输 → 前端接收 → 状态更新 → 视图渲染。**任何一环断了，用户看到的现象都是「界面不动」——所以现象本身不能定位问题。**

**三个最快的检查**：

| 检查 | 结果 | 结论 |
| --- | --- | --- |
| 事件流里还有没有新数据帧 | 没有 | 问题在服务端或更底层 |
| 有帧但心跳也停了 | 是 | 连接层可能有问题 |
| 有帧、有心跳，但界面不动 | 是 | 问题在前端 |

这三步能把范围砍掉大半。

**然后逐层往里查，但不把间接证据当结论**：

- **会话文件是否增长**——能反映执行有没有推进，**但落盘发生在消息定稿时，流式增量不落盘**，文件不增长也可能只是正在生成长回复。
- **心跳停了**——通常说明连接有问题，**但也可能是服务端写入失败后静默导致的**，不能直接断定网络断开。
- **有数据帧但页面不动**——可能是事件内容无效、被状态守卫拦截（第 4 题的假阴性）、或者状态更新了但没产生预期渲染。得进事件入口和状态里确认。

- **项目对照**：主动说清防不住什么——没有超时检测，底层真卡住界面会一直显示运行中；写入失败后流不会主动关闭，浏览器感知不到是死连接；没有服务端日志，看不到事件有没有到达封装层；没有分阶段耗时，分不清是模型慢、工具慢还是重试在拖。
- **改进顺序**：先补分阶段埋点和服务端日志——**没有数据就无法定位瓶颈**，这是后面所有工作的前提。

### 12. 模型变慢、变贵、输出不稳定，怎么设计监控和降级？

**考察点**：能否把模型调用当成有服务等级和预算约束的外部依赖，而不是透明函数调用。

**回答**

**第一步是能区分「是谁的问题」。** 关键认知：总耗时 = 模型推理 + 工具执行 + 排队 + 重试。如果只有一个总数，模型变慢、工具卡住、并发超标、重试放大这四种情况的曲线完全一样，无法定位。

所以分阶段埋点是基础。但它有前提——**每一阶段都得有可记录的位置**，不是加个计时器就能拿到全部数据。

| 指标 | 分几段 |
| --- | --- |
| 延迟 | 首字延迟、模型段、工具段、排队段、重试段 |
| 成本 | 输入 token、输出 token、缓存命中、按会话/按任务聚合 |
| 稳定性 | 失败类型分布、重试次数、超限次数、压缩次数 |

**成本控制分三层，顺序不能颠倒**：

| 层 | 内容 | 为什么这个顺序 |
| --- | --- | --- |
| 可见 | 展示 token 与成本 | 看不见就无从管理 |
| 可限 | 预算上限、任务级成本熔断 | **只做可见不做可限等于只报警不刹车** |
| 可优 | 按复杂度选模型、缓存复用 | 需要前两层的数据支撑 |

**降级策略的取舍**：

- **重试**适合瞬时故障，但会放大成本——重试段本身就是延迟和费用的放大器。
- **切换模型**要小心，不同模型的工具调用格式、上下文窗口、多模态支持都可能不同，切换要验证适配层。
- **无法自动恢复时，明确提示用户比假装成功好**——这和「未确认态」是同一条原则。

- **项目对照**：**只有「可见」**。有 token 和成本展示、上下文占用警戒色、重试进度提示。没有预算上限、没有任务级超时、没有分阶段耗时、没有审计日志，也不能按复杂度自动选模型。
- **改进顺序**：先补分阶段埋点，再做预算上限——**没有分阶段数据，就不知道该把预算卡在哪一层**。

### 13. 从零设计一个 Agent 工作台，你会怎么划分前后端职责？

**考察点**：能否先推导约束再谈选型，以及能否纠正「前端所有状态都是派生值」这种过于绝对的说法。

**回答**

**第一步：确定执行层放哪。** 三个约束——要读文件、要执行命令，所以需要本机能力；模型密钥不能下发浏览器；任务可能跑几分钟，生命周期不能绑页面。三条都指向**执行放服务端**。这不是设计选择，是被约束推出来的。

**第二步：划职责——这里有个容易讲错的地方。**
「前端所有状态都是派生值」过于绝对。真实情况分两类：

| 类别 | 例子 | 权威在哪 |
| --- | --- | --- |
| **业务事实** | 会话历史、执行状态、任务队列 | 服务端，前端必须能对账 |
| **交互状态** | 草稿、滚动位置、面板展开 | 前端自己，服务端不关心 |

把交互状态也当成必须从服务端重建，是过度设计。

而且「前端能不能重建」取决于三件事：**数据来源**是什么、**服务端持久化**了什么、**恢复协议**愿意补发什么。同一个「刷新恢复」，不同设计下能做到的程度完全不同——这个项目里草稿在本地存储所以能恢复，会话历史在磁盘所以能恢复，流式内容只在内存、靠服务端补快照才能恢复，断线期间的事件没有补发机制所以永久丢失。

**第三步：定协议。** 上行是离散命令、要明确成败，用 HTTP；下行是持续事件，用 SSE。最关键一条：**上行和下行的生命周期必须独立**——HTTP 返回不代表任务结束，连接断开也不代表任务停止。

**第四步：划清职责，不让职责重叠。** 比如前端不要判断「这条命令该入队还是开新轮」。

**第五步（最容易被忽略，也最能体现深度）：预先定义边界行为。** 断线怎么办、重复提交怎么办、超时怎么分层。

关于「服务端重启后恢复任务」，有个常见误解要专门说：**仅仅把任务记录写进数据库是不够的**。还要解决执行状态怎么恢复、已发生的工具副作用怎么算、以及「续跑」是断点继续还是整体重来。这三件没解决，任务持久化只是存了记录。

- **项目对照**：前四步都实现了，**第五步基本没做**——没有命令幂等、没有分层超时、没有任务持久化。这也是重做一遍会优先补的部分。
- **判断标准**：一个 Agent 工作台成熟与否，看它有没有第五步；有没有第四步只决定它能不能用。

### 14. 这个项目要从「本机工具」变成「团队协作产品」，需要补什么？

**考察点**：能否从「哪个隐含假设不成立了」推出改造清单，而不是罗列「加鉴权、加多用户」。

**回答**

先说当前的信任模型。作为本机工具，它有两个隐含前提：

| 前提 | 换成团队后 |
| --- | --- |
| **访问者可信**——只有本机用户能访问 | 不成立，接口无鉴权 |
| **执行范围可信**——只在自己机器上跑 | 不成立，Agent 能执行任意命令 |

所有改造都是从「哪个前提不成立了」推出来的。按五个维度补：身份授权、数据隔离、执行隔离、凭证保护、成本治理。

**三组最容易混的概念**：

**① 登录 ≠ 授权。** 认证回答「你是谁」，授权回答「你能访问什么、能做什么」。只做前者，用户登录后照样能改请求参数访问别人的会话。

**② 共享存储 ≠ 分布式执行协调。** 把实例注册表挪到 Redis 只解决「状态放哪」，没解决「请求和事件流怎么路由到同一个实例」以及「进程崩溃后正在跑的任务怎么办」。后两个要先确定会话归属模型——哪个实例独占执行哪个会话。

**③ 任务持久化 ≠ 任务可恢复。** 任务记录写进数据库只说明「有过这个任务」，不说明进行到哪一步、已发生的副作用怎么算。

**优先级按「改的是假设还是加功能」排**：

| 项 | 成本 | 理由 |
| --- | --- | --- |
| 执行隔离、多实例 | **最高** | 改的是架构假设 |
| 数据隔离 | 中高 | 要改会话文件与工作区的定位方式 |
| 身份授权 | 中 | 有成熟方案，但要贯穿到每个接口 |
| 凭证保护、成本治理 | 中 | 可在现有结构上加 |

- **项目对照**：五项都没有。必须主动说当前定位是本机工具，否则「为什么接口没鉴权」会变成对能力的质疑。
- **追问**：**最快能上线的一版怎么做？** 反向代理 + SSO 挡在入口、每用户一个工作区根目录、执行放进容器、费用按用户限额。这四项都不改核心逻辑，是「先能用」的最小集合。
