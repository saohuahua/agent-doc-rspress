# 02 核心设计的取舍

> 对应简历：**「前端用纯函数 reducer 按内容索引组装流式消息，工具调用与结果通过 toolCallId 关联」**；**「刷新后能恢复会话与流式状态，配合会话 ID、代次、序号三层校验防止竞态覆盖；接入上下文压缩与 Token 统计。」**
>
> 本篇只讲机制层的取舍：为什么这么设计、不这么设计会出什么问题、边界在哪。项目背景与选型见 [01 项目定位与选型](./01-project-and-selection)，故障与架构题见 [03 场景与综合](./03-scenarios)。

## 一、请求与执行解耦

### 1. 长任务为什么不放在 HTTP 请求里等？

**考察点**：能否说清「请求生命周期」和「任务生命周期」是两件事，以及拆开之后失败语义怎么区分。

**回答**

命令接纳和任务完成必须是两个信号。SDK 在同步校验通过时回调 `preflightResult`，接到自己创建的 Promise 上，HTTP 就在这里返回；任务结束由 `prompt()` 的返回 Promise 表示，结束后通过 SSE 发 `prompt_done`。

不拆的代价有三个，最后一个才是根本：

- 长任务阻塞请求，连接一直挂着；
- 必然撞上中间件或浏览器超时——5 分钟的任务没有哪种默认超时配置能兜住；
- **无法区分「发送失败」和「执行失败」**。一个错误响应可能意味着命令根本没被接受，也可能意味着接受之后执行崩了，前端对这两种情况的处理完全相反：前者可以安全重试，后者重试就是重复执行。

- **边界一**：SDK 同步抛错时也要把「未完成计数」减回去。发命令前加 1，抛错路径不处理，计数就永久泄漏，接口会一直报该会话在运行，而实际什么都没发生。这类计数泄漏在长连接场景里很典型。
- **边界二**：连接错误发生在接纳之后，**不能自动重试**。任务可能已在执行，重试会重复执行。正确做法是保留用户输入、提示先核对状态、主动拉一次权威数据对账。
- **推广**：任何「提交长任务」的场景都是这个模式——接纳走同步响应，完成走异步事件。

### 2. 会话实例为什么要缓存两次？

**考察点**：能否看出「只缓存已完成的实例」有一个创建期空档，以及这个空档在并发下会坏在哪。

**回答**

`AgentSession` 是有状态的重对象，初始化要打开会话文件、加载配置、注册工具，耗时几百毫秒到几秒。所以需要缓存。但只缓存「已完成」的实例会留一个空档：两个请求几乎同时进来，都查不到，于是各自创建一个执行对象，两个 Agent 同时往同一个会话文件写，行为不可预期。

所以做两级复用：

| 级别 | 缓存内容 | 挡住什么 |
| --- | --- | --- |
| 一级 | 已创建的实例 | 常规重复创建 |
| 二级 | **正在创建中的 Promise** | 并发请求撞进创建窗口 |

第二个请求直接 await 同一个 Promise，拿到同一个实例。

三个容易出错的细节：

- **注册用 SDK 返回的真实会话 ID，不是调用方传进来的**。新建会话时真实 ID 要等创建完才知道，提前用临时 ID 注册会导致后续所有请求都查不到。
- **新建会话必须用随机临时 ID**。如果两个新建请求用同一个占位 ID，第二级合并会把它们当成「同一个会话的初始化」，用户点两次「新建」拿到同一个会话。
- **锁一定要释放，包括创建失败**。否则一次失败让这个 ID 永久卡死。

- **必须说清的边界**：这个锁只合并初始化，**不提供命令幂等**。同一条消息因双击提交两次，两次都会走到发送逻辑，锁识别不出来。要做防重得引入命令 ID 和服务端去重记录。
- **另一层是接纳串行化**：SDK 判断「入队还是开新轮」依赖当前执行状态，两个命令并发进来会都读到「空闲」，但 SDK 只允许一个任务在跑。所以接纳判断被串行化到一条链上。撤回队列也要排这条链，否则可能撤到一个马上要被消费的队列。
- **空闲回收**：10 分钟无活动且没有 SSE 监听者时释放实例，释放前必须确认监听者为 0，否则会把正在被观看的会话拆掉。

**追问**

- **存在运行中 Prompt 时能回收吗？** 不能。判据是 `pendingPromptCount > 0 || inner.isStreaming`，两者任一为真都拒绝回收。

## 二、事件协议与推流

### 3. SDK 事件为什么要裁剪？

**考察点**：能否从数据结构推出复杂度问题，而不是「减少点数据量总是好的」。

**回答**

SDK 的 `message_update` 事件带一个 `partial` 字段，是**当前消息的全量快照**。流式回复一轮几百条增量，每条都带完整内容，传输量是 O(n²)：回复越长，放大倍数越大。一轮 500 条增量的回复，裁剪后累计约 5×10⁵ 字符；不裁剪的话最后一次快照就是完整内容，累计约 8×10⁶ 量级，相差一个数量级还多。

所以在包装层加一道裁剪：剥掉 `partial`，丢掉前端不用的事件类型（`turn_start` / `turn_end` / 原始 `message_start` 等），只留结构性事件。

裁剪带来一个必须处理的连带问题：**工具标识本来藏在 `partial` 里**。剥掉快照，前端就拿不到 `toolCallId`，卡片也就没法关联结果。所以裁剪时要把 `id`、`toolName` 提升到事件顶层。

这层适配的第二个价值是**防腐层**：SDK 升级改字段名，只改这一个转换函数，前端不动。这也是 `shared` 层不能直接 import SDK 包的原因——它是纯 ESM 加内嵌 WASM 的重包，进不了浏览器产物。

- **代价**：为了让事件更小，结束事件的附带信息被削掉了，前端无法从 `message_end` 判断这轮会不会重试，只能无条件对账一次。重试状态改由 `auto_retry_start` / `auto_retry_end` 单独传达。
- **边界**：裁剪是纯函数，不碰网络和状态，所以能单独写单测。这是把「协议适配」和「传输」分开的直接收益。

### 4. 一条 SSE 通道必须保留哪些语义？

**考察点**：能否说出每个语义对应的具体故障，而不是罗列「心跳、重连、补发」。

**回答**

三个语义，每个都对应一个真实的坑：

**① 先开通道、后握手**

冷启动要打开会话文件、初始化服务，可能要几秒。这期间 SDK 已经在产生事件，但监听器还没装上。所以握手之前的事件先缓冲，握手之后按序补发。

两个容易忽略的细节：流建立后要**立即写一帧注释行**，因为 SSE 的响应头只有在第一次写入时才真正发给浏览器，不先写这一帧，浏览器侧会一直 pending；响应头要显式设 `X-Accel-Buffering: no`，否则中间层会把事件攒起来批量发，流式效果就没了。

**② 流式快照重放**

用户刷新页面时如果 Agent 正在输出，刷新期间的增量全丢了。所以连接建立后，服务端在握手包里补发一条带完整内容的流式消息快照。

这**不是优化，是必要条件**——前端的组装逻辑要求流式消息先存在，没有快照的话后续所有增量都会被丢弃，用户看到的是一个永远空着的流式气泡。

**③ 心跳**

每 30 秒发一帧注释行。常见中间层超时是 60 秒，留一倍余量。用注释行是因为 SSE 协议规定冒号开头的行客户端会忽略，不会污染业务事件。

- **取舍**：写失败时必须 `cleanup(false)` 拆掉连接，不能静默跳过。否则一个已经死掉的连接会一直留在订阅者集合里，服务端以为有人在看。
- **待核实的边界**：快照和缓冲事件之间有一个去重逻辑，用**引用相等**判断「这条事件是否已经包含在快照里」。单测里用手工构造的对象验证过逻辑正确，但真实链路上 SDK 是否复用同一个对象引用，没有验证过。如果它每次都克隆，这条去重会失效。

### 5. 一条事件从 SDK 到浏览器经过哪些环节？

**考察点**：能否说清每层为什么单独存在。答成「SDK 发出来前端收到」的人，讲不了可测试性和背压。

**回答**

```text
服务端
 ① SDK emit 事件
 ② 会话包装层原样广播给该会话的所有订阅者
 ③ 事件流：与快照比对去重 → 裁剪 → 序列化写进响应流
 ④ 网络
客户端
 ⑤ 连接层：归属判定（还是不是当前连接）→ 握手状态机
 ⑥ 状态层：按事件类型分派
 ⑦ 流式组装：纯函数 reducer 按 contentIndex 写入块
 ⑧ 视图：消息组件渲染
```

四个环节是项目的（②③⑤⑥⑦里除 SDK 外），一个是 SDK 的，一个是浏览器原生的。

每层单独存在的理由：

| 层 | 为什么单独 | 合并掉的损失 |
| --- | --- | --- |
| 裁剪层 | 纯函数，不依赖网络与状态 | 无法脱离网络单测 |
| 广播层 | 一个会话可能被多个浏览器标签订阅 | 多标签会互相抢事件 |
| 连接层 | 只管重连和归属，与业务无关 | 业务代码里到处判断「这还是当前连接吗」 |
| 状态层 | 知道每个事件该改哪个 state | 状态变更散落，查不到入口 |

- **代价**：服务端广播是同步的，客户端网络慢时写入流会积压，当前没有背压处理。这是长连接场景里容易被忽略的问题，也是「事件链路」这道题里唯一能体现深度的地方。

**追问**

- **为什么不在包装层就直接裁剪？** 广播层要给所有订阅者发同一份数据，裁剪属于「传输编码」而不是「业务分发」，放在流这一层才能做到一次裁剪多路复用。

## 三、前端状态一致性

### 6. 流式消息为什么用纯函数 reducer 按内容索引组装？

**考察点**：是否理解「助手消息不是字符串，是块文档」，以及为什么用索引而不是「找最后一个同类型块」。

**回答**

Agent 一轮回复的真实形态是「先思考、再调工具、拿到结果再输出文本」，这些块交替出现，顺序就是真实发生的顺序。表示成字符串就没法把工具调用渲染成可折叠卡片，也没法在卡片里展示参数和结果。所以消息是**块数组**，流式事件带 `contentIndex` 指明这个增量属于第几块。

**为什么用索引，而不是「找最后一个同类型块」**：一轮里可能有多个同类型块。去找最后一个文本块时，第二段文本的第一个增量到达时那个块还没被创建，会被错误地追加到第一段后面。索引消除了这个歧义。

组装做成纯函数，不依赖框架也不依赖 SDK。好处有两个：能直接写单测（给状态和事件，断言输出，不用模拟网络）；流式状态变更收敛到一个入口，要查「哪里会改状态」搜一个函数名就够。

九个事件分支按行为分三类，这个分类是整个容错策略的骨架：

| 类型 | 行为 | 性质 |
| --- | --- | --- |
| 幂等（`_start`） | 块存在就保留，不存在就创建 | 重复到达不出错 |
| 增量有损（`_delta`） | 要求当前块类型匹配，不匹配就丢弃 | 会丢内容，但不会写错位置 |
| 权威（`_end`） | 不检查当前块，直接用事件内容覆盖 | **能自愈**，中间全丢也能修正 |

由此得到一条关键特性：**中间丢事件不会导致最终结果错误，只会导致过程中的显示不完整。**

- **为什么快照是必要的**：没有 `message_start` 时流式消息为空，守卫会拦下所有增量——包括那个本该自愈的 `_end`。所以服务端补发快照不是可选优化。
- **纯函数和状态库不是二选一**：纯函数负责「给定事件算出新状态」，状态库负责「什么时候处理、处理完还要做什么」。比如收到 `message_start` 时状态库先判断当前是否还在运行，已结束就是迟到事件，处理它会让已经消失的气泡复活，直接跳过。
- **实现边界**：公共函数 `updateContentBlock` 只检查索引下界，不检查上界。增量类分支因为要做类型匹配，越界时自然返回空、是安全的；但幂等类和权威类会创建新块，越界时在数组里留下空洞。正常路径不触发，**且没有测试覆盖**。要修的话得按类型区分上界：幂等类允许在末尾新建，权威类应要求块已存在。

### 7. 工具调用和结果怎么关联？拿不到结果时界面显示什么？

**考察点**：第二问才是重点。只说 `toolCallId` 关联是及格线，能指出「没结果显示成完成」是把未知说成成功，才是加分点。

**回答**

**关联**：工具调用在助手消息的 `content` 块里，结果是一条独立的 `toolResult` 消息，唯一关联标识是 `toolCallId`。关联关系做成**派生值**（computed）而不是独立状态——独立状态就要手动同步，结果更新时容易漏；派生值自动跟着消息列表重建，只有一份事实来源。

**状态判断**：不能用「消息是不是还在流式」来判断工具是否在跑。**助手消息在工具开始执行之前就已经定稿了**，定稿后流式标记是 false，但工具才刚开始跑。所以另有一个「正在执行的工具」映射，`tool_execution_start` 写入、`tool_execution_end` 删除。

真正的问题是状态语义。有三种情况都会导致「没有结果」：

| 情况 | 当前显示 | 应该显示 |
| --- | --- | --- |
| 工具还在跑 | 执行中 | 执行中 |
| 结果事件丢了 | **完成** | 未确认 |
| 工具根本没启动 | **完成** | 未确认 |

后两种把未知说成了成功。用户看到「完成」就会以为可以继续下一步，这是真实的产品问题。正确做法是加第四个状态「未确认」：拿不到结果、也不在正在执行的集合里，就是未确认。纯前端改动，成本几乎为零。

- **抽象原则**：用证据驱动状态，而不是用「没消息就是好消息」推断。有明确成功信号才算成功，有明确失败信号才算失败，两者都没有就显示「无法确认」。这条适用于所有「发起操作 + 异步等结果」的界面——支付、构建、部署。
- **其他异常输入**：标识缺失时归一化给空串，多个缺标识的工具会互相串；结果找不到对应调用时渲染成不显示的空节点，**用户看不到「有个结果没配上」**，问题被静默了；执行结束到结果到达之间有短暂窗口，卡片会闪一下「完成」但结果区是空的。

### 8. 流式内容、已定稿消息、工具状态为什么要分层？

**考察点**：能否用「生命周期和权威性不同」把三者分开，而不是「代码组织更清晰」。

**回答**

判断依据是**生命周期和权威性不同**：

| | 流式消息 | 已定稿消息 | 正在执行的工具 |
| --- | --- | --- | --- |
| 来源 | 增量事件拼出来 | 会话文件 | `tool_execution_start/end` |
| 权威性 | 临时，可能不完整 | 权威，持久 | 实时，只在内存 |
| 稳定标识 | 无 entryId | 有 entryId | 用 toolCallId |
| 可编辑 | 否 | 是 | 否 |
| 列表键 | 无（始终是最后一个节点） | 用 entryId | 用 toolCallId |

混在一个列表里会遇到三个具体问题：**对账时不知道该不该覆盖**（重新拉权威数据应整体替换已定稿部分，但不该碰正在流式的内容）；**编辑功能无法定位**（编辑历史消息要用 entryId 定位树节点，流式消息没有，只能分开传参）；**列表复用策略不同**（一个用稳定键，一个始终是尾节点）。

还有一层容易被忽略：**运行状态条**。它显示「此刻正在跑什么」，工具卡片显示「已完成消息里的工具调用」——两个不同时间维度的信息，不能互相替代。状态条读的是 `activeTools`，卡片读的是消息内容。

- **顺序敏感的细节**：消息定稿时必须**先把内容追加到已定稿列表、再清空流式气泡**。顺序反了会闪一帧重复或一帧空白。这类「交接顺序」在分层设计里很容易踩坑。
- **不维护多余状态的例子**：思考耗时没有计时器，而是用相邻两条消息的时间戳差算。对账后计时器会丢失，但时间戳从会话文件读出来，永远能重算。

### 9. 异步结果返回时，怎么判断它还算不算数？

**考察点**：能否说出「为什么不用 AbortController」和「三层判据各挡什么」。只答「用会话 ID 判断」的人，会被「切走再切回怎么办」追问到卡住。

**回答**

根本问题是：**异步操作完成时，发起它的上下文可能已经不存在了**。

先说一条判断：**不要试图用取消请求解决这个问题**。取消能省带宽，但**不能保证回调不执行**——已经缓冲的数据仍可能触发回调。所以在**写入点校验**，数据真正写进状态之前判断它还算不算数。

三层是逐步加出来的，每层被一个具体场景逼出来：

| 层 | 判据 | 挡住什么 | 不加会怎样 |
| --- | --- | --- | --- |
| 1 | `sessionId` | 响应回来时已切到别的会话 | 会话 B 的界面被 A 的数据覆盖 |
| 2 | `sessionGeneration` | 切走又切回同一会话 | 第一层放行，但响应属于**上一轮**生命周期 |
| 3 | `reloadSequence` | 同一会话内两次查询乱序返回 | 旧数据晚于新数据到达，界面「倒退」 |

代次在每次关闭会话时递增，请求发出前记下、回来时比对。序号在每次查询前递增。最严格的写法三个条件同时成立才写入。

整个 store 里有十几处校验点，原则是**每个 `await` 之后都要重新确认**，因为 await 期间用户可能切了会话。

同一个问题换了形态出现在队列状态上：队列有两个写入源——SSE 推送（实时）和 HTTP 拉取（有延迟）。拉取飞行期间如果推送落地了，返回的快照就是过期的，直接覆盖会让排队数量倒退。做法是给状态带版本号，请求前记下，返回时版本没变才写。

- **判断要不要加守卫，看的是「有没有第二个写入源」**，而不是「这个状态重不重要」。同一个函数里 `contextUsage` 是直接覆盖的，因为它只有拉取一个来源，且服务端每次现算。
- **抽象规则**：异步结果写入状态前，要同时确认**归属**（属于哪个实体）和**代次**（是不是最新一次操作）。两者缺一不可——只有归属会漏「同一实体被重复操作」，只有代次会漏「实体已经换了」。
- **已知缺口**：`workspaceStore.syncFromSessionCwd()` 缺 sessionId 守卫。这是从代码推导的，没实测过，影响范围限于工作区选择器显示。

**追问**

- **为什么不用 AbortController？** 取消请求和阻止过期结果生效是两件事。取消省带宽，但服务端可能已经开始执行，`fetch` 的 reject 也不保证 `then` 里的代码不跑。写入点校验是更可靠的防线。
- **这个模式还能用在哪？** 搜索联想、表单异步校验、切换详情页、并发保存——凡是「发起异步请求 + 等待期间用户可能改变上下文」的场景都一样。

## 四、恢复与失效

### 10. 刷新后恢复了什么、没恢复什么？

**考察点**：能否把「界面恢复」和「任务恢复」分开。答「刷新后什么都没丢」的人，没想清楚任务跑在哪。

**回答**

先拆概念：刷新之后要恢复的是「界面」。界面由三种数据拼出来：

| 来源 | 提供什么 | 补不上的时候 |
| --- | --- | --- |
| 会话文件 | 已落盘消息、分支结构、entry 树 | 页面空白 |
| 流式快照（握手包） | 刷新时正在输出的那条消息的完整内容 | 气泡永远空着，后续增量全被丢弃 |
| 增量事件 | 快照之后的新内容 | 界面停在快照那一刻 |

第二种最容易被低估。它不是优化，是必要条件——组装逻辑要求流式消息先存在。

但这三种补的都是**界面**。任务一直跑在服务端进程里，浏览器只是重新订阅。所以：

| | 刷新页面 | 服务端重启 |
| --- | --- | --- |
| 界面 | 恢复 | 恢复（从文件读） |
| 任务 | **继续跑** | **永久丢失** |

- **必须主动修正的一个说法**：不能说「最终状态一定正确，因为每次落定都会重新对账」。对账请求失败时是**静默**的——`fetchSessionDetail(id).catch(() => null)`，失败既不重试也不提示。准确说法是：对账机制存在，但它的成功依赖网络和会话状态，失败时界面停在上一次的数据，用户不知道可能已经过期。
- **正确性分级**：

| 场景 | 正确性 |
| --- | --- |
| 正常流式 | 最终一致 |
| 断线重连 | 快照后一致，中间过程丢 |
| 对账请求失败 | 停留在旧数据，静默 |
| 服务端重启 | 历史对，任务错，且前端不知道被中断 |

- **补偿逻辑**：断线期间任务若正好结束，落定事件是在没有连接时发的，永久丢失。处理重连信号时判断「服务端说没在跑、本地仍认为在跑」，就主动合成落定。

### 11. 上下文压缩是你做的吗？

**考察点**：能否主动划清归属。把 SDK 的算法说成自己的，是这类项目最容易被拆穿的地方。

**回答**

**压缩算法是 SDK 的，项目做的是接入和状态展示。**

SDK 有两条路径：手动压缩由用户触发，会先中止当前正在跑的任务，压缩后**不继续**被中断的轮次；自动压缩有两种 reason——`threshold`（上下文接近上限）和 `overflow`（模型已报超限后的恢复性压缩，会重试一次）。

一个容易答错的前提：**触发条件是 token 差额，不是百分比阈值**。判据是 `contextTokens > contextWindow - reserveTokens`，默认 `reserveTokens = 16384`。所以不同窗口下触发的百分比完全不同——200k 窗口约在 91.8% 触发，32k 窗口约在 48.8%。界面上那个 80% 只是展示用的警戒色，跟真实触发点没有对应关系。

项目侧做三件事：

- **对接事件**：`compaction_start` 驱动「压缩中」状态，`compaction_end` 触发对账，因为压缩会改变消息链。
- **手动压缩入口**：沿用和发命令一样的思路——HTTP 返回只代表命令被接纳，压缩真正结束要等事件。所以成功路径**不回滚**状态，只在失败时回滚。按「请求成功就算完成」写，界面会在压缩还没结束时就不显示进度。
- **展示**：压缩产生的 entry 在消息流里渲染成一条可折叠记录。

- **最容易被误解的点**：**压缩不删历史**。会话文件是只追加的，压缩只是追加一条摘要记录，被摘要的内容还在文件里，只是发给模型时被省略。所以「压缩后界面还能看到完整历史」是正常行为，不是 bug。
- **实现噪音**：代码里保留了 `auto_compaction_start` / `auto_compaction_end` 的兼容分支，但当前 SDK 版本里这两个事件**零匹配、永不命中**，是移植时留下的死代码。

### 12. 上下文占用和累计 Token 为什么不能相加？

**考察点**：能否用「统计范围不同」区分两个指标，而不是「一个是当前的、一个是总的」。

**回答**

| | 上下文占用 | 累计 Token |
| --- | --- | --- |
| 统计范围 | 此刻模型能看到的内容 | 整个会话文件 |
| 压缩后 | **下降** | 不变 |
| 分支切换 | 跟着变 | **不变**（含未激活分支） |
| 反映什么 | 容量压力 | 真实计费 |
| 是否估算 | 是（字符数 ÷ 4） | 部分锚定真实用量 |

占用是可变量，累计是单调量，两者口径不同，**不能相加**——代码注释里写死了这一点。

三个精度与边界：

- **占用是估算值**。SDK 的口径是字符数除以一个系数，注释说偏保守。只有在能拿到服务商返回的真实用量时才锚定到准确值，之后新增内容仍是估算。
- **刚压缩完的那一刻，占用是未知的**。压缩前的用量反映的是压缩前的规模，用它显示会严重高估，所以 SDK 返回空值，前端降级成**显示问号而不是 0%**。「未知」和「确定是空的」是两个语义，显示 0% 会让人以为上下文被清空了。
- **有一处承认的偏差**：项目自研的 `computeSessionStats(entries)` 只累加了压缩记录的用量，SDK 的统计还包含分支摘要。项目未启用分支摘要，所以实际无影响，但注释里「与 SDK 同一口径」的表述不准确。

- **为什么不用 SDK 的统计接口**：`getSessionStats()` 会读文件；服务端本来就要读这个文件来组装会话详情，所以顺手从 entries 算，省一次 IO。代价是口径需要自己维护。

### 13. 服务端重启时，正在跑的任务会怎样？

**考察点**：能否说出「哪些在内存、哪些在磁盘」，以及为什么这决定了完整方案不可行。答「加个持久化就好了」的人，没考虑执行状态本身不可序列化。

**回答**

先分清状态在哪：

| 状态 | 位置 | 重启后 |
| --- | --- | --- |
| 会话消息、entry 树 | 磁盘会话文件（JSONL） | 读得回来 |
| 执行实例 | 进程内存 | 丢失 |
| 正在跑的工具与子进程 | 进程内存 + 外部进程 | 丢失 / 不确定 |
| 运行队列、运行中消息 | 进程内存 | 丢失 |

直接结论：**任务永久丢失，而且前端不知道它被中断了。**

比结论更值得讲的是**为什么不能简单修好**。Agent 执行不是一个可序列化的状态，它是活的进程——里面有正在接收的模型流式响应、正在跑的子进程、内部状态机。所以「能恢复的只有结果，不能恢复的是过程」。这个判断决定了完整方案不在可行范围内。

一个容易被忽略的后果：**单纯恢复历史消息不够**。历史里没有「有一个任务被中断了」这个事实，重启后接口返回空数组，前端以为一切正常。如果中断发生在一次工具调用之后，会话文件里会留下「有调用但没有结果」的半截数据，而界面把它显示成「完成」——这是主动误导。

- **必须说得精确**：进程重启后执行上下文必然丢失，但外部子进程是否一定退出**不确定**，取决于它有没有脱离父进程组。项目没有显式管理这个，属于待核实，不能说成「一定退出」。
- **改进按成本排序，不按效果排序**：
  1. **状态语义修正**（零成本，纯前端）：查不到结果就标「未完成」而不是「完成」。消除的是主动误导，最该先做。
  2. **执行状态落盘**：记录「运行中 / 已完成 / 已中断」，启动时把残留的「运行中」改写成「已中断」，前端至少能告诉用户上次的任务断了。
  3. **命令幂等**：命令 ID + 服务端去重记录，防止重试导致重复执行。
  4. 完整任务恢复：需要 SDK 支持序列化执行状态，当前不提供，不可行。

## 本篇小结

| 设计 | 解决什么 | 代价 |
| --- | --- | --- |
| 接纳与完成分离 | 长任务不阻塞 HTTP | 前端要处理多个信号与乱序 |
| 两级实例缓存 | 并发创建的空档 | 只合并初始化，不保证命令幂等 |
| 事件裁剪 + 字段提升 | O(n²) 传输 | 结束事件信息不足，只能无条件对账 |
| 三个 SSE 语义 | 冷启动丢事件、刷新空白、中间层超时 | 去重依赖引用相等，未在真实链路验证 |
| 纯函数 reducer + 内容索引 | 块文档正确组装、可单测 | 上界不校验，越界会留空洞 |
| 三层判据 + 版本号 | 竞态覆盖 | 校验点分散，漏一处就退化 |
| 分层展示 | 对账、编辑、复用的差异化处理 | 交接顺序敏感 |

**这套设计的共同底色**：前端是投影不是事实来源，所以每个写入点都要重新确认归属；容错靠「权威事件自愈」而不是「不丢事件」；所有不可靠的地方都要显式降级（未知显示问号、无结果显示未确认）。
