# pi-web-vue 项目面经

> 项目一句话：**给 pi 这个终端 coding agent 做了一套 Web 工作台——Node 服务端嵌入 Pi Agent SDK，把 SDK 事件适配成前端事件经 SSE 推送；前端用纯函数 reducer 组装流式消息，用三层判据防竞态覆盖。**
>
> 技术栈：Vue / Nuxt（`ssr: false`）· Nitro · `@earendil-works/pi-coding-agent@0.85.1` · SSE · Pinia。

## 一、三篇怎么分工

由浅到深，对应面试里三种不同的提问方式：

| 篇 | 回答什么 | 对应面试场景 | 题量 |
| --- | --- | --- | --- |
| [01 项目定位与选型](./01-project-and-selection) | 这是什么、链路怎么走、职责怎么划、为什么这样选型 | 「介绍一下你的项目」「这个项目你做了什么」 | 6 |
| [02 核心设计的取舍](./02-design-tradeoffs) | 每个机制为什么这么设计、不这么设计会怎样、边界在哪 | 「为什么不用 X」「这里怎么保证不出错」 | 13 |
| [03 场景与综合](./03-scenarios) | 出故障怎么办、换场景怎么设计 | 「如果……你怎么办」「限时设计一个」 | 14 |

## 二、选题标准

这 33 道题不是按代码结构列的，是按**「面试官真的会问吗」**筛的。进过筛子的必须满足至少一条：

| 标准 | 说明 | 例子 |
| --- | --- | --- |
| **简历上写了** | 简历里的每个技术词都可能被展开 | SSE、竞态、上下文压缩 |
| **有可追问的分层** | 答完还有第二层、第三层，能持续区分高低 | 三层判据、九分支三类 |
| **是常见误解点** | 多数人的答法是错的，答对立刻拉开差距 | 压缩是百分比阈值、超时等于没执行 |
| **有真实的失败面** | 能讲清「哪里会坏、凭什么判断」 | 对账静默失败、去重依赖引用相等 |
| **边界容易被夸大** | 需要主动划清归属的地方 | 移植 vs 自研、算法 vs 接入 |

被筛掉的：纯代码导航（「这个函数在哪个文件」）、纯配置说明、需要看屏幕才能讲清的行号级细节。这些面试不会问，问了也讲不出深度。

## 三、最该先说清的五个结论

面试前十分钟复习这五条，其余都从这里长出来：

1. **动机是呈现模型，不是 CLI 缺功能。** CLI 有 `/tree` `/fork` `/clone`，Web 端补的是「跑一会儿再回来看」这种用法需要的结构化视图。
2. **接纳与完成是两个时点。** HTTP 返回只代表命令被收下；不拆开就无法区分「发送失败」和「执行失败」。
3. **前端是投影，不是事实来源。** 所以每个 `await` 之后都要重新确认结果还算不算数——三层判据（会话 ID / 代次 / 序号）就是这条的直接产物。
4. **容错靠权威事件自愈，不靠不丢事件。** 中间丢增量只会显示不全，`_end` 一到就修正；但前提是流式消息先存在，所以快照重放是必要条件而非优化。
5. **不可靠的地方要显式降级。** 占用未知显示问号而不是 0%，结果未知显示「未确认」而不是「完成」。

## 四、能力归属：四类分清

被问「这个项目你做了什么」时，**按四类答，不要笼统说「自研」**：

| 类别 | 内容 |
| --- | --- |
| **SDK 提供** | 执行循环、模型调用、工具执行、会话文件读写、**上下文压缩算法**、占用估算、分支导航、原生事件 |
| **从 pi-web 移植** | 28 个文件：流式消息组装、事件连接与适配、归一化、会话统计、事件流、会话读取、会话管理器 |
| **改写或新增** | 实例注册与并发合并、两个完成时点与自造事件、接纳串行链、三层判据与队列版本、编辑历史的分支流程、停止前撤回队列、图片三层防护 |
| **未实现** | `fork` / `clone`、事件重放与补发、任务级恢复与持久化、结果验证层、MCP、RAG、多用户 |

判断方法不能只看目录——`server/utils/event-stream.ts` 在服务端目录下但它是移植的。可靠的是两条：查第三方来源声明；看事件名能不能在 SDK 里搜到（`agent_settled` 搜得到是原生，`prompt_done` 搜不到是自造）。

## 五、最需要主动划清的边界

这几条**主动说**是加分，被追问出来是减分：

| 边界 | 正确说法 |
| --- | --- |
| 移植 vs 自研 | 28 个文件是移植的，不做从零宣称 |
| 压缩 | 算法是 SDK 的，项目做接入和展示 |
| 路径校验 vs 沙箱 | 文件接口的路径校验不等于命令执行被隔离 |
| 重连 vs 补发 | 有重连，没有游标和补发，断线期间事件永久丢失 |
| 对账 | 机制存在，但失败时静默，界面会停在旧数据 |
| 验证层 | 没有。界面展示执行过程，不保证结果正确 |
| 鉴权 | 没有。定位是本机工具，仅限本机使用 |

## 七、开场怎么讲这个项目

三十秒版本，按「问题 → 约束 → 方案 → 取舍」四步：

> pi 是终端里的 coding agent，能力和 CLI 一样完整，但终端的信息组织方式不适合长时间回看——工具调用是文本流里插的几行，执行状态只能看最后一行有没有在刷。
>
> 三个约束决定了架构：工具要碰本机文件系统、模型密钥不能下发浏览器、任务可能跑几分钟。所以执行放 Node 服务端，浏览器只做投影。
>
> SDK 的事件流适配成前端事件走 SSE，前端用纯函数 reducer 按内容索引组装块文档。最难的部分不是传输，是**一致性**——异步结果回来时上下文可能已经变了，所以每个写入点都要确认归属和代次。
>
> 代价是这套东西只能单机跑，多用户要补鉴权和执行隔离。

**接着等追问，不要一次讲完。** 上面四段每一段都能被展开成一整题，主动留接口比一次说完更容易拿到追问的主动权。
