# Agent 基础概念

> 依据《2026 秋招 Agent 全栈速成高频分析报告》：概念题是 Agent 面试的开场题，几乎每场必问。
> 定位：基础概念与核心设计认知；工程落地深挖见《01-Agent Runtime与架构》。
> 每题末尾的引用块是面试版回答，口述 1~2 分钟，可直接背，均结合实际开发视角收尾。

## 1. 你认为的 Agent 是什么？它和大模型、Workflow 的区别

- 一句话定义：Agent 是以 LLM 为决策核心，能自主完成"感知 -> 决策 -> 行动"闭环、通过工具与环境交互、循环执行直到完成目标的系统
- 定义里的四个关键词：
  1. LLM 决策核心：模型是大脑，但大脑本身不是 Agent
  2. 工具使用：能调工具产生真实副作用（查库、执行代码、改数据）
  3. 自主循环：自己决定下一步、要不要继续、何时结束
  4. 目标导向：对任务结果负责，不是单轮问答

```latex
Agent 的最小闭环
  -> 感知：接收任务 + 工具结果回灌
  -> 决策：LLM 基于上下文决定下一步
  -> 行动：执行工具或输出最终答案
  -> 循环：直到目标达成或触发终止条件
```

- 与大模型的区别——"能力"和"系统"的区别：

| 维度 | 大模型（LLM） | Agent |
| --- | --- | --- |
| 本质 | 能力/组件：文本进出 | 系统/产品形态：多组件组装 |
| 状态 | 每次调用独立，不记得上次 | 有 State，跨轮次、跨会话 |
| 行动 | 只能生成文本 | 能调工具产生真实副作用 |
| 目标 | 完成一次生成 | 完成一个任务并对结果负责 |
| 类比 | 大脑 | 大脑 + 手 + 记忆 + 工作流 |

- 与 Workflow 的区别一句话：控制流在谁手里——Workflow 是开发者用代码写死控制流，LLM 只在节点内干活；Agent 是模型决定控制流
- 与 Chatbot 的区别：Chatbot 一问一答、无目标无工具；Agent 有目标、自主多步、对结果负责
- 三者怎么选的完整决策维度见《01》第 1 题

> 我认为 Agent 是以大模型为决策核心，能自主完成"感知、决策、行动"闭环的系统：模型决定调什么工具、要不要继续、什么时候结束，循环执行直到完成目标。它有四个特征——LLM 做决策、能用工具、自主循环、对结果负责。
>
> 它和大模型的区别是"能力"和"系统"的区别：大模型只负责文本进出，本身无状态、不能做事，两次调用之间什么都不记得；Agent 是把模型当大脑组装出来的系统，加了工具、状态、记忆和循环。实际开发里感受很直接：裸调 LLM 写个摘要函数，和做一个能自己查库、改数据、汇报结果的 Agent，工程量差一个量级，多出来的部分全是外围系统的活。
>
> 和 Workflow 的区别就一条：控制流在谁手里。Workflow 是我用代码写死步骤，模型只在节点里干活；Agent 是模型自己决定下一步。我项目里两种都用：固定流程走 Workflow 保确定性，开放任务交给 Agent，两者共用同一套工具层。

## 2. Agent 的核心架构是什么

- 面试常问形式是"画一下你的 Agent 架构"，答分层架构 + 一条数据流

```latex
治理层（横切所有层）
  -> 权限门禁 / 沙箱隔离 / 预算控制 / Trace / 评测

编排层（核心）
  -> Agent Loop：组装上下文 -> 调模型 -> 执行工具 -> 结果回灌 -> 判断终止
  -> 状态机 + Checkpoint 持久化 + 断点恢复

模型层
  -> LLM 推理决策；结构化输出（tool_calls / JSON）

工具层
  -> Function Calling / MCP：工具注册、Schema、执行、超时

记忆层
  -> 短期：会话上下文（State）
  -> 长期：记忆检索注入

交互层
  -> 对话 / 任务入口；SSE 流式输出
```

- 数据流一句话：`用户输入 -> 组装上下文（System Prompt + 记忆 + 历史） -> 模型决策 -> 工具执行 -> 结果回灌 -> 循环 -> 最终输出`
- 核心中的核心是编排层的 Loop——它把模型、工具、记忆串成闭环，没有 Loop 就只是 Workflow
- 组件清单与 Harness 的深挖见《01》第 3 题

> 我会分六层讲：最底下交互层负责对话和任务入口、SSE 流式输出；模型层是 LLM 推理决策加结构化输出；工具层管 Function Calling 和 MCP 工具的注册执行；记忆层分短期会话上下文和长期记忆检索；再往上是核心的编排层，Agent Loop 加状态机加 Checkpoint，把前面几层串成"组装上下文、调模型、执行工具、结果回灌、判断终止"的闭环；最外面还有横切的治理层，管权限、沙箱、预算和 Trace。
>
> 实际开发里我的体会是：模型层和工具层最容易做，真正决定项目能不能上生产的是编排层和治理层——Loop 怎么停、状态怎么恢复、权限怎么管。我项目就是这个结构：固定环节用 Workflow 节点，开放环节走 Loop，工具和记忆层两边共用。

## 3. Workflow、Agent、Tools 的概念和区别

- 先纠正一个隐含误区：三者不是并列关系，不在同一维度
  1. Tools 是"能力"维度：原子接口，被调用方，自己没有控制流
  2. Workflow 和 Agent 是"编排"维度：两种决定控制流的方式
  3. 层级关系：`编排层（Workflow 或 Agent） -> 调用 -> 工具`

| 概念 | 本质 | 控制流 | "下一步干什么"谁说了算 | 例子 |
| --- | --- | --- | --- | --- |
| Tool | 原子能力接口 | 无，被调用方 | 不回答，只执行 | 搜索、SQL 查询、执行代码、发邮件 |
| Workflow | 编排范式 | 开发者代码写死 | 代码逻辑 | 固定 RAG 管道、审批流 |
| Agent | 编排范式 | 模型循环中决定 | LLM 决策 | Coding Agent、排障 Agent |

- 三者的关系：
  1. Agent 的最小实现 = LLM + Tools + Loop；没有工具的 Agent 只能聊天，成不了事
  2. Workflow 同样能调 Tools，只是调用顺序写死
  3. 生产系统通常是混合体：外层 Workflow 控制阶段，某些节点内部是 Agent Loop
- Tool 的三个特征：Schema 定义（名字、描述、入参）、执行无状态（幂等靠调用方保证）、结果回灌（Observation 进上下文）

> 这三个不是同一维度的概念。Tool 是能力维度，一个原子接口，用 Schema 定义名字、描述和入参，它自己没有控制流，只负责执行返回；Workflow 和 Agent 是编排维度，是两种决定"下一步干什么"的方式——Workflow 是开发者用代码写死控制流，Agent 是模型在循环里自己决定。所以层级关系是编排层调用工具，而不是三者平级并列。
>
> Agent 的最小实现就是 LLM 加 Tools 加 Loop，没有工具的 Agent 只能聊天；Workflow 一样能调工具，只是顺序写死。实际开发里我们的系统是混合体：外层用 Workflow 控制阶段，比如先检索、再生成、再校验，其中"生成"节点内部是一个 Agent Loop，让模型自己决定查几次库、要不要重试。这样确定性和灵活性都有。

## 4. Agent 设计范式有哪些（重点：ReAct 与其实现）

- 范式回答的问题是：Agent 怎么组织"推理"和"行动"——同一个 Loop 的不同填法

ReAct 详解（重点，Yao 等 2022）：
- 全称 Reason + Act，核心思想：推理和行动交替进行，用行动结果修正推理
- 执行流：

```latex
Thought     -> 我需要什么信息 / 下一步该做什么
Action      -> 发起工具调用
Observation -> 工具返回结果
（循环，直到模型认为可以给最终答案）
Answer      -> 最终输出
```

- 具体示例：

```text
用户：北京明天适合跑步吗？
Thought: 需要先查北京明天的天气
Action: get_weather(city="北京", date="明天")
Observation: 小雨，气温 15-22℃，空气质量优
Thought: 有雨不适合户外跑，可以给结论了
Answer: 明天北京有小雨，不建议户外跑步；想动的话室内更合适
```

- 为什么有效：
  1. 推理链显式化：Thought 相当于逐步的 Chain-of-Thought，边想边做比一口气蒙答案错误率低
  2. 观察反馈：每步工具结果进上下文，错误在线纠正，不会一条路错到底
  3. 可解释可审计：整个决策链可回放，出问题能定位到是哪次决策
  4. 论文效果：在决策类任务（ALFWorld、WebShop）上大幅超过模仿学习和强化学习基线；知识问答上比纯推理链幻觉更少
- 原版与现代实现的区别：原版 ReAct 是纯 Prompt 范式，模型输出 "Action: search[...]" 这类文本，程序用正则解析后执行；现代实现换成 Function Calling 结构化输出（tool_calls 字段），本质循环不变。现在主流 Agent 的工具调用循环，本质都是 ReAct 的工程化变体
- 核心实现（现代版，二十行以内）：

```typescript
async function reactAgent(question: string, tools: Tool[]): Promise<string> {
  const messages: Message[] = [
    { role: 'system', content: SYSTEM_PROMPT },   // 角色 + 工具规范 + 终止要求
    { role: 'user', content: question },
  ];

  for (let step = 0; step < MAX_STEPS; step++) {
    // Reason + Act：模型决策，返回文本或 toolCalls
    const resp = await llm.call(messages, { tools: tools.map(t => t.schema) });

    // 终止判断：没有工具调用 => Answer
    if (!resp.toolCalls?.length) return resp.text;

    messages.push(resp.message);                  // Thought + Action 进上下文

    // 执行 Action，Observation 回灌
    for (const call of resp.toolCalls) {
      const tool = tools.find(t => t.name === call.name);
      const observation = tool
        ? await tool.execute(call.args)
        : `Error: 工具 ${call.name} 不存在`;      // 幻觉工具也回灌，让模型自纠
      messages.push({ role: 'tool', toolCallId: call.id, content: observation });
    }
  }
  throw new ReActLoopExceeded();                   // 最大步数兜底
}
```

- 实现的四个关键点：
  1. System Prompt 写清角色、工具使用规范和终止要求（"信息足够时直接回答"），不写清楚模型会无限调工具
  2. 工具描述质量直接决定 Action 选择准确率——描述要写"什么时候用"，不只写"是什么"
  3. 错误也要作为 Observation 回灌：工具不存在、执行失败都拼回上下文让模型自纠，而不是抛异常断掉整个循环
  4. 双重终止：模型不调工具（显式）+ MAX_STEPS（兜底）
- ReAct 的缺点：
  1. 走一步看一步，长任务缺全局规划，容易绕路
  2. 轮数多、Token 消耗高
  3. 依赖模型推理质量，弱模型的 Thought 不靠谱

其他范式（简述，对比表见《01》第 8 题）：
1. Plan-and-Execute：先全局规划再分步执行，补 ReAct 的全局性短板
2. Reflection / Reflexion（Shinn 等 2023）：执行后自我评审再重试，补质量短板
3. Multi-Agent 协作：拆角色分工协作，见第 7 题
4. 端到端自主循环（AutoGPT 式）：纯模型驱动无固定模式，灵活但最难控

> 我最熟的是 ReAct，Reason 加 Act，核心是推理和行动交替：模型先想清楚这步要干什么（Thought），发起工具调用（Action），拿到结果（Observation）再决定下一步，循环到能给出最终答案。它有效的点有三个：推理链显式化，让模型边想边做而不是一口气蒙答案；每步都有真实反馈在线纠错；整个决策链可回放好审计。比如问"北京明天适不适合跑步"，它会先想需要天气数据，调天气工具，看到下雨才下结论，而不是凭参数瞎编。
>
> 早期 ReAct 是纯 Prompt 范式，模型输出 Action 文本再由程序解析执行；现在的实现基本换成了 Function Calling 结构化输出，循环本质没变，主流 Agent 的工具调用循环就是 ReAct 的工程化变体。实现上核心就四件事：System Prompt 约定角色和终止要求，注册工具 Schema，循环里解析 tool_calls、执行后把 Observation 回灌，模型不再调工具就返回答案，外加最大步数兜底。有个容易漏的细节：执行错误也要作为 Observation 回灌，让模型自己换路，而不是抛异常把循环断掉。它的缺点是走一步看一步，长任务缺全局规划，而且轮数多 Token 贵，所以现在主流做法是混合：先 Plan 拆解再 ReAct 执行，关键产物加 Reflection 评审。我项目里的排障 Agent 就是这个结构，单步 ReAct，整体先出计划。

## 5. 复杂任务怎么拆分？为什么要拆？效果如何提升？

- 为什么拆（四个硬理由）：
  1. 上下文装不下：复杂任务的全部信息超出窗口，拆开后每步只装本步需要的信息
  2. 单步决策空间太大：让模型一步做太多事错误率飙升；拆小后每步目标单一，成功率高
  3. 可并行：无依赖的子任务并行执行，降总延迟
  4. 可恢复可审计：每步有 checkpoint 和完成标准，失败只重试该步，排障能定位到步
- 成功率的数学直觉（面试亮点）：

```latex
整体成功率 = 各步成功率的乘积
  -> 不拆：一步到位 60%
  -> 拆三步：每步 90% => 0.9 * 0.9 * 0.9 ≈ 73%
  -> 前提：拆分真的让每步变简单；否则步数越多乘积越小，拆了反而更差
```

- 怎么拆（三种方法）：
  1. 模型规划拆分（Plan-and-Execute）：先让 LLM 产出结构化任务清单，代码按清单执行，必要时 Re-plan
  2. 模板拆分（工程控制）：已知任务类型按固定阶段拆（需求理解 -> 检索 -> 生成 -> 校验 -> 交付），确定性强
  3. 递归拆分：子任务仍过大就继续拆，形成任务树；叶子任务 = 单工具或单次推理可完成
- 拆分产物要结构化：

```typescript
interface TaskPlan {
  goal: string;          // 总目标
  steps: TaskStep[];     // 拆解后的步骤
}

interface TaskStep {
  id: string;
  description: string;   // 这一步做什么
  dependsOn: string[];   // 依赖的步骤 id，空数组 = 可并行
  tool: string;          // 预期使用的工具
  done: boolean;         // 单步可验证的完成标准
}
```

- 拆分三原则：
  1. 单步可验证：每步有明确完成标准（测试过、字段全、返回码 200）
  2. 步间契约化：输出输入结构化传递，不靠自然语言猜
  3. 依赖显式建模：DAG 标注并行机会，无依赖的并发跑
- 效果怎么验证：盯四个指标——任务成功率、平均轮数、Token 成本、P95 延迟；Badcase 归因到具体步骤，再加强该步 Prompt 或调整拆分粒度，评测集回归
- 粒度权衡：太粗单步还是难，太细通信和 Token 开销大，按评测指标找平衡点

> 为什么要拆，我讲两个硬理由。一是上下文装不下，复杂任务的信息量超窗口，拆开后每步只装需要的信息；二是单步决策空间太大错误率会飙升，拆小之后每步目标单一。这里有个数学直觉：整体成功率是各步成功率的乘积，一步到位 60% 的任务，拆成三步每步 90%，总体就是 73%；但前提是拆分真的让每步变简单，不然步数越多乘积越小，反而更差。
>
> 怎么拆我常用三种：开放任务让模型先出结构化计划再逐步执行，也就是 Plan-and-Execute；已知类型的任务用固定阶段模板拆，代码控制确定性强；子任务还太大就递归拆成任务树。拆的时候守三个原则：每步可验证、步间契约化传数据、依赖建成 DAG 能并行的并行。
>
> 效果我盯任务成功率、平均轮数、Token 成本和 P95 延迟，Badcase 归因到具体步骤再调那一环。我项目里做过一次把"一次生成完整报告"拆成"检索、生成大纲、分节生成、校验合并"四步，成功率从五成多提到八成以上，收益就是每步变简单了，而且失败只重试单步，不用整个任务重来。

## 6. Agent 的长短期记忆系统：怎么做、怎么存、粒度、怎么用

- 为什么需要记忆：上下文窗口装不下全部历史；跨会话要连续（记住用户是谁、干过什么）；任务中间状态要留存
- 分层设计（三层）：

```latex
短期记忆（工作记忆）
  -> 内容：当前会话的消息历史、工具结果、任务 State
  -> 存储：进程内 / Redis，会话结束归档
  -> 粒度：message 级，每条 user / assistant / tool 消息
  -> 用法：每轮组装进上下文；超窗时滑窗裁剪 + 摘要压缩

会话摘要（中期）
  -> 内容：上一阶段或上一次会话的压缩摘要
  -> 目的：用几百 token 保住长对话的关键事实和结论

长期记忆
  -> 内容：用户偏好、事实（姓名/地址/习惯）、历史任务结论、领域知识
  -> 存储：向量库（语义检索）+ 结构化库（精确事实），带时间戳与来源
  -> 粒度：事实级，一条独立记忆一个条目，不存整段对话
  -> 写入：显式提取——会话结束后异步任务从对话里抽取值得记的事实，过校验再入库
  -> 读取：当前任务作为 query 检索 top-k 相关记忆，注入 System Prompt 或上下文
```

- 记忆条目的结构（事实级粒度的落地）：

```typescript
interface MemoryItem {
  id: string;
  userId: string;
  content: string;   // 一条独立事实，如"用户偏好中文回复"
  type: 'fact' | 'preference' | 'task_summary';
  ts: number;        // 时间戳，冲突时取最新
  source: string;    // 来源会话 id，可溯源
}
```

- 记忆冲突与过期（高频追问）：
  1. 新旧冲突（用户搬家）：记忆带时间戳，检索按时间取最新，或写入时显式作废旧条目
  2. 过期弱化：长期不命中、未被引用的记忆降权或归档淘汰
  3. 矛盾不强行合并：保留两条按时间排序注入，让模型结合上下文判断
- 粒度的权衡：太细（碎片）检索噪声大，太粗（整段）检索不准还浪费 token，事实级是常用平衡点
- 存储选型一句话：热会话 Redis、精确事实 MySQL、语义检索向量库，三层各司其职

> Agent 的记忆我分三层说。短期记忆就是当前会话的上下文，消息历史加工具结果加任务 State，存 Redis，粒度是 message 级，每轮组装进 prompt，超窗时做滑窗裁剪加摘要压缩。中间加一层会话摘要，用几百 token 保住长对话的关键结论。长期记忆存用户偏好、事实和历史任务结论，粒度是事实级，一条独立记忆一个条目，不存整段对话——整段检索既不准又浪费 token。
>
> 写入不是什么都记：会话结束后有异步提取任务，从对话里抽出值得长期记的事实，校验后入库，向量库做语义检索，精确事实放 MySQL 带时间戳。读取是拿当前任务当 query 检索 top-k 注入上下文。冲突是高频追问点，比如用户搬家：记忆带时间戳按时间取最新，或者写入时直接作废旧条目，长期不命中的降权归档。
>
> 实际开发里我最大的体会是写入门槛比检索精度更重要——什么都记，检索再准也会被噪声污染，所以提取这步宁缺毋滥，宁可漏记也不要错记。

## 7. 什么是 Multi-Agent？

- 定义：多个各有分工的 Agent，通过消息传递协作完成一个总体任务；每个 Agent 有自己的角色、上下文和工具子集
- 为什么需要（单 Agent 的三个瓶颈）：
  1. 上下文装不下：任务大了，单个 Agent 上下文爆炸
  2. 职责太杂：工具一多选择准确率下降，所有规范塞一个 Prompt 里互相干扰
  3. 无法并行：单 Agent 只能串行执行
- 典型架构（四种）：
  1. 主子架构（Orchestrator-Worker）：主 Agent 拆解分发，子 Agent 执行，结果汇总——最常用
  2. 流水线（Pipeline）：上一步输出是下一步输入，如"写码 Agent -> 评审 Agent"
  3. 辩论 / 评审（Debate / Review）：生成与 Critic 互查，提升质量
  4. 对等协商（Peer）：Agent 间多轮对话协商，如 AutoGen 的协作模式
- 通信方式：结构化消息传递（任务描述 + 约束 + 输入），或共享 State（各写各的 namespace）
- 必须主动说代价：通信有损、错误会传播、延迟叠加、调试复杂度上升——所以默认不拆，出现信号才拆（何时拆、状态竞争怎么处理见《01》第 12 题）
- 代表实现：Claude Code 的 SubAgent、MetaGPT 的角色分工、AutoGen 的多 Agent 对话

> Multi-Agent 是多个各有分工的 Agent 协作完成任务，每个 Agent 有自己的角色、上下文和工具子集，通过消息传递协作。它解决单 Agent 的三个瓶颈：任务大了上下文装不下、职责太杂工具选择准确率下降、串行执行没法并行。
>
> 常见四种架构：最常用的是主子架构，主 Agent 拆解分发、子 Agent 执行、结果汇总；流水线是上游输出做下游输入，像写码和评审分工；辩论评审是生成加 Critic 互相挑错提质量；还有对等协商的多轮对话式。通信上用结构化消息传任务描述加约束，子 Agent 不共享完整上下文，只把结果写回主 Agent。
>
> 但我会主动说代价：通信有损、错误会传播、延迟叠加、调试复杂度上升，所以我的默认立场是能单 Agent 就不拆。实际开发里我的用法是"单 Agent 为主、按需拆子 Agent"：主对话一个 Agent，重检索、重生成的环节拆出去，这样上下文聚焦，出问题也好定位。

## 8. Single-Agent 和 Multi-Agent 的设计方案

- 答题思路：先说方案跟着任务特征走，再分别给两套方案蓝图，最后给演进路径

```latex
Single-Agent 设计方案（一个 Loop 打天下）
  -> 单一 Agent Loop：一个模型实例、一份上下文、一个工具集
  -> 工具组织
     -> 按域分组注册（检索组 / 数据组 / 执行组）
     -> 工具多时渐进加载：先给工具索引，选中域再展开 Schema
  -> 上下文管理
     -> 近期对话全量 + 远期摘要
     -> 长期记忆按需检索注入
  -> State：任务状态 + 槽位 + 工具结果，单写者
  -> 治理：预算 / 权限 / Trace / 评测
  -> 适用：任务域单一、工具 20 个以内、上下文可控
```

```latex
Multi-Agent 设计方案（主子架构为例）
  -> 编排器（主 Agent）
     -> 拆解：产出结构化子任务（目标 + 约束 + 输入）
     -> 路由：按子 Agent 的能力描述分发
     -> 汇聚：结果合并、冲突裁决、最终输出
  -> 子 Agent
     -> 各自独立 Loop、独立上下文、独立工具子集
     -> 只领任务，不共享主 Agent 完整上下文
  -> 通信契约：结构化消息（任务描述 + 约束 + 输入 / 结果 + 置信度）
  -> 状态同步：共享 State 分 namespace，子 Agent 只写自己的子树
  -> 共享层：长期记忆、工具注册中心、全局 Trace 串联
  -> 适用：跨域任务、子任务可并行、需要上下文隔离
```

| 维度 | Single-Agent | Multi-Agent |
| --- | --- | --- |
| 上下文 | 一份，连贯但易膨胀 | 各自精简聚焦 |
| 工具选择 | 集中，多了易选错 | 分散到域，各自少而精 |
| 通信成本 | 无 | 有，消息有损 |
| 失败影响 | 单点 | 可隔离，子 Agent 失败只重试该子任务 |
| 调试 | 简单，一条链路 | 复杂，需要全局 Trace |
| 延迟 | 串行 | 可并行降延迟 |

- 演进路径（实际落地顺序）：先 Single-Agent 跑通 -> 出现上下文膨胀 / 工具过载信号 -> 把独立域拆成子 Agent -> 编排器只管拆解和汇聚
- 概念与架构类型见第 7 题；何时拆的信号与状态竞争见《01》第 12 题

> 我的设计原则是方案跟着任务特征走：先看任务是不是单域、工具规模和上下文压力，再定单还是多。
>
> Single-Agent 方案就是单一 Loop：一个模型实例、一份上下文、一个按域分组的工具集。设计重点是工具组织和上下文管理——工具超过二十个做渐进加载，先给索引再展开 Schema；上下文做近期全量加远期摘要，长期记忆按需检索注入。它胜在链路简单、上下文连贯、好调试，任务域单一时是首选。
>
> Multi-Agent 我用主子架构：编排器负责拆解、路由和汇聚，子 Agent 各有独立 Loop、上下文和工具子集，用结构化消息通信，共享 State 分 namespace 各写各的，长期记忆和 Trace 全局共享。它换来上下文隔离、工具分散更准、子任务并行和失败隔离，代价是通信损耗和调试复杂度。实际落地我建议先 Single 跑通，出现上下文膨胀或工具过载信号再拆域，不要一上来就多 Agent。

## 9. Agent 记忆压缩通常有哪些方法

- 前提认知：上下文窗口有限，多轮对话 + 工具结果持续膨胀，压缩是刚需
- 六种方法（按侵入性从低到高）：

```latex
1. 滑窗裁剪（最简单）
   -> 只保留最近 N 轮，旧的直接丢
   -> 便宜、可预期；缺点是硬丢信息

2. 摘要压缩
   -> 旧轮次用 LLM 压成一段摘要，保留关键事实、结论、实体
   -> 摘要替换原文进入上下文，原文外存留档可回查

3. 检索式外置（记忆外置）
   -> 全量历史转 embedding 入向量库，每轮按当前任务检索 top-k 回灌
   -> 上下文里只放"相关的"，不放"最近的"

4. 结构化抽取
   -> 把对话中的事实抽成 KV / 表格（姓名、日期、约束条件），代替原文
   -> 精确注入，token 占用最小

5. 工具结果压缩（常被忽略的大头）
   -> 工具返回的大 JSON / 长文本先截断或摘要，只留结论和关键字段
   -> 实际项目里工具结果往往占上下文一半以上

6. 分层保留策略（组合拳）
   -> System Prompt 永久保留
   -> 近期轮次全量、远期摘要、工具结果截断
```

- 触发时机三种：
  1. 阈值触发：上下文用量超过窗口 70~80% 时压缩
  2. 轮次触发：每 N 轮固定压缩一次
  3. 异步定时：后台任务压缩不阻塞当前轮（体验最好，要做新旧快照切换）
- 压缩质量保障（高频追问：怎么保证不丢关键信息）：
  1. 摘要 Prompt 明确要求保留：实体、数字、用户明确偏好、未完成事项
  2. 保留指针：摘要条目带原文引用 id，需要时可回查全文
  3. 压缩后验证：用问答对做压缩前后对照测试，关键信息仍在才算过
- 参考：Claude Code 接近上下文上限时会自动做压缩（auto-compact），思路就是摘要式压缩
- 三层记忆的完整设计见第 6 题

> 记忆压缩我按侵入性从低到高讲六种。最简单是滑窗裁剪，只留最近 N 轮，便宜但硬丢信息；第二是摘要压缩，旧轮次用 LLM 压成一段保留关键事实；第三是检索式外置，全量历史进向量库，每轮按需检索回灌，上下文里只放相关的不放最近的；第四是结构化抽取，把事实抽成 KV 表代替原文，token 最省；第五是工具结果压缩，这个常被忽略，实际项目里工具返回的大 JSON 往往占上下文一半以上，要先截断摘要只留结论；最后是分层保留组合拳：System Prompt 永久、近期全量、远期摘要、工具结果截断。
>
> 触发时机我倾向阈值触发，超过窗口七八成就压，也可以按轮次或后台异步压。关键是怎么保证不丢信息：摘要 Prompt 明确要保留实体、数字、用户偏好和未完成事项；条目带原文指针可回查；压缩后用问答对做前后对照验证。Claude Code 的 auto-compact 就是这个思路。我项目里用"近期全量 + 远期摘要 + 工具结果截断"三层组合，Token 占用降了一半以上，关键信息没出过丢失。

## 10. Agent 的上下文工程怎么设计

- 一句话定位：上下文工程回答"每轮调用时，窗口里放什么、放多少、按什么顺序"——Prompt 工程只是其中一个分区
- 演进关系：Prompt Engineering（怎么问）-> Context Engineering（放什么进上下文）
- 上下文分区管理（核心设计）：

```latex
上下文的组成（按分区管理，各有生命周期）
  -> System Prompt：角色、规则、工具规范（静态，版本化管理）
  -> 长期记忆：检索 top-k 注入（按需，每轮可能不同）
  -> 任务 / 会话状态：目标、槽位、进度（结构化注入，防跑偏的锚）
  -> 近期对话：最近 N 轮全量
  -> 远期摘要：压缩后的历史
  -> 工具结果：截断 / 摘要后的 Observation
  -> RAG 检索片段：本任务相关的知识
```

- 设计五原则：
  1. 分区管理：每个区域独立的生命周期和更新策略，不能一锅粥
  2. 按需注入：记忆、知识走检索，不是全量塞
  3. 动态组装：每轮根据任务重建上下文，而不是只追加
  4. 预算分配：每个分区设 token 预算，超了先压低优先级区域
  5. 位置讲究：关键指令放 System Prompt（开头），当前任务相关放结尾——模型对开头和结尾的内容注意力最强，中间容易丢（lost in the middle 现象）
- Token 预算分配示例：

```text
128k 窗口的预算分配（示例）
  System Prompt    2k   静态
  长期记忆         1k   检索 top-3
  任务状态         1k   结构化注入
  近期对话        16k   最近 10 轮
  远期摘要         2k   压缩历史
  工具结果        24k   截断后
  RAG 片段         4k   top-6
  输出预留         8k   响应空间
```

- 三个失败模式（面试亮点）：
  1. 上下文污染：无关信息进上下文干扰决策——工具结果不截断、检索不准
  2. 注意力稀释：塞太多"可能有用"的内容，模型反而抓不住重点
  3. 压缩雪崩：压缩丢信息 -> 模型重复提问 -> 轮次变多 -> 更快触顶
- 压缩方法见第 9 题，记忆分层见第 6 题

> 我理解的上下文工程，是回答"每轮调模型时窗口里放什么、放多少、按什么顺序"，Prompt 工程只是其中一个分区。
>
> 我的设计是分区管理：System Prompt 放角色、规则和工具规范，静态、版本化管理；长期记忆和 RAG 知识按需检索注入；任务状态结构化注入，这是防跑偏的锚；近期对话全量、远期摘要、工具结果截断。五个原则：分区各自有生命周期；按需注入不全量塞；每轮动态组装而不是只追加；每区设 token 预算，超了先压低优先级区；位置有讲究——关键指令放开头，当前任务相关放结尾，因为模型对开头和结尾的注意力最强，中间的内容容易丢。
>
> 实际开发里我踩过"注意力稀释"的坑：早期把检索结果全塞进去，觉得信息越全越好，结果模型反而抓不住重点，后来按相关度截断 top-k，效果反而更好。所以上下文工程的核心不是塞得多，是塞得准。

## 11. Agent 的多轮对话状态如何管理？如何防止跑偏并支持中断恢复

- 三个子问题分开答：状态管理、防跑偏、中断恢复

- 状态管理：状态内容结构化，不只是一串 messages

```typescript
interface ConversationState {
  sessionId: string;
  goal: string;                    // 本会话任务目标（防跑偏的锚）
  slots: Record<string, string>;   // 已收集的槽位字段
  stage: 'idle' | 'collecting' | 'executing' | 'clarifying' | 'done';
  pendingClarify?: {               // 澄清挂起：问出去了还没答
    question: string;
    askedAt: number;
  };
  toolHistory: ToolCall[];         // 工具调用历史
  updatedAt: number;
}
```

- 存储与流转：
  1. 存储：Redis 会话级热状态 + DB 持久化，跨请求可重建
  2. 状态机：idle -> collecting -> executing -> clarifying（挂起）-> done

- 防跑偏（三个手段，从软到硬）：
  1. 目标锚定：每轮把 goal + slots + stage 结构化注入上下文，模型永远看得到"当前在干嘛、还缺什么"——不靠模型记住，靠状态注入
  2. 偏题检测：新输入与目标相关性低时，先确认"是否切换任务"再继续；切换则归档旧任务、开新状态
  3. 约束兜底：System Prompt 写明只处理当前任务相关请求；超轮数 / 超时强制收敛

- 中断恢复：
  1. 挂起现场：用户离开或等审批时，把 state + 对话摘要持久化，会话标 suspended
  2. 恢复：用户回来 -> 重建上下文（state 注入 + 近期对话 + 摘要）-> 从 stage 断点继续，已收集的槽位不重问
  3. 超时策略：长期不回（如 24h）-> 会话过期归档，记忆层留摘要；再进入走新会话 + 记忆召回
- 任务级 Checkpoint 与宕机恢复见《01》第 10、11 题（本篇答对话级）

> 这题我分状态、防跑偏、恢复三段说。
>
> 状态上我不靠一串 messages 裸奔，而是结构化管理：任务目标、槽位、当前阶段、澄清挂起项、工具历史，存 Redis 会话级，用状态机管流转：空闲、收集、执行、澄清、完成。防跑偏三个手段，最核心的是目标锚定——每轮把 goal 和 slots 结构化注入上下文，模型永远知道在干嘛、还缺什么，不靠它自己记；其次是偏题检测，新输入和目标相关性低时先确认要不要切任务；最后 System Prompt 约束加轮数兜底。
>
> 中断恢复：用户离开或等审批时把 state 加对话摘要持久化，标挂起；回来后重建上下文从断点继续，收集过的槽位不重复问；长期不回就过期归档，记忆层留摘要，下次进来新会话加记忆召回。
>
> 实际开发里最深的体会是：跑偏的根因基本都是状态只存在对话原文里，模型聊着聊着就忘了目标。把状态显式抽出来每轮注入后，多轮任务的完成率明显提升。

## 12. 如何评估一个 Agent 的效果？评测集和指标怎么设计

- 评测分两层：离线评测（发布前门禁）+ 在线评测（灰度与线上监控）

- 评测集构建：
  1. 来源三角：真实用户 query 抽样（保分布）+ 边界与对抗 case（保鲁棒）+ 历史 Badcase 回流（保回归）
  2. 结构：输入 + 预期（工具调用轨迹 / 参考答案 / 关键字段）+ 评分标准
  3. 每条带归因标签：问题出在模型 / 检索 / 工具 / Prompt 哪一层
  4. 规模与版本化：先 50~100 条跑通闭环再扩；评测集跟代码一起版本化演进

```typescript
interface EvalCase {
  id: string;
  input: string;              // 用户输入 / 任务描述
  expectedTools?: string[];   // 预期工具调用轨迹
  expectedAnswer?: string;    // 参考答案或关键字段
  rubric: string;             // 评分标准（给 judge 或人工）
  tags: string[];             // 归因标签：model / retrieval / tool / prompt
}
```

- 指标四层：

| 层 | 指标 | 说明 |
| --- | --- | --- |
| 过程 | 工具选择准确率、参数正确率 | 轨迹级，规则断言可算 |
| 成本 | 轮次、Token、延迟 P95 | 工程指标，决定能不能上线 |
| 结果 | 任务完成率、答案正确率 | 核心业务指标 |
| 体验与安全 | 人工干预率、重试率、注入拦截率 | 线上采集 |

- 三种评测方法（组合用）：
  1. 规则断言：轨迹匹配、字段校验、Schema 校验——便宜、确定，适合过程指标
  2. LLM-as-judge：模型按 rubric 打分——覆盖开放任务；必须与人工抽检对齐校准，裁判本身会有偏
  3. 人工评估：金标准，贵，只做抽样校准

- 线上闭环：灰度发布 -> 看完成率 / 干预率 -> Badcase 回流入评测集 -> 归因到层 -> 修复后回归 -> 达标全量
- 门禁示例：新版评测集通过率不低于基线 -1%，且无新增高危 case，才允许发布

> Agent 评测我分离线和在线两层。
>
> 离线评测集构建是三角来源：真实 query 抽样保分布、边界和对抗 case 保鲁棒、历史 Badcase 回流保回归。每条 case 有输入、预期轨迹或参考答案、评分标准，还要打归因标签——出了问题知道是模型、检索、工具还是 Prompt 层的锅。规模上先五十一条跑通闭环再扩，评测集跟代码一起做版本化。
>
> 指标分四层：过程层看工具选择准确率和参数正确率，规则断言就能算；成本层看轮次、Token、P95 延迟；结果层看任务完成率和答案正确率，这是核心；线上再补人工干预率、重试率和注入拦截率。方法三件套组合：规则断言管确定性的，LLM-as-judge 管开放任务但要和人工抽检对齐校准，人工只做抽样。
>
> 上线走灰度，Badcase 回流评测集，归因修复后回归，达标才全量。我项目里的门禁是新版通过率不低于基线减一个点、无新增高危 case，这样每次改 Prompt 或工具都有数可依，不凭感觉上线。
