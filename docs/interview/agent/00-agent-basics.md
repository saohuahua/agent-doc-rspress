# Agent 基础概念

> 定位：What / Why / When——Agent 是什么、为什么需要、什么时候该用、什么时候不该用。
> 职责边界：Runtime 实现见《01 Agent Runtime 与架构》；Memory 与上下文工程实现见《03 Memory 与 Context 工程》；框架见《02 LangChain 与 LangGraph》；RAG 见《05》；MCP 见《06》。
> 引用块是面试版回答，1~2 分钟口述量。

## 1. Agent 是什么？它和大模型、Workflow、Chatbot 的区别

- 定义：Agent 是以 LLM 为决策核心，能自主完成"感知 -> 决策 -> 行动"闭环、通过工具与环境交互、循环执行直到完成目标的系统
- 定义里的四个关键词：
  1. LLM 决策核心：模型是大脑，但大脑本身不是 Agent
  2. 工具使用：能调工具产生真实副作用（查库、执行代码、改数据）
  3. 自主循环：自己决定下一步、要不要继续、何时结束
  4. 目标导向：对任务结果负责，不是单轮问答

```latex
Agent 的最小闭环
  -> 感知：接收任务 + 工具结果回灌
  -> 决策：LLM 基于上下文决定下一步
  -> 行动：执行工具或输出最终答案
  -> 循环：直到目标达成或触发终止条件
```

- 与大模型的区别是"能力"和"系统"：

| 维度 | 大模型（LLM） | Agent |
| --- | --- | --- |
| 本质 | 能力/组件：文本进出 | 系统/产品形态：多组件组装 |
| 状态 | 每次调用独立，不记得上次 | 有 State，跨轮次、跨会话 |
| 行动 | 只能生成文本 | 能调工具产生真实副作用 |
| 目标 | 完成一次生成 | 完成一个任务并对结果负责 |
| 类比 | 大脑 | 大脑 + 手 + 记忆 + 工作流 |

- 与 Workflow 的区别是控制流在谁手里：Workflow 是开发者用代码写死控制流，LLM 只在节点内干活；Agent 是模型决定控制流
- 与 Chatbot 的区别：Chatbot 一问一答、无目标无工具；Agent 有目标、自主多步、对结果负责
- 完整选型见第 2 题

**面试版回答**

> 我认为 Agent 是以大模型为决策核心，能自主完成"感知、决策、行动"闭环的系统：模型决定调什么工具、要不要继续、什么时候结束，循环执行直到完成目标。它有四个特征——LLM 做决策、能用工具、自主循环、对结果负责。
>
> 它和大模型的区别是"能力"和"系统"的区别：大模型只负责文本进出，本身无状态、不能做事，两次调用之间什么都不记得；Agent 是把模型当大脑组装出来的系统，加了工具、状态、记忆和循环。实际开发里感受很直接：裸调 LLM 写个摘要函数，和做一个能自己查库、改数据、汇报结果的 Agent，工程量差一个量级，多出来的部分全是外围系统的活。
>
> 和 Workflow 的区别就一条：控制流在谁手里。Workflow 是我用代码写死步骤，模型只在节点里干活；Agent 是模型自己决定下一步。我项目里两种都用：固定流程走 Workflow 保确定性，开放任务交给 Agent，两者共用同一套工具层。

## 2. 为什么不是所有任务都应该使用 Agent？

- Agent 不是 Workflow 的升级版，而是**用不确定性换取路径泛化能力**：把"下一步做什么"的决定权从代码交给模型，代价是成本、延迟和可评测性
- 判断顺序：路径能不能预先枚举 -> 是否需要环境反馈 -> 错误代价和延迟容忍度
- 能用确定性代码 / SQL / Workflow 解决的部分，优先确定性；Agent 只用在路径确实无法枚举的地方
- 生产系统通常是混合体：头部高频场景走规则或 Workflow 保确定性，长尾走 Agent

```text
任务
 ↓
路径能否预先枚举？
 ├── 能 ─────→ Workflow（固定编排）/ 代码 / SQL
 │
 └── 不能
      ↓
   是否需要环境反馈？
      ├── 不需要（一次生成就够）→ 单次 LLM 调用
      └── 需要 ─────────────→ Agent
```

| 方案 | 控制流 | 适合 | 成本 / 延迟 | 评测难度 | 典型场景 |
| --- | --- | --- | --- | --- | --- |
| 单次 LLM 调用 | 无 | 摘要、分类、改写、抽取 | 最低 / 最低 | 低，比对输出 | 工单自动打标 |
| 代码 / SQL / Tool | 代码 | 有明确数据源的结构化问题 | 低 / 低 | 低，可断言 | "上月华东销售额是多少" |
| Workflow | 开发者（DAG） | 步骤可枚举、有合规或资金要求 | 中 / 可预测 | 中，按节点校验 | 报销审批、固定 RAG 管道 |
| Agent | 模型（Loop） | 路径依赖中间结果、分支不可枚举 | 高 / 尾延迟长 | 高，要看轨迹 | 开放式故障排查、编码 |

**为什么 Agent 更贵、更慢、更难评测**：

1. **成本**：每一轮都要带完整上下文调模型，Token 随轮次累积，还要叠加检索与工具调用开销
2. **延迟**：轮次由模型决定，没法预先估 P95；一次工具超时或重试会把尾延迟拉长
3. **可靠性**：单步错误会沿链路传播，需要重试、降级、幂等和补偿
4. **评测**：输出不是唯一答案，必须评轨迹（工具选择、参数、步数），还要压住成本和延迟

**什么情况下应该优先确定性**：

- 涉及资金、权限、数据变更等不可回滚的副作用
- 步骤可枚举，规则能覆盖全部或绝大部分流量
- SLA 紧、需要可复现结论、需要向审计解释
- 头部高频场景：用规则兜住的成本远低于每次调用模型

**业务例子**：

```text
固定审批流程（三级审批 + 金额阈值）
  → Workflow：步骤可枚举，规则明确，出错要能审计

"上个月华东区的销售额是多少"
  → SQL / Tool：一次查询 + 一次生成，不需要 Agent

"线上订单服务偶发 502，帮我排查原因"
  → Agent：先查日志，根据结果决定看网关还是下游，
     可能要对比配置、必要时回滚——路径无法预先枚举
```

**面试官追问**

**1. Agent 是不是比 Workflow 更"智能"？**
不是同一个维度的比较。Workflow 把控制流写死在代码里，确定性高、成本可预测；Agent 把控制流交给模型，换来的是处理长尾和未知路径的能力。选型看任务的路径能不能枚举，不是看哪个更先进。

**2. 什么时候该把 Agent 降级回 Workflow？**
Badcase 聚类后如果发现某类任务的路径已经稳定、可以枚举，就把这条路径固化成 Workflow 节点，只把真正开放的部分留给模型；另外当延迟或成本成为硬约束、或需要更强审计时，也应该收窄 Agent 的决策空间。

**3. Workflow 里能不能用 Agent？**
可以，而且生产上最常见。外层 Workflow 控制阶段（检索、生成、校验），其中某个节点内部是一个 Agent Loop，让模型自己决定调几次工具、要不要重试。确定性和灵活性各取一部分。

**4. 如果必须用 Agent，怎么降低它的不确定性成本？**
收窄决策空间：关键决策给枚举选项而不是开放生成；把审批、资金、数据变更这类步骤固定成 Workflow 或加人工闸门；输出过 Schema 校验；上线走评测门禁和灰度。Runtime 侧的手段见《01 Agent Runtime 与架构》。

**Trade-off**

| 选择 | 换来什么 | 付出什么 | 什么时候选 |
| --- | --- | --- | --- |
| 优先确定性（代码 / SQL / Workflow） | 成本可控、延迟可预测、结果可复现、易审计 | 规则维护成本随场景线性增长，长尾覆盖不了 | 路径可枚举、有资金或合规要求 |
| 用 Agent | 路径泛化、长尾可覆盖、改工具描述比改代码快 | 成本高、尾延迟长、评测复杂、需要治理层 | 分支不可枚举、步间有反馈、需求频繁变化 |
| 混合（规则兜头部 + Agent 兜长尾） | 兼顾成本与覆盖率 | 两套链路都要维护，归因更复杂 | 头部流量大且稳定的生产系统 |

**面试版回答**

> 我不会说 Agent 一定更好。Agent 的本质是用不确定性换路径泛化能力：把"下一步做什么"从代码交给模型。所以我会先问任务本身——路径能不能预先枚举？如果需要一次生成就够，那是单次调用；如果步骤固定、有合规或资金要求，那是 Workflow 或直接用代码；如果能用一个 SQL 或查询解决，就不该套 Agent。只有路径确实依赖中间结果、分支没法提前写死时，才值得上 Agent。
>
> 代价我会主动讲：成本随轮次累积，延迟尾部长，单步失败会传播，评测也要看轨迹而不只是答案。所以生产上我做混合：头部高频场景走规则和 Workflow 保确定性和成本，长尾交给 Agent。比如固定审批流程肯定写成工作流，查销售额直接走 SQL，但"线上偶发 502 帮我排查"这种就只能交给 Agent。

## 3. Agent 的核心架构是什么

- 架构题只需要回答四件事：谁决策、谁行动、谁把两者串起来、状态放在哪
- 简化模型：LLM 决策、Tools 行动、Loop 执行闭环、State 当前运行状态
- 生产级再加一层横切能力：Permission、Checkpoint、Trace、Sandbox——这里点到为止，实现见《01 Agent Runtime 与架构》

```text
             Agent
               │
       ┌───────┴───────┐
       ↓               ↓
      LLM            Tools
       │               │
       └──────→ Loop ←─┘
                  │
                State
```

- 四个部分各自的职责：
  1. LLM：决策，决定调哪个工具、要不要继续、什么时候结束
  2. Tools：行动，与外部世界交互，产生真实副作用
  3. Loop：执行闭环，把决策、执行、观察串起来，并判断是否终止
  4. State：当前运行状态，是上下文组装的数据来源，也是恢复的依据
- 一次请求的数据流：`用户输入 -> 组装上下文 -> LLM 决策 -> 工具执行 -> 结果回灌 -> 判断终止 -> 输出或继续循环`
- 横切能力：Permission（能不能做）、Checkpoint（断了能不能续）、Trace（做过什么）、Sandbox（在哪做）

**面试官追问**

**1. 为什么把 State 单独拿出来说？**
因为 State 决定了"下一轮看到什么"和"断了能不能恢复"。上下文组装、终止判断、断点恢复、前端进度都依赖它；只把历史消息当状态，任务一复杂就会跑偏或无法恢复。

**2. 没有 Loop 会怎样？**
那就是 Workflow 或单次调用：路径由代码写死，模型只在节点内干活。Loop 的意义是让"下一步"由观察结果动态决定，这也是 Agent 与 Workflow 的分界线。

**3. 为什么权限要放在架构层，而不是 Prompt 里？**
Prompt 是概率性约束，模型可能不遵守；权限一旦进入执行链，就要在工具调用前后由程序校验。架构上把"能不能执行"和"如何决策"分开，才能解释和审计。

**4. 架构要画到多细？**
面试画到"LLM / Tools / Loop / State + 横切治理"就够，再往下讲就是 Runtime 的细节：一次 Run 的完整链路、Tool 执行边界、Checkpoint 与恢复，见《01》。

**面试版回答**

> 架构我会用四块讲：LLM 负责决策，Tools 负责行动，Loop 把两者串成闭环，State 保存当前运行状态。数据流是用户输入进来，先组装上下文，调模型决策，需要工具就执行并把结果回灌，然后判断是否终止——不终止就进入下一轮。生产级还要加一层横切能力：权限、Checkpoint、Trace 和沙箱。
>
> 我的体会是这四块里，模型和工具最容易做，决定能不能上生产的是 Loop 和 State：Loop 决定它会不会停、什么时候停，State 决定它断了能不能续、下一轮看到什么。权限我不会放在 Prompt 里让模型自觉遵守，而是放在执行链上由程序校验。更细的运行时实现——一次 Run 的完整链路、工具由谁执行、断点恢复——见 Runtime 那篇。

## 4. Tool 在 Agent 中是什么？Workflow / Agent / Tools 的关系

- 三者不是并列关系，不在同一维度
  1. Tools 是"能力"维度：原子接口，被调用方，自己没有控制流
  2. Workflow 和 Agent 是"编排"维度：两种决定控制流的方式
  3. 层级关系：`编排层（Workflow 或 Agent） -> 调用 -> 工具`

| 概念 | 本质 | 控制流 | "下一步干什么"谁说了算 | 例子 |
| --- | --- | --- | --- | --- |
| Tool | 原子能力接口 | 无，被调用方 | 不回答，只执行 | 搜索、SQL 查询、执行代码、发邮件 |
| Workflow | 编排范式 | 开发者代码写死 | 代码逻辑 | 固定 RAG 管道、审批流 |
| Agent | 编排范式 | 模型循环中决定 | LLM 决策 | Coding Agent、排障 Agent |

- 三者的关系：
  1. 工程实现上的最小实用 Agent 模型 = LLM + Tools + Loop；Tools 是模型与外部环境交互的关键能力，但 Agent 的核心不是"必须有工具"，而是目标驱动的自主决策与多步执行闭环
  2. Workflow 同样能调 Tools，只是调用顺序写死
  3. 生产系统通常是混合体：外层 Workflow 控制阶段，某些节点内部是 Agent Loop
- Tool 的三个特征：Schema 定义（名字、描述、入参）、执行无状态（幂等靠调用方保证）、结果回灌（Observation 进上下文）

**面试版回答**

> 这三个不是同一维度的概念。Tool 是能力维度，一个原子接口，用 Schema 定义名字、描述和入参，它自己没有控制流，只负责执行返回；Workflow 和 Agent 是编排维度，是两种决定"下一步干什么"的方式——Workflow 是开发者用代码写死控制流，Agent 是模型在循环里自己决定。所以层级关系是编排层调用工具，而不是三者平级并列。
>
> 工程上的最小实用模型是 LLM 加 Tools 加 Loop，Tools 是模型与外部环境交互的关键能力；但 Agent 的核心不是必须有工具，而是目标驱动的自主决策和多步执行闭环。Workflow 一样能调工具，只是顺序写死。实际开发里我们的系统是混合体：外层用 Workflow 控制阶段，比如先检索、再生成、再校验，其中"生成"节点内部是一个 Agent Loop，让模型自己决定查几次库、要不要重试。这样确定性和灵活性都有。

## 5. Agent 设计范式有哪些（ReAct 为主）

- 范式回答的问题是：Agent 怎么组织"推理"和"行动"——同一个 Loop 的不同填法

ReAct（Yao 等 2022）：
- 全称 Reason + Act，核心思想：推理和行动交替进行，用行动结果修正推理
- 执行流：

```latex
Thought     -> 我需要什么信息 / 下一步该做什么
Action      -> 发起工具调用
Observation -> 工具返回结果
（循环，直到模型认为可以给最终答案）
Answer      -> 最终输出
```

- 表述上注意：经典 ReAct 用文本组织推理与行动，现代 Agent 通常换成结构化 tool call 表达行动。应用层看到的内容（reasoning 摘要、工具参数）**不等于**模型内部完整的推理过程，不要把它当成可直接读取的内部 CoT

- 具体示例：

```text
用户：北京明天适合跑步吗？
Thought: 需要先查北京明天的天气
Action: get_weather(city="北京", date="明天")
Observation: 小雨，气温 15-22℃，空气质量优
Thought: 有雨不适合户外跑，可以给结论了
Answer: 明天北京有小雨，不建议户外跑步；想动的话室内更合适
```

- 为什么有效：
  1. 推理与行动交替：经典 ReAct 把 reasoning trace 和 action 交替组织，边做边用观察修正判断
  2. 观察反馈：每步工具结果进上下文，错误在线纠正，不会一条路错到底
  3. 可解释可审计：整个决策链可回放，出问题能定位到是哪次决策
  4. 论文效果：在决策类任务（ALFWorld、WebShop）上大幅超过模仿学习和强化学习基线；知识问答上比纯推理链幻觉更少
- 原版与现代实现的区别：原版 ReAct 是纯 Prompt 范式，模型输出 "Action: search[...]" 这类文本，程序用正则解析后执行；现代实现换成 Function Calling 结构化输出（tool_calls 字段），本质循环不变。现在主流 Agent 的工具调用循环，本质都是 ReAct 的工程化变体
- 核心实现（现代版，二十行以内）：

```typescript
async function reactAgent(question: string, tools: Tool[]): Promise<string> {
  const messages: Message[] = [
    { role: 'system', content: SYSTEM_PROMPT },   // 角色 + 工具规范 + 终止要求
    { role: 'user', content: question },
  ];

  for (let step = 0; step < MAX_STEPS; step++) {
    // Reason + Act：模型决策，返回文本或 toolCalls
    const resp = await llm.call(messages, { tools: tools.map(t => t.schema) });

    // 终止判断：没有工具调用 => Answer
    if (!resp.toolCalls?.length) return resp.text;

    messages.push(resp.message);                  // Thought + Action 进上下文

    // 执行 Action，Observation 回灌
    for (const call of resp.toolCalls) {
      const tool = tools.find(t => t.name === call.name);
      const observation = tool
        ? await tool.execute(call.args)
        : `Error: 工具 ${call.name} 不存在`;      // 幻觉工具也回灌，让模型自纠
      messages.push({ role: 'tool', toolCallId: call.id, content: observation });
    }
  }
  throw new ReActLoopExceeded();                   // 最大步数兜底
}
```

- 实现的四个关键点：
  1. System Prompt 写清角色、工具使用规范和终止要求（"信息足够时直接回答"），不写清楚模型会无限调工具
  2. 工具描述质量直接决定 Action 选择准确率——描述要写"什么时候用"，不只写"是什么"
  3. 错误也要作为 Observation 回灌：工具不存在、执行失败都拼回上下文让模型自纠，而不是抛异常断掉整个循环
  4. 双重终止：模型不调工具（显式）+ MAX_STEPS（兜底）
- ReAct 的缺点：
  1. 走一步看一步，长任务缺全局规划，容易绕路
  2. 轮数多、Token 消耗高
  3. 依赖模型推理质量，弱模型的 Thought 不靠谱

其他范式：
1. Plan-and-Execute：先全局规划再分步执行，补 ReAct 的全局性短板
2. Reflection / Reflexion（Shinn 等 2023）：执行后自我评审再重试，补质量短板
3. Multi-Agent 协作：拆角色分工协作，见第 7 题
4. 端到端自主循环（AutoGPT 式）：纯模型驱动无固定模式，灵活但最难控

| 范式 | 结构 | 全局性 | 成本 | 适用 |
| --- | --- | --- | --- | --- |
| ReAct | 单循环交替 | 局部 | 中 | 路径开放的探索任务 |
| Plan-and-Execute | 计划 + 执行两段 | 全局 | 前置高 | 可分解的复杂长任务 |
| Reflection | 执行 + 评审双循环 | 局部 | 高 | 质量敏感的生成/编码 |
| 混合模式 | 先 Plan 再 ReAct，产物加 Review | 全局 + 局部 | 最高 | 复杂且路径不确定 |

**面试版回答**

> 我最熟的是 ReAct，Reason 加 Act，核心是推理和行动交替：模型先想清楚这步要干什么（Thought），发起工具调用（Action），拿到结果（Observation）再决定下一步，循环到能给出最终答案。它有效的点有三个：推理与行动交替，让模型边做边用观察修正判断，而不是一口气蒙答案；每步都有真实反馈在线纠错；整个决策链可回放好审计。比如问"北京明天适不适合跑步"，它会先想需要天气数据，调天气工具，看到下雨才下结论，而不是凭参数瞎编。
>
> 早期 ReAct 是纯 Prompt 范式，模型输出 Action 文本再由程序解析执行；现在的实现基本换成了 Function Calling 结构化输出，循环本质没变，主流 Agent 的工具调用循环就是 ReAct 的工程化变体。实现上核心就四件事：System Prompt 约定角色和终止要求，注册工具 Schema，循环里解析 tool_calls、执行后把 Observation 回灌，模型不再调工具就返回答案，外加最大步数兜底。有个容易漏的细节：执行错误也要作为 Observation 回灌，让模型自己换路，而不是抛异常把循环断掉。它的缺点是走一步看一步，长任务缺全局规划，而且轮数多 Token 贵，所以现在主流做法是混合：先 Plan 拆解再 ReAct 执行，关键产物加 Reflection 评审。我项目里的排障 Agent 就是这个结构，单步 ReAct，整体先出计划。

## 6. 复杂任务怎么拆分？为什么要拆？

- 为什么要拆：
  1. 上下文装不下：复杂任务的全部信息超出窗口，拆开后每步只装本步需要的信息
  2. 单步决策空间太大：让模型一步做太多事错误率飙升；拆小后每步目标单一，成功率高
  3. 可并行：无依赖的子任务并行执行，降总延迟
  4. 可恢复可审计：每步有 checkpoint 和完成标准，失败只重试该步，排障能定位到步
- 成功率的数学直觉（面试亮点）：

```latex
简化模型（各步相互独立、任一步失败即整体失败）：
  整体成功率 ≈ 各步成功率的乘积
  -> 不拆：一步到位 60%
  -> 拆三步：每步 90% => 0.9 * 0.9 * 0.9 ≈ 73%
  -> 这只是直觉模型：真实 Agent 有 retry、fallback、reflection、
     人工介入，部分失败可以恢复，不能当普适公式用
  -> 唯一可靠的前提：拆分真的让每步变简单，否则步数越多成功率越低
```

- 怎么拆（三种方法）：
  1. 模型规划拆分（Plan-and-Execute）：先让 LLM 产出结构化任务清单，代码按清单执行，必要时 Re-plan
  2. 模板拆分（工程控制）：已知任务类型按固定阶段拆（需求理解 -> 检索 -> 生成 -> 校验 -> 交付），确定性强
  3. 递归拆分：子任务仍过大就继续拆，形成任务树；叶子任务 = 单工具或单次推理可完成
- 拆分产物要结构化：

```typescript
interface TaskPlan {
  goal: string;          // 总目标
  steps: TaskStep[];     // 拆解后的步骤
}

interface TaskStep {
  id: string;
  description: string;   // 这一步做什么
  dependsOn: string[];   // 依赖的步骤 id，空数组 = 可并行
  tool: string;          // 预期使用的工具
  done: boolean;         // 单步可验证的完成标准
}
```

- 拆分三原则：
  1. 单步可验证：每步有明确完成标准（测试过、字段全、返回码 200）
  2. 步间契约化：输出输入结构化传递，不靠自然语言猜
  3. 依赖显式建模：DAG 标注并行机会，无依赖的并发跑
- 效果怎么验证：盯四个指标——任务成功率、平均轮数、Token 成本、P95 延迟；Badcase 归因到具体步骤，再加强该步 Prompt 或调整拆分粒度，评测集回归
- 粒度权衡：太粗单步还是难，太细通信和 Token 开销大，按评测指标找平衡点

**面试版回答**

> 为什么要拆，我讲两个硬理由。一是上下文装不下，复杂任务的信息量超窗口，拆开后每步只装需要的信息；二是单步决策空间太大错误率会飙升，拆小之后每步目标单一。这里有个简化模型：假设各步相互独立、任一步失败整体就失败，整体成功率可以近似看作各步成功率的乘积，一步到位 60% 的任务拆成三步每步 90%，总体约 73%。但真实系统有重试、降级、反思和人工介入，部分失败能恢复，所以这是直觉模型不是普适公式；而且前提是拆分真的让每步变简单。
>
> 怎么拆我常用三种：开放任务让模型先出结构化计划再逐步执行，也就是 Plan-and-Execute；已知类型的任务用固定阶段模板拆，代码控制确定性强；子任务还太大就递归拆成任务树。拆的时候守三个原则：每步可验证、步间契约化传数据、依赖建成 DAG 能并行的并行。
>
> 效果我盯任务成功率、平均轮数、Token 成本和 P95 延迟，Badcase 归因到具体步骤再调那一环。我项目里做过一次把"一次生成完整报告"拆成"检索、生成大纲、分节生成、校验合并"四步，成功率从五成多提到八成以上，收益就是每步变简单了，而且失败只重试单步，不用整个任务重来。

## 7. Multi-Agent 是什么？Single-Agent 和 Multi-Agent 怎么选

- Multi-Agent 是多个各有分工的 Agent 协作完成一个总体任务，每个 Agent 有自己的角色、上下文和工具子集
- 它的核心收益不是"实现并行"，而是**上下文、职责、工具和执行边界的隔离**；并行只是隔离带来的附带效果
- 纠正一个常见说法：单 Agent 并不是只能串行——同一个 Loop 里，彼此独立的 Tool Call 可以并行执行；Multi-Agent 的并行发生在子任务级
- 默认立场是**能不拆就不拆**：Multi-Agent 增加了通信、状态一致性和调试成本，是组织复杂度的手段，不是免费的提效

**单 Agent 的三个瓶颈**

1. 上下文装不下：任务域一多，工具规范和中间结果挤在一个窗口里
2. 职责与工具过杂：工具数量上升后选择准确率下降，多套规范塞进一个 Prompt 会互相干扰
3. 失败不隔离：单点出错影响整个任务，也无法按子任务独立评测

**常见架构四种**

| 架构 | 形态 | 适合 |
| --- | --- | --- |
| 主子（Orchestrator-Worker） | 主 Agent 拆解分发，子 Agent 执行，结果汇总 | 最常用，跨域任务 |
| 流水线（Pipeline） | 上一步输出是下一步输入，如写码 -> 评审 | 职责串行、阶段清晰 |
| 辩论 / 评审（Debate / Review） | 生成者与 Critic 互查 | 质量敏感、可自校验 |
| 对等协商（Peer） | Agent 间多轮对话协商 | 需要多方权衡的开放问题 |

**选型信号**

- 该拆：工具数量过多导致选择准确率下降；不同子任务需要完全不同的专业上下文；职责边界天然清晰；子任务之间可以并行
- 不该拆：任务域单一、上下文可控、延迟敏感、评测能力还没建起来——这些情况下拆完往往更慢更难查

| 维度 | Single-Agent | Multi-Agent |
| --- | --- | --- |
| 上下文 | 一份，连贯但易膨胀 | 各自精简聚焦 |
| 工具选择 | 集中，多了易选错 | 分散到域，各自少而精 |
| 通信成本 | 无 | 有，消息有损 |
| 失败影响 | 单点 | 可隔离，子 Agent 失败只重试该子任务 |
| 调试 | 简单，一条链路 | 复杂，需要全局 Trace 串联 |
| 延迟 | 单 Loop 内并行独立 Tool Call | 子任务级并行，但多出通信和调度开销 |

- 演进路径：先 Single-Agent 跑通 -> 出现上下文膨胀或工具过载信号 -> 把独立域拆成子 Agent -> 编排器只管拆解与汇聚
- 写回与状态：子 Agent 只写自己的状态子树，全局字段由编排器更新；并发覆盖靠 namespace、单一写者和乐观锁，由程序保证而不是 Prompt（通信契约、结果契约和状态竞争的完整处理见《01》第 13 题）

**面试官追问**

**1. Multi-Agent 是并行的前提吗？**
不是。单 Agent 在同一轮里可以把互不依赖的 Tool Call 一起发出去并行执行；Multi-Agent 换来的并行是子任务级的，代价是通信和调度开销。如果只是为了并行，先看单 Agent 有没有把独立工具调用并发起来。

**2. 子 Agent 该共享主 Agent 的上下文吗？**
默认不共享。子 Agent 只领任务描述、约束和输入，用自己精简的上下文干活，结果按结构化契约写回。共享完整上下文等于把"上下文膨胀"的问题从主 Agent 搬到子 Agent。

**3. 什么时候该退回单 Agent？**
拆完之后如果发现：子任务之间通信频繁且反复来回、子 Agent 的上下文和主 Agent 差不多、或者大部分时间只有一个子 Agent 在跑——说明拆的边界不成立，应该合并回去。

**4. 两个 Agent 同时改一块状态怎么办？**
靠程序，不靠 Prompt。分 namespace 让每个 Agent 只写自己的子树，全局关键字段单一写者，再加版本号做乐观锁，冲突时合并或重试。

**Trade-off**

| 选择 | 换来什么 | 付出什么 | 什么时候选 |
| --- | --- | --- | --- |
| Single-Agent | 链路简单、上下文连贯、好调试、成本可控 | 工具一多选择变差、上下文膨胀、失败不隔离 | 任务域单一、工具规模可控（默认起点） |
| Multi-Agent | 上下文隔离、工具分散更准、子任务并行、失败可隔离 | 通信有损、延迟叠加、状态一致性复杂、调试成本高 | 跨域任务、职责边界清晰、子任务可并行 |

**面试版回答**

> Multi-Agent 是多个有分工的 Agent 协作完成一个任务，每个有自己的角色、上下文和工具子集。我先纠一个常见说法：单 Agent 并不是只能串行，同一个循环里互不依赖的工具调用可以并行；Multi-Agent 真正的收益是上下文、职责、工具和执行边界的隔离，并行只是附带效果。
>
> 它的动机是单 Agent 的三个瓶颈：上下文装不下、工具一多选择准确率下降、失败不隔离。常见形态有主子架构、流水线、辩论评审和对等协商，最常用的是主子架构。但我的默认立场是能不拆就不拆，因为拆完通信有损耗、错误会传播、延迟叠加、调试也需要全局 Trace。出现信号才拆：工具过多、上下文放不下、职责边界清晰、子任务能并行。
>
> 实际落地我先用单 Agent 跑通，出现上下文膨胀或工具过载再按域拆子 Agent，编排器只管拆解和汇聚。状态并发的问题我不会用 Prompt 约束，而是分 namespace、单一写者加乐观锁，由程序保证。

## 8. Agent 为什么需要 Memory？短期、长期和 Context 的区别

- 需要 Memory 的三个原因：上下文窗口装不下全部历史；跨会话要连续（记住用户是谁、做过什么）；任务中间状态要留存
- 分三层：短期（会话上下文 / 工作记忆）、中期（会话摘要）、长期（用户偏好、事实、历史任务结论）
- Memory 和 Context 不是一回事：**Memory 解决"存什么、怎么取"，Context 解决"这一轮往窗口里放什么"**；Memory 是 Context 的一个来源

| 层 | 存什么 | 生命周期 | 用法 |
| --- | --- | --- | --- |
| 短期 | 当前会话的消息、工具结果、任务 State | 会话内 | 每轮组装进上下文，超窗时裁剪或压缩 |
| 中期 | 上一阶段或上一次会话的压缩摘要 | 跨轮、跨会话 | 用少量 Token 保住关键事实和结论 |
| 长期 | 用户偏好、稳定事实、历史任务结论 | 长期 | 按当前任务检索 top-k 注入上下文 |

- 长期记忆按**事实级**粒度存：一条独立记忆一个条目，不存整段对话——整段检索既不准又浪费 Token
- 写入比检索更关键：会话结束后异步提取"值得长期记"的事实，过校验再入库；宁缺毋滥，什么都记会被噪声污染
- Memory Schema、写入策略、检索排序、冲突与过期、压缩实现属于工程层，见《03 Memory 与 Context 工程》

**面试官追问**

**1. 为什么长期记忆按事实存，而不是存整段对话？**
整段对话里大部分内容是过程性的，检索命中后还要模型自己去筛，既浪费 Token 又引入噪声；事实级条目可以精确匹配、可以带时间戳和来源，冲突时也能按时间裁决。

**2. Memory 和 RAG 有什么区别？**
RAG 检索的是外部知识（文档、制度、代码），Memory 存的是"关于这次交互和这个用户"的状态与事实。两者都是上下文的来源，但生命周期、更新方式和隔离要求不同：Memory 要按用户隔离，RAG 要按权限过滤。

**3. 记忆冲突了怎么办？**
记忆条目带时间戳和来源，检索时取最新或保留两条并列注入，让模型结合当前上下文判断；写入时也可以显式作废旧条目。完整的冲突、过期和淘汰策略见《03》。

**4. 多轮对话跑偏，是 Memory 的问题吗？**
大多数时候不是记忆问题，而是任务状态没有被显式注入——模型只看到历史消息，看不到"当前目标是什么、还缺什么"。这属于对话状态管理，见第 10 题。

**面试版回答**

> Agent 需要 Memory 有三个原因：上下文装不下全部历史；跨会话要连续，得记住用户是谁、之前做过什么；任务中间状态要留存。我一般分三层：短期是当前会话的消息、工具结果和任务 State；中期是会话摘要，用少量 Token 保住关键结论；长期存用户偏好、稳定事实和历史任务结论，按当前任务检索 top-k 注入。
>
> 有一点我会强调：Memory 和 Context 不是一回事。Memory 解决存什么、怎么取，Context 解决这一轮往窗口里放什么，Memory 只是 Context 的一个来源。长期记忆我按事实级存，一条一个条目，不存整段对话；写入用异步提取加校验，宁缺毋滥，因为什么都记的话检索再准也会被噪声污染。
>
> 至于 Memory 的表结构、写入时机、冲突和过期策略，那是工程实现问题，展开在 Memory 与 Context 工程那篇。

## 9. 记忆压缩和上下文工程：概念入口

- 前提：窗口有限，而多轮对话和工具结果会持续膨胀，所以压缩与上下文组装是刚需
- 上下文工程回答的是"每轮调用时，窗口里放什么、放多少、按什么顺序"；Prompt 工程只是其中一个分区
- 压缩方法按侵入性从低到高：滑窗裁剪 -> 摘要压缩 -> 检索式外置 -> 结构化抽取 -> 工具结果压缩 -> 分层保留组合
- 触发时机：阈值触发（用量到 70%~80%）、轮次触发、后台异步压缩
- 三个失败模式：上下文污染（无关信息干扰决策）、注意力稀释（塞太多"可能有用"的）、压缩雪崩（压缩丢信息 -> 重复提问 -> 轮次变多 -> 更快触顶）

| 方法 | 做法 | 代价 |
| --- | --- | --- |
| 滑窗裁剪 | 只留最近 N 轮 | 最便宜，但硬丢信息 |
| 摘要压缩 | 旧轮次压成摘要，保留事实与结论 | 一次模型调用，可能丢细节 |
| 检索式外置 | 全量历史入向量库，每轮按需检索 | 上下文里放"相关的"而非"最近的"，需要检索质量 |
| 结构化抽取 | 事实抽成 KV / 表格代替原文 | 最省 Token，抽取错误会放大 |
| 工具结果压缩 | 大 JSON / 长文本先截断或摘要，只留结论和关键字段 | 常被忽略的大头，截断策略要按工具定制 |
| 分层保留 | System Prompt 永久 + 近期全量 + 远期摘要 + 工具结果截断 | 组合效果最好，规则最复杂 |

- 位置也重要：关键指令放开头，当前任务相关放结尾，中间容易丢（lost in the middle）
- 压缩的具体实现、触发阈值、质量校验和预算分配见《03 Memory 与 Context 工程》

**面试官追问**

**1. 压缩怎么保证不丢关键信息？**
摘要 Prompt 明确要求保留实体、数字、用户偏好和未完成事项；摘要条目带原文引用可以回查；压缩后用问答对做前后对照测试，关键信息还在才算通过。

**2. 压缩和 RAG 是不是一回事？**
不是。RAG 从外部知识库取证据，压缩是管理"已经在上下文里的历史"；两者都会往窗口里放内容，但一个治知识缺失，一个治窗口膨胀。

**3. 什么时候该压缩？**
按用量阈值触发最常见（到窗口 70%~80%），也可以按轮次或后台异步压。异步压缩体验最好，但要做新旧快照切换，避免压缩过程中状态被写坏。

**面试版回答**

> 上下文工程回答的是每轮调模型时窗口里放什么、放多少、按什么顺序，Prompt 工程只是其中一块。压缩方法我按侵入性从低到高说：滑窗裁剪最便宜但硬丢信息；摘要压缩把旧轮次压成摘要；检索式外置是把历史放进向量库按需回取，窗口里只放相关的不放最近的；结构化抽取把事实抽成 KV 表，最省 Token；工具结果压缩是最容易被忽略的大头；最后是分层保留的组合拳。
>
> 我会盯三个失败模式：上下文污染、注意力稀释和压缩雪崩。塞得多不等于效果好，早期我把检索结果全塞进去，模型反而抓不住重点，后来按相关度截断反而更准。具体阈值、校验和预算分配是工程细节，展开在 Memory 与 Context 工程那篇。

## 10. 多轮对话状态怎么管理？如何防止跑偏并支持中断恢复

- 状态管理：状态内容结构化，不只是一串 messages

```typescript
interface ConversationState {
  sessionId: string;
  goal: string;                    // 本会话任务目标（防跑偏的锚）
  slots: Record<string, string>;   // 已收集的槽位字段
  stage: 'idle' | 'collecting' | 'executing' | 'clarifying' | 'done';
  pendingClarify?: {               // 澄清挂起：问出去了还没答
    question: string;
    askedAt: number;
  };
  toolHistory: ToolCall[];         // 工具调用历史
  updatedAt: number;
}
```

- 存储与流转：
  1. 存储：Redis 会话级热状态 + DB 持久化，跨请求可重建
  2. 状态机：idle -> collecting -> executing -> clarifying（挂起）-> done

- 防跑偏（三个手段，从软到硬）：
  1. 目标锚定：每轮把 goal + slots + stage 结构化注入上下文，模型永远看得到"当前在干嘛、还缺什么"——不靠模型记住，靠状态注入
  2. 偏题检测：新输入与目标相关性低时，先确认"是否切换任务"再继续；切换则归档旧任务、开新状态
  3. 约束兜底：System Prompt 写明只处理当前任务相关请求；超轮数 / 超时强制收敛

- 中断恢复：
  1. 挂起现场：用户离开或等审批时，把 state + 对话摘要持久化，会话标 suspended
  2. 恢复：用户回来 -> 重建上下文（state 注入 + 近期对话 + 摘要）-> 从 stage 断点继续，已收集的槽位不重问
  3. 超时策略：长期不回（如 24h）-> 会话过期归档，记忆层留摘要；再进入走新会话 + 记忆召回
- 任务级 Checkpoint 与宕机恢复见《01》第 11、12 题（本篇只答对话级状态）

**面试版回答**

> 这题我分状态、防跑偏、恢复三段说。
>
> 状态上我不靠一串 messages 裸奔，而是结构化管理：任务目标、槽位、当前阶段、澄清挂起项、工具历史，存 Redis 会话级，用状态机管流转：空闲、收集、执行、澄清、完成。防跑偏三个手段，最核心的是目标锚定——每轮把 goal 和 slots 结构化注入上下文，模型永远知道在干嘛、还缺什么，不靠它自己记；其次是偏题检测，新输入和目标相关性低时先确认要不要切任务；最后 System Prompt 约束加轮数兜底。
>
> 中断恢复：用户离开或等审批时把 state 加对话摘要持久化，标挂起；回来后重建上下文从断点继续，收集过的槽位不重复问；长期不回就过期归档，记忆层留摘要，下次进来新会话加记忆召回。
>
> 实际开发里最深的体会是：跑偏的根因基本都是状态只存在对话原文里，模型聊着聊着就忘了目标。把状态显式抽出来每轮注入后，多轮任务的完成率明显提升。

## 11. 如何评估一个 Agent 的效果？评测集和指标怎么设计

- 评测分两层：离线评测（发布前门禁）+ 在线评测（灰度与线上监控）

- 评测集构建：
  1. 来源三角：真实用户 query 抽样（保分布）+ 边界与对抗 case（保鲁棒）+ 历史 Badcase 回流（保回归）
  2. 结构：输入 + 预期（工具调用轨迹 / 参考答案 / 关键字段）+ 评分标准
  3. 每条带归因标签：问题出在模型 / 检索 / 工具 / Prompt 哪一层
  4. 规模与版本化：先 50~100 条跑通闭环再扩；评测集跟代码一起版本化演进

```typescript
interface EvalCase {
  id: string;
  input: string;              // 用户输入 / 任务描述
  expectedTools?: string[];   // 预期工具调用轨迹
  expectedAnswer?: string;    // 参考答案或关键字段
  rubric: string;             // 评分标准（给 judge 或人工）
  tags: string[];             // 归因标签：model / retrieval / tool / prompt
}
```

- 指标四层：

| 层 | 指标 | 说明 |
| --- | --- | --- |
| 过程 | 工具选择准确率、参数正确率 | 轨迹级，规则断言可算 |
| 成本 | 轮次、Token、延迟 P95 | 工程指标，决定能不能上线 |
| 结果 | 任务完成率、答案正确率 | 核心业务指标 |
| 体验与安全 | 人工干预率、重试率、注入拦截率 | 线上采集 |

- 三种评测方法（组合用）：
  1. 规则断言：轨迹匹配、字段校验、Schema 校验——便宜、确定，适合过程指标
  2. LLM-as-judge：模型按 rubric 打分——覆盖开放任务；必须与人工抽检对齐校准，裁判本身会有偏
  3. 人工评估：金标准，贵，只做抽样校准

- 线上闭环：灰度发布 -> 看完成率 / 干预率 -> Badcase 回流入评测集 -> 归因到层 -> 修复后回归 -> 达标全量
- 门禁示例：新版评测集通过率不低于基线 -1%，且无新增高危 case，才允许发布

**面试版回答**

> Agent 评测我分离线和在线两层。
>
> 离线评测集构建是三角来源：真实 query 抽样保分布、边界和对抗 case 保鲁棒、历史 Badcase 回流保回归。每条 case 有输入、预期轨迹或参考答案、评分标准，还要打归因标签——出了问题知道是模型、检索、工具还是 Prompt 层的锅。规模上先 50~100 条跑通闭环再扩，评测集跟代码一起做版本化。
>
> 指标分四层：过程层看工具选择准确率和参数正确率，规则断言就能算；成本层看轮次、Token、P95 延迟；结果层看任务完成率和答案正确率，这是核心；线上再补人工干预率、重试率和注入拦截率。方法三件套组合：规则断言管确定性的，LLM-as-judge 管开放任务但要和人工抽检对齐校准，人工只做抽样。
>
> 上线走灰度，Badcase 回流评测集，归因修复后回归，达标才全量。我项目里的门禁是新版通过率不低于基线减一个点、无新增高危 case，这样每次改 Prompt 或工具都有数可依，不凭感觉上线。
