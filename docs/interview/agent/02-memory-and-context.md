# Memory 与 Context 工程

> 依据《2026 秋招 Agent 全栈面经统一版》：Memory 与 Context 覆盖 35/53 篇（66%），P0。高频追问是写入规则、冲突、按需读取、超窗压缩、拼接顺序。
> 定位：工程层。`00` 扫概念，本篇回答怎么写、怎么读、满了怎么压、怎么证明没丢。State 落盘与长任务恢复见《01》，知识库冲突见《05》。
> 每题末尾的引用块是面试版回答。口述按换行停顿，比概念题多一层「为什么这么做」。

## 1. State、Context、Memory、Checkpoint 分别是什么？Session、Sandbox 怎么放？

- 先把四个词拆开，后面所有题都建立在这张表上：

| 概念 | 是什么 | 生命周期 | 进模型窗口吗 |
| --- | --- | --- | --- |
| State | 这次任务/会话的运行数据：消息、目标、槽位、工具状态 | 任务开始到归档 | 不整份进去，只投影需要的字段 |
| Context | 本轮采样时实际交给模型的 token | 一轮推理 | 就是窗口本身 |
| Memory | 窗口外、后续轮次或后续任务还要用的信息 | 跨轮、跨会话 | 按需检索再注入 |
| Checkpoint | State 在某时刻的持久化快照 | 按轮/按节点落盘 | 不直接进窗口，恢复时用来重建 State |

```text
完整宇宙（磁盘、向量库、对象存储、工具可回读的原文）
  -> State：当前任务还活着的那一份
       -> Context：本轮筛出来喂给模型的投影
  -> Memory：跨任务还想留的事实 / 摘要 / 偏好
  -> Checkpoint：State 的快照，给恢复和回放，不是给模型「记住用户是谁」
```

- Session：一次连续对话的边界，通常对应一个 `sessionId` / LangGraph `thread_id`
- Sandbox：工具执行的隔离环境（文件系统、网络、凭据）。记忆可以召回，副作用必须关在沙箱里
- 和 LangGraph 的对应（框架参照，不是行业定律）：Checkpointer = thread 内短记忆 + 可恢复 State；Store = 跨 thread 的长期记忆
- 面经里「MCP 有 Memory 模式」是串台：MCP 管工具连接，不负责记用户搬家

> 这四个词不在同一层，混用是这题最常见的扣分点。
>
> State 是一次任务的运行数据：消息、目标、槽位、工具调用状态。它活在服务端，Loop 每轮都读它、写它。
>
> Context 是本轮真正交给模型的那一串 token。它是从 State、记忆、知识里筛出来的投影，不是把 State 原样塞进去。
>
> Memory 是窗口装不下、但以后还要用的信息：用户事实、偏好、阶段摘要。它可以完全不在当前 Context 里。
>
> Checkpoint 是 State 某个时刻的快照，用来宕机恢复和回放。恢复靠它，个性化不靠它。
>
> Session 划会话边界，Sandbox 划执行隔离。记忆可以跨 Session 召回，写文件、跑命令必须关在 Sandbox。MCP 连工具，不负责记用户是谁。

### 容易答错的地方

- 把 Redis 里的会话缓存直接叫长期记忆
- 把 Checkpoint 当成 Memory：重启能续跑 ≠ 下个月还记得用户地址
- 把企业知识库当成用户 Memory：权限、更新、删除生命周期不同，那是 RAG

## 2. 什么是 Context Engineering？和 Prompt Engineering、Harness Engineering 怎么演进？

- 一句话演进：怎么问 → 每轮窗口里放什么 → 整套 Agent 怎么跑得可靠

```text
Prompt Engineering     写系统指令、few-shot、输出格式
Context Engineering    每一轮推理时，窗口里那组 token 怎么选、怎么排、怎么更新
Harness Engineering    Loop、工具执行、权限、预算、Trace、恢复——模型外面那圈壳
```

- Anthropic 的工程口径：Context 是有限注意力预算。Transformer 里 token 两两相关，窗口变长，单位 token 的有效注意力被摊薄，再叠加 **context rot**——needle 实验里，越长越容易找不回中间的关键信息
- 所以目标不是「把能放的都放进去」，而是：**最少的高信号 token，最大概率引出目标行为**
- Prompt 仍然要写，但它只是 Context 的一个分区。Agent 多轮跑起来之后，工具结果、检索片段、子 Agent 回传会持续污染窗口，单靠改一句系统提示救不了
- Harness 决定 Context 能不能被执行：压缩谁触发、工具结果谁截断、记忆谁注入。没有 Harness，Context Engineering 只是每次手工拼 Prompt

| | 管什么 | 典型失败 |
| --- | --- | --- |
| Prompt | 指令含糊 / 过死 | 模型不知道何时停、何时调工具 |
| Context | 窗口塞满低信号 | 选错工具、忘了目标、重复问已经说过的槽位 |
| Harness | 循环和副作用失控 | 死循环、重复扣款、断了不能续 |

> Context Engineering 回答的是：每一轮调模型时，窗口里放什么、放多少、按什么顺序。
>
> 和 Prompt Engineering 的差别是范围。Prompt 管怎么写指令；Context 管这一轮所有 token，包括系统提示、工具定义、记忆、历史、工具结果。指令写得再好，窗口被 20 段工具 JSON 塞满，模型照样会糊。
>
> Harness 是更外一圈：Loop 怎么停、工具怎么校验、状态怎么落盘、压缩谁来触发。Context 是「喂什么」，Harness 是「整台机器怎么转」。
>
> 这层之所以独立出来，是因为窗口是有限注意力预算，不是越大越好。上下文一长，中间的关键信息更容易丢，这叫 context rot。工程目标是最少的高信号 token，不是把知识库和聊天记录一次性倒进去。

### 容易答错的地方

- 「窗口 200k 了，不用做 Context Engineering」——长窗口仍然有 rot，成本也线性涨
- 把 Context Engineering 说成换个 Prompt 模板
- 把 Harness 说成框架名。LangGraph 是实现选项，Harness 是问题域

## 3. 为什么需要记忆？短、中、长期怎么分层？企业知识库算不算 Memory？

- 需要记忆的三个硬原因：
  1. 窗口装不下全部历史，硬塞会贵、会慢、会糊
  2. 跨会话要连续：用户是谁、偏好是什么、上次做到哪
  3. 任务中间状态要留：槽位、待办、已确认的约束，不能只活在模型「印象」里
- 三层按**召回范围**分，不按存储品牌分：

```text
短期（thread 内工作记忆）
  内容：本轮及近几轮消息、工具结果、任务 State
  粒度：message 级
  用法：每轮组装进 Context；超窗先裁工具原文，再滑窗 / 摘要

中期（阶段摘要）
  内容：上一阶段或上一次会话的压缩结论、未完成项
  粒度：一段结构化摘要，通常几百 token
  用法：替换已经不需要原文的旧轮次
  注意：不是每次模型调用都去向量库拉一遍「中期记忆」

长期（跨 thread）
  内容：用户事实、明确偏好、可验证的任务结论
  粒度：事实级条目，一条一个 key
  用法：按当前任务检索 top-k 注入，禁止全量塞 System Prompt
```

- 认知科学那套也可答，但落到工程上要能对上：语义记忆 = 事实；情景记忆 = 做过的任务轨迹；程序记忆 = 系统提示 / Skill。面试优先讲工程三层，被追问再映射
- **企业知识库不是用户 Memory。** 产品手册、制度、代码走 RAG：有版本、有权限、有生效期。用户「住在浦东」是 Memory；「退款政策 v3」是知识
- Skill / 第三方知识也不进用户档案：Skill 的 `references/` 是打法，RAG 是证据，Memory 是「这个用户 / 这个项目」的事实。三条检索链分开，注入时分区放
- 不做长期记忆：跨天任务失忆、重复收集槽位、无法个性化。乱写的长期记忆更糟——错误偏好会在所有会话里被检索出来

> 记忆要解决三件事：窗口装不下、跨会话要连续、任务中间状态不能只活在模型印象里。
>
> 工程上分三层。短期是当前 thread 的工作记忆，消息、工具结果、任务 State，粒度是一条条 message。中期是阶段摘要，用几百 token 保住结论和未完成项，把已经用过的旧轮次换掉。长期是跨会话的事实和偏好，粒度是一条独立事实，按当前任务检索 top-k，绝不把整个记忆库塞进 System Prompt。
>
> 中期摘要不要每次调用都去向量库捞一遍。它是「这段对话已经折叠成的结论」，只在组装 Context 时作为一块固定分区出现。向量检索留给长期事实和知识库。
>
> 企业知识库不算用户 Memory。手册、制度、代码有版本和权限，走 RAG。Skill 的参考文档是打法，也不写进用户档案。用户地址、回复语言、上次任务结论才是 Memory。长期记忆可以没有，但不能乱写——错记比漏记危害大，因为它会在以后每次检索里反复出现。

### 容易答错的地方

- 「短期一定 Redis、长期一定 MySQL」——常见选型，不是定律
- 把 RAG 检索结果当成长期记忆写入用户档案
- 中期记忆每次调用都走 Chroma：多一次检索、多一次噪声，还把摘要和事实检索混在一条链上

## 4. 一轮调用的上下文由哪些部分构成？短中长期怎么拼接、什么顺序？

- 按分区管，每区有自己的生命周期和 token 预算，不能追加成一锅粥：

```text
1. System Prompt          角色、硬规则、工具使用规范     静态，版本化
2. 长期记忆 top-k         和本任务相关的事实 / 偏好      按需，每轮可不同
3. 任务 State             目标、槽位、阶段、未完成项      结构化，防跑偏的锚
4. 中期摘要               已被折叠的历史结论              随压缩更新
5. 近期对话原文           最近 N 轮 user / assistant     近端全量
6. 本轮工具结果           截断后的 Observation            最大头，先截再留
7. RAG 片段（如有）       本任务证据                      带引用，有阈值
8. 输出预留               给模型生成留空                  不占满窗口
```

- 拼接顺序的工程原因：模型对**开头和结尾**更稳，中间容易 lost in the middle。稳定规则放前，当前任务和最新观察放后
- 「第十一轮该给什么」按上面的分区答，不要答「把前十轮原样再发一遍」：

```text
第十一轮最少给：
  - 仍然生效的 System 规则
  - 和本问相关的 1~3 条长期事实（有则给，没有不强塞）
  - 当前 goal + slots + 未完成项
  - 覆盖前十轮的一段摘要
  - 最近 2~3 轮原文（含用户刚说的话）
  - 本轮真正要用的工具结果，而不是第 2 轮那份 20k JSON
```

- 预算被打穿时的降级顺序：先砍旧工具原文 → 再缩短 RAG → 再减少长期记忆条数 → 最后才动近期原文和 State。State 和当前用户话不要先砍
- 动态组装：每轮按任务重建，不是只在数组尾部 append。长期记忆这一区本轮相关才出现

```typescript
function buildContext(state: AgentState, memories: MemoryItem[], summary: string) {
  return [
    systemPrompt,
    formatMemories(memories.slice(0, 3)),   // 长期，按需
    formatState(state.goal, state.slots),   // 锚
    summary,                                // 中期
    state.recentMessages,                   // 近端原文
    clipToolResults(state.pendingObs),      // 本轮观察
  ]
}
```

> 一轮 Context 不是一段聊天记录，是若干分区拼出来的。
>
> 稳定的 System 规则放最前。然后是和本任务相关的长期记忆 top-k，没有相关的就不放。再放结构化的任务 State：目标、槽位、未完成项，这是防跑偏的锚。再往后是中期摘要、近几轮原文、本轮截断后的工具结果。输出还要留空，别把窗口占满。
>
> 顺序不是随便排的。模型对开头和结尾更稳，中间容易丢。所以规则靠前，当前任务和最新观察靠后。
>
> 被问第十一轮给什么，就按分区答：规则、相关长期事实、当前目标和未完成项、前十轮的摘要、最近两三轮原文、本轮真正用到的工具结果。前十轮的大 JSON 不要再原样塞进去。预算不够时，先砍旧工具原文，最后才动 State 和用户刚说的话。

### 容易答错的地方

- 只追加不重建：窗口里会留下早已过期的检索片段
- 把长期记忆放在消息列表最末，把最新用户话挤到中间
- 给不出「先砍谁」：说明没有分区预算

## 5. 记忆如何按需读取？什么可以丢、什么必须留？存在哪里？

- 读取的默认姿态是 **JIT**：Context 里只放指针和少量高相关条目，原文在外，用到再回读

```text
启动 / 每轮
  -> 用当前 query + 任务 State 检索长期记忆 top-k（带权限过滤）
  -> 命中的是「id + 一句话 + 时间」，不是整段聊天
  -> 模型认为不够，再通过工具按 id 回读全文
  -> 工具结果同样先留结论和指针，大报文进对象存储
```

- 可丢 vs 必留，按「丢了能不能续跑、会不会做错」判：

| 可丢 | 必留 |
| --- | --- |
| 已完成步骤的原始工具 JSON | 任务目标、硬约束、未完成项 |
| 重复出现的检索片段 | 用户明确偏好（「用中文」「不要电话销售」） |
| 过程性思考、失败重试的中间报错全文 | 数字、实体、时间、金额 |
| 过期的新闻、已作废的旧地址全文 | 来源指针（会话 id、文档 id、tool_call_id） |
| 子 Agent 的探索轨迹 | 权限边界、租户、保密标记 |

- 存在哪，答「按访问模式选」，不要背死品牌：

```text
热会话 State / 近期消息     常见 Redis：TTL、按 session 重建快、多实例能读到
精确事实（地址、偏好 key）  常见结构化库：可更新、可作废、可按 userId 查
语义召回                    向量库：只存「一条事实的 embedding + 引用 id」
大工具结果 / 日志           对象存储，Context 里只留摘要和 URI
```

- Redis 适合热会话的原因：过期自然淘汰、key 带 `tenant:user:session` 做隔离、断线后用 sessionId 把 State 拉回来。不适合当长期事实的唯一真源——重启策略、内存、难以做冲突作废
- 隔离和「用户 A 消耗用户 B 的 Token」是同一类门禁：检索过滤必须在召回前按 userId / 租户做，不能先搜全库再让模型忽略
- 业务线复用：按 `tenant / user / bizLine` 分 namespace。公共偏好可复用，订单 / 工单默认不跨线召回；当前轮只取当前业务线 top-k

> 按需读取的意思是：长期记忆不要全塞进 System Prompt，用当前任务当 query 取 top-k；大段原文放在外面，Context 里先放 id 和一句话，模型要细节再回读。
>
> 可以丢的是已经做完的步骤原文、重复检索、过期新闻、子 Agent 的探索过程。必须留的是目标、未完成项、用户明确偏好、数字和实体、权限边界，以及能找回原文的指针。指针很关键——压缩和裁剪都允许丢正文，但不允许找不到。
>
> 存储按访问模式选。热会话常见 Redis，带 TTL，key 里带租户和用户，断线能重建。精确事实放结构化库，才能按 key 作废旧地址。语义相似才走向量库。大日志进对象存储，窗口里只留摘要。Redis 不是长期记忆的唯一真源，它强在热数据和隔离，弱在冲突作废和持久事实。
>
> 检索必须先按用户过滤。先全库召回再靠 Prompt 说「不要看别人的」，会串数据和串 Token。其他业务线要复用记忆，按 namespace 拆：公共偏好可以共享，订单和工单默认不跨线召回，当前轮只注入当前业务线的 top-k。

### 容易答错的地方

- 「记忆都在 Redis」——热数据和长期事实的更新语义不同
- 把可丢定义成「模型觉得不重要的」——丢的标准要可执行：已完成、可回读、无权限
- 召回后才做租户过滤：向量库已经把别人的事实算进 top-k 了

## 6. 长期记忆写什么、怎么写？筛选靠模型还是规则？

- 写什么，用排除法更稳：

```text
写     稳定事实（姓名、地址、时区）
       用户明确说的偏好（语言、沟通方式）
       可验证的任务结论（「工单 1234 已关」）
不写   一次性操作（「刚才帮我查了天气」）
       情绪和猜测
       工具原始返回
       新闻、活动价、验证码——默认短 TTL，不当永久事实
       别人的数据、密钥、完整证件号
```

- 怎么写，两条路径都要会说：

| | 热路径（回复前写） | 后台（会话后异步抽） |
| --- | --- | --- |
| 优点 | 本轮就能用上最新事实 | 不挡 TTFT，可做更重的校验 |
| 缺点 | 增加本轮延迟，失败会拖回复 | 可能漏掉刚说的那句「我搬家了」 |
| 适用 | 用户明确更正关键档案 | 常规偏好、任务结论沉淀 |

- 筛选分工，不要「全交给模型」或「全写规则」：
  1. **规则先挡**：无 userId、含密钥模式、操作日志、工具 JSON、权限不足 → 直接丢
  2. **模型做候选**：从对话里抽出「可能值得记」的事实，带类型和置信度
  3. **程序再校验**：Schema、和旧条目是否同 key、来源会话、过期策略；低置信或冲突进待确认，不直接入库
- 被问「为什么摘要满 N 条才写 / 出现两次才记」：N 是门禁不是魔法。过小会把噪声当事实，过大会漏掉搬家这种一次就该生效的更正。一次明确更正走热路径立刻覆盖；统计类偏好才用次数阈值。阈值用误记率、漏记率调，不背死数字
- 宁缺毋滥：错记会在以后每次 top-k 里被放大

```typescript
interface MemoryItem {
  id: string
  userId: string
  key?: string                 // 同 key 用于覆盖，如 "home_address"
  content: string
  type: 'fact' | 'preference' | 'task_summary'
  confidence: number
  sourceSessionId: string
  ts: number
  expiresAt?: number
}
```

> 长期记忆只写稳定事实、用户明确偏好、可验证的任务结论。一次性操作、工具原文、新闻、密钥不写。新闻类就算抽出了，也给短 TTL，不当永久档案。
>
> 写入分两条路。用户明确说「我搬家了」，走热路径，本轮回复前覆盖旧地址，否则下一句还在用旧事实。常规偏好和任务结论走后台异步抽，不挡这一轮的 TTFT。
>
> 筛选不能全交给模型。规则先把操作噪声、工具 JSON、没权限的数据挡掉；模型只出候选；入库前程序做 Schema、同 key 覆盖、来源和有效期校验。低置信或冲突的进待确认，不要直接进检索集。
>
> 被问阈值怎么定：一次明确更正立刻写；统计类偏好才看重复次数。N 用误记率和漏记率调。写入门槛比检索算法更重要——什么都记，检索再准也是在放大噪声。

### 容易答错的地方

- 会话结束把整段对话 embedding 进向量库当长期记忆
- 用「模型觉得重要」当唯一写入条件
- 把热路径和后台说成只能选一个。关键更正和批量沉淀本来就该两套

## 7. 记忆冲突、完全冲突、过期淘汰怎么处理？

- 先分类，再谈处理。面经里的「搬家」和「完全冲突」不是同一题：

```text
更新冲突     同一 key，新值替代旧值
             「现在住浦东」覆盖「住在静安」
完全冲突     两条都像真的，时间 / 来源 / 权限裁不了
             两个账号都说自己是本人；或系统档案和用户口述互斥且都缺时间戳
时效冲突     旧事实曾正确，现在过期
             去年的活动价、已离职的部门、过期新闻
```

- 处理顺序：**程序先裁，裁不了再问人，不要两条一起塞进 Context 让模型猜**

```text
1. 权限：当前用户看不到的条目直接不参与
2. 同 key：ts 新的覆盖，旧条目标作废，保留历史只为审计，不进检索默认集
3. 带 expiresAt 且已过期：不召回
4. 仍冲突：向用户澄清一句，澄清结果写回，再继续
5. 新闻 / 外部事件：默认短 TTL 或根本不进用户长期记忆，走实时检索
```

- 过期弱化：长期不命中可以降权，但「地址」这种关键档案不要因为几个月没问就自动删。删档案要有用户侧入口或明确更正
- 条目必须带 `userId / key / ts / source / expiresAt`，否则程序无法裁，只能退化成「都给模型」
- 和 RAG 知识冲突分开答：知识库看文档版本和生效期；用户 Memory 看用户更正。两套真源不要写进同一条记录

> 冲突先分类。同一 key 的新值覆盖旧值，比如搬家：新地址写入，旧地址作废，检索默认只出新的，旧的留着审计不进 Context。
>
> 完全冲突是两条都像真、程序裁不了：缺时间戳、来源平级、权限内都能见。这种不要两条一起注入让模型自己挑——模型会编一个折中故事。停下来问用户一句，把裁决写回再继续。
>
> 过期另说。新闻、活动价、验证码不进长期记忆，或给很短的 TTL。长期不命中可以降权，但地址这种档案不因为几个月没问就自动删，等用户更正或用户自己删。
>
> 能这么做的前提是每条记忆都有用户、key、时间、来源、有效期。缺这些字段，冲突题就只能靠 Prompt 碰运气。知识库的版本冲突走 RAG 治理，不要和用户档案写进同一张表。

### 容易答错的地方

- 「把两条都给模型，它会判断」——`00` 里这句不稳，面试会追问完全冲突
- 用相似度合并两条地址：合并比覆盖更容易造出不存在的地址
- 过期策略套在所有类型上：偏好、身份、新闻的 TTL 不是同一个数量级

## 8. 上下文超窗怎么办？消息裁剪和压缩有何区别？滑窗、摘要、向量召回怎么选？

- 超窗不是单一算法，是一组按侵入性升级的手段。先选「还要不要原文」：

| 手段 | 做什么 | 丢原文吗 | 何时 |
| --- | --- | --- | --- |
| 消息裁剪 | 删旧消息或清空旧 tool 结果，只留一句结论 + id | 硬丢，可回读则安全 | **永远先做**，最轻 |
| 滑窗 | 只保留最近 N 轮原文 | 硬丢 | 旧轮对当前任务无用 |
| 结构化抽取 | 把槽位、待办、数字抽成 KV，替换长对话 | 原文可归档 | 约束和实体比原话重要 |
| 摘要 / compaction | 旧轮压成一段高保真摘要，新窗口带着摘要续跑 | 可能丢细节 | 还要连贯的长任务 |
| 向量外置 | 全文在外，按当前 query 回读 | 可能召不回 | 历史很长，当前只相关一段 |
| 子 Agent | 大检索在干净窗口里做，只回 1~2k 摘要 | 主窗口不进探索过程 | 多跳搜索、读大文件 |

- **裁剪 ≠ 压缩。** 裁剪是删除或替换指定块，便宜、可预期、不额外调模型。压缩是再用模型写摘要，有丢细节的风险，还多一次采样（费钱、费延迟、可能重复压）
- 工具结果通常占窗口一半以上。最划算的第一步是：工具一结束，把大 JSON 落到外存，Context 里只留 `status + digest + uri`
- 选型口诀：不要原文 → 裁；只要近端 → 滑窗；要槽位 → 抽 KV；要连贯 → 摘要；要海量历史里找一段 → 外置检索。生产上是组合，不是五选一
- JIT 和预检索：Claude Code 把路径、CLAUDE.md 这种轻量索引常驻，文件用到再 read。法律/客服那种每次都要同一份政策的，可以预检索一小段，其余仍 JIT

> 窗口要满时，先问还要不要原文，再选手段。
>
> 消息裁剪和压缩不是一回事。裁剪是把旧消息、旧工具结果删掉或换成指针，不额外调模型，最轻也最安全。压缩是让模型写摘要再续跑，能保连贯，但会丢细节，还多一次推理。
>
> 具体怎么选：旧轮已经没用就滑窗；目标和数字比原话重要就抽成 KV；还要接着做同一件长任务就摘要；历史特别长、当前只跟其中一段有关，就外置检索，按需回读。工具返回的大 JSON 永远先裁——它通常是窗口里最肥的一块，留结论和 uri 就够。
>
> 这些手段是组合拳。常见落地是：每轮先裁工具原文，接近阈值再摘要，长期事实走检索，大搜索丢给子 Agent，主窗口只回收摘要。不要一超窗就上向量库，也不要指望超大窗口替代这套治理。
>
> 这套机制本身的缺点也要主动说。裁剪会硬丢还可能用到的细节；摘要有信息损失还多一次调用；检索会召不回；子 Agent 有通信损耗。压缩过头会出现压缩雪崩：丢了约束 → 模型反复问 → 轮次变多 → 更快再触顶。所以要留指针、要评测保真，不能只看窗口变短。

### 容易答错的地方

- 把滑窗叫压缩：滑窗不产生新信息，只丢旧信息
- 一上来就做 LLM 摘要：贵，还可能把还要用的数字摘要没了
- 「有向量库就不需要摘要」——检索解决相关，摘要解决连贯，不是替代

## 9. 压缩怎么保证少丢关键信息？如何评估？Claude Code / Anthropic 的长上下文做法是什么？

- 少丢信息，靠摘要提示词 + 结构 + 指针，不靠「模型自己知道什么重要」：

```text
摘要必须保留：
  目标与约束、未完成项、用户明确偏好
  实体 / 数字 / 时间 / 金额、关键决策
  文件路径、id、url 等可回读指针
摘要可以丢掉：
  重复的工具原文、已关闭的探索分支、客套话
禁止：
  把「可能相关」的大段检索再抄进摘要
  对已经压缩过的段落再压一次
```

- 防重复压缩：压缩块带 `covers: [msg_id_from, msg_id_to]` 和版本号。下一轮 summarizer 只看「未覆盖的新消息 + 已有摘要」，不要把旧摘要当原文再喂进去
- 评估分三层，没有评测集就说「还没量化」，不要编降幅：

| 层 | 怎么测 | 用来回答什么 |
| --- | --- | --- |
| 信息保真 | 压缩前后用同一批关键问题考：地址、数字、未完成项还能不能答对 | 有没有把搬家、金额摘要丢了 |
| 任务续跑 | 压缩后接着把任务做完，看完成率、重复提问次数 | 能不能接着干，而不是只看起来变短 |
| 成本 | 输入 token、轮次、P95 | 变短是否真的省钱；若轮次变多，说明压过头了 |

- 面经里的「Claude Code 三层压缩」没有官方同名 API。对齐 Anthropic 长任务三板斧来答：

```text
1. Compaction
   接近窗口上限时把旧对话压成摘要，带着摘要续跑
   Claude Code 压缩后：系统提示、磁盘上的 CLAUDE.md / 记忆会重新注入
   最近读过的文件会回读一部分（过大则只留路径）

2. Structured notes（外置笔记 / Memory）
   Agent 把进度写到窗口外的 NOTES / 记忆文件
   窗口重置后先读自己的笔记，而不是指望摘要里什么都在

3. Sub-agent
   探索、读大文件、多跳搜索在子窗口做
   主 Agent 只回收 1~2k 结论，主窗口不被探索轨迹污染
```

- 压缩 Prompt 先追求高召回（关键点都在），再收精度（删掉废话）。官方建议用真实长轨迹调这条提示词，而不是用短聊天调

> 压缩丢不丢信息，看三件事：摘要提示词强制保留什么、有没有留下回读指针、有没有避免重复压。
>
> 必须留在摘要里的是目标、未完成项、用户偏好、数字和实体、关键决策，以及文件路径、id 这类指针。工具原文和已经走死的探索可以扔。已经压过的段落打上覆盖范围，下一轮只摘要新消息，否则会越压越空。
>
> 评估不能只看 token 降了多少。先用压缩前后的问答对考关键事实还在不在；再看压缩之后任务能不能续跑、会不会反复问已经确认过的槽位；最后才看成本和轮次。轮次变多说明压过头了，模型在补信息。没有评测集就直接说还没量化，不编「降了一半」。
>
> 面经说的 Claude Code 三层压缩，按 Anthropic 的长任务三板斧答，不要编一个产品名。第一层 compaction，触顶摘要续跑，系统提示和磁盘记忆重注。第二层把进度写到窗口外的笔记，重置后读回来。第三层大检索交给子 Agent，主窗口只回收摘要。外置真源加摘要续跑，比单靠一段 summary 稳。

### 容易答错的地方

- 把「三层压缩」说成官方功能开关
- 只用 token 降幅证明压缩成功
- 压缩后不重注 System / 项目记忆：模型会忘掉自己是谁、项目约定是什么

## 10. 压缩何时触发？跨会话、跨天怎么接上？多线程 Token 和指代怎么处理？

- 触发看 **token 阈值**，不看拍脑袋的「每 8 轮」。官方 compaction 也是 `input_tokens` 触发。阈值用「触顶报错率、压缩后保真、TTFT」调：太低白烧摘要调用，太高会直接 400
- 同步 vs 异步：

```text
已经触顶 / 再发一轮会报错     同步压，挡本轮，但能续上
日常接近阈值（例如 70%~80%） 后台压，下一轮切换到新快照
后台还没压完又来了新消息     新消息先写入 State；摘要基于「启动压缩时的序号」
                             切换时把序号之后的原文拼回摘要后面，禁止丢这中间一段
```

- 跨会话：新 thread **不搬全部聊天记录**。带 `userId + 项目/业务 namespace` 检索长期记忆，再加一条可选的「上次会话摘要」。权限仍按当前身份滤
- 跨天 / 项目化上下文：目标、约束、进行中的待办放结构化 State 或笔记文件，对话原文不当唯一真源。跨天任务续跑先读笔记和 State，再决定要不要回读某段原文
- 多线程 / 多 Agent 控 Token：
  1. 子 Agent 自带干净窗口，主会话只回收摘要（这是最有效的降本）
  2. 并行工具的结果先各自截断，禁止 N 路全文同时回灌主 Context
  3. System Prompt、工具 Schema 保持稳定前缀，方便 Prompt Cache；**不要把每轮都变的长期记忆插到最前面**，会把缓存打穿
- 指代（「这个」「上次那个」）：
  1. 先用当前 State 的槽位和最近原文补全
  2. 不够再按实体检索长期记忆或 RAG
  3. 仍不确定就问一句，不靠模型猜错对象还继续调工具
- 上一轮结果哪些不该塞进下一轮：完整日志、完整设计稿 JSON、子 Agent 的探索轨迹。留 digest + uri，需要时再读

> 压缩触发看 token 阈值，不看「每 N 轮」。已经要撞窗口就同步压，否则后台压，避免挡 TTFT。后台压的时候新消息还在进，摘要要带序号，切换时把摘要之后的新原文拼回去，不能把这中间一段吃掉。
>
> 跨会话不搬全量聊天记录。新 thread 用用户和项目 namespace 检索长期记忆，必要时加一条上次摘要。跨天任务把目标和待办放在结构化 State 或笔记里，先读笔记再决定回读哪段原文，对话记录不当唯一真源。
>
> 多线程降 Token，最有效的是子 Agent 自带窗口，主会话只回收摘要。并行工具的结果各自截断再回灌。System 和工具 Schema 当前缀稳住，好走 Prompt Cache；每轮都变的记忆不要插到最前面，否则缓存全失效。
>
> 指代先补槽位和近端原文，不够再检索，还不确定就问人。上一轮几十 MB 的日志只留摘要和指针。Context 工程的最后一公里，就是让下一轮看见「现在还需要的」，而不是「曾经出现过的」。

### 容易答错的地方

- 定时压缩不考虑正在进行的工具调用：摘要和工具结果对不上
- 跨会话把旧 thread 的 messages 数组整段复制过来
- 用 Prompt Cache 的同时每轮改 System 前缀：等于没用
- 指代只靠模型：多对象场景会调错工具
