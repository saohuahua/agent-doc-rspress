# MCP 面经

## 1. 什么是 MCP？它解决什么问题？

### 先给结论

- MCP（Model Context Protocol，模型上下文协议）是 Anthropic 于 2024 年 11 月开源发布的一套协议，标准化 AI 应用与外部工具、数据源之间的连接方式
- 底层基于 JSON-RPC 2.0：所有交互都是带 `method`、`params`、`result` 的 JSON 消息
- 官方类比是"AI 应用的 USB-C 接口"：一个标准接口，任意模型应用接任意工具。注意类比的局限——USB-C 标准化的是物理连接，MCP 标准化的是消息格式、工具发现机制和连接生命周期

### 没有 MCP 之前怎么调工具

必须先说清一个事实：**MCP 不是"让模型能调工具"的技术**。没有 MCP 一样能工具调用，流程是：

```text
1. 应用开发者手写每个工具的 JSON Schema 描述
2. Schema 塞进模型请求（Function Calling）
3. 模型返回结构化调用意图（函数名 + 参数）
4. 应用自己写执行代码、拿结果、拼回上下文、进入下一轮
```

问题出在生态层面，即 **M x N 集成问题**：M 个 AI 应用（ChatGPT、Claude、各 IDE、各 Agent 框架）x N 个外部系统（GitHub、数据库、Slack），每对组合都要写一遍私有适配——插件协议、工具格式、鉴权方式互不兼容。MCP 把它变成 M + N：每个应用实现一次 Client，每个工具方实现一次 Server，中间靠协议解耦。

### 演进时间线（答"了解多深"时用）

| 时间 | 事件 |
| --- | --- |
| 2024-11 | Anthropic 开源发布 MCP，初版规范版本号 2024-11-05（stdio + HTTP+SSE 两种传输） |
| 2025-03 | OpenAI 宣布采纳（Agents SDK 当日可用）；同月规范 2025-03-26 用 Streamable HTTP 取代 HTTP+SSE |
| 2025-04 | Google 宣布 Gemini 将支持 MCP |
| 2025-06 | 规范 2025-06-18：OAuth 2.1 授权体系、elicitation、工具结构化输出 |
| 2025-11 | 规范 2025-11-25：工具命名指南、tasks（实验性）、错误语义澄清 |
| 2025-12 | Anthropic 将 MCP 捐赠给 Linux 基金会旗下 Agentic AI Foundation（AAIF），共创方 Anthropic、Block、OpenAI，支持方 Google、Microsoft、AWS、Cloudflare 等 |
| 2026-07 | 2026-07-28 修订对 Streamable HTTP 做不兼容调整（移除 GET 流端点与协议级会话），规范仍在快速演进 |

### 面试版回答

> MCP 是 Anthropic 2024 年 11 月开源的协议，基于 JSON-RPC 2.0，标准化 AI 应用和外部工具之间的连接。要说清它解决什么问题，得先说没有它时怎么调工具：开发者手写工具 Schema、塞进模型请求、模型返回调用意图、应用自己执行再回灌——单看一个工具没问题，问题在生态：M 个应用 x N 个工具，每对组合都要私有适配一遍。MCP 把 M x N 变成 M + N：应用实现一次 Client，工具方实现一次 Server，中间靠标准协议解耦，官方类比是 AI 应用的 USB-C。
>
> 它的采纳速度很快：2025 年 3 月 OpenAI 宣布支持，4 月 Google 跟进，2025 年 12 月捐给了 Linux 基金会旗下的 Agentic AI Foundation，由中立基金会治理。所以我不会把它说成"Anthropic 的私有协议"，它现在是行业连接标准。
>
> 一个容易答错的点：MCP 不是让模型能调工具——没有 MCP 照样 Function Calling。它标准化的是应用和工具之间的连接层：工具怎么被发现、怎么被调用、跨应用怎么复用。

### 容易答错的地方

- "MCP 让大模型能调用工具"——错，Function Calling 早于此存在；MCP 管的是连接与复用
- "MCP 是 Anthropic 的"——2025-12 起归 AAIF 中立治理
- 把 USB-C 类比说过头：MCP 不标准化物理层，也不保证接上的工具有质量保证

## 2. MCP 由什么组成？

一句话：三类角色（Host / Client / Server）+ 三类协议对象（Tools / Resources / Prompts），再加 Sampling、Elicitation 这类反向能力。

### 三类角色：Host、Client、Server

```text
┌──────────────── Host（Claude Desktop / IDE / 你的 Agent 应用）────────────────┐
│   Agent Loop、模型调用、权限确认、安全策略                                      │
│  ┌────────── Client ──────────┐  ┌────────── Client ──────────┐               │
│  │ 与一个 Server 1:1 有状态连接 │  │ 与一个 Server 1:1 有状态连接 │  ...          │
│  └────────────┬───────────────┘  └────────────┬───────────────┘               │
└───────────────┼────────────────────────────────┼───────────────────────────────┘
                ▼                                ▼
        ┌──────────────┐                 ┌──────────────┐
        │ MCP Server A │                 │ MCP Server B │
        │ （GitHub 等） │                 │ （数据库等）  │
        └──────────────┘                 └──────────────┘
```

1. **Host**：承载用户交互和 Agent Loop 的应用，负责模型调用、权限确认、安全策略，是"决策与闸门"
2. **Client**：Host 内的连接器，与一个 Server 维持 1:1 有状态连接，负责协议握手、消息编解码与路由
3. **Server**：暴露工具、资源、提示词的进程或服务，如 GitHub、Playwright、高德 MCP Server

### 三类协议对象：Tools、Resources、Prompts

按**控制方**分三类，这是规范的原生分类方式：

| 对象 | 控制方 | 用途 | 例子 |
| --- | --- | --- | --- |
| Tools | 模型控制 | 模型自主决定是否调用的动作 | 创建 issue、查天气 |
| Resources | 应用控制 | 暴露给应用读取、注入上下文的数据 | 文件内容、数据库 schema |
| Prompts | 用户控制 | 用户主动选用的提示词模板 | 斜杠命令 |

设计判断（重要）：什么做成 Tool、什么做成 Resource——**模型应该自主决定的动作用 Tool；只是被读取参考的数据用 Resource**。把大量只读数据做成 Tool 会稀释工具选择空间、拉低选工具准确率，这是工具治理的常见反模式。

### 反向能力（防知识盲区追问）

1. **Sampling**：Server 反向请求 Host 的模型做生成，Server 不用自带 LLM
2. **Roots**：Client 告诉 Server 可操作的文件系统边界
3. **Elicitation**（2025-06-18）：Server 请求用户补充信息，如"请输入 API Key"
4. **Tasks**（2025-11-25，实验性）：长任务的持久化跟踪与延迟取结果

### 面试版回答

> MCP 的角色分 Host、Client、Server。Host 是承载 Agent Loop 的应用，管模型调用和权限；Client 是 Host 里的连接器，和一个 Server 维持一对一的有状态连接；Server 是暴露能力的进程或服务。
>
> 协议对象上，MCP 不只有 Tools，还有 Resources 和 Prompts，按控制方分：Tools 是模型控制的动作，Resources 是应用控制的数据，Prompts 是用户选的模板。我的设计原则是：模型要自主决定的才做 Tool，纯参考数据做 Resource，不然工具列表一膨胀，选工具准确率就往下掉。

## 3. 一次 MCP 调用是怎么完成的？

一句话：模型只产生意图，Host 过权限闸门，Client 发 tools/call，Server 执行，结果回灌模型进入下一轮。

### 先把链路说清：谁发起、谁执行

```text
1. 模型      只产生"要调什么工具 + 什么参数"的意图（Function Calling 输出），不发起协议调用
2. Host      收到意图 -> 查权限策略 -> 决定放行 / 人工确认 / 拒绝
3. Client    把意图翻译成 JSON-RPC 的 tools/call 请求发给 Server
4. Server    真正执行（调 GitHub API、查库），返回结果
5. Host      结果回灌模型，进入下一轮 Loop
```

关键句：**模型永远不直接触达 Server**，中间隔着 Host 的权限闸门——这是 MCP 安全模型的根基，也是第 10 题所有防御设计的前提。

### 完整交互时序

```text
Client                                          Server
  │ ── initialize(protocolVersion,               │
  │     capabilities, clientInfo) ─────────────▶ │ ① 握手：版本协商 + 能力声明
  │ ◀── result(serverInfo, capabilities) ─────── │
  │ ── notifications/initialized ──────────────▶ │ ② 进入正常会话
  │ ── tools/list ─────────────────────────────▶ │ ③ 发现：拉工具清单
  │ ◀── result(tools: name/description/schema) ─ │    Host 转成模型的 function schema
  │           … 模型产生调用意图（FC）…            │
  │ ── tools/call(name, arguments,               │
  │     _meta.progressToken) ──────────────────▶ │ ④ 调用：JSON-RPC 请求
  │ ◀── notifications/progress ───────────────── │    （长任务进度上报，可选）
  │ ◀── result(content[], isError) ───────────── │ ⑤ 结果：文本/图片/资源/结构化
  │           Host 回灌模型，进入下一轮            │
  │ ── 关闭连接 ──────────────────────────────▶ │ ⑥ 结束
```

### 每步的工程要点

1. **握手**：Client 带上自己支持的 protocolVersion 与能力清单（是否支持 sampling、roots 等）；Server 回自己的版本与能力。双方能力交集决定后续可用特性
2. **能力协商的纪律**：能力是双向声明的——Client 声明 sampling、roots、elicitation，Server 声明 tools、resources、prompts、logging；对端没声明的能力就不能发起相应请求（Client 没声明 sampling，Server 就不能向它请求生成），新增能力全靠握手时声明，这是版本兼容的机制基础（第 7 题）
3. **工具发现**：tools/list 返回 name、description、inputSchema（JSON Schema）；Host 组装进模型请求；工具清单在会话中变更时 Server 发 tools/list_changed 通知
4. **结果不是纯文本**：content 数组可含 text、image、audio、embedded resource；`isError: true` 表示工具执行失败但结果给模型看（让它自纠错）；2025-06-18 起支持 outputSchema 与 structuredContent，下游程序可按 Schema 消费
5. **长任务**：请求带 `_meta.progressToken`，Server 通过 notifications/progress 流式上报进度；Agent 主动放弃用 notifications/cancelled
6. **会话管理**：Streamable HTTP 下 Server 在握手后分配 `Mcp-Session-Id`，后续请求都要带（版本演进点：2026-07-28 修订移除了协议级会话，答题时提一句"规范在向更无状态演进"是加分项）
7. **结束**：协议没有独立的 shutdown 方法，断开方式是传输相关的——stdio 由 Client 关闭 stdin 等待进程退出，Streamable HTTP 由 Client 发 DELETE 请求销毁会话

### 面试版回答

> 一次调用谁发起谁执行，我按链路说：模型只产生调用意图，就是 Function Calling 的输出；Host 拿到意图先过权限闸门；Client 把它翻译成 JSON-RPC 的 tools/call 请求发给 Server；Server 真正执行，比如调 GitHub API；结果回到 Host 再回灌模型进下一轮。这里面最关键的设计是模型永远不直接触达 Server，中间隔着 Host 的权限层，这是整个安全模型的根基。
>
> 完整流程我按生命周期讲。第一步 initialize 握手：Client 发协议版本和能力声明，Server 回它的版本和能力，后续可用特性由双方能力交集决定。第二步工具发现：tools/list 拉回工具的名称、描述和 JSON Schema，Host 把它转成模型的 function schema。第三步调用：模型产生意图后，Client 发 tools/call，参数里可以带 progressToken，长任务时 Server 会持续发进度通知。第四步结果：content 数组带文本或结构化内容，isError 标记执行失败——失败信息也会回灌给模型，让它自己决定改参数、换工具还是放弃。最后断开连接结束会话——协议没有单独的 shutdown 方法，stdio 是关闭 stdin 等进程退出，Streamable HTTP 是 DELETE 端点销毁会话。
>
> 两个工程细节：一是结果从 2025-06-18 版起支持 outputSchema 结构化输出，下游不用再解析自由文本；二是 Streamable HTTP 有 Mcp-Session-Id 做会话标识，不过最新修订在把协议往无状态方向改，说明官方也在平衡有状态会话和云原生扩展的矛盾。

## 4. MCP 和 Function Calling、Skill、A2A 有什么区别？

### 先给结论：四者不在同一层，不是互相替代关系

```text
模型层        Function Calling   模型怎么"表达"要调工具（输出结构化意图）
连接层        MCP                工具从哪来、怎么被发现、怎么跨应用复用
能力封装层    Skill              一套打法/流程/知识怎么打包给模型用
协作层        A2A                Agent 和 Agent 之间怎么委派任务、交换结果
```

| 维度 | Function Calling | MCP | Skill | A2A |
| --- | --- | --- | --- | --- |
| 回答什么问题 | 模型如何表达调用意图 | 应用如何连接工具 | 如何沉淀复用一套流程 | Agent 间如何协作 |
| 形态 | 模型 API 能力 | 开放协议（JSON-RPC） | 打包的指令 + 脚本 + 资源 | Agent 间协议 |
| 谁执行 | 应用侧执行器 | MCP Server | 模型按指令执行，内部可调 MCP | 对端 Agent |
| 典型例子 | OpenAI tools 参数 | GitHub MCP Server | SKILL.md 及配套脚本 | 任务委派给另一个 Agent |

### 最关键的加分点：MCP 之下仍然靠 Function Calling

这是多数回答会漏的关系细节：Host 从 Server 拿到 tools/list 结果后，要把工具清单**转换成模型 API 的 function schema** 塞进请求；模型用 Function Calling 输出调用意图；Host 再把意图翻译成 tools/call 的 JSON-RPC 请求发给 Server。所以 MCP 没有替代 FC，而是在 FC 之上补了标准化的发现、传输和复用层——FC 管"模型怎么说"，MCP 管"工具怎么来、怎么连"。

### 选型

1. 单一应用、少量私有工具：直接 Function Calling，别为 MCP 而 MCP
2. 工具要跨应用、跨团队复用，或要接第三方 Server：MCP
3. 把一套复杂流程（怎么做 Code Review、怎么排障）沉淀给模型：Skill，Skill 内部可以再调 MCP 工具
4. 多个自治 Agent 分工协作：A2A，每个 Agent 各自用 MCP 连自己的工具

### 面试版回答

> 这四个概念不在同一层。Function Calling 是模型侧的 API 能力，解决"模型怎么表达要调工具"——输出结构化的函数名和参数，执行靠应用。MCP 是应用和工具之间的连接协议，解决"工具从哪来、怎么被发现、怎么跨应用复用"。Skill 是能力封装层，把一套流程、指令和知识打包，教模型"这类任务怎么做"，内部还可以调 MCP 工具。A2A 是协作层，解决 Agent 和 Agent 之间的任务委派和结果交换。
>
> 一个容易被追问的关系细节：MCP 之下仍然靠 Function Calling。Host 从 MCP Server 拉到工具清单后，要转成模型 API 的 function schema，模型用 FC 表达意图，Host 再翻译成 tools/call 发出去。所以 MCP 不是 FC 的替代品，是在它之上补了标准化的发现和传输层。
>
> 选型我的判断：单应用三五个私有工具直接 FC；工具要跨团队跨产品复用就上 MCP；要把一套打法沉淀复用就做 Skill；多个自治 Agent 协作才需要 A2A。

### 容易答错的地方

- "MCP 取代 Function Calling"——错，见上
- "Skill 和 MCP 二选一"——错，Skill 内可以调用 MCP 工具，一个管打法一个管连接
- 把 A2A 和 MCP 说成竞争关系——互补：MCP 连工具，A2A 连 Agent

## 5. MCP 有什么优点和短板？

一句话：核心价值是把 M x N 的集成收敛成 M + N，但它只管连接——工具质量、上下文膨胀、安全落地都不归它管，协议管连接，不管好坏。

### 解决了什么

1. **集成碎片化**：M x N 适配收敛为 M + N，工具方写一次 Server，所有兼容 Host 都能挂
2. **工具复用生态**：GitHub、Playwright、高德等官方或社区 Server 写一次到处用，不用每个团队重复封 API
3. **标准化生命周期**：连接握手、能力协商、工具发现（tools/list）、调用（tools/call）、进度与取消都是协议规定的
4. **职责解耦**：工具开发者不用懂某个 Agent 框架；Agent 开发者不用懂每个工具的 SDK 和鉴权细节

### 没解决什么（短板，主动说加分）

1. **不保证工具质量和描述质量**：选错工具、参数编错，还是模型和工具设计的问题
2. **不解决上下文膨胀**：工具越多，Schema 越吃 token；MCP 反而让"挂工具"变得太容易，加剧这个问题
3. **不自动解决安全**：协议给了 OAuth 授权规范，但鉴权落地、权限最小化、注入防护都是接入方自己的工程（见第 10 题）
4. **调试链路变长**：跨进程、跨网络、JSON-RPC 套一层，问题定位比进程内函数调用难
5. **无性能保障**：慢工具还是慢，协议不管超时和熔断，都要 Host 侧治理

### 算不算中间件

- 严格口径：MCP 是**协议规范**，不是中间件产品。类比 JDBC：JDBC 是规范，数据库驱动才是实现；MCP 是规范，各语言 SDK 和具体 Server 才是实现
- 工程口径上，一套"MCP 接入层 + 网关"确实承担了中间件的角色（鉴权、路由、审计），但那是部署形态不是协议本身
- 和传统中间件的边界：消息队列、RPC 框架解决"服务与服务"的通信，双方都是确定性的代码；MCP 的消费方是"会误解描述的模型"，所以协议里有工具发现、Schema 协商、给模型看的语义化描述这些为 LLM 设计的部分

### 面试版回答

> MCP 的价值我分"解决"和"没解决"说。解决的是集成碎片化：M 个应用 x N 个工具的私有适配收敛成 M + N，工具方写一次 Server 所有兼容应用都能挂，这就是它相对传统业务代码的核心优势——以前接一个新数据源要为每个客户端单独封一遍，现在按协议实现一次。协议还把握手、能力协商、工具发现、调用这些生命周期标准化了。
>
> 但短板也要主动讲：它不保证工具质量和描述质量；不解决上下文膨胀——反而因为挂工具太容易，工具一多 Schema 就吃 token；安全上协议只给了 OAuth 规范，落地还是自己的事；调试链路比进程内调用长。
>
> 至于算不算中间件：严格说它是协议规范不是中间件产品，类比 JDBC 规范和数据库驱动的关系。它和传统中间件的差异在于消费方不同——RPC 的调用方是确定性的代码，MCP 工具的调用方是会误解描述的模型，所以协议里有 Schema 协商和语义化描述这种为 LLM 设计的部分。

## 6. MCP 有哪几种传输方式？怎么选？

一句话：本地用 stdio，远程用 Streamable HTTP；旧的 HTTP+SSE 已在 2025-03-26 规范里被取代。

### 三种传输对比

| 维度 | stdio | HTTP+SSE（2024-11-05，已废弃） | Streamable HTTP（2025-03-26 起） |
| --- | --- | --- | --- |
| 部署 | 本地子进程 | 远程 | 远程为主，也可本地 |
| 通信方式 | stdin/stdout 管道，日志走 stderr | POST 上行 + SSE 长连接下行，双端点 | 单一端点（路径如 /mcp）：POST 发请求，响应可为 JSON 或升级为 SSE 流，可选 GET 开服务器流 |
| 状态 | 进程生命周期即会话 | 有状态，依赖长连接 | 服务器可无状态多实例，会话用 Mcp-Session-Id 标识 |
| 鉴权 | 依赖本机信任 | OAuth | OAuth 2.1（第 10 题） |
| 适用 | 本地工具、IDE、低延迟 | 已被取代 | 生产远程部署 |

### 回答时主动给出的三个版本知识点

1. **SSE 形态已废弃**：2025-03-26 规范明确用 Streamable HTTP 取代 HTTP+SSE。能说出这一点，说明真的读过规范而不是背博客
2. **Streamable HTTP 解决了什么**：旧形态双端点、必须维持长连接、难水平扩展；新形态单端点、服务器可无状态部署、支持会话标识，2025-11-25 起还允许服务器主动断流、客户端轮询重连
3. **演进方向**：2026-07-28 修订进一步移除 GET 流端点与协议级会话——趋势是更无状态、更云原生

stdio 没有鉴权的原因：Server 是用户本机上的子进程，信任边界就是本机操作系统；凭据走环境变量传入，但要防工具描述注入骗模型读取环境变量（第 10 题）。

### 如何同时适配多种传输

关键认知：**传输层与协议层分离**——MCP 消息（JSON-RPC）在所有传输上完全一致，差异只在字节怎么搬运。

```text
业务层（工具注册、调用逻辑）      只面向 JSON-RPC 消息编程，不感知传输
    ▲
抽象传输接口  start / send / close / onMessage
    ▲
┌───┴────────┬─────────────────┐
StdioTransport  StreamableHttpTransport  （旧 SDK 的 SSETransport）
```

1. 官方 SDK 本来就是这个架构：TS/Python SDK 里传输类可替换，`server.connect()` 接不同 Transport 即可
2. 自研时照抄这个分层：上层只认消息，传输做成可插拔 adapter
3. 选型：本地开发、桌面工具用 stdio（零网络开销、进程级隔离）；生产集中部署用 Streamable HTTP + 网关（统一鉴权、审计、扩容）

### 面试版回答

> MCP 传输形态三种：stdio 是 Server 作为本地子进程，消息走标准输入输出，适合 IDE 和本地工具，信任边界就是本机；SSE 形态是早期的远程方案，POST 上行加 SSE 长连接下行，但它在 2025-03-26 版规范里已经被 Streamable HTTP 取代了；Streamable HTTP 是单一 HTTP 端点（路径如 /mcp），POST 发请求，响应可以是 JSON 也可以升级成 SSE 流，服务器能无状态多实例部署，用 Mcp-Session-Id 标识会话，这是现在生产远程部署的标准形态。
>
> 同时适配多种传输的关键是 MCP 的分层设计：协议消息在所有传输上完全一致，差异只在字节搬运。所以工程上抽象一个传输接口——start、send、close、onMessage——stdio 和 Streamable HTTP 各实现一个 adapter，上层只面向 JSON-RPC 编程。官方 SDK 本来就是这么做的，connect 换个 Transport 就切换部署形态。
>
> 我的选型原则：本地和桌面场景用 stdio，零网络开销还自带进程隔离；生产集中部署用 Streamable HTTP，前面再加一层网关统一鉴权和审计。

## 7. Client 和 Server 协议版本不一致怎么办？

一句话：initialize 握手时协商版本——Server 支持就返回同一版本，不支持就返回自己支持的；再靠"忽略未知字段、能力声明才启用"两条原则兜底。

### 规范层怎么定的

1. **版本号是日期制**：2024-11-05 -> 2025-03-26 -> 2025-06-18 -> 2025-11-25（此后还有 2026-07-28 修订）
2. **协商规则**：initialize 时 Client 发自己期望的 protocolVersion；Server 支持就原样返回同一版本，不支持就返回自己支持的版本，Client 不接受则断开连接
3. **兼容三原则**：接收方必须忽略未知字段（向前兼容）；未知 method 返回 Method Not Found 错误而不是断连；可选能力（sampling、elicitation 等）必须在握手 capabilities 里声明才启用
4. **SDK 分级**：2025-11-25 起建立 SDK tiering，不同等级 SDK 有明确的特性支持和维护承诺

### 工程上怎么处理

1. 锁定 SDK 版本，规范升级跟着 SDK 版本走，不自己手写协议层
2. 跨版本组合的坑：新 Host 连旧 Server，新特性不可用但基础调用不受影响——靠能力协商降级；旧 Host 连新 Server 同理。真正危险的是自己绕过协商直接用新字段
3. Server 多版本共存：按 Client 声明的版本路由或双端点部署，灰度观察错误率再放量
4. 自研协议层的纪律：忽略未知字段、不做严格 Schema 校验、未知 method 报错不断连、对 capabilities 做防御式判断

### 面试版回答

> MCP 的版本是日期制的，比如 2024-11-05、2025-03-26、2025-06-18。兼容机制核心是 initialize 握手时的版本协商：Client 发自己期望的版本，Server 支持就返回同一版本，不支持就返回自己支持的最近版本，Client 不接受就断开。再配三条原则：未知字段必须忽略、未知方法返回 Method Not Found 而不是断连、sampling 这类可选能力必须在握手的能力声明里出现过才能用。
>
> 工程上我的做法是锁 SDK 版本跟着官方走，不手写协议层；升级时靠能力协商自然降级——新特性不可用，但基础调用不断；Server 侧要支持多版本共存时，按 Client 声明的版本路由，灰度观察错误率再放量。真实踩坑点一般不在协议，而在各语言 SDK 更新节奏不一致，所以要固定 SDK 版本并在 CI 里加握手冒烟测试。

## 8. 怎么开发一个 MCP Server？工具入参怎么设计？

一句话：Server 本身用官方 SDK 十几行就能跑起来，真正的工作量在工具设计——工具是写给模型看的接口。

### 工具设计原则（写给模型看的设计）

1. **粒度**：一个工具 = 一个可验证的业务动作；避免"万能工具"（do_anything 型）和过度碎片（get_user_1、get_user_2 型）
2. **命名**：动词 + 对象，蛇形命名（2025-11-25 规范附有工具命名指南）。工具名是模型最强的路由信号，比 description 权重更高
3. **description 写给模型看**：三句话——干什么、什么时候该用、什么时候别用。反例是写给人看的营销文案；歧义描述是选错工具的第一原因
4. **参数少而结构化**：枚举优于自由文本（城市用 enum 而不是 string）；必填项最小化；每个参数带 description；能从上下文推导的参数不要让模型填
5. **返回控制体积**：大结果要截断、分页或摘要，绝不把 10MB JSON 灌进上下文；content 面向模型消费，structuredContent 面向程序消费
6. **声明副作用注解**：annotations 里 readOnlyHint / destructiveHint / idempotentHint / openWorldHint（2025-03-26 起）——注意这是给 Host 做策略参考的提示，不是强制约束，Server 仍可能说谎

### 最小代码示例（TypeScript SDK）

```typescript
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "order-mcp", version: "1.0.0" });

server.tool(
  "query_order",                                   // 动词+对象
  "按订单号查询订单状态。用户给出一串订单号时使用；查询历史订单列表请用 list_orders",
  { orderId: z.string().describe("订单号，形如 ORD-2026-xxxx") },
  async ({ orderId }) => {
    const order = await db.findOrder(orderId);     // 真正执行
    return {                                       // content 回给模型
      content: [{ type: "text", text: JSON.stringify(order) }],
      isError: !order,                             // 执行失败让模型自纠错
    };
  }
);

await server.connect(new StdioServerTransport());  // 换 StreamableHttpTransport 即远程部署
```

要点：注册即声明 Schema（zod 自动转 JSON Schema）；传输一行切换；isError 把失败暴露给模型而不是吞掉。

### 高德 MCP 场景题：工具、权限、调用边界

1. **工具分层**：高频只读（地理编码、POI 搜索、路径规划）默认挂载；低频或按量计费的（驾车导航完整版）做成按需加载；写操作类（收藏地点、共享位置）必须走人工确认
2. **权限**：API Key 由 Host 侧注入（环境变量或 OAuth 流程），绝不进模型上下文；按用户等级限流配额；地图数据合规边界要主动提（坐标纠偏、测绘资质）
3. **调用边界**：坐标、城市名等参数做白名单校验；返回结果脱敏（不回吐用户位置历史）；高频只读工具加缓存，配额超限降级到静态地理数据
4. **失败语义**：配额超限、服务不可用时返回明确的 isError 信息，让模型知道"地理工具暂不可用"而不是编造结果

### 统一封装的兼容性坑

把 MCP 工具封装成内部统一 Tool 接口时，兼容性问题集中在四处：各 Server **错误语义不齐**（有的报协议错误、有的报业务错误，适配层要归一化）；**命名冲突**（两个 Server 都有 search 工具，要加命名空间）；**能力差异**（有的不支持 progressToken 和结构化输出）；**Schema 方言差异**（JSON Schema 校验宽松度不同）。

### 面试版回答

> 我写 MCP Server 的工具设计原则：粒度上一个工具对应一个可验证的业务动作；命名用动词加对象，因为工具名是模型最强的路由信号；description 按三句话写——干什么、什么时候用、什么时候别用；参数尽量用枚举和结构化类型，必填最小化；返回结果控制体积，大结果分页或摘要。代码上用官方 SDK，注册工具时用 zod 声明 Schema 自动转 JSON Schema，isError 把执行失败暴露给模型自纠错。
>
> 如果设计高德 MCP，我会把工具分层：地理编码、POI 搜索这类高频只读默认挂；导航完整版这种计费的按需加载；收藏、共享位置这类写操作必须人工确认。API Key 由 Host 注入不进上下文，参数做白名单校验，高频只读加缓存，配额超限降级到静态数据而不是让模型硬编。
>
> 统一封装的坑主要在兼容性：不同 Server 的错误语义、命名冲突、能力差异、Schema 校验宽松度都不一样，适配层要做归一化，这是封装层存在的核心价值。

## 9. 你的蓝湖 MCP 项目是怎么做的？

一句话定位：逆向蓝湖接口拿设计稿结构化数据，自研 Sketch 图层转 HTML/CSS 引擎与 Design Tokens 提取，再把组件库映射、代码规范和"读稿 -> 生成 -> 走查"流程封装成 Skill。

### 发现问题：转码链路的损耗在哪

1. 手工链路：设计师出稿 -> 前端打开蓝湖肉眼对照 -> 量间距、取色值、导切图 -> 手写还原。重复劳动集中在"读稿"环节，还原质量依赖人的耐心
2. 直接用 AI 的尝试及其失败原因——把设计稿截图丢给多模态模型，丢了三样东西：
   - **结构**：图层树、精确坐标、嵌套关系，模型只能从像素"猜"
   - **精确样式**：字号字重、色值、阴影参数全靠目测，走查时全是误差
   - **资产**：切图图标仍要手动导出
3. 结论：瓶颈不在模型不会写代码，而在**喂给模型的是像素，不是结构化数据**——设计工具的私有数据进不了模型上下文

### 分析问题：三个子问题，三个技术判断

| 子问题 | 判断 | 落点 |
| --- | --- | --- |
| 数据从哪来 | 蓝湖无开放 API，但 Web 端本身就在调一套完整接口 | 逆向接口 |
| 数据怎么变成代码 | Sketch 文档 JSON 是最接近设计稿"真值"的数据 | 自研转码引擎 |
| 质量怎么可持续 | 模型每次现想流程不可控，映射规则和规范会漂移 | 固化成 Skill |

载体选择：Cursor、Windsurf、Claude Code/Desktop 全是现成的 MCP Host，做成 MCP Server 一次实现全端复用——第 1 题 M + N 的直接体现。

### 推进与解决：数据层、转换层、流程层

**数据层：逆向蓝湖接口**

- DevTools 抓包梳理 Web 端调用链：项目/设计稿列表、设计稿详情、Sketch 文档 JSON、结构化 schema、切图 CDN
- 两套域名两套认证：主站 API 伪装浏览器头 + Cookie；DDS 资源域独立认证，分别封装
- 链接形态统一解析（邀请链接、普通设计稿、detach 稿、PRD）；超时 + 自动重试 + 5 并发多稿并行

**转换层：双路径转码引擎**

- 主路径：优先取蓝湖 DDS 的结构化 schema，生成带 flex 布局语义的 HTML，可读、可二次开发
- 兜底路径：schema 不可用的稿型直接解析原始 Sketch JSON，绝对定位像素级还原——圆角四值、阴影（光照角度三角换算成 x/y 偏移）、渐变、描边、文本样式逐一映射
- 部分失败不整体失败：每个设计稿按输出项（html/tokens/layers/image）标记 success / partial_success / error，文本解析降级成 warning 继续跑——"让失败对模型可读"的实践（第 11 题）
- 上下文体积控制：include 参数按需选输出物、layer_depth 控制图层树深度，避免把几 MB 图层 JSON 灌进上下文（第 12 题的问题在这里先遇到）
- Design Tokens：全量图层统计颜色/字体/阴影/圆角，按使用频次排序，既是生成的样式约束也是走查基准
- 工具设计按第 8 题原则落地：mode 用枚举切换 list/analyze/tokens/slices，参数全部带语义描述

**流程层：Skill 编排**

- 分工：MCP 工具提供原子能力（读稿、tokens、切图、PRD 解析），Skill 固化打法——设计稿组件到组件库 API 的映射、团队代码规范、"读稿 -> 生成 -> 走查"流程（对应第 4 题的层次划分）
- 走查闭环：design-review 流程对比实现与 Design Tokens，不一致项结构化列出回给模型修
- 另配 Resources（项目设计稿列表）和 Prompts（frontend-dev / design-review），供用户直接选用

### 权衡与遗留问题（主动讲）

1. **像素级 vs 语义化**：绝对定位保真但不可维护——所以 schema 语义路径优先、Sketch 像素路径兜底，组件库映射再把"像素稿"升级为"组件代码"
2. **逆向接口的脆弱性**：无官方 API，蓝湖改版必须跟——接口访问集中封装在一个模块收敛变更面，错误信息带定位提示
3. **Cookie 认证边界**：用户自己的 Cookie 通过环境变量注入 Host，绝不进模型上下文（第 10 题的原则）

### 面试版回答

> 这个项目解决的是设计稿转代码的链路损耗。以前的流程是对着蓝湖肉眼还原，或者把设计稿截图丢给多模态模型——但截图丢掉了图层结构、精确样式和切图资产，模型只能靠猜。我做下来得出的判断是：瓶颈不在模型不会写代码，而在喂给它的是像素不是结构化数据。
>
> 分析之后拆成三段做。第一段数据获取：蓝湖没有开放 API，我用 DevTools 逆向了 Web 端接口，梳理出项目列表、Sketch 文档 JSON、切图 CDN 的调用链；主站和资源域是两套认证，分别封装；链接形态做了统一解析，配了超时重试和五路并发。第二段是核心转码引擎，双路径设计：优先走蓝湖的结构化 schema 生成语义化 flex 布局；schema 拿不到的稿型兜底解析原始 Sketch JSON，绝对定位像素级还原，阴影角度到偏移量这种细节都做了换算。工程上每个输出项独立标记成功、部分成功或失败，失败信息回灌给模型自纠错；再用 include 参数和图层深度控制返回体积；全量图层统计出按频次排序的 Design Tokens。第三段把组件库映射、代码规范和读稿、生成、走查的流程封装成 Skill——MCP 提供原子工具，Skill 固化打法，走查环节拿 Tokens 对比实现形成闭环。
>
> 两个权衡主动讲：像素级和语义化之间，我让语义路径优先、像素路径兜底，组件映射再把像素稿升级成组件代码；逆向接口天然脆弱，我把接口访问收敛到一个模块控制变更影响面。这个项目也让我对 MCP 的边界有了实感——它解决连接和复用，"怎么用好工具"的流程规范要靠 Skill 层解决，两者是互补不是替代。

## 10. MCP 怎么做鉴权？有哪些安全风险？

一句话：远程传输走 OAuth 2.1（Server 是 Resource Server），stdio 靠本机信任，Host 再做工具级权限；最大的坑不是没鉴权，而是 token 透传和各类注入。

### 分层看鉴权

1. **传输/通道层（HTTP 类传输）**：2025-06-18 规范规定远程 Server 是 OAuth 2.1 Resource Server
   - 依赖 RFC 9728 Protected Resource Metadata 做发现（401 响应引导 Client 找到授权服务器）、强制 PKCE、RFC 8707 资源指示符把 token 绑定到具体 Server
   - 流程：Client 首次连接 -> Server 返回 401 + 元数据发现 -> 走 OAuth 授权码流程 -> 后续请求带 access token
2. **本地传输（stdio）**：无 HTTP 鉴权，信任边界是本机操作系统；凭据通过环境变量传给子进程，而不是让模型经手
3. **应用层**：Host 内做工具级权限——哪些工具可自动执行、哪些必须人工确认、哪些按租户隔离

### 为什么说鉴权/安全是 MCP 最关键的问题

MCP 把第三方代码和服务直接拉进 Agent 的决策回路，且模型会读 Server 提供的一切内容——攻击面从"人看 UI"变成"模型读消息"，而模型对注入没有天然免疫力。核心风险四件套：

1. **Token 透传**：Host 把高权限的用户 token 直接透传给 Server，Server 拿到就能干所有事，等于把钥匙串交给陌生人
2. **描述注入**：恶意 Server 在工具 description 里埋指令，骗模型调用其它工具或外泄数据
3. **Rug pull**：接入审核时工具无害，上线后更新描述变成恶意行为
4. **工具结果注入**：工具返回内容里夹带 prompt injection（网页内容、issue 正文都是入口）

### 防御清单

1. **最小权限**：每个 Server 单独的 OAuth scope 和 token，绝不共享用户全局 token；按工具而非按 Server 授权
2. **上下文隔离**：工具结果明确标记为数据而非指令，不进 System Prompt 区；对返回内容做注入检测
3. **人工闸门**：写操作、花钱、删数据类工具默认人工确认（引《01》的 waiting_approval 设计）
4. **变更审计**：工具清单和 description 的 diff 监控、来源锁定版本、上线后禁止静默变更
5. **全链路 Trace**：每次 tools/call 记录调用方、参数、结果、耗时，出事可回放（第 12 题）

### 面试版回答

> MCP 鉴权我分三层：远程传输层走 OAuth 2.1，2025-06-18 规范把远程 Server 定义成 Resource Server，用 RFC 9728 做授权发现，PKCE 和资源指示符把 token 绑定到具体 Server；本地 stdio 没有鉴权，信任边界是本机，凭据走环境变量；再往上是 Host 应用层的工具级权限。
>
> 为什么说鉴权是最关键的问题：MCP 把第三方直接拉进 Agent 的决策回路，而且模型会读 Server 给的所有内容，攻击面从人看 UI 变成模型读消息。四个典型风险：token 透传把高权限凭证交给不信任的 Server；工具描述注入骗模型执行恶意指令；rug pull 式的上线后改描述；工具结果里夹带注入。
>
> 防御我的清单是：每 Server 独立最小权限 token，绝不透传全局凭证；工具结果标记为数据不进 System Prompt 区；写操作类工具挂人工确认闸门；工具 description 做 diff 审计锁版本；全链路 Trace 每次 tools/call 可回放。这些在协议规范里都只有原则，落地全是 Host 侧的工程。

## 11. MCP 调用失败了怎么办？

一句话：先分类——协议错误 Host 拦下、工具执行错误用 isError 回灌给模型自纠错、传输失败重连对账；核心原则是让失败对模型可读。

### 失败分类与语义（先分类再谈处理）

| 类别 | 例子 | 模型可见？ | 处理方 |
| --- | --- | --- | --- |
| 协议错误（JSON-RPC error） | 方法不存在、JSON 格式错、无效请求 | 否，Host 层拦截 | Host 修协议问题，修不了断开连接 |
| 工具执行错误（isError: true） | 参数校验失败、下游 500、配额超限 | 是，回灌模型 | 模型自纠错：改参数、换工具或放弃 |
| 传输层失败 | 超时、断连 | 否 | 重连 + 未完成调用对账 |

关键规范细节（2025-11-25 明确）：**输入校验错误应作为工具执行错误返回，而不是协议错误**——目的就是给模型自纠错的机会。这就是"调用失败如何处理"的规范层答案：失败处理的第一步是让失败"对模型可读"，而不是 Host 层吞掉。

### 重试与幂等

1. 读取类工具天然幂等，可安全自动重试
2. 写入类工具：Server 端实现幂等键；Host 端区分可重试（超时、5xx、限流）与不可重试（4xx 业务错）
3. 指数退避加抖动；单 Server 连续失败超阈值熔断摘除，路由到备用 Server 或明确告知模型"该工具不可用"——后者比硬编造好得多

### Server 挂掉怎么办

1. **检测**：健康检查 + 调用超时双重判定
2. **隔离**：熔断摘除该 Server，不影响其它 Server 的调用
3. **恢复**：无状态 Server 直接多实例负载均衡；有会话状态的要粘性路由或会话外置
4. **降级**：工具不可用时把"当前不可用"作为观察结果回灌模型，模型会改道其它工具；关键链路准备备用工具
5. **兜底**：任务级失败不等于会话失败——失败步骤显式标注，Checkpoint 从断点续跑（衔接《01》第 10 题）

### 长任务与"结果能否流式输出"

- tools/call 的**最终结果是一次性返回的**（一个 JSON-RPC response），协议没有"工具结果分块流给模型"的一等支持——这是"能否流式输出"的准确答案
- 但有三条流式/异步通道，说全即是高分：
  1. **进度通知**：请求带 progressToken，Server 持续发 notifications/progress，Host 可转发给前端 SSE
  2. **Streamable HTTP 的流式响应**：Server 可在返回最终结果前通过 SSE 流先发中间消息
  3. **Tasks（2025-11-25，实验性）**：把长请求变成持久任务，轮询或延迟取结果
- 场景答法（工具要跑 100 秒、Agent 只容忍 50 秒）：
  1. **缩短感知等待**：progressToken 每 5~10 秒心跳加进度事件，让"逻辑等待"和"物理等待"分离
  2. **超时预算分层**：50 秒是 Agent 对同步等待的预算，超了就转异步——挂后台任务，Agent 释放去干别的，完成后取结果
  3. **取消机制**：notifications/cancelled 让 Agent 能主动放弃
  4. **工具侧拆分**：100 秒的大操作拆成可上报进度的子操作

### 面试版回答

> MCP 调用失败我先分类：协议错误是 Host 层拦截的，模型看不见；工具执行错误用 isError 标记，结果回灌给模型，让它自纠错——改参数、换工具或者放弃；传输层失败靠重连和对账。规范在 2025-11-25 还明确了一点：参数校验错误应该按工具执行错误返回，就是为了保留模型自纠错的机会，这是失败处理的第一设计原则：让失败对模型可读。
>
> 重试策略：读工具天然幂等可自动重试，写工具靠幂等键；可重试和不可重试错误分开，超时和 5xx 退避重试，4xx 业务错直接回灌；单 Server 连续失败就熔断摘除。Server 整个挂掉就隔离、降级——把"工具不可用"作为观察结果给模型，它会改道，比让它硬编好得多；关键任务再靠 Checkpoint 断点续跑。
>
> 结果能否流式：最终结果是一次性返回的，但有三条通道——progressToken 进度通知、Streamable HTTP 的流式中间消息、新版实验性的 tasks 长任务机制。工具 100 秒而 Agent 只等得起 50 秒的场景，我会用心跳加进度把感知等待压下来，超预算转异步后台任务，配取消机制，再考虑把大工具拆成可进度的子操作。

## 12. MCP 工具太多怎么办？

一句话：绝不全量挂载——按需发现、按域拆分、统一封装、网关治理，让模型每次只面对当前任务相关的十几个工具。

### 问题本质

100 个 Server x 每个 10 个工具 = 1000 个工具 Schema：上下文爆炸（光工具描述就吃掉几万 token）、选择准确率下降（工具越多模型选错率越高，描述相似的工具互相干扰）、性能开销（握手与 tools/list 的连接成本、冷启动）。

### 解法分层

1. **按需发现与延迟加载**：
   - 会话开始只挂核心工具，其余按任务域路由后动态 tools/list
   - 工具检索：把工具描述做 Embedding，任务进来先语义检索 top-k 工具子集再挂载
   - 渐进披露：先给目录级工具（list_domains），模型选中再展开该域细节
2. **统一封装兼容层**（第 8 题末尾的四处坑）：内部定义统一 Tool 接口，MCP 只是工具来源之一，错误语义、命名空间、能力差异在适配层归一化
3. **多路 MCP 选型**：按业务域拆 Server（检索类/数据类/操作类），天然形成工具命名空间，路由先行缩小选择范围
4. **网关与治理**：
   - MCP 网关集中做鉴权、限流配额、审计日志、工具注册中心（版本、owner、健康度）
   - 调用审计：谁在哪个会话调了什么工具、参数、结果、耗时，Trace 必须落到 tools/call 粒度
   - 新 Server 上线走影子流量验证再放量

### 面试版回答

> 工具太多的问题本质是三个：上下文爆炸、选择准确率下降、连接和加载的性能开销。我的解法分四层。
>
> 第一层按需加载：不预挂全部工具，会话只挂核心集，其余按任务域动态拉取；更进一步把工具描述向量化，任务进来先语义检索出相关工具子集再挂载，或者用目录级工具做渐进披露。第二层统一封装：内部定义统一 Tool 接口，MCP 只是来源之一，各 Server 的错误语义和命名冲突在适配层归一化。第三层多路 MCP 按业务域拆 Server，路由先缩小选择空间。第四层网关治理：集中鉴权限流、工具注册中心管理版本和健康度、审计落到每次 tools/call，新 Server 影子流量验证再放量。
>
> 这样治理后，模型面对的不是 1000 个工具，而是当前任务相关的十几个，选择准确率和 token 成本同时改善。

## 13. 怎么知道 MCP 链路做得好不好？

一句话：工具层看选择准确率、性能层看 P95、Agent 层看任务完成率、治理层看审计覆盖率；失败按四类归因，回流评测集。

### 指标分层

| 层 | 指标 | 说明 |
| --- | --- | --- |
| 工具层 | 工具选择准确率、参数 Schema 校验通过率、调用成功率 | 过程指标，Trace 里规则断言可算 |
| 性能层 | tools/call P95/P99、工具描述占用 token、重试率 | 决定能不能上线 |
| Agent 层 | 任务完成率、因工具失败导致的任务失败占比、降级触发率 | 业务结果指标 |
| 治理层 | 高危工具人工确认率、审计覆盖率、注入拦截率 | 线上安全指标 |

### 归因方法

失败按四类归因：**选错工具**（描述歧义 -> 改 description 或加消歧）、**参数错**（Schema 设计问题 -> 加枚举和约束）、**Server 故障**（可用性问题 -> 重试熔断多实例）、**结果被误读**（回灌格式问题 -> 结构化输出加引用）。每类分别回流评测集，形成闭环。

### 面试版回答

> MCP 链路的评测我分四层看：工具层看工具选择准确率、参数校验通过率、调用成功率；性能层看调用 P95、工具描述占的 token、重试率；Agent 层看任务完成率和因工具失败导致的失败占比；治理层看高危工具人工确认率和审计覆盖率。失败要归因到四类——选错工具、参数错、Server 故障、结果被模型误读——分别对应改描述、改 Schema、做容错、改回灌格式，然后回流评测集。这样每次改工具定义都有数可依，不凭感觉。
