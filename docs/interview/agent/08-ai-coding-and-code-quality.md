# AI Coding 与代码质量

> 定位：**在已有代码库里，用 AI 完成可控、可验证的工程改动**。不介绍工具功能，也不重复讲模型原理。
> 边界：Agent 概念与适用场景见《00》；执行循环、状态与恢复见《01》；上下文与记忆的组织与压缩见《Memory 与 Context 工程》；Skill 与 Hook 的机制见《03》；工具权限与连接协议见《06》；评测、Trace 与归因方法见《Agent 评估》。本篇只回答"怎么改代码、怎么控范围、怎么证明改对了"。
> 内容标签：**【当前实现】**源码与测试可核验；**【历史实验】**旧版本或已变更行为；**【示例场景】**为讲概念构造；**【方案建议/未验证】**尚未实现或未验证。未标注的工程做法属于通用经验，不代表某个项目已经落地。
> 读法：每题先给结论，再讲"为什么这么做"，然后用真实案例或证据展开；面试版回答用列表整理，便于直接口述。

## 1. 【P0】你平时怎么用 AI 写代码？讲一个真实需求，从接到需求到交付你实际怎么走？

- 核心结论：**AI 负责在明确边界内产出实现，人负责定义问题、划定边界、验证结果**。工作流不是仪式，每一步都在消除一类特定风险
- 为什么不能直接让 AI 开写：模型会用"最省事"的方式补全你没说清的约束——默认值、只处理正常路径、跳过校验、按自己的理解改接口。这些错误**运行时不一定报错**，只在业务上错

| 步骤 | 这一步的产出 | 为什么需要它 | 跳过会怎样 |
| --- | --- | --- | --- |
| 需求与验收条件 | 可判断的"做完"标准、异常路径 | 把"偶尔不对"变成可观察行为 | 做完才发现理解错，返工最贵 |
| 代码上下文 | 入口、调用链、数据所有权、相关测试 | 改动要落在正确的层 | 改错层，或在多处重复实现 |
| 先分析再修改 | 调用链、竞态/分支假设、证据位置 | 让 AI 的推断可被核对 | 把推测当根因，越改越乱 |
| 方案比较 | 2~3 个方案的适用范围与代价 | 避免最小补丁掩盖结构问题 | 修了症状，换个时序又复发 |
| 分步实施 | 每步可运行、可回滚的改动 | 出错能定位到具体一步 | 大 Diff 无法审阅，只能整体回退 |
| 验证与 Review | 断言、测试结果、影响面结论 | 证明"改对了"而不是"跑起来了" | 编译通过被当成功能正确 |
| 沉淀与限制 | 新增测试、规则或文档；未证明的部分 | 防止复发，也防止过度自信 | 同一个坑反复踩，或高估覆盖度 |

- 容易忽略的一点：**要求 AI 写计划的价值是让我审查它的理解**，不是让计划显得专业。计划里出现"顺便重构相关模块""统一命名"这类描述，说明范围失控，先砍掉再继续

**面试版回答**

> 结论先说：AI 在明确边界内产出实现，我负责定义问题、划边界、验证结果。具体这么走：
> 1. 把需求变成可验证的验收条件（正常路径、边界、失败路径、什么算做完）——因为「偶尔不对」这种描述无法判断做没做完，返工也最贵。
> 2. 让 AI 只读相关片段建立上下文：入口、调用链、类型与接口、相关测试，并明确允许改哪些文件、哪些不要动——改错层或在多处重复实现，代价远高于多花十分钟读代码。
> 3. 要求它先产出分析而不是代码：调用链、状态归属、可能的竞态或分支、依据在哪个文件——这一步的价值是让我审查它的理解，不是让计划显得专业。
> 4. 计划里有多个方案时，让它说清各自解决什么、代价是什么——避免用最小补丁把结构问题盖住。
> 5. 分步实施，每步小到能单独验证和回滚；改完先看 Diff 和影响面，再跑针对性测试与类型检查——因为出错时要能定位到具体一步。
> 6. 最后补回归、更新规则，并写清「这次证明了什么、没证明什么」。
>
> 我不会一上来就让它写：没被说清的约束，模型只会用最省事的方式补全，代价在测试或线上才暴露。

## 2. 【P0】主案例：界面被旧异步结果覆盖，你会怎么用 AI 一起定位、修复并证明修好了？

这道题是综合题：同时考需求定义、代码库理解、根因分析、方案取舍、改动范围控制和验证。案例来自一个 Nuxt 4 + Vue 3 + TypeScript 的 Coding Agent Web 客户端（pi-web-vue）。**【当前实现】**部分均已核到源码与测试。

### 2.1 先把"要保证什么"写清楚

用户视角的现象是"偶尔显示错了"，这种描述无法验证。先转成不变量：

1. 切换会话后，**旧会话的响应不得修改新会话的任何状态**（消息、统计、草稿、运行标记）
2. 同一会话内，**后发出的查询不得被先发出的查询覆盖**；同一次打开产生的多个请求也要有先后关系
3. 发送失败时，**只能撤回本次提交造成的临时状态**；发送期间用户新增的输入不能被清掉

> 为什么先写不变量：后面所有方案判断和测试断言都从它推导。没有它，"加个 requestId 就好了"这类说法无法证伪。

### 2.2 失败是怎么出现的

```text
时序一（跨会话）：打开 A → 打开 B 并返回 → A 的旧响应才返回
                 若旧响应无条件写状态，B 页面会显示 A 的内容
时序二（A→B→A）：第一次 A 的请求仍在等待 → 用户经 B 回到 A
                 此时 sessionId 相同，只比较 ID 无法拒绝第一次 A 的旧响应
时序三（同代乱序）：同一次打开里两个 reload 倒序返回
                 需要额外定义"谁更新"
```

三层失败指向同一个设计问题：**"这份数据属于谁"（会话身份）和"这份数据是否还新"（版本/顺序）是两件事，不能用一个字段同时表达。**

### 2.3 复现与证据

- 真实模型和网络不可控，靠"多点几次碰运气"无法复现。做法是**用受控 Promise 掌控返回顺序**：让旧请求保持 pending，先完成新请求，再放行旧请求，最后断言最终状态
- 项目里已有的相关测试（`tests/app/stores/`，【当前实现】）：
  - `chat.test.ts`：「快速连续打开两个会话 慢的旧响应被丢弃 最终内容属于后选的会话」「切走再回到同一会话时旧失败不能清除新一轮运行状态」「同名会话重入时旧握手等待者不能提交旧消息」「只发送本批附件 成功后保留发送期间新增附件」
  - `chat-races.test.ts`：「同名会话重入后旧撤回结果不覆盖新队列和草稿」「同名会话重入后旧提交不解除新提交的草稿保护」「导航恢复读取期间切换会话不会回退旧会话或锁住新会话」「重连发现任务已结束时清理运行态并恢复权威消息」
  - `chat-queue.test.ts`：「abort 失败时保持运行态等待事件对账」

> 为什么这些测试名值得记：它们把"旧请求不能覆盖新状态"拆成了**不同入口、不同分支**的反例，而不是只验证一条最顺利的时间线。

### 2.4 根因

| 层次 | 问题 | 只解决它会怎样 |
| --- | --- | --- |
| 会话身份 | 只比较 `sessionId` | A→B→A 时 ID 相同，旧响应仍被当作合法 |
| 生命周期 | 打开动作没有"代次"概念 | 不同打开动作之间的结果无法区分 |
| 请求顺序 | 同一次打开内多个请求没有先后定义 | 倒序返回时旧数据覆盖新数据 |
| 数据新鲜度 | 历史查询与 SSE 增量谁更新没有规则 | 历史快照可能盖掉刚到的事件 |

### 2.5 方案比较：为什么最终是"代次 + 序号 + 提交资格检查"

| 方案 | 解决什么 | 不解决什么 | 代价 |
| --- | --- | --- | --- |
| 只比较 `sessionId` | 跨会话污染 | A→B→A、同会话乱序 | 几乎为零，但覆盖不足 |
| 会话代次（generation） | 区分不同"打开/关闭"动作 | 同一次打开内的乱序 | 需要在所有异步出口做比较 |
| 请求序号（sequence） | 同一次打开内的先后 | 跨代场景 | 需要为每个入口定义自己的序号 |
| `AbortController` 取消请求 | 少做无用功、尽快释放 | **不能保证旧结果不写状态**（取消是尽力而为，回调可能已入队） | 需要额外处理取消与终态对账 |
| 服务端幂等/去重 | 网络层重复执行 | 前端状态归属 | 需要协议与存储支持，**【方案建议/未验证】** |

> 为什么不能"给所有异步函数加一个计数器就算了"：不同入口的失效条件不同——会话详情要 ID + 代次 + 序号，发送要 ID + 代次，事件连接要判断来源是否仍为 current，文件预览要比较加载版本。**每个异步入口都需要自己的提交资格**。

### 2.6 当前实现（节选，完整实现在源码里）

```ts
// app/stores/chat.ts：发送流程在等待前固定会话身份，await 之后核对
const id = sessionId.value;
const generation = sessionGeneration;
await connection.ensureConnected(id);
if (sessionId.value !== id || generation !== sessionGeneration) return null;
```

```ts
// app/stores/chat.ts：会话详情查询同时核对代次与本次查询序号
const sequence = ++reloadSequence;
const generation = sessionGeneration;
// ...await 历史查询...
if (sessionId.value !== id || generation !== sessionGeneration || sequence !== reloadSequence) return;
```

- `close()` 会同时递增 `sessionGeneration` 与 `reloadSequence`（`chat.ts` 第 498~499 行），因此 A→B→A 之后即便 ID 相同，旧发送仍因代次不符而失效
- 发送流程用**三个返回值**表达"本次提交对当前页面的意义"：`true` 提交成功、`false` 本次失败（可条件恢复草稿）、`null` 代次已失效（组件必须直接退出，不能把旧草稿塞进新会话）
- 回滚只撤本次仍占位的临时状态：比较 Vue 代理背后的原对象（`toRaw`）再决定是否 `pop`；附件按发送时的快照按对象身份过滤，发送期间新增的图片不会被清掉
- 停止的顺序是：撤回未消费队列 → 等 abort 返回 → 启动兜底计时 → 必要时重读历史。**兜底计时安装在 abort 返回之后**，所以不存在"点击后最多几秒结束"的保证（`chat.ts` 的 `stopFallbackTimer`）

### 2.7 不变量与验证：怎么证明"修好了"

| 要证明的性质 | 用什么输入 | 断言什么 |
| --- | --- | --- |
| 旧会话响应不改新会话 | 让旧请求 pending，先放行新请求 | 当前会话 ID、消息、统计仍属于新会话 |
| 同名会话重入不污染 | A→B→A，让第一次 A 最晚返回 | 代次不符的提交与撤回结果被丢弃 |
| 同代乱序以新为准 | 两个 reload 倒序完成 | 只有序号最新的结果写入 |
| 失败分支也不越权 | 旧失败晚于新提交 | 新会话运行标记不被旧失败清除 |
| 回滚只撤本次 | 发送期间新增附件 | 本次快照被移除、期间新增附件保留 |

- 测试设计上有三个要点值得讲：**用受控 Promise（如 `Promise.withResolvers()`）而不是等待真实超时**；**保留真实响应式容器**（把 Vue 深响应式数组换成普通数组，会让 `toRaw` 引用比较"看起来通过"，从而漏掉真问题）；**检查旁证防假通过**（例如断言加载函数只被调用一次，排除"其实重新请求了一遍"）
- 项目自己的文档也明确了证明范围（`docs/learning/11-测试体系与验证边界.md`）：测试名提到"重连"，但事件流测试实际只验证流的握手与关闭，没有打开浏览器；符号链接测试在无法创建链接的环境会跳过核心断言——**测试进程成功不等于该场景执行过**

**面试版回答**

> 结论：这类问题的本质不是「模型不听话」，而是**状态归属**没定义清楚。我会这样推进：
> 1. 先写不变量：旧会话响应不得写新会话状态；同会话内后发的查询不能被先发的覆盖；失败时只撤回本次造成的临时状态——后面所有方案和断言都从它推导。
> 2. 用受控 Promise 稳定复现：让旧请求一直 pending，先完成新请求再放行旧请求——靠快速点击碰运气既不可复现，也无法证明修好了。
> 3. 定位时分开两件事：数据**属于谁**（会话身份）和**是否还新**（代次、序号）。只比较 `sessionId` 覆盖不了 A→B→A，因为 ID 会一样。
> 4. 方案上保留两层：代次解决不同打开动作之间的失效，序号解决同一次打开内的先后；`AbortController` 只减少无用工作，不能替代提交资格检查——取消是尽力而为，回调可能已经入队。
> 5. 检查放在所有异步出口：成功、失败、清理分支都要重新核对身份——项目里就有「旧失败晚于新提交」的用例，只查成功分支不够。
> 6. 验证补针对性用例，并保留真实响应式语义（否则 `toRaw` 引用比较会假通过），再用调用次数这类旁证防止假通过。
> 7. 最后说边界：reload 的全部交错、真实网络恢复、abort 永不返回的超时闭环尚未验证；进程退出也不是持久任务恢复。
>
> 这么答的原因：面试官想听的是「你怎么把不确定的时序变成可验证的不变量」，而不是「加个 requestId 就行」。

### 2.8 追问

**1. 为什么不直接用 `AbortController` 代替代次检查？**
取消请求只保证"尽量不再产生后续工作"，不保证已经进入回调链的旧结果不写状态。**取消解决资源浪费，提交资格检查解决状态归属**，两者不能互换，取消之后仍要做终态对账。

**2. 为什么成功、失败、清理三个分支都要检查？**
因为每个分支都会写状态。项目里有针对性用例：「切走再回到同一会话时旧失败不能清除新一轮运行状态」——只检查成功分支，旧失败照样能破坏新会话。

**3. AI 在这个案例里具体做了什么？你怎么限制它？**
让它先读项目规则与设计约定，再给出调用链与状态归属分析，然后产出候选方案；我只放行经过比对的最小改动，每一步限定文件范围，改完由我核对 Diff、跑针对性测试。**判断句（哪些出口要检查、要不要引入新机制）由我决定**，因为这类边界一旦放宽，回归面很大。

**4. 怎么防止"测试通过但问题还在"？**
断言不变量而不是实现细节；用受控 Promise 制造倒序返回；检查调用次数之类的旁证避免假通过；并明确写下测试没证明什么。

## 3. 【P0】接手一个不熟的代码库，你怎么让 AI 先理解再改？怎么确认它不是瞎猜？

- 核心结论：**"让模型看到代码"不等于"让模型理解约束"**。要它先产出可核对的认知，再动手
- 为什么不能把仓库整块塞进去：噪声会稀释关键约束、成本上升、还容易抓错重点（压缩与预算机制见《Memory 与 Context 工程》）。按任务挑相关片段更稳
- 四类上下文按性价比排序：

| 来源 | 提供什么 | 为什么可信 |
| --- | --- | --- |
| 类型定义与接口契约 | 数据形状、必填字段、取值约束 | 机器可校验的规格 |
| 测试用例 | 真实行为与边界 | 写明了"什么算对" |
| 项目规则与设计文档 | 命令、目录职责、改动前置约定 | 把每次都要重复解释的约束沉淀一次 |
| Git 历史与提交说明 | 为什么这么写、绕开过什么坑 | 能识别"看着多余实则必要"的兼容逻辑 |

- 在这个 Web 客户端项目里，真实可用的入口是：根目录 `CLAUDE.md`（命令、目录职责、编码规范）、`AGENTS.md`（UI 改动前的文档阅读顺序与样式契约）、分步执行计划目录（每步标注参考实现与验收标准）、以及 `tests/` 下与业务文件一一对应的测试。**【当前实现】**
- 怎么确认"真的理解了"——让它回答四件事：**入口在哪、这个需求会经过哪些调用链、要改哪几个文件、哪些文件不能动**。答错说明认知有偏差，先纠正再写
- 遇到错误推断：要求它给出依据（文件 + 符号），再对照源码核实；纠正后的结论写回规则或文档，避免下次重踩

**面试版回答**

> 结论：先让 AI 产出**可核对的认知**，再允许它改代码。
> 1. 上下文优先选机器可校验的东西：类型与接口定义、相关测试；其次是项目规则与设计文档；最后才是 Git 历史——类型和测试写明了「什么算对」。
> 2. 要求它回答四个问题：入口在哪、经过哪些调用链、要改哪几个文件、哪些文件不能动；答不上来就说明上下文不够，先补再改。
> 3. 在这个 Web 客户端项目里，可用的是根目录规则文件、UI 改动前必读的设计契约、分步计划里标注的参考实现，以及与业务文件一一对应的测试。
> 4. 不把整个仓库塞进去：噪声会稀释关键约束、成本也高，按任务挑片段更稳。
> 5. 如果它推断了错误结构，要它给出文件和符号作为依据，核对后把结论写回规则，避免重复踩。
>
> 为什么这么做：模型说「我理解了」很廉价，**能被核对的认知**才值钱。

## 4. 【P0】AI 一次改了二十个文件，你怎么判断该不该合、怎么证明没破坏别的功能？

- 核心结论：**范围控制靠结构，不靠提醒**——先给允许清单与冻结的接口契约，再用小步提交和回归兜底
- 四层控制手段：

| 手段 | 怎么做 | 挡住什么 |
| --- | --- | --- |
| 文件边界 | 明确允许修改的文件与禁止触碰的目录 | 顺手重构、误伤无关模块 |
| 接口契约 | 先定函数签名与返回结构，再改实现 | 改了签名遗漏调用方 |
| 分阶段实施 | 按"契约 → 数据层 → 展示层"推进，每层各自验证 | 前后端同时改，出错无法定位 |
| 小步提交 + 回归 | 每次改动可单独回退；关键路径有自动化断言 | 出问题只能整体回退 |

- 判断"该不该合"之前先问三个影响面问题：**谁调用了它、谁依赖它的返回结构、有没有监控或埋点依赖它**。这三个问题比事后回归便宜得多
- 用主案例做对照：修一个竞态问题，**最小改动是"在异步出口补提交资格检查"**，而不是重写整个会话管理。后者会让 Diff 覆盖几十个文件，Review 无法逐段解释，回滚成本也高。**先改在正确的层，再谈要不要重构**
- 为什么 Demo 里"让 AI 自由发挥"可行、业务系统不行：业务系统有大量看不见的依赖（其他调用方、权限中间件、缓存键、埋点、历史兼容逻辑），改动的真实影响面远超文件本身
- 【P2】多执行体并行改代码：用文件级所有权避免同时改同一文件，公共契约文件串行修改；合并前跑全量检查。多数情况下不建议并行改代码，收益是吞吐，代价是一致性

**面试版回答**

> 结论：范围控制靠结构，不靠提醒。
> 1. 先设结构：允许改的文件清单、禁止碰的目录、先冻结接口契约。
> 2. 改之前问三个影响面问题：谁调用它、谁依赖它的返回结构、有没有监控或埋点依赖它——这比事后回归便宜得多。
> 3. 判断该不该合，看的是「有没有超出范围」和「有没有第二套业务逻辑被悄悄实现」，而不是逐行读完 Diff。
> 4. 分阶段加小提交：出问题时我宁愿回退一个文件，也不愿整体回滚。
> 5. 主案例里我选最小改动（在异步出口补提交资格检查），而不是重写会话管理——先改在正确的层，再讨论要不要重构，因为大 Diff 无法逐段解释、回滚代价也高。
> 6. 多执行体并行只在任务独立、契约已冻结时才用，否则冲突与一致性成本会吃掉收益。

## 5. 【P1】一个 Bug 让 AI 改了三轮还没好，你接下来怎么做？

- 核心结论：**连续追加修改是在"没有定位"的前提下碰运气**。先止损，再定位，最后才决定怎么改
- 顺序与理由：

```text
1 停止追加：避免在错误方向上继续叠加，让 Diff 越来越难读
2 最小复现：把触发条件缩到最小，确认它稳定复现
3 拿证据：日志、失败断言、状态快照、网络与数据库的真实返回
4 核对根因：当前修法是否作用在根因上；不能证伪就不算找到
5 必要时回滚：回到已知良好状态重新规划，而不是在脏状态上继续
6 限制每轮改动：一次只改一个假设，改完必须验证
7 补回归：修复前先有一条能复现问题的测试
```

- 为什么追加常常无效：模型看到的是"当前代码 + 你的描述"，而不是真实运行结果。当描述本身基于错误猜测时，它只会朝错误方向做出更复杂的改动
- 必须防的"作弊式修复"：为了让测试变绿而**删除断言、放宽校验、吞掉异常、改测试而不是改实现、顺手改无关文件**。防护是结构性的：测试与实现分开提交、测试改动需人工确认、关键用例在 CI 里受保护。**【方案建议/未验证】**：当前 Web 客户端项目没有配置 git hook 或 CI，靠的是每步收尾执行命令的纪律，不能声称有自动拦截

**面试版回答**

> 结论：先止损，再定位，最后决定怎么改；连续追加是在没定位的情况下碰运气。
> 1. 停止追加——避免在错误方向上叠加，让 Diff 越来越难读。
> 2. 回到最小复现，确认触发条件稳定；拿证据：日志、失败断言、状态快照、真实接口返回。
> 3. 核对根因是否找对：如果这个假设成立，把相关代码改回去错误应该重现；只能「改了好像好了」不算。
> 4. 改乱了就整体回滚重新规划，不在脏状态上继续叠加。
> 5. 之后每轮只改一个假设，改完必须验证；修复前先补一条能复现的测试。
> 6. 特别防「作弊式修复」：删断言、放宽校验、吞异常、改测试不改实现——做法是测试与实现分开提交、测试改动人工确认、关键用例纳入保护。
>
> 为什么强调这一点：AI 的目标是「让检查通过」，我的目标是「让行为正确」，两者冲突时必须以行为为准。

## 6. 【P1】你怎么证明 AI Coding 真的提效了，而不是感觉快了？

- 核心结论：**衡量"从需求到可交付"的总时长和返工率，而不是生成速度或代码行数**
- 全成本要算清：首次实现 + 人工修改 + 测试验证 + Review + 返工 + 后续维护。只看前两项就会得出"提效"的错误结论

| 指标 | 说明 | 为什么值得看 |
| --- | --- | --- |
| 需求交付周期 | 接需求到上线的时间 | 最接近业务感受 |
| 返工轮次 | 同一需求被退回修改的次数 | 反映需求理解与上下文是否到位 |
| Review 实质问题密度 | 每千行发现的业务/边界问题数 | 直接对应评审成本 |
| 缺陷逃逸率 | 上线后发现缺陷的占比 | 衡量断言是否覆盖真实不变量 |
| 回归/回滚次数 | 改动引发的其他故障 | 衡量范围控制 |
| AI 生成占比、行数 | 只能当过程指标 | 与业务价值无直接关系 |

- 怎么设计有意义的对照：**同一类需求、同一套验收条件、同一个人**，比较前后两个阶段的交付周期、返工轮次和逃逸缺陷；样本少时只做趋势观察，不给百分比结论
- 诚实说明当前项目能测什么：这个 Web 客户端项目有 50 个测试文件、`package.json` 里固定了 `typecheck` / `test` / `format:check` 三条命令，**但没有配 git hook 或 CI**，所以目前只能做本地前后对照与定向测试记录（项目文档里也明确写过"定向测试不等于全量套件结论"）。**【当前实现】**
- 三个常见误区：把生成速度当收益；把"AI 写的比例"当 KPI（会鼓励多生成而不是少返工）；用没有采集的数据充当成果

**面试版回答**

> 结论：看「从需求到可交付」的总时长和返工率，不看生成速度或代码行数。
> 1. 全成本要算清：首次实现、人工修改、测试验证、Review、返工、后续维护；其中返工与评审最容易被低估。
> 2. 指标看：交付周期、返工轮次、Review 每千行发现的实质问题、上线缺陷逃逸率、回归与回滚次数。
> 3. 对照要控制变量：同一类需求、同一套验收条件、同一个人，比较前后两个阶段；样本少时只谈趋势。
> 4. 诚实说现状：项目有 50 个测试文件和三条固定命令，但没有 hook 或 CI，所以只能做本地定向对照，不能宣称「提效了百分之多少」。
> 5. AI 生成占比只当过程指标——它跟业务价值没有直接关系，还会鼓励「多生成」而不是「少返工」。
>
> 为什么较真指标：指标用错，团队就会去优化「生成得更多」，而不是「交付得更稳」。

## 7. 【P2】Spec、Plan、Harness、Hook、Skill、SubAgent 你实际用了吗？分别解决什么问题？

- 核心结论：**它们不是同一层能力，也不能互相替代**；判断标准是"当前流程里出现了哪一类具体问题"
- 边界与引入时机：

| 机制 | 解决什么 | 何时值得引入 | 代价 |
| --- | --- | --- | --- |
| Spec（验收条件） | 把"做完"定义清楚 | 需求有歧义、验收靠感觉 | 几乎为零，收益最高 |
| Plan（实施计划） | 暴露理解偏差、限定范围 | 跨模块改动、陌生代码 | 少量沟通成本 |
| Harness（执行环境与反馈） | 让模型能跑命令、拿到失败反馈 | 需要真实的构建/测试闭环 | 环境与权限设计 |
| Hook（生命周期钩子） | 在固定节点强制执行检查或治理 | 有"必须每次执行、不能靠自觉"的规则 | 维护成本，过度使用拖慢流程 |
| Skill（可复用流程） | 把重复任务的做法沉淀下来 | 同类任务反复出现 | 版本与维护成本 |
| SubAgent（子代理） | 上下文隔离与任务拆分 | 探索型任务、职责清晰的子任务 | 通信损耗、结果需校验 |

- 这个项目实际用到的是**规则文件（Spec 与约束）+ 分步执行计划（Plan）+ 测试与命令（Harness 的反馈面）**；没有配 Hook、CI，也没有引入 Skill 与 SubAgent。**【当前实现】**原因很直接：那些问题还没反复出现到值得引入机制的程度
- 机制细节见《01 Agent Runtime 与架构》与《03 Skill 机制》，这里只回答"该不该用"

**面试版回答**

> 结论：这些不是同一层能力，不能互相替代；判断标准是当前流程里出现了哪一类具体问题。
> 1. Spec 定义「做完」，Plan 暴露理解偏差和范围，Harness 提供真实执行反馈，Hook 强制固定检查，Skill 沉淀重复流程，SubAgent 做上下文隔离。
> 2. 这个项目实际用的是规则文件、分步计划和测试命令；没有上 Hook、CI、Skill 或 SubAgent。
> 3. 原因很直接：那些痛点还没反复出现到值得引入机制——机制越多，理解和维护成本越高。
> 4. 真要引入，我会先看它能否对应一个可验证的行为改善，而不是因为「看起来很专业」。

## 8. 一个对照短例（【示例场景】）：会员优惠的"展示与提交同源"

业务规则：结算页展示会员折扣，折扣可与满减叠加，最终价以后端计算为准。

- 验收条件：展示明细之和等于最终价；最终价等于接口返回值；提交值等于接口返回的最终价；非会员/优惠过期/金额为 0 时不展示优惠行；接口失败按原价展示并提示，不静默降级
- 典型错误症状：页面显示优惠价，提交时却传了原价或前端自算的价；优惠顺序（先满减还是先打折）与后端不一致
- 关键失败分支与取舍：前端**不重复实现优惠规则**（否则出现两套真源）；代价是必须等接口返回，首屏多一次请求

> 为什么这一节只做对照：它的业务规则密集，但证据链是"接口契约 + 断言"这一层，深度不如第 2 节的状态归属问题。**保留它是为了说明一类典型错误（展示与提交不同源），不适合再做第二个完整案例。**
