# Prompt、意图识别与模型调用工程

> 定位：**在一个真实的 Agent 业务任务里，把用户输入变成可执行的模型决策，并用确定性边界、调用治理和评测控制风险**。不写 Prompt 技巧清单，也不重复讲检索、上下文、评测的机制。
> 边界：上下文组织与压缩见《Memory 与 Context 工程》；检索、召回与排序见《05 RAG 面经》；工具协议与连接见《06 MCP 面经》；执行循环、状态与恢复见《01 Agent Runtime 与架构》；数据集、Judge、Trace 与归因方法见《Agent 评估》。
> 内容标签：**【当前实现·默认入口】**指项目当前默认持久入口中可核验的行为；**【当前实现·其他路径】**指同一仓库里其他入口或契约层的实现；**【历史实验】**指早期路径或已变更行为；**【示例场景】**为讲概念构造；**【方案建议/未验证】**尚未实现。
> 读法：核心结论先行，"为什么"紧跟其后；面试版回答用列表整理，便于直接口述。

## 1. 【P0】客户只说"东西有问题，想退"，从这句话到退款真正执行，链路要经过哪些环节？哪些必须由确定性逻辑兜住？

- 核心结论：**模型只负责理解与决策，副作用路径固化为确定性工作流**。一条售后请求要穿过"澄清 → 查证 → 判定 → 授权 → 执行 → 沟通"六个环节，其中**判定、授权、执行三环不允许模型拍板**
- 为什么这样分工：退款涉及钱和不可回滚的副作用。如果把"能不能退、退多少、谁来批"交给模型，错误无法通过评测消除，只能靠事后补偿

```text
客户: 东西有问题 想退
   ↓
① 澄清（ask_user 协议工具）
   缺订单号 → 先查最近订单并请客户选择，不替客户确认
   ↓
② 查证（只读工具）
   订单、物流、历史退款记录；政策条款用 search_policy 检索
   ↓
③ 判定（确定性领域逻辑）
   退款资格、可退金额、是否需人工审批 —— 由政策与规则计算
   ↓
④ 授权（审批令牌 / 人工审批）
   超阈值走人工；审批通过才发放一次性令牌
   ↓
⑤ 执行（工作流 + 三道防线）
   幂等键 → 审批令牌 → 网关级去重，重复退款被结构性排除
   ↓
⑥ 沟通（模型）
   依据工具结果解释，必须显式 conclude 才算完结
```

| 环节 | 谁负责 | 为什么不能交给模型 |
| --- | --- | --- |
| 澄清 | 模型发起，`ask_user` 协议工具承载 | 纯文本提问不会被系统感知，无法形成检查点 |
| 查证 | 只读工具 | 模型没有实时数据，凭记忆回答会编造订单状态 |
| 判定 | 领域逻辑 | 资格与金额是业务规则，模型只能解释不能裁定 |
| 授权 | 审批令牌 / 人工 | 涉及资金，必须可审计、可追责 |
| 执行 | 确定性工作流 | 资金动作永不直接经过模型 |
| 沟通 | 模型 | 模型擅长解释，但必须约束"以工具结果为准" |

- 机制落点（【当前实现·其他路径】）：工具目录由契约层的 Zod 契约生成，只读工具直接执行，业务动作工具经槽位校验后路由到确定性工作流；`ask_user`（提问权交给模型、暂停等待用户）与 `conclude`（任务完结协议工具）是协议工具，从结构上区分"提问"和"完结"
- **需要如实说明的边界**：项目 README 明确写着，当前**默认持久入口**使用完整模型轮次确认、**冻结版本工具集合**与**字符政策检索**；旧版的逐 token 事件、**动态查单门控**和上下文压缩不能当作该入口已启用的能力。**每步动态收紧工具目录**的机制属于另一条路径（`packages/agent/src/agent.ts` 的 `prepareStepTools`），不能混说成默认入口行为

**面试版回答**

1. 我把这条链路拆成六环：澄清、查证、判定、授权、执行、沟通。
2. 澄清必须走协议工具（如 `ask_user`），因为纯文本提问不会被系统记录，形不成暂停点。
3. 查证只能用只读工具：订单、物流、历史退款、政策条款都要有工具结果作为依据。
4. 判定、授权、执行由确定性逻辑负责：资格和金额由政策规则算，超阈值走人工审批，执行由工作流完成。
5. 模型负责理解意图和解释结果，但必须遵循"以工具结果为准"，不能凭记忆编造政策或金额。
6. 我会主动说边界：默认入口用的是冻结的工具版本集合和字符检索；动态收紧工具目录是另一条路径的机制，不能混为一谈。

## 2. 【P0】为什么政策检索只能提供解释依据，退款资格和金额必须由确定性逻辑判定？

- 核心结论：**检索解决"我该怎么解释"，规则解决"我能不能退、退多少"**。把检索结果当授权，等于让相似度决定业务合法性
- 为什么容易混淆：政策条款里确实写着"七天无理由""运费由买家承担"这类规则，模型读完很像"可以退了"。但**条款文本是解释材料，不是可执行规则**——它缺订单状态、缺时间窗口的计算、缺例外与优先级

| 事项 | 依据什么 | 如果改用模型判断会怎样 |
| --- | --- | --- |
| 是否在可退窗口内 | 订单签收时间 + 规则计算 | 日期算错、时区与边界含混 |
| 可退金额 | SKU 明细与差价规则 | 金额被"约等于"，财务无法对账 |
| 是否需要人工审批 | 金额阈值等硬条件 | 阈值形同虚设，资金风险不可控 |
| 怎么向客户解释 | 检索到的条款原文 | 这正是检索应该发挥作用的地方 |

- 当前实现（【当前实现·其他路径】）：政策检索是**两级**——先用确定性关键词打分召回候选（`KeywordPolicyScorer`），再把候选交给模型精排打分（`ChatModelPolicyScorer`），注释里写明"关键词预筛与评测同算法，保证召回层行为一致"，并限制候选数量以控制请求体大小
- 边界要说清：**没有基于向量的检索实现**——检索器注释明确写着「不依赖 embedding 接口」；仓库里有早期的检索对照实验（`docs/experiments/rag-baseline-v1.md`、`rag-dataset-v1.md`），属于**【历史实验】**线索，不代表当前默认入口

**面试版回答**

1. 我区分两件事：检索回答"怎么解释"，规则回答"能不能退、退多少、谁来批"。
2. 政策条款是解释材料，不是可执行规则——它不知道订单状态，也不含时间窗口计算和例外优先级。
3. 所以资格、金额、审批阈值都由确定性逻辑判定，检索结果只用于向客户解释依据。
4. 当前实现是两级检索：关键词预筛召回候选，模型在候选里精排，保证召回层与评测同算法。
5. 我会明确边界：没有基于向量的检索实现，仓库里只有早期对照实验。

## 3. 【P0】工具参数通过了 JSON Schema，为什么还不能直接执行？中间还要过哪些校验？

- 核心结论：**Schema 只保证"形状对"，不保证"这件事现在合法"**。从模型输出到真正执行，至少要过五层：语法/结构 → 领域授权 → 状态前置条件 → 副作用防线 → 结果对账
- 为什么不能靠 Schema 兜底：模型完全可能生成一个格式完美、但订单不属于当前客户、或订单状态不允许退款的调用

| 层次 | 检查什么 | 失败后的处理 |
| --- | --- | --- |
| 结构 | 字段、类型、必填、受控枚举 | 回灌错误让模型改参数，有限次后降级 |
| 归属 | 资源是否属于当前客户/租户 | 直接拒绝，记审计 |
| 状态前置 | 订单是否已签收、是否已退过款 | 拒绝并说明原因与替代路径 |
| 授权 | 是否超阈值需要审批、是否持有有效令牌 | 走人工审批或拒绝 |
| 防线 | 幂等键、审批令牌、网关去重 | 重复请求返回首次结果，拦截落事件 |

- 【当前实现·其他路径】证据：契约层定义了业务幂等键的构造函数（退款、收货、补偿、价保各一套），工具输入输出契约里带 `idempotencyKey`、可选 `approvalToken` 与 `gatewayDeduped` 字段；`GUARD_LAYERS = ['idempotency', 'approval_token', 'gateway']` 把三道防线写进契约，注释说明"网关级去重是最后一道兜底，防止前两道被绕过"
- 必须守住的诚实边界：README 提示**模拟资金渠道不等于真实支付集成**，所以不能把这三道防线说成"全局绝对保证"

**面试版回答**

1. Schema 只保证形状正确，不保证业务合法；我会把校验分成五层。
2. 结构层查字段、类型、必填和受控枚举，失败就把错误回灌让模型改参数，有限次后降级。
3. 归属与状态层查这笔订单是否属于当前客户、状态是否允许退款，这层由服务端判定。
4. 授权层查是否超阈值需要人工审批、是否持有有效审批令牌。
5. 防线层用业务幂等键、一次性审批令牌和网关级去重，保证重复请求只生效一次。
6. 我会补一句边界：项目里的资金渠道是模拟的，这三层是设计保证，不能讲成生产环境的绝对承诺。

## 4. 【P0】审批通过、流程恢复之后，模型还在说"正在等审批"，这类问题你怎么定位、怎么修、怎么验证？

- 核心结论：这不是"模型不听话"，而是**恢复时把陈旧状态喂给了模型**。根因在引擎的断点恢复，不在提示词
- 现象与证据（【历史实验】的失败追踪，含复现命令与轮次统计）：某用例共 8 轮导出，7 轮失败。业务断言（退款已执行）其实通过，**失败的是沟通层**：客服反复输出"审批通过后会通知您"，从不告知最终结果

```text
根因一（引擎层）
  resumeAfterApproval 跳过已完成步骤直接恢复
  断点里的 state.policyOutcome 仍是历史的 needs_approval
  模型可见的摘要带着陈旧状态 → 模型据此判断"还在等审批"
根因二（评测工具链）
  Judge 在 reason 里转述对话原文时用了未转义的英文双引号
  产出非法 JSON → 解析失败被判 judge 失败（保守方向）
  掩盖了"模型行为其实已经正确"的事实
```

- 修复（三层，缺一不可）：
  1. 工作流引擎：审批通过分支在恢复后**覆写摘要里的 `policyOutcome` 为 `approved`**，消除模型可见的陈旧状态
  2. 提示词：工具使用约束追加"审批决策恢复后，必须先用文本告知最终结果、金额与到账渠道，再调用 `conclude`"
  3. Judge：提示词禁止在 reason 里用英文双引号，解析层加正则兜底逐项提取；兜底仍失败则维持"判失败"的保守方向
- 为什么三个都要修：只改提示词，模型仍会读到陈旧状态；只改引擎，模型仍可能不说结果；只改 Judge，真实的行为缺陷会被"解析成功"掩盖
- 验证方式与证明范围：该用例复跑通过（35s）；【历史实验】中真实模型 L2 曾记录任务成功率 31.4% → 52.3%，README 明确提醒**历史百分比不能当作当前质量**；稳定性需要 `Pass^k` 多轮，而不是单轮通过就算修复

**面试版回答**

1. 我先看这条链路的分层：业务动作是否执行、模型可见状态是什么、沟通层输出是什么。
2. 这个案例里业务断言通过、沟通失败，说明问题不在执行，而在"模型看到了什么"。
3. 顺着恢复路径查下去，根因是断点恢复跳过了已完成步骤，摘要里的 `policyOutcome` 还是历史的 `needs_approval`。
4. 同时发现评测工具链的第二个问题：Judge 输出的 JSON 因为未转义双引号解析失败，把一次正确的模型行为判成失败——**评测口径错了会看起来像模型错了**。
5. 修复分三层：引擎恢复后覆写摘要状态、提示词明确恢复后必须先告知结果再结束、Judge 加解析兜底且保持保守判失败。
6. 验证上我会强调：单轮复跑通过只能说明这条路径通了，稳定性要看 `Pass^k` 多轮；历史真实模型成绩不能当成当前质量。

## 5. 【P0】模型行为不达标时，你怎么归因？怎么避免"一失败就改提示词"？

- 核心结论：**先分层归因，再决定改哪里**。项目把失败映射成四层，正是为了避免把引擎、场景、评测的问题都算到模型头上

| 归因层 | 典型证据（判据来源） | 该改什么 |
| --- | --- | --- |
| 状态层 | 业务状态与网关结果不符（如退款未执行、重复扣款） | 工作流引擎、幂等与授权 |
| 轨迹层 | 工具调用序列、是否发起澄清、是否该升级 | 工具目录、协议工具、路由 |
| 参数层 | 工具参数校验失败、字段缺失 | 工具描述、Schema、槽位约束 |
| 回复质量层 | 解释不全、该告知却沉默、语气问题 | 提示词规则、沟通要求 |

- 两个真实失败类型（【历史实验】失败追踪，各有复现命令）：
  1. **工具纪律与调用冗余**：某澄清用例第一轮用纯文本提问、没走 `ask_user`，于是补问事件缺失、链路没继续；第二轮链路全通但工具调用 6 次超过上限 5。修复不是打补丁，而是**结构性收紧**：动作工具在订单未加载前不进目录，补问阶段可见工具集收窄，投机调用随之减少。诚实声明也写明了：单轮复验通过，真实模型有随机性，稳定性留待多轮
  2. **场景设计缺陷**：某恢复用例连续 4 轮全败，因为判据要求"客服解释无需重复操作的原因"，但模拟客户从头到尾没提出重复提交——判据与对话证据脱钩。修复是**强化场景剧本**，让重复提交成为开场诉求。这暴露了一条原则：判据必须二元且可从对话验证，这就要求场景真的触发目标行为，否则判据只是永远无法满足的空断言
- 为什么"一失败就改提示词"是错的：上面前两类的根因分别在**工具目录**和**场景设计**，改提示词既解决不了，还会把已验证的规则搅乱

**面试版回答**

1. 我先按四层归因：状态层（业务是否真的执行）、轨迹层（工具与澄清路径）、参数层（参数与槽位）、回复质量层（解释与沟通）。
2. 分层之后各改各的：状态层改引擎与幂等，轨迹层改工具目录与协议工具，参数层改契约与描述，沟通层才动提示词。
3. 举个例子：澄清请求失败是因为模型用纯文本提问、没走协议工具，同时调用次数超限；修法是结构性收紧工具目录，而不是加一句"请调用工具"。
4. 另一个例子更值得警惕：恢复用例连续失败四轮，最后发现是场景没触发目标行为，判据无据可依——**这是评测设计问题，不是模型问题**。
5. 所以我的习惯是先看证据属于哪一层，再决定改哪里；改完必须说清这次改动证明了什么、没证明什么。

## 6. 【P1】模型调用一共花多少钱、失败了怎么算账？超时和重试你会怎么处理？

- 核心结论：**先有账本，再谈优化**。调用前预占、按尝试记录、用有效用量结算，并把"结果未知"单列——否则成本会被低报，重试会被重复计费或漏计
- 为什么需要"预占"：模型调用可能超时、返回未知状态。如果只在成功时记账，失败重试的成本就消失了；如果只在发起时记账，"实际用量"又无从修正

| 账本字段（语义） | 解决什么 |
| --- | --- |
| 调用标识 | 一次尝试一条记录，能对账到具体请求 |
| 预占金额 | 发起前占用预算，防止并发超额 |
| 实际用量 | 结算时用有效 usage 修正 |
| 状态与结果 | 区分成功/失败/未知，未知单独保留而不是归零 |
| 未知与挂账汇总 | 报表里单列"未知"与"仍在挂账"的部分 |

- 【当前实现·其他路径】证据：持久层有账本实现（`P7Ledger`，字段含调用标识、预占、实际、状态、结果），运行时组合里创建了账本并交给模型网关；评测侧的成本报告会分别汇总预占、实际、未知与挂账；网关契约里定义了预算引用与 `BUDGET_EXCEEDED` 这类错误码
- 重试要分性质：**只读、可安全重放**的调用可以有限重试并带退避；**会产生副作用或结果未知**的调用不能默认重试。README 的表述是"两类退款通过业务授权、发送意图和原交易查询恢复，**未知资金不自动重发**"——这正是重试边界的业务体现
- 【当前实现·其他路径】重试不靠约定而靠错误契约：全系统统一一种错误形状并带 `retryable` 标记，默认把 `RATE_LIMITED`、`TIMEOUT`、`UPSTREAM_ERROR` 视为可重试，工作流与 Agent 据此决定重试、换路还是转人工；会话网关会把 HTTP 状态归一化（429 归为限流、4xx 归为配置错误、5xx 归为上游错误），并且**每次尝试独立预占与记账**
- 边界（【方案建议/未验证】）：**分布式限流、请求队列、多模型自动回退尚未实现**。错误分类与限流识别不等于限流治理——前者只是「知道发生了什么」，后者需要排队、背压、配额与降级顺序；真要扩展，触发条件是队列长度与等待时长超阈值、429 比例持续偏高，验证指标是 P95、失败率与单位成功成本，不能讲成已有能力

**面试版回答**

1. 我会先建立账本：一次调用一条记录，记录预占、实际用量、状态和结果。
2. 预占是防止并发超预算；结算用有效 usage 修正；结果未知的记录单独保留，不归零也不当作成功。
3. 报表里把"未知"和"仍在挂账"单列，否则成本会被系统性低报。
4. 重试按性质分：只读可重放的调用有限重试加退避；有副作用或结果未知的调用不能默认重试，先查状态再决定。
5. 项目里的业务约束是"未知资金不自动重发"，这就是重试边界在业务上的表达。
6. 我会说明还没做的部分：错误契约能识别限流与超时并标记可重试，但分布式限流、请求队列、多模型自动回退都还没实现，属于生产扩展方向。

## 7. 【P1】Prompt 怎么版本化？改了以后你怎么知道它真的变好了？

- 核心结论：**提示词是代码**——有版本号、有回归集、有对照，改动前后都能解释"哪条规则导致了什么变化"
- 为什么必须版本化：提示词里一条规则的调整可能同时修好一类失败、弄坏另一类。没有版本和回归集，你无法回答"这次上线到底改了什么"

| 做法 | 具体是什么 | 防止什么 |
| --- | --- | --- |
| 版本号常量 | 提示词文件顶部标注版本，改动写清原因 | 说不清线上跑的是哪一版 |
| 纯函数组装 | 输入参数 → 提示词文本，同输入可复现 | 隐藏状态导致不可复现 |
| 规则可判定 | 每条规则对应一个可验证行为 | 规则膨胀、互相冲突 |
| 历史试错留档 | 注释里记录哪一版踩了什么坑 | 同一个坑反复踩 |
| 两级评测 | L1 脚本化回归（零成本、进 CI）+ L2 模拟用户多轮对话 | 只凭一次成功对话下结论 |

- 【历史实验/其他路径】证据：提示词文件带版本号，注释里记录了试错结论——某版本把三类越权诉求合并处理，纯攻击拦截率从 40% 掉到 7.7%；另一个版本过度合并，又把正当诉求卡进人工队列（有 L2 用例因此失败）。L1 侧当前有 **124 条**脚本化用例（用例目录内 `id` 计数），L2 侧由模型扮演客户与 Agent 多轮对话
- 说清证明范围：L1 是脚本化模型的治理回归，**只能证明系统层与流程层行为，不代表模型智能表现**；L2 里的真实模型成绩属于历史实验记录（31.4% → 52.3%），**不能当作当前质量**

**面试版回答**

1. 我把提示词当代码：文件带版本号、改动写明原因、纯函数组装保证同输入可复现。
2. 规则写成可判定的动作，规则多了就做消融——每条规则都应该能对应一个可验证行为。
3. 历史试错写进注释：比如某版本合并了越权分类，纯攻击拦截率从 40% 掉到 7.7%；另一个版本又过度合并，把正当诉求卡进人工队列。
4. 验证走两级：L1 是脚本化回归（124 条，零成本、进 CI），L2 是模拟用户多轮对话。
5. 我会强调两级各自的证明范围：L1 证明的是流程与治理行为，不代表模型智能；L2 里的历史百分比也不能当作当前质量。
6. 稳定性还要看 `Pass^k` 多轮，而不是单轮通过。

## 8. 【P2】需不需要单独做一个意图分类器或路由器？

- 核心结论：**当前没有一个独立的路由模块**，模型决策、工具目录、协议工具和提示词规则共同承担了"走哪条路"。要不要单独加路由层，取决于是否出现"路径选择本身成为主要失败来源"
- 当前是怎么分工的（【当前实现】）：
  1. 工具目录决定"能做什么"：不同入口下发的工具集合不同，模型只能在可见工具里选
  2. 协议工具决定"什么时候停"：`ask_user` 让澄清成为可观测的暂停点，`conclude` 把"完结"从自然语言里分离出来
  3. 提示词规则决定"优先级与边界"：先查证再作答、以工具结果为准、拒绝时给依据与替代路径
  4. 确定性工作流决定"能不能执行"：判定、授权、执行都不在模型手里
- 什么时候值得引入显式路由层（【方案建议/未验证】）：出现下面任一信号时——同一句话频繁走错路径且提示词改不动；不同路径的成本/延迟差异巨大需要按请求分流；需要按路径做独立的评测与灰度；需要给不同租户/场景下发不同的能力集
- 引入代价：多一层分类就有多一层错误，且分类结果要被下游当作契约消费，否则错误会被放大（评测与归因方法见《Agent 评估》）

**面试版回答**

1. 当前没有独立的意图分类器或路由模块，路径选择由四样东西共同承担。
2. 工具目录决定"能做什么"：不同入口下发的工具集合不同，模型只能在可见范围内选。
3. 协议工具决定"什么时候停"：`ask_user` 把澄清变成可观测的暂停点，`conclude` 把完结从自然语言里分离出来。
4. 提示词规则约束优先级：先查证再作答、以工具结果为准、拒绝要给依据和替代路径。
5. 判定、授权、执行由确定性工作流负责，模型没有执行权。
6. 只有当"路径选择本身成为主要失败来源"或需要按路径分流与灰度时，才值得加显式路由层，而且要接受多一层分类就多一层错误。
