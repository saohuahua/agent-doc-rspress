# Agent Runtime 与架构

> 工程题统一答题骨架：`目标与约束 -> 架构和数据流 -> 失败路径 -> 指标与验证 -> 权衡与降级`。

## 1. Agent、Workflow、单次 LLM 调用怎么选（含 Agent vs Chatbot/AI）

- 三者的本质区别就三个维度：**控制权在谁**、**有没有 Loop**、**有没有状态反馈**

```latex
单次 LLM 调用
  -> 输入 -> 一次生成 -> 输出
  -> 无状态、无循环、不决定下一步
  -> 适合：摘要、翻译、分类这类路径确定的单步任务

Workflow（工作流）
  -> 开发者用代码预先编排好执行路径（DAG / 固定节点）
  -> LLM 只在节点内干活，不决定"下一步做什么"，控制权在代码
  -> 适合：步骤可枚举、对确定性和合规要求高的流程

Agent（智能体）
  -> 模型在循环中自主决定：调什么工具、要不要继续、何时结束
  -> 控制权在模型，工具结果回灌上下文，影响下一步
  -> 适合：目标明确但路径开放、无法预先枚举步骤的任务
```

| 维度 | 单次调用 | Workflow | Agent |
| --- | --- | --- | --- |
| 控制权 | 无 | 代码 | 模型 |
| 是否有 Loop | 无 | 无（图写死） | 有 |
| 中间反馈 | 无 | 节点间传递 | 工具结果回灌模型 |
| 确定性 | 高 | 高 | 低，需要治理 |
| 需求变更成本 | 改 Prompt | 改代码/图 | 改 Prompt + 工具描述 |
| 典型场景 | 摘要/翻译 | 审批流、固定 RAG 管道 | 开放式排障、编码、研究 |

- 概念辨析：
  1. Agent vs Chatbot：Chatbot 是多轮对话，一问一答，没有目标和工具；Agent 有目标、会拆解、调工具、对结果负责。最快判断标准 = 有没有"工具调用 + 自主多步"
  2. Agent vs AI：AI 是技术大类（模型、生成、检索都算），Agent 是用 LLM 构建的一种系统形态
- 权威定义参照：Anthropic《Building Effective Agents》的定义——Workflow 是"LLM 和工具按预定义代码路径编排"，Agent 是"LLM 动态主导自己的过程和工具使用"

> 我认为 Agent、Workflow 和单次 LLM 调用的核心区别，是控制权在谁手里。单次调用就是一次性生成，没有循环没有状态，适合摘要、分类这种单步任务。Workflow 是开发者预先编排好固定路径，LLM 只在节点里干活，不决定下一步做什么，所以确定性强，适合步骤可枚举、容错要求高的流程。Agent 是把控制权交给模型，在一个循环里自己决定调什么工具、要不要继续、什么时候结束，工具结果会回灌上下文影响下一步。
>
> 选型我看三个条件：路径能不能枚举、错误代价多大、时延容忍多少。能枚举就用 Workflow，省钱省心还好评测；路径开放、步骤依赖中间结果，才用 Agent。Chatbot 和 Agent 的区别就在有没有目标和工具调用——一问一答是 Chatbot，带着目标自主多步执行并对结果负责的才是 Agent。我项目里就是固定前置环节走 Workflow，中间开放式的解决问题环节交给 Agent。

## 2. 为什么选 Agent，而不是"大模型 + 查询"或写死的 Python 脚本

- 这题的考察点：你是真选过型，还是跟风用了 Agent。必须先讲任务特征，再讲为什么 Agent 匹配
- 适合 Agent 的任务特征：
  1. 分支不可枚举：输入多样，处理路径依赖中间结果
  2. 多步且步间有反馈：查了 A 才知道要不要查 B
  3. 需求频繁变化：改 Prompt 和工具描述，比改脚本逻辑再发版快
  4. 长尾场景多：脚本只能覆盖头部规则，长尾靠模型泛化
- "Python 脚本也能做"怎么回应：
  1. 脚本 = 把所有分支写死，规则数量随场景线性膨胀，每个新 case 都要改代码发版
  2. Agent = 把分支决策外包给模型，维护对象从"规则代码"变成"工具 + 描述"
  3. 有人工复核时 Agent 仍有价值：省的是"开发维护规则"的成本，不是"复核"的成本
- 反向承认边界（加分项）：高精度、强确定性、规则能全覆盖的场景不该用 Agent；生产上常见"规则兜头部 + Agent 兜长尾"的混合形态

> 为什么选 Agent 而不是脚本或"大模型加查询"，我会先讲任务特征再回答：如果一条规则、一个 SQL 查询就能覆盖，我肯定不用 Agent，直接"大模型加查询"甚至纯脚本。我选 Agent 是因为当时的任务分支不可枚举：系统要根据输入决定先查什么，查完根据结果决定下一步，步骤之间有依赖，这种路径没法提前写死。
>
> 用 Python 脚本做，等于把所有分支写成 if-else，规则数量随场景线性膨胀，每来一个新 case 就要改代码、走发布；Agent 的做法是把分支决策交给模型，我只维护工具和工具描述，长尾场景靠模型泛化兜住。即使有人工复核，Agent 省的也是开发和维护规则的成本，不是复核的成本。
>
> 反过来我也承认代价：成本更高、延迟更长、结果有不确定性。所以高精度、强确定性、规则能全覆盖的场景就不该用 Agent。我们线上是混合的：头部高频场景走固定规则保确定性和成本，长尾交给 Agent，这比全量 Agent 划算。

## 3. Agent 的组成部分；Harness 是什么、怎么自研（含：模型变强后 Harness 变厚还是变薄）

- Agent 最小组成（五块）：
  1. 模型：决策大脑
  2. 上下文/记忆：System Prompt + 对话历史 + 工具结果
  3. 工具：与外部世界交互的手
  4. Loop 编排：把前两者串成执行循环
  5. State/持久化：跨轮、跨进程保存运行状态
- 生产级再加一层治理：权限、沙箱、评测、Trace、预算
- Harness 概念（本题重点）：
  1. 定义：模型外圈的工程壳。模型只负责产出 token 和调用决策，Harness 负责把"不确定的模型"约束成"可靠系统"的全部工程
  2. 传递关系：Harness 组装上下文（System Prompt、工具 Schema、历史）传给模型 -> 模型返回决策 -> Harness 负责执行、校验、落状态、决定下一步。同一模型套不同 Harness，可靠性完全不同
  3. 具体包含：上下文组装与压缩、工具定义与执行、权限门禁、沙箱隔离、Loop 控制（终止/预算）、State 与 Checkpoint、Hooks（生命周期挂点）、SubAgent、日志与 Trace、评测
  4. 参照物：Claude Code 是典型 Harness 形态——固定工具集（Read/Edit/Bash 等）、权限模式与确认、Hooks、SubAgent、Skill 渐进加载
  5. Harness ≠ 框架：框架（LangChain/LangGraph）是编排层的实现选项；Harness 是问题域，框架是工具
- 自研 Harness 的模块划分（面试追问直接给这张图）：
  1. 模型网关：多模型路由、重试、限流、成本统计
  2. 编排/Loop：状态机、终止条件、预算控制
  3. State 与 Checkpoint：会话状态、断点恢复
  4. Tool 层：Schema 注册、权限、超时、幂等
  5. 上下文管理：裁剪、压缩、分层注入
  6. 可观测：结构化 Trace（每轮决策、工具调用、Token 消耗）
  7. 安全：注入防护、沙箱、人工审批闸门
- 观点题：模型越来越强，Harness 变厚还是变薄
  1. 执行细节层会变薄：简单规划、格式校验这类任务能力会被模型吸收
  2. 治理层会变厚：权限、审计、恢复、评测这些"模型不能替你担责"的部分只会更重
  3. 结论：内层变薄、治理层变厚，总代码量不一定减少

> 我理解 Agent 的组成可以拆成五块：模型是决策大脑，上下文给它提供信息，工具让它和外部世界交互，Loop 把三者串成执行循环，State 负责把运行状态持久化。生产级还要加一层治理：权限、沙箱、评测和 Trace。
>
> Harness 我理解是模型外面那圈工程壳。模型只负责产出 token 和调用决策，剩下所有事都是 Harness 的：组装上下文、定义和执行工具、管权限、控 Loop、落状态、做恢复。同一个模型套不同 Harness，出来的可靠性完全不同，所以我会说 Harness 就是把"不确定的模型"变成"确定的系统"的那部分工程。Claude Code 是很典型的参照：固定的工具集、权限确认、Hooks、SubAgent、Skill 渐进加载，这些都是 Harness 的一部分。
>
> 自研的话我按七个模块划分：模型网关管路由和成本，编排层管状态机和终止条件，State 层管断点恢复，Tool 层管 Schema、权限和幂等，再加上下文管理、全链路 Trace 和安全闸门。至于模型越来越强 Harness 会怎么变——我认为执行细节那层会变薄，比如简单规划和格式校验模型自己就能做好；但权限、审计、恢复、评测这些模型不能替你担责的部分只会变厚。总体是内层变薄、治理层变厚。

## 4. LangGraph、LangChain、手写状态机怎么选

- 三者不在同一层，一句话定位：

| 选项 | 形态 | 擅长 | 不擅长 |
| --- | --- | --- | --- |
| LangChain | 链式/管道组合 | 线性流程：RAG、预处理管道 | 环、分支回跳、中断恢复 |
| LangGraph | 图 + 共享 State（状态机） | 环、分支、Checkpoint 持久化与断点恢复、人工中断 | 简单场景用它偏重 |
| 手写状态机 | 自研代码 | 零依赖、行为完全可控、好调试 | 恢复/并发/可视化都要自己造 |

- 选型三问：流程需不需要环和中断恢复？团队想不想自己维护底层？现有技术栈是什么？
- 追问"节点如何抽象"时的答法：节点 = 输入输出契约 + 执行体（模型或代码）+ 重试策略 + 超时 + 降级路径

> 我认为这三个不是同一层的东西。LangChain 偏线性管道，适合 RAG 这种固定流程；LangGraph 把 Agent 建模成图加共享状态，支持环、Checkpoint 持久化恢复、还能中断等人工输入，所以做需要循环和恢复的 Agent 我优先考虑它；手写状态机适合流程基本固定的简单场景，胜在可控，但恢复和并发都要自己造。我的项目因为需要 Loop 加断点恢复，所以选了 LangGraph 这类图状态机方案，而不是只有链式能力的框架。

## 5. Agent Loop 的最小核心实现（要求能写伪代码）

- 最小实现就是一个 while 循环：

```typescript
async function runAgentLoop(task: Task, state: AgentState): Promise<string> {
  for (let round = 1; round <= MAX_ROUNDS; round++) {
    const messages = buildContext(state);                // 1. 组装上下文
    const resp = await llm.call(messages, TOOL_SCHEMAS); // 2. 带工具 Schema 调模型
    state.append(resp);                                  // 3. 先落盘，再执行
    await checkpoint(state);

    if (!resp.toolCalls?.length) {                       // 模型不再调工具 => 最终答案
      return resp.text;                                  // 显式终止
    }

    for (const call of resp.toolCalls) {                 // 4. 执行工具（带超时）
      const result = await executeTool(call, { timeout: 30_000 });
      state.append(toolMessage(call.id, result));        // 结果回灌，进入下一轮
    }

    await checkpoint(state);                             // 5. 轮末再落一次（工具结果已入 State）
    checkBudget(state, round);                           // 6. 轮数 / Token 预算检查
  }
  throw new LoopExceededError();                         // 硬终止兜底
}
```

- 高频追问："除 Function Calling 外，靠什么驱动循环"——三件套：
  1. 终止条件：每轮判断是否到达结束状态
  2. State 更新与回灌：工具结果必须写回上下文，模型才能基于观察决策，否则循环退化成重复调用
  3. 预算与守卫：轮数、Token、超时，没有边界循环就不会停
- 每轮必须做的三件工程事：写 State/Checkpoint、判终止、上报事件（Trace/前端进度）

> 我认为 Agent Loop 的最小实现就是一个 while 循环：每轮先根据 State 组装上下文，带着工具 Schema 调模型；模型返回两种可能——不再调工具，那就是最终答案，循环结束；要调工具，就执行工具、把结果作为 tool 消息写回状态，进入下一轮。每轮还要做三件工程上的事：把状态落一次盘、检查轮数和 Token 预算、把本轮决策和工具调用上报到 Trace。
>
> 有个容易被忽略的点：驱动这个循环的不只是 Function Calling，还有终止条件和状态回灌。工具结果必须写回上下文，模型才能基于观察决定下一步，否则循环就退化成重复调用。所以我总结 Loop 等于模型决策加状态更新加终止判断，三部分缺一不可。

## 6. Agent 的终止条件与结束状态

- 显式终止（正常退出）：
  1. 模型本轮不再发起工具调用 -> 输出最终答案
  2. 目标达成（可校验任务：测试全过、字段填全）
  3. 人工审批通过或拒绝（human-in-the-loop 中断点）
  4. 用户主动取消
- 硬性终止（兜底退出）：
  1. 最大轮数
  2. Token / 金额预算耗尽
  3. 整体超时
  4. 连续 N 次工具失败
  5. 死循环检测：同一工具 + 相同参数反复出现、状态长时间无变化
- 结束状态枚举：

```latex
completed         正常完成
failed            失败（区分可重试 / 不可重试）
cancelled         用户取消
timeout           超时
waiting_approval  等人工审批（挂起，不是结束）
needs_input       等用户补充输入（挂起，恢复后从断点继续）
```

- 关键认知：不能只信模型说"我做完了"。模型有提前宣布成功的倾向，可校验的任务要配结构化输出 + 校验器，校验不过不算 completed

> 我认为终止条件要分两类看。显式的是正常退出：模型不再调工具、输出最终答案，或者目标可校验地达成，再就是人工审批和用户取消。硬性的是兜底：最大轮数、Token 预算、整体超时、连续工具失败，还有死循环检测——同一工具加相同参数反复出现就强制断掉。
>
> 结束状态我一般设计六种：completed、failed、cancelled、timeout、waiting_approval、needs_input。后两个是挂起不是结束，恢复后从断点继续跑。
>
> 另外一个关键点：不能只靠模型自己宣布完成。模型有提前说"我做完了"的倾向，所以可校验的任务我会配结构化输出加校验器，校验不过就不算 completed，退回去继续或者按 failed 处理。

## 7. 如何防止死循环与任务挂死（单机 + 分布式）

- 目标与约束：Agent 有不确定性，失控的四种表现——轮数爆炸、Token 爆炸、任务挂死、重复调用同一工具
- 单机层（四件套）：
  1. 硬上限：最大轮数、单轮/总 Token 预算、整体超时
  2. 重复检测：同一工具 + 相同参数哈希连续 N 次 -> 先注入系统提示让模型换策略，无效再强杀（先干预后击杀，成本低）
  3. 工具级防护：超时、熔断、连续失败计数，超阈值直接终止
  4. 上下文干预：检测到绕圈时注入一条提醒消息，比直接杀任务便宜
- 分布式层（单机上限不够，任务会漂移、会重试）：
  1. 幂等：工具调用带 idempotency key，重试不产生重复副作用
  2. 租约锁：同一会话同一时刻只有一个 worker 持有租约，防双跑
  3. 分布式计数：轮数/Token 用 Redis 跨实例累计，不能只存在进程内存
  4. Watchdog：后台扫描 running 超时任务，强制标 failed 并回收沙箱资源
- 指标与验证：轮数分布 P99、Token 分布、死循环拦截次数、挂死任务数
- 权衡：限太紧伤完成率，太松烧钱 -> 上限按任务类型分级可配置

> 怎么防死循环和挂死，我分单机和分布式两层说。单机是四件套：最大轮数加 Token 预算这类硬上限；重复动作检测，同一工具加相同参数连续出现，先注入一条系统提示让模型换策略，无效再强杀；工具级超时和熔断，连续失败直接终止；最后是整体超时。
>
> 分布式下光有单机上限不够，因为任务会漂移、会重试，要补四件事：工具调用全带幂等键，重试不产生重复副作用；会话用租约锁，保证同一时刻只有一个 worker 在跑；轮数和预算用 Redis 做跨实例累计；再加一个 watchdog 定时扫描 running 超时的任务，强制标失败并回收沙箱。
>
> 权衡上，限太紧伤完成率，太松就是烧钱，所以上限按任务类型做成可配置，再用轮数 P99 和死循环拦截次数这两个指标回归调整。

## 8. ReAct 之外的 Loop 范式

```latex
ReAct（Reason + Act，Yao 等 2022）
  -> 单循环：Thought -> Action -> Observation 交替，边想边做
  -> 优点：灵活，每步基于最新观察
  -> 代价：轮数多、Token 高；长任务容易失去全局视野

Plan-and-Execute（先计划后执行，源自 Plan-and-Solve，LangGraph 有标准范式）
  -> 两阶段：Planner 先产出完整步骤清单，Executor 按步执行，计划过时触发 Re-plan
  -> 优点：全局视野；计划可审计、可缓存；步骤可并行
  -> 代价：前置延迟高；需要重规划机制

Reflection / Reflexion（Shinn 等 2023）
  -> 执行后加自我评审：评价输出 -> 生成改进建议 -> 重试
  -> 优点：自我纠错，质量敏感场景收益明显
  -> 代价：轮数和 Token 翻倍，可能过度自我否定
```

| 范式 | 结构 | 全局性 | 成本 | 适用 |
| --- | --- | --- | --- | --- |
| ReAct | 单循环交替 | 局部 | 中 | 路径开放的探索任务 |
| Plan-and-Execute | 计划 + 执行两段 | 全局 | 前置高 | 可分解的复杂长任务 |
| Reflection | 执行 + 评审双循环 | 局部 | 高 | 质量敏感的生成/编码 |
| 混合模式 | 先 Plan 再 ReAct，产物加 Review | 全局 + 局部 | 最高 | 复杂且路径不确定 |

> 除了 ReAct，我重点会讲两个范式。一个是 Plan-and-Execute：先让 Planner 产出完整计划，再按步骤执行，执行中计划过时就触发重规划。它比 ReAct 多了全局视野，计划还能审计和并行执行，代价是前置延迟和要维护重规划机制。另一个是 Reflection：执行后加一个自我评审环节，根据评审意见重试，适合质量敏感的场景，但 Token 成本明显上升。
>
> 生产上很少只用一种。我的做法是混合：复杂任务先 Plan 拆解，单步执行用 ReAct 灵活处理，关键产物再加一次 Review。范式选择本质是在全局视野和响应灵活之间做权衡，按任务的稳定性和质量要求定。

## 9. State、运行内存、Checkpoint 的区别；State 全局管理与并发覆盖

- 一句话关系：State 是数据模型，运行内存是载体之一，Checkpoint 是 State 的持久化快照

```latex
State（运行状态）
  -> 一次任务运行的结构化数据：消息历史、任务目标、变量、工具结果、当前步骤
  -> 生命周期：任务开始创建，结束归档
  -> 是 Loop 的数据载体：模型每轮决策的上下文都由 State 组装而来

运行内存（In-memory）
  -> 进程内的临时数据：缓存、连接、中间变量
  -> 进程挂了就没了，不参与恢复

Checkpoint（检查点）
  -> State 在关键节点的持久化快照，每轮 / 每节点落一次
  -> 带版本号和时间戳，用于宕机恢复和回滚重放
```

- State 全局管理三点：
  1. 单一数据源：权威 State 只在服务端一份，前端、子 Agent 看到的都是投影
  2. Schema 化：messages、task、variables、tool_results 分字段，不是一坨字符串
  3. 读写边界：只有编排层写 State，工具和子 Agent 通过返回值间接写
- 多个 Agent 并发会不会覆盖状态：会，解法按强度排：
  1. 分 namespace：每个 Agent 只写自己的子树（如 `state.researcher.*`）
  2. 版本号/乐观锁：写入带版本，冲突时合并或重试
  3. 单一写者：关键全局字段只允许主 Agent 更新
- Tool Message 为什么单独建模：要带 tool_call_id 关联请求与结果、带执行状态（成功/失败），因为恢复时必须精确到"哪个调用没完成"，不能盲目重试

> State、运行内存、Checkpoint 的区别，我先一句话说清：State 是任务运行的结构化数据模型，比如消息历史、任务目标、变量和工具结果；运行内存是进程里的临时载体，进程挂了就没了；Checkpoint 是把 State 定期持久化成快照，带版本号，用来宕机恢复和回滚重放。
>
> State 全局管理我抓三点：一份权威版本只在服务端，前端和子 Agent 看到的都是投影；Schema 化，消息、任务、变量、工具结果分字段存；写入口收敛到编排层，工具和子 Agent 只能通过返回值间接改状态。
>
> 多个 Agent 并发确实会互相覆盖，解法是分 namespace，每个 Agent 只写自己的子树；关键状态加版本号做乐观锁；或者干脆单一写者，只有主 Agent 能改全局字段。另外工具消息我会单独建模，带 tool_call_id 和执行状态，因为恢复时必须知道哪个调用没完成，不能盲目重试。

## 10. Checkpoint 如何实现，宕机后如何恢复

- 何时存：每个 Loop 轮次结束、每个 Workflow 节点完成、工具调用执行前后各记一次（执行前记"待执行"，成功后更新状态）
- 存什么：

```typescript
interface Checkpoint {
  version: string;          // Schema 版本，升级兼容
  sessionId: string;        // 会话 / 任务标识
  seq: number;              // 递增序号，防乱序、防旧快照覆盖新状态
  state: AgentState;        // 全量 State：messages + 任务状态 + 变量
  pendingCalls: ToolCall[]; // 已发起未确认的工具调用（恢复时对账）
  ts: number;
}
```

- 存哪：LangGraph 内置 Checkpointer（SQLite/Postgres 等）；自研一般 MySQL 存全量快照 + Redis 存热状态支撑快速恢复
- 恢复五步：
  1. 按 session/task 找最新 checkpoint
  2. 校验版本与完整性
  3. 对账 pendingCalls：已执行的用幂等键去重，未执行的补跑
  4. 从断点重建上下文，继续 Loop
  5. 恢复后先降速观察，确认健康再放量
- 服务端宕机 vs Agent 宕机，分开答：
  1. 服务端（编排进程）宕机：State 在存储里，新实例接管即可，影响小
  2. Agent/沙箱宕机：正在执行的工具会中断 -> 靠幂等键对账 + 沙箱重建，长任务从 checkpoint 续跑
- 关键前提：工具幂等，否则恢复重放会产生重复副作用

> Checkpoint 的实现我概括成三件事：何时存、存什么、存哪。时机上每个 Loop 轮次或每个节点结束落一次，工具调用前后各记一次，这样恢复时知道哪些调用已确认。内容是全量 State 加版本号加递增序号，还要记录已发起但未确认的工具调用。存储上我一般 MySQL 存全量快照，Redis 存热状态支撑快速恢复。
>
> 恢复五步：按会话找最新 checkpoint，校验版本，对账未完成的工具调用——用幂等键去重，已执行的跳过，没执行的补跑，然后从断点重建上下文继续跑，恢复后先降速观察再放量。
>
> 服务端和 Agent 宕机要分开说：编排进程挂了，State 在存储里，新实例接管就行；沙箱里的 Agent 挂了，正在执行的工具会中断，所以幂等是恢复的前提，重放才不会产生重复副作用。

## 11. Agent 长任务整体设计：状态、执行、恢复

- 目标与约束：任务 10 分钟级，用户会关页面、服务会重启发布 -> 可靠性目标：进度不丢、状态可查、断了能续
- 架构与数据流：

```text
前端(SSE 订阅进度) -> 网关 -> 任务服务(落任务表, 返回 task_id) -> MQ -> Worker 池(跑 Agent Loop)
                                   |                              |
                                   +- MySQL: 任务表 + 步骤表 <----+ 每步更新状态 + Checkpoint
                                   +- Redis: 热状态 / 进度 / 租约
```

- 状态拆解：
  1. 任务状态机：pending -> running -> succeeded/failed/cancelled，中间加 suspended（等审批/等输入挂起）
  2. 步骤表：任务拆步骤，记录每步的 checkpoint 指针，步骤是断点续跑的最小单位
- 执行：
  1. 异步化：创建任务落库入队就返回，Worker 从 MQ 领任务跑 Loop，前后端解耦，页面关闭不影响
  2. 进度上报：Worker 每步写 Redis 进度 + 发事件，前端 SSE 订阅；重连后先查任务表补齐状态再续订
  3. 租约：Worker 持租约跑任务，心跳续期；Worker 挂了租约过期，任务可被其他实例重新领取
- 恢复：
  1. 服务重启：状态在 DB/Redis 不随进程丢；重启后扫描 running 超时的任务重新入队
  2. 断点续跑：从最新 checkpoint 重建 State 继续；工具带幂等键，重放不产生重复副作用
  3. 优雅启停：发布时先停领新任务，等在跑任务到安全点或迁移租约，再下线
- 为什么十分钟长链路可接受：异步执行不用盯 + 进度可视化 + 失败可续跑而不是从头再来
- 指标与验证：任务成功率、断点续跑率、平均恢复耗时、挂死任务数

> 整体设计一个 Agent 长任务，我会按状态、执行、恢复三块说。状态上，任务有一张任务表加步骤表，状态机是 pending、running、suspended、succeeded、failed、cancelled，步骤是最小断点单位，每步落 checkpoint。执行上全部异步化：前端创建任务，服务落库入队就返回，Worker 从 MQ 领任务跑 Loop，进度写 Redis 再通过 SSE 推给前端——页面关了任务照跑，重连后先查任务表补状态再续订进度。Worker 持租约加心跳，挂了租约过期，任务能被别的实例重新领走。
>
> 恢复上，服务重启不怕，状态都在 DB 和 Redis，重启后扫描 running 超时的任务重新入队；任务断了就从最新 checkpoint 重建上下文续跑，工具全带幂等键，重放不会重复副作用。发布下线走优雅启停：先停领新任务，等在跑任务到安全点或迁移租约再下线。
>
> 十分钟长链路用户能接受，前提就是三件事：异步不用等、进度可视化、失败可续跑。我监控任务成功率、断点续跑率和恢复耗时。

## 12. 单 Agent vs Multi-Agent：何时拆、如何通信、状态竞争

```latex
单 Agent
  -> 优点：上下文连贯、无通信损耗、链路简单好调试
  -> 缺点：工具多时选择变差、上下文膨胀、职责混杂难评测

Multi-Agent
  -> 优点：职责隔离、每个 Agent 上下文精简聚焦、可并行、可独立评测
  -> 缺点：通信有损、错误会传播、整体延迟上升、状态一致性复杂
```

- 何时拆（四个信号，满足越多越该拆）：
  1. 工具数量过多，单 Agent 选工具准确率下降
  2. 上下文装不下，不同子任务需要不同专业上下文
  3. 职责边界天然清晰（检索 / 写码 / 评审）
  4. 子任务可并行
- 默认立场先说"不拆"：Multi-Agent 不是免费的性能提升，是组织复杂度的手段——这是加分答法
- 常见形态与通信：
  1. 主子架构：主 Agent 负责拆解与汇总，子 Agent 只领领域任务，互不共享完整上下文
  2. 通信方式：结构化消息（任务描述 + 约束 + 输入），不直接共享内存
  3. 结果回灌：子 Agent 输出作为消息写回主 Agent 的 State
- 状态竞争：两个 Agent 推进同一状态时，约束靠程序还是 Prompt？
  1. 结论：**靠程序，不靠 Prompt**。Prompt 约束是"建议"，并发正确性必须程序保证
  2. 手段：分 namespace、单一写者、版本号乐观锁，共享资源加锁或排队串行化

> 单 Agent 还是 Multi-Agent，我的默认立场是能不拆就不拆，因为 Multi-Agent 会引入通信损耗和错误传播，不是免费午餐。出现四个信号才考虑拆：工具多到选择准确率下降、上下文装不下、职责边界天然清晰、子任务能并行。
>
> 拆的话我常用主子架构：主 Agent 负责拆解和汇总，子 Agent 只领领域任务，互相通过结构化消息通信，传的是任务描述加约束加输入，不共享完整内存，这样每个 Agent 的上下文都保持聚焦，子 Agent 的结果作为消息写回主 Agent 的状态。
>
> 两个 Agent 推进同一状态的竞争问题，我的答案很明确：靠程序不靠 Prompt。Prompt 里的约束只是建议，模型可能不遵守，并发正确性必须程序保证——分 namespace 让每个 Agent 只写自己的子树，关键字段单一写者，再加版本号乐观锁，共享资源用锁或队列串行化。

## 13. 如何把不确定的 Agent 改造成相对确定的系统

- 先给本质：确定性不靠等模型变强，而是**收窄模型的决策空间**——从"任意发挥"变成"有限选项内选择"
- 五层手段（从约束到兜底）：
  1. 收窄输入输出：关键决策给枚举选项而不是开放生成；输出过 JSON Schema 校验
  2. 关键路径 Workflow 化：审批、资金、数据变更这些步骤不交给模型，模型只在固定节点做受限选择
  3. 工具结果校验：工具返回过 Schema 校验，非法结果不进上下文，防止错误沿链路传播
  4. 评测门禁：上线前跑评测集，通过率达标才发布；灰度看完成率和人工干预率
  5. 人工闸门：高风险动作挂 waiting_approval，人确认后继续
- 失败路径：仍会出错 -> 可重试的带幂等重试，不可重试的降级到规则或 fail-fast 标 failed
- 指标与验证：任务完成率、人工干预率、Badcase 率——目标是让干预率持续下降，不是追求 100% 自动化

> 怎么把不确定的 Agent 改造成确定的系统，我的理解是：确定性不靠等模型变强，靠收窄模型的决策空间，把它从"任意发挥"变成"有限选项里选"。
>
> 具体五层手段：第一，输入输出结构化，关键决策给枚举选项，输出过 Schema 校验；第二，关键路径 Workflow 化，像审批、资金、数据变更这些步骤不交给模型，模型只在固定节点做受限选择；第三，工具结果校验，非法结果不进上下文，防止错误沿链路传播；第四，评测门禁，上线前跑评测集，灰度里看完成率和干预率；第五，人工闸门，高风险动作挂起等确认。
>
> 即便这样还是会出错，所以失败路径要配好：可重试的带幂等重试，不可重试的降级到规则或直接 fail-fast。目标不是追求百分之百自动化，而是让人工干预率和 Badcase 率持续下降。
