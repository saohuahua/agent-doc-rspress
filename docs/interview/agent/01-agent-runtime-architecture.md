# Agent Runtime 与架构

> 定位：How / Failure / Production——Agent 运行时到底怎么跑起来、会怎么失败、怎么保证可靠。
> 职责边界：Agent 是什么、为什么用、怎么选型见《00 Agent 基础概念》；框架 API 见《02 LangChain 与 LangGraph》；Memory 与上下文工程见《03》；RAG 见《05》；MCP 见《06》。
> 答题骨架：`目标与约束 -> 架构与数据流 -> 失败路径 -> 指标与验证 -> 权衡与降级`。
> 引用块是面试版回答，1~2 分钟口述量。

## 1. Agent Runtime 到底是什么？

- Agent Runtime 是**把模型的决策真正变成可靠执行过程的运行时系统**：模型负责"想做什么"，Runtime 负责"能不能做、怎么做、做完记在哪、失败怎么办"
- 分工：**LLM = 决策能力，Runtime = 执行与治理**
- 五项必备能力：执行（工具调用）、约束（权限与校验）、状态（State 与 Checkpoint）、恢复（重试与续跑）、可观测（Event 与 Trace）

```text
LLM
 ↓  决策
Runtime
 ↓  Policy / Validation
Tool
 ↓  执行
Result
 ↓  回灌
State
 ↓
Loop
```

- 为什么不能只有模型：模型只能生成"意图"，无法承担副作用。越权操作、重复扣款、无限循环这些风险，靠的不是模型自觉，而是 Runtime 的边界
- Runtime 不等于框架：LangGraph 这类框架是编排层的一种实现选项；Runtime 是问题域——怎么把不确定的模型变成可控的执行过程
- Runtime 不等于业务：金额阈值、审批链这类业务规则应该落在工具与策略层，不要混进 Loop

**面试官追问**

**1. Runtime 和 Harness 是一回事吗？**
基本同指。Harness 强调"模型外圈的工程壳"，Runtime 强调"让一次 Run 跑起来的那套机制"；面试里可以把 Harness 看成 Runtime 的实现形态。

**2. 没有 Runtime，直接让模型调函数会怎样？**
参数没人校验、权限没人拦、失败没法重试、断点无法恢复、出事无法审计。Demo 能跑，生产不行。

**3. Runtime 的最小可用集是什么？**
工具 Schema 与参数校验、权限闸门、State 持久化（Checkpoint）、终止与预算控制、结构化 Trace。五样缺一个就无法支撑长任务。

**4. Runtime 越厚越好吗？**
不是。执行细节层要薄，把模型能可靠完成的事交给模型；治理层要厚，权限、状态、恢复、审计这些模型不能替你担责的部分必须留在程序里。

**Trade-off**

| 选择 | 换来什么 | 付出什么 | 什么时候选 |
| --- | --- | --- | --- |
| 薄 Runtime（几乎全交给模型） | 实现快、灵活、模型能力升级直接受益 | 越权与副作用不可控、失败无法恢复、不可审计 | 本地实验、只读工具、无副作用的场景 |
| 厚 Runtime（强治理） | 权限、幂等、恢复、审计都有保障 | 开发与维护成本高，过度约束会限制模型发挥 | 有写操作、长任务、多租户或合规要求 |

**面试版回答**

> Runtime 我理解成"把模型的决策变成可靠执行过程"的那套运行时系统。分工很清楚：LLM 提供决策能力，负责想做什么；Runtime 负责执行与治理——这个工具能不能调、参数对不对、有没有权限、超时了怎么办、失败了能不能续跑、整个过程能不能审计。
>
> 它的必要性在于模型只能生成意图，不能承担副作用。参数越权、重复扣款、无限循环这些都不是靠模型自觉，而是靠程序边界拦住的。所以同一句"帮我退款"，模型输出只是意图，真正执行的是 Runtime，而且执行前要过 Schema 校验、权限和审批。
>
> 我也区分两个概念：Runtime 不等于框架，LangGraph 只是编排层的一种实现选择；Runtime 也不等于业务，金额阈值和审批链应该落在工具和策略层，不要混进循环里。

## 2. 一次 Agent Run 完整发生了什么？

- 一次 Run 就是"加载状态 -> 组装上下文 -> 模型决策 -> 校验与执行 -> 落结果 -> 更新状态 -> 判断终止"的循环，直到产出答案或触发终止条件
- 每一步都要做三件事：写 Trace（可观测）、写 Checkpoint（可恢复）、查预算（可终止）
- 最关键的顺序：模型返回工具调用后，**先把 pending 调用落盘，再执行工具**——否则宕机后无法判断这次调用到底执行过没有

```text
User Request
      ↓
Create Run
      ↓
Load State
      ↓
Build Context
      ↓
Call LLM
      ↓
Tool Call?
   ↙       ↘
 No         Yes
 ↓           ↓
Answer    Policy Check
             ↓
         Execute Tool
             ↓
         Persist Result
             ↓
         Update State
             ↓
       Check Termination
             ↓
          Continue
```

| 步骤 | 做什么 | 漏了会怎样 |
| --- | --- | --- |
| Create Run | 建 Run 记录、分配 run_id、置 pending | 无法追踪、无法重试、无法限流 |
| Load State | 从 Checkpoint 和存储加载状态，对账挂起的调用 | 恢复时重复执行或漏执行 |
| Build Context | 按预算组装 System、记忆、State、近期对话、工具结果 | 上下文污染、注意力稀释、超预算 |
| Call LLM | 带工具 Schema 调模型（含超时、重试、模型路由） | 卡死、成本失控、模型抖动无人兜底 |
| Policy Check | Schema 校验、权限、参数范围、审批闸门 | 越权与非法参数直达外部系统 |
| Execute Tool | 超时、重试、幂等键、沙箱隔离 | 重复副作用、资源泄漏、影响其他租户 |
| Persist Result | 结果与执行状态写回 State | 上下文缺失，循环退化成重复调用 |
| Update State / Checkpoint | 落盘快照与序号 | 宕机后无法续跑，只能从头再来 |
| Check Termination | 模型不再调工具、目标校验通过、预算耗尽 | 死循环、任务挂死 |

**业务例子**：客服 Agent 处理"查一下我上月的订单，把那笔重复扣款退掉"

```text
Create Run        -> 会话里已确认用户身份
Call LLM          -> 决策：query_orders(user, 上月)
Policy Check      -> 只读工具，直接执行
Persist Result    -> 发现两笔同金额订单
Call LLM          -> 决策：refund(order_id, amount)
Policy Check      -> 金额超阈值 -> 挂 waiting_approval
                  -> 写 Checkpoint + 发进度事件
用户批准          -> Load State 发现 pending 审批
                  -> 带幂等键执行 refund
                  -> Update State -> 输出答案
```

**面试官追问**

**1. 为什么先落盘 pending，再执行工具？**
因为工具可能有副作用且不可回滚。落盘后再执行，宕机恢复时能通过 pending 记录和幂等键判断"这次调用执行没执行"，避免重复扣款；只在内存里记，进程一挂就永远不知道。

**2. 模型一次返回多个 tool call 怎么办？**
互不依赖的并发执行，各自校验、各自记状态，结果一起回灌下一轮；有依赖关系的按依赖序执行，不要盲目并发。

**3. 每轮都重建上下文，会不会很贵？**
会，所以要做预算和分层：静态 System Prompt 复用、远期对话用摘要、工具结果截断。重建的目的是"每轮都基于真实状态"，不是每轮都全量拼装。

**4. 审批挂起算 Run 结束吗？**
不算结束，是挂起状态（waiting_approval）。Run 记录保留，用户批准后从 Checkpoint 继续，而不是新开一个 Run。

**Trade-off**

| 选择 | 换来什么 | 付出什么 | 什么时候选 |
| --- | --- | --- | --- |
| 关键节点落盘（模型决策后、工具执行前后） | 可靠性高，恢复粒度细 | 写放大、延迟增加 | 有写操作、长任务（默认） |
| 只读工具轻量处理、仅在轮末落盘 | 性能好、实现简单 | 崩溃可能丢失一轮，需重跑 | 纯查询类、可安全重放的场景 |

**面试版回答**

> 一次 Run 我按链路讲：接请求后先创建 Run 记录，从存储和 Checkpoint 加载状态；然后按预算组装上下文，带工具 Schema 调模型。模型返回两种结果：不再调工具就是最终答案；要调工具，就先做策略检查和参数校验，再执行工具，把结果和状态写回 State，然后检查终止条件，没到就进入下一轮。
>
> 这条链路上有三个动作每一轮都要做：写 Trace 保证可观测、写 Checkpoint 保证可恢复、查预算保证能停下来。最关键的一个顺序是先把待执行的工具调用落盘再执行——因为工具可能有不可回滚的副作用，宕机恢复时要靠这条记录和幂等键判断到底执行过没有，否则就会重复扣款。
>
> 比如客服 Agent 处理退款：查订单是只读工具直接执行；到退款这一步触发金额阈值，就挂起等审批并落盘，用户批准后从 Checkpoint 继续，而不是重新跑一遍。

## 3. Agent 的组成部分是什么？Harness 又是什么

- Agent 最小组成（五块）：
  1. 模型：决策大脑
  2. 上下文/记忆：System Prompt + 对话历史 + 工具结果
  3. 工具：与外部世界交互的手
  4. Loop 编排：把前两者串成执行循环
  5. State/持久化：跨轮、跨进程保存运行状态
- 生产级再加一层治理：权限、沙箱、评测、Trace、预算
- Harness 是什么：
  1. 定义：模型外圈的工程壳。模型只负责产出 token 和调用决策，Harness 负责把"不确定的模型"约束成"可靠系统"的全部工程
  2. 传递关系：Harness 组装上下文（System Prompt、工具 Schema、历史）传给模型 -> 模型返回决策 -> Harness 负责执行、校验、落状态、决定下一步。同一模型套不同 Harness，可靠性完全不同
  3. 具体包含：上下文组装与压缩、工具定义与执行、权限门禁、沙箱隔离、Loop 控制（终止/预算）、State 与 Checkpoint、Hooks（生命周期挂点）、SubAgent、日志与 Trace、评测
  4. 参照物：Claude Code 是典型 Harness 形态——固定工具集（Read/Edit/Bash 等）、权限模式与确认、Hooks、SubAgent、Skill 渐进加载
  5. Harness ≠ 框架：框架（LangChain/LangGraph）是编排层的实现选项；Harness 是问题域，框架是工具
- 自研 Harness 的模块划分：
  1. 模型网关：多模型路由、重试、限流、成本统计
  2. 编排/Loop：状态机、终止条件、预算控制
  3. State 与 Checkpoint：会话状态、断点恢复
  4. Tool 层：Schema 注册、权限、超时、幂等
  5. 上下文管理：裁剪、压缩、分层注入
  6. 可观测：结构化 Trace（每轮决策、工具调用、Token 消耗）
  7. 安全：注入防护、沙箱、人工审批闸门
- 模型越来越强，Harness 变厚还是变薄
  1. 执行细节层会变薄：简单规划、格式校验这类任务能力会被模型吸收
  2. 治理层会变厚：权限、审计、恢复、评测这些"模型不能替你担责"的部分只会更重
  3. 结论：内层变薄、治理层变厚，总代码量不一定减少

**框架、手写 Runtime 怎么定位**

- LangChain：Agent / LLM 应用的组件与抽象（模型、工具、检索、管道）
- LangGraph：有状态、可循环、可分支、带 Checkpoint 与 HITL 的 Agent 编排
- 手写 Runtime：最大控制权，代价是恢复、并发、可视化都要自己造
- 不要把 LangChain 简化成"只能做线性 Chain"：它也有 Agent 与工具抽象，只是状态与恢复能力不如图状态机方案
- 框架选型与 API 细节见《02 LangChain 与 LangGraph》，本篇只讲运行时机制

**面试版回答**

> 我理解 Agent 的组成可以拆成五块：模型是决策大脑，上下文给它提供信息，工具让它和外部世界交互，Loop 把三者串成执行循环，State 负责把运行状态持久化。生产级还要加一层治理：权限、沙箱、评测和 Trace。
>
> Harness 我理解是模型外面那圈工程壳。模型只负责产出 token 和调用决策，剩下所有事都是 Harness 的：组装上下文、定义和执行工具、管权限、控 Loop、落状态、做恢复。同一个模型套不同 Harness，出来的可靠性完全不同，所以我会说 Harness 就是把"不确定的模型"变成"确定的系统"的那部分工程。Claude Code 是很典型的参照：固定的工具集、权限确认、Hooks、SubAgent、Skill 渐进加载，这些都是 Harness 的一部分。
>
> 自研的话我按七个模块划分：模型网关管路由和成本，编排层管状态机和终止条件，State 层管断点恢复，Tool 层管 Schema、权限和幂等，再加上下文管理、全链路 Trace 和安全闸门。至于模型越来越强 Harness 会怎么变——我认为执行细节那层会变薄，比如简单规划和格式校验模型自己就能做好；但权限、审计、恢复、评测这些模型不能替你担责的部分只会变厚。总体是内层变薄、治理层变厚。

## 4. Agent Loop 的最小核心实现

- 最小实现就是一个 while 循环：

```typescript
async function runAgentLoop(task: Task, state: AgentState): Promise<string> {
  for (let round = 1; round <= MAX_ROUNDS; round++) {
    const messages = buildContext(state);                // 1. 组装上下文
    const resp = await llm.call(messages, TOOL_SCHEMAS); // 2. 带工具 Schema 调模型
    state.append(resp);                                  // 3. 先落盘，再执行
    await checkpoint(state);

    if (!resp.toolCalls?.length) {                       // 模型不再调工具 => 最终答案
      return resp.text;                                  // 显式终止
    }

    for (const call of resp.toolCalls) {                 // 4. 执行工具（带超时）
      const result = await executeTool(call, { timeout: 30_000 });
      state.append(toolMessage(call.id, result));        // 结果回灌，进入下一轮
    }

    await checkpoint(state);                             // 5. 轮末再落一次（工具结果已入 State）
    checkBudget(state, round);                           // 6. 轮数 / Token 预算检查
  }
  throw new LoopExceededError();                         // 硬终止兜底
}
```

- 除 Function Calling 外，靠什么驱动循环？三件套：
  1. 终止条件：每轮判断是否到达结束状态
  2. State 更新与回灌：工具结果必须写回上下文，模型才能基于观察决策，否则循环退化成重复调用
  3. 预算与守卫：轮数、Token、超时，没有边界循环就不会停
- 每轮必须做的三件工程事：写 State/Checkpoint、判终止、上报事件（Trace/前端进度）

**面试版回答**

> 我认为 Agent Loop 的最小实现就是一个 while 循环：每轮先根据 State 组装上下文，带着工具 Schema 调模型；模型返回两种可能——不再调工具，那就是最终答案，循环结束；要调工具，就执行工具、把结果作为 tool 消息写回状态，进入下一轮。每轮还要做三件工程上的事：把状态落一次盘、检查轮数和 Token 预算、把本轮决策和工具调用上报到 Trace。
>
> 有个容易被忽略的点：驱动这个循环的不只是 Function Calling，还有终止条件和状态回灌。工具结果必须写回上下文，模型才能基于观察决定下一步，否则循环就退化成重复调用。所以我总结 Loop 等于模型决策加状态更新加终止判断，三部分缺一不可。

## 5. Tool Call 到底由谁执行？

- 模型只产出**调用意图**（工具名 + 参数），执行永远由 Runtime 负责；模型不能直接触碰外部副作用
- 程序必须掌握：参数校验（Schema）、权限与策略、人工审批、超时与重试、幂等、审计
- MCP 标准化的是工具的连接与发现，执行与治理仍在 Host / Runtime 手里；MCP 本身不提供权限模型
- 原则：**执行前的闸门越多，事后补偿越少**；不可回滚的副作用必须前置拦截

```text
LLM
 ↓
Tool Call Intent
 ↓
Runtime
 ↓
Schema Validation
 ↓
Permission / Policy
 ↓
Human Approval?
 ↓
Tool Execution
 ↓
Result
 ↓
State
```

- 为什么容易产生"模型直接调了工具"的错觉：Function Calling 只是模型输出结构化参数，真正的 HTTP、SQL、文件操作都是应用代码执行的
- 参数校验失败怎么办：把错误作为 Observation 回灌，让模型修正参数，而不是抛异常断掉循环；同一调用连续失败到阈值就终止
- 并行与依赖：互不依赖的调用可以并发，各自校验、各自记账；有依赖的按依赖序执行
- 业务例子：只读查询工具免审批直接执行；退款工具要校验金额上限和订单归属，带幂等键，超阈值走人工审批；危险命令进沙箱并走白名单

**面试官追问**

**1. Function Calling 和 MCP 谁负责执行工具？**
都不负责执行。Function Calling 是模型输出调用意图的格式，MCP 是工具连接与发现的协议，真正执行并治理的都是应用侧（Host / Runtime）。

**2. 参数校验失败怎么反馈给模型？**
当成一次工具执行结果回灌：告诉它哪个字段非法、合法范围是什么，让模型重新生成调用。断掉循环反而让模型失去了自纠机会。

**3. 幂等键应该由谁生成？**
Runtime 生成并随调用一起记录，不能交给模型——模型每次生成的键可能不同，重复执行就防不住。键的粒度通常是"一次业务意图 + 一个工具调用"。

**4. 为什么高风险操作要人工确认？**
因为副作用不可回滚、自动判断的准确率不足以承担后果。HITL 把不可逆动作变成可逆流程：挂起、给人看参数、批准后带幂等键执行。

**Trade-off**

| 选择 | 换来什么 | 付出什么 | 什么时候选 |
| --- | --- | --- | --- |
| 严格前置校验 + 人工闸门 | 副作用安全、可审计 | 交互变多、延迟上升、可能打断流程 | 资金、权限、数据变更、生产环境 |
| 宽松执行 + 事后补偿 | 流程顺畅、延迟低 | 补偿逻辑复杂，部分副作用不可逆 | 只读工具、可安全重放、内部低风险任务 |

**面试版回答**

> 我会明确一点：模型不执行工具，它只输出工具名和参数，也就是调用意图；真正执行的是 Runtime。这中间是一串程序流程：Schema 校验参数、权限和策略判断能不能调、高风险操作挂起等人工审批、执行时带超时重试和幂等键，最后把结果写回状态并留审计记录。
>
> 原因是模型的输出不可信：它会幻觉出不存在的工具，会生成越权的参数，也可能被检索到的恶意内容诱导。副作用一旦发生可能无法回滚，所以闸门必须在前面。MCP 也是一样，它标准化的是工具怎么被发现和连接，不负责权限，也不负责执行。
>
> 工程上有个细节我会提：参数校验失败不要抛异常断链路，而要作为一次观察结果回灌给模型，让它自己改参数；同时同一调用连续失败到阈值就强制终止。只读工具可以免审批直接跑，写操作和资金操作必须过闸门、带幂等键。

## 6. Agent 的终止条件与结束状态

- 显式终止（正常退出）：
  1. 模型本轮不再发起工具调用 -> 输出最终答案
  2. 目标达成（可校验任务：测试全过、字段填全）
  3. 人工审批通过或拒绝（human-in-the-loop 中断点）
  4. 用户主动取消
- 硬性终止（兜底退出）：
  1. 最大轮数
  2. Token / 金额预算耗尽
  3. 整体超时
  4. 连续 N 次工具失败
  5. 死循环检测：同一工具 + 相同参数反复出现、状态长时间无变化
- 结束状态枚举：

```latex
completed         正常完成
failed            失败（区分可重试 / 不可重试）
cancelled         用户取消
timeout           超时
waiting_approval  等人工审批（挂起，不是结束）
needs_input       等用户补充输入（挂起，恢复后从断点继续）
```

- 关键认知：不能只信模型说"我做完了"。模型有提前宣布成功的倾向，可校验的任务要配结构化输出 + 校验器，校验不过不算 completed

**面试版回答**

> 我认为终止条件要分两类看。显式的是正常退出：模型不再调工具、输出最终答案，或者目标可校验地达成，再就是人工审批和用户取消。硬性的是兜底：最大轮数、Token 预算、整体超时、连续工具失败，还有死循环检测——同一工具加相同参数反复出现就强制断掉。
>
> 结束状态我一般设计六种：completed、failed、cancelled、timeout、waiting_approval、needs_input。后两个是挂起不是结束，恢复后从断点继续跑。
>
> 另外一个关键点：不能只靠模型自己宣布完成。模型有提前说"我做完了"的倾向，所以可校验的任务我会配结构化输出加校验器，校验不过就不算 completed，退回去继续或者按 failed 处理。

## 7. 如何防止死循环、Token 爆炸与任务挂死

- 目标与约束：Agent 有不确定性，失控的四种表现——轮数爆炸、Token 爆炸、任务挂死、重复调用同一工具
- 单机层（四件套）：
  1. 硬上限：最大轮数、单轮/总 Token 预算、整体超时
  2. 重复检测：同一工具 + 相同参数哈希连续 N 次 -> 先注入系统提示让模型换策略，无效再强杀（先干预后击杀，成本低）
  3. 工具级防护：超时、熔断、连续失败计数，超阈值直接终止
  4. 上下文干预：检测到绕圈时注入一条提醒消息，比直接杀任务便宜
- 分布式层（单机上限不够，任务会漂移、会重试）：
  1. 幂等：工具调用带 idempotency key，重试不产生重复副作用
  2. 租约锁：同一会话同一时刻只有一个 worker 持有租约，防双跑
  3. 分布式计数：轮数/Token 用 Redis 跨实例累计，不能只存在进程内存
  4. Watchdog：后台扫描 running 超时任务，强制标 failed 并回收沙箱资源
- 指标与验证：轮数分布 P99、Token 分布、死循环拦截次数、挂死任务数
- 权衡：限太紧伤完成率，太松烧钱 -> 上限按任务类型分级可配置

**面试版回答**

> 怎么防死循环和挂死，我分单机和分布式两层说。单机是四件套：最大轮数加 Token 预算这类硬上限；重复动作检测，同一工具加相同参数连续出现，先注入一条系统提示让模型换策略，无效再强杀；工具级超时和熔断，连续失败直接终止；最后是整体超时。
>
> 分布式下光有单机上限不够，因为任务会漂移、会重试，要补四件事：工具调用全带幂等键，重试不产生重复副作用；会话用租约锁，保证同一时刻只有一个 worker 在跑；轮数和预算用 Redis 做跨实例累计；再加一个 watchdog 定时扫描 running 超时的任务，强制标失败并回收沙箱。
>
> 权衡上，限太紧伤完成率，太松就是烧钱，所以上限按任务类型做成可配置，再用轮数 P99 和死循环拦截次数这两个指标回归调整。

## 8. Session、Run、Step、State、Event、Checkpoint 怎么区分？

- 六个概念：Session 是长期容器，Run 是一次任务执行，Step 是一次循环，State 是当前状态，Event 是发生过的事实，Checkpoint 是状态快照
- 最容易混的三个概念：**State = 当前是什么，Event = 发生过什么，Checkpoint = 如何恢复**
- 运行内存不是 State：进程内的缓存和中间变量挂了就没了，不参与恢复

```text
Session
 ├── Run #1
 │    ├── Step
 │    ├── ToolCall
 │    └── Checkpoint
 │
 └── Run #2
      ├── Step
      └── Checkpoint
```

| 概念 | 回答什么 | 生命周期 | 典型存储 |
| --- | --- | --- | --- |
| Session | 谁在和 Agent 长期交互、会话上下文是什么 | 跨多次任务，天到月级 | 会话表 + 热状态（Redis） |
| Run | 一次具体任务执行到哪一步了 | 创建到终态 | 任务表（含状态机） |
| Step | Run 里的一次决策-执行循环 | 单轮 | 随 State 与 Event 记录 |
| State | 当前任务进展：目标、槽位、消息、变量、工具结果 | Run 内，随 Checkpoint 持久化 | 全量快照 + 热状态 |
| Event | 已经发生过的事实（结构化、有序） | 追加写，长期保留可归档 | 事件表 / 事件流 |
| Checkpoint | State 的持久化快照：版本、序号、pending 调用 | 每轮或每节点 | MySQL 全量 + Redis 热状态 |

- 为什么 Session 和 Run 必须分开：一个会话里可以有多个任务（"先查订单"再"申请退款"），重试、并发任务、断点续跑都以 Run 为单位；把两者混在一起，失败重试会污染会话
- Checkpoint 与备份的区别：备份是数据保护，Checkpoint 是运行语义的一部分——它带版本、序号和未确认的工具调用，是"从哪里继续"的依据

**面试官追问**

**1. 为什么不直接用 messages 当 State？**
messages 只是 State 的一个字段。任务目标、槽位、当前阶段、pending 调用、版本号这些都不是对话原文能表达的；只存 messages，任务一复杂就既没法防跑偏也没法恢复。

**2. Event 和日志有什么区别？**
Event 是结构化、有语义和顺序的领域事实，能被程序消费、能重放、能驱动前端时间线；日志是面向人的文本记录，可以采样、可以分级。不是每条日志都是 Event，也不是每个 Event 都要写日志（详见第 10 题）。

**3. Session 和 Run 为什么要拆开建模？**
因为生命周期和并发粒度不同：会话是长期容器，Run 是可重试、可取消、可并发的执行单元。退款审批挂起时，会话还在继续，但那个 Run 处于挂起状态。

**4. Checkpoint 越多越好吗？**
不是。落盘频率对应写放大和延迟，按步骤重要性分级：写操作前后必落，只读步骤可以合并到轮末；同时要控制快照体积，必要时用"快照 + 增量事件"组合。

**面试版回答**

> 这六个概念我会这样区分：Session 是用户和 Agent 的长期会话容器；Run 是这个会话里一次具体任务的执行；Step 是 Run 里的一次决策-执行循环；State 是当前任务进展的结构化数据；Event 是已经发生过的事实的结构化记录；Checkpoint 是 State 的持久化快照。
>
> 最容易混的是 State、Event 和 Checkpoint：State 回答"现在是什么"，Event 回答"发生过什么"，Checkpoint 回答"怎么恢复"。另外运行内存不等于 State，进程里的缓存挂了就没了，不参与恢复。Session 和 Run 也一定要拆开：一个会话可以发起多个任务，重试、取消、并发都以 Run 为单位。

## 9. State 如何设计？如何解决并发覆盖？

- State 要 Schema 化，不是一坨 messages：任务目标、槽位、变量、工具结果分字段存
- 单一数据源：权威 State 只在服务端一份，前端和子 Agent 看到的都是投影
- 读写边界：只有编排层写 State，工具和子 Agent 通过返回值间接写
- 并发覆盖靠程序，不靠 Prompt：分 namespace、单一写者、版本号乐观锁
- Tool Message 单独建模：带 tool_call_id 和执行状态（成功 / 失败），恢复时才能精确知道哪个调用没完成，不盲目重试

```latex
State（运行状态）
  -> 一次任务运行的结构化数据：消息历史、任务目标、变量、工具结果、当前步骤
  -> 生命周期：任务开始创建，结束归档
  -> 是 Loop 的数据载体：模型每轮决策的上下文都由 State 组装而来

Checkpoint（检查点）
  -> State 在关键节点的持久化快照，每轮 / 每节点落一次
  -> 带版本号和时间戳，用于宕机恢复和回滚重放
```

- 多 Agent 并发写同一状态时的处理强度，从弱到强：
  1. 分 namespace：每个 Agent 只写自己的子树，如 `state.researcher.*`
  2. 版本号 / 乐观锁：写入带版本，冲突时合并或重试
  3. 单一写者：关键全局字段只允许主 Agent 更新
- 冲突处理的兜底：共享资源加锁或排队串行化；写入冲突要能被检测到并重放，而不是静默覆盖

**面试官追问**

**1. 为什么并发正确性不能靠 Prompt 保证？**
Prompt 只是建议，模型可能不遵守，而且两个 Agent 并发写入时，谁先谁后根本不由 Prompt 决定。并发正确性必须由 namespace、单一写者、版本号这些程序机制保证。

**2. State 里要不要存完整对话历史？**
要分字段存，但不必全量注入上下文。State 是数据模型，上下文是每一轮的选择结果：近期全量、远期摘要、工具结果截断，具体组装策略见第 2 题的 Build Context。

**3. State 版本升级怎么办？**
State 和 Checkpoint 都带 Schema 版本号，升级时做兼容读或迁移；序号递增防止旧快照覆盖新状态，这也是恢复安全的前提。

**面试版回答**

> State 我会按数据模型设计，不是一坨 messages：任务目标、槽位、变量、工具结果分字段存，权威版本只在服务端一份，前端和子 Agent 看到的都是投影，写入口收敛到编排层，工具和子 Agent 只能通过返回值间接改。
>
> 并发覆盖一定会发生，我的答案很明确：靠程序不靠 Prompt。手段按强度排：分 namespace 让每个 Agent 只写自己的子树；关键全局字段设单一写者，只有主 Agent 能改；再给状态加版本号做乐观锁，冲突时合并或重试，共享资源加锁或排队。
>
> 还有两个细节我会提：工具消息要单独建模，带 tool_call_id 和执行状态，因为恢复时必须知道哪个调用没完成；State 和 Checkpoint 都带 Schema 版本和递增序号，防止旧快照覆盖新状态。

## 10. Event / Trace 为什么需要独立于 State？

- State 只保留"当前"，Event 记录"过程"；审计、Trace、Debug、Replay、指标和用户任务时间线都依赖事件流
- Event 是结构化、有语义、有顺序的领域事实，日志是面向人的文本记录，两者不能互相替代
- Replay 的前提是 Event 有序且工具幂等，否则回放会产生重复副作用

```text
RunCreated
   ↓
LLMCalled
   ↓
ToolCallRequested
   ↓
ToolStarted
   ↓
ToolSucceeded
   ↓
StateUpdated
   ↓
CheckpointCreated
   ↓
RunCompleted
```

| 维度 | State | Event | 日志 |
| --- | --- | --- | --- |
| 回答的问题 | 现在是什么 | 发生过什么 | 当时发生了什么（给人看） |
| 形态 | 结构化快照，可覆盖 | 结构化、追加写、有序 | 文本，分级与采样 |
| 消费者 | Runtime 与上下文组装 | 前端时间线、审计、指标、Replay | 开发者排查 |
| 保留策略 | 只保最新或少量版本 | 长期保留、可归档 | 按成本和合规设 TTL |

- Event 支撑的四件事：前端任务时间线（进度可视化）、审计（谁在什么时候批准了什么）、指标（每步耗时、工具成功率、轮数分布）、Replay（重建状态做回归验证）
- 状态与事件的配合方式：周期打 Checkpoint + 持续写 Event；恢复时用最近 Checkpoint 做基线，用之后的 Event 补齐增量

**面试官追问**

**1. 事件持续增长，存不下怎么办？**
快照加事件的组合：定期打 Checkpoint 做基线，事件流可以归档或按 TTL 清理；审计要求高的场景保留关键事件（审批、写操作），高频只读事件可以采样。

**2. Event 和 Trace 是同一个东西吗？**
Trace 是围绕一次 Run 的事件集合，Event 是其中一条事实。Trace 提供的是"可回放的一次执行"，Event 是构成它的最小单位。

**3. 为什么不能只靠日志排查？**
日志是文本、可能被采样、字段不固定，无法稳定地驱动 UI 时间线、算指标或做 Replay；而结构化 Event 可以被程序直接消费。

**面试版回答**

> State 和 Event 面向的问题不同：State 回答"现在是什么"，是可以被覆盖的快照；Event 回答"发生过什么"，是追加写的、有序的领域事实。我要审计、要指标、要前端任务时间线、要做回放，都得靠事件流，这些靠 State 是拿不到的。
>
> 它和日志也不是一回事。日志是面向人的文本，可能被采样；Event 是结构化的、能被程序消费的。我会把关键事件定义清楚：RunCreated、LLMCalled、ToolCallRequested、ToolStarted、ToolSucceeded、StateUpdated、CheckpointCreated、RunCompleted。有了事件流，出问题能还原时间线，改完 Prompt 或工具也能用同一批事件做回放对比。
>
> 存储上我用"快照加事件"的组合：定期打 Checkpoint 做基线，事件流负责过程和审计，恢复时用最近快照加增量事件补齐。

## 11. Checkpoint 如何实现？宕机后怎么恢复

- 何时存：每个 Loop 轮次结束、每个 Workflow 节点完成、工具调用执行前后各记一次（执行前记"待执行"，成功后更新状态）
- 存什么：

```typescript
interface Checkpoint {
  version: string;          // Schema 版本，升级兼容
  sessionId: string;        // 会话 / 任务标识
  seq: number;              // 递增序号，防乱序、防旧快照覆盖新状态
  state: AgentState;        // 全量 State：messages + 任务状态 + 变量
  pendingCalls: ToolCall[]; // 已发起未确认的工具调用（恢复时对账）
  ts: number;
}
```

- 存哪：LangGraph 内置 Checkpointer（SQLite/Postgres 等）；自研一般 MySQL 存全量快照 + Redis 存热状态支撑快速恢复
- 恢复五步：
  1. 按 session/task 找最新 checkpoint
  2. 校验版本与完整性
  3. 对账 pendingCalls：已执行的用幂等键去重，未执行的补跑
  4. 从断点重建上下文，继续 Loop
  5. 恢复后先降速观察，确认健康再放量
- 服务端宕机 vs Agent 宕机，分开答：
  1. 服务端（编排进程）宕机：State 在存储里，新实例接管即可，影响小
  2. Agent/沙箱宕机：正在执行的工具会中断 -> 靠幂等键对账 + 沙箱重建，长任务从 checkpoint 续跑
- 关键前提：工具幂等，否则恢复重放会产生重复副作用

**面试版回答**

> Checkpoint 的实现我概括成三件事：何时存、存什么、存哪。时机上每个 Loop 轮次或每个节点结束落一次，工具调用前后各记一次，这样恢复时知道哪些调用已确认。内容是全量 State 加版本号加递增序号，还要记录已发起但未确认的工具调用。存储上我一般 MySQL 存全量快照，Redis 存热状态支撑快速恢复。
>
> 恢复五步：按会话找最新 checkpoint，校验版本，对账未完成的工具调用——用幂等键去重，已执行的跳过，没执行的补跑，然后从断点重建上下文继续跑，恢复后先降速观察再放量。
>
> 服务端和 Agent 宕机要分开说：编排进程挂了，State 在存储里，新实例接管就行；沙箱里的 Agent 挂了，正在执行的工具会中断，所以幂等是恢复的前提，重放才不会产生重复副作用。

## 12. Agent 长任务怎么设计：状态、执行、恢复

- 目标与约束：任务 10 分钟级，用户会关页面、服务会重启发布 -> 可靠性目标：进度不丢、状态可查、断了能续
- 架构与数据流：

```text
前端(SSE 订阅进度) -> 网关 -> 任务服务(落任务表, 返回 task_id) -> MQ -> Worker 池(跑 Agent Loop)
                                   |                              |
                                   +- MySQL: 任务表 + 步骤表 <----+ 每步更新状态 + Checkpoint
                                   +- Redis: 热状态 / 进度 / 租约
```

- 状态拆解：
  1. 任务状态机：pending -> running -> succeeded/failed/cancelled，中间加 suspended（等审批/等输入挂起）
  2. 步骤表：任务拆步骤，记录每步的 checkpoint 指针，步骤是断点续跑的最小单位
- 执行：
  1. 异步化：创建任务落库入队就返回，Worker 从 MQ 领任务跑 Loop，前后端解耦，页面关闭不影响
  2. 进度上报：Worker 每步写 Redis 进度 + 发事件，前端 SSE 订阅；重连后先查任务表补齐状态再续订
  3. 租约：Worker 持租约跑任务，心跳续期；Worker 挂了租约过期，任务可被其他实例重新领取
- 恢复：
  1. 服务重启：状态在 DB/Redis 不随进程丢；重启后扫描 running 超时的任务重新入队
  2. 断点续跑：从最新 checkpoint 重建 State 继续；工具带幂等键，重放不产生重复副作用
  3. 优雅启停：发布时先停领新任务，等在跑任务到安全点或迁移租约，再下线
- 为什么十分钟长链路可接受：异步执行不用盯 + 进度可视化 + 失败可续跑而不是从头再来
- 指标与验证：任务成功率、断点续跑率、平均恢复耗时、挂死任务数

**面试版回答**

> 整体设计一个 Agent 长任务，我会按状态、执行、恢复三块说。状态上，任务有一张任务表加步骤表，状态机是 pending、running、suspended、succeeded、failed、cancelled，步骤是最小断点单位，每步落 checkpoint。执行上全部异步化：前端创建任务，服务落库入队就返回，Worker 从 MQ 领任务跑 Loop，进度写 Redis 再通过 SSE 推给前端——页面关了任务照跑，重连后先查任务表补状态再续订进度。Worker 持租约加心跳，挂了租约过期，任务能被别的实例重新领走。
>
> 恢复上，服务重启不怕，状态都在 DB 和 Redis，重启后扫描 running 超时的任务重新入队；任务断了就从最新 checkpoint 重建上下文续跑，工具全带幂等键，重放不会重复副作用。发布下线走优雅启停：先停领新任务，等在跑任务到安全点或迁移租约再下线。
>
> 十分钟长链路用户能接受，前提就是三件事：异步不用等、进度可视化、失败可续跑。我监控任务成功率、断点续跑率和恢复耗时。

## 13. Single-Agent / Multi-Agent 在 Runtime 层怎么通信

```latex
单 Agent
  -> 优点：上下文连贯、无通信损耗、链路简单好调试
  -> 缺点：工具多时选择变差、上下文膨胀、职责混杂难评测

Multi-Agent
  -> 优点：职责隔离、每个 Agent 上下文精简聚焦、可并行、可独立评测
  -> 缺点：通信有损、错误会传播、整体延迟上升、状态一致性复杂
```

- 何时拆（四个信号，满足越多越该拆）：
  1. 工具数量过多，单 Agent 选工具准确率下降
  2. 上下文装不下，不同子任务需要不同专业上下文
  3. 职责边界天然清晰（检索 / 写码 / 评审）
  4. 子任务可并行
- 默认立场是不拆：Multi-Agent 不是免费的性能提升，而是用组织复杂度换隔离
- 常见形态与通信：
  1. 主子架构：主 Agent 负责拆解与汇总，子 Agent 只领领域任务，互不共享完整上下文
  2. 通信方式与结果契约：结构化消息（任务描述 + 约束 + 输入）+ 结构化结果（产出 + 置信度 + 错误码），不直接共享内存
  3. 结果回灌：子 Agent 输出作为消息写回主 Agent 的 State
- 状态竞争：两个 Agent 推进同一状态时，约束靠程序还是 Prompt？
  1. 结论：**靠程序，不靠 Prompt**。Prompt 约束是"建议"，并发正确性必须程序保证
  2. 手段：分 namespace、单一写者、版本号乐观锁，共享资源加锁或排队串行化

**面试版回答**

> 单 Agent 还是 Multi-Agent，我的默认立场是能不拆就不拆，因为 Multi-Agent 会引入通信损耗和错误传播，不是免费午餐。出现四个信号才考虑拆：工具多到选择准确率下降、上下文装不下、职责边界天然清晰、子任务能并行。
>
> 拆的话我常用主子架构：主 Agent 负责拆解和汇总，子 Agent 只领领域任务，互相通过结构化消息通信，传的是任务描述加约束加输入，不共享完整内存，这样每个 Agent 的上下文都保持聚焦，子 Agent 的结果作为消息写回主 Agent 的状态。
>
> 两个 Agent 推进同一状态的竞争问题，我的答案很明确：靠程序不靠 Prompt。Prompt 里的约束只是建议，模型可能不遵守，并发正确性必须程序保证——分 namespace 让每个 Agent 只写自己的子树，关键字段单一写者，再加版本号乐观锁，共享资源用锁或队列串行化。

## 14. 如何把不确定的 Agent 改造成相对确定的系统

- 确定性不靠等模型变强，而是**收窄模型的决策空间**：从"任意发挥"变成"有限选项内选择"
- 五层手段（从约束到兜底）：
  1. 收窄输入输出：关键决策给枚举选项而不是开放生成；输出过 JSON Schema 校验
  2. 关键路径 Workflow 化：审批、资金、数据变更这些步骤不交给模型，模型只在固定节点做受限选择
  3. 工具结果校验：工具返回过 Schema 校验，非法结果不进上下文，防止错误沿链路传播
  4. 评测门禁：上线前跑评测集，通过率达标才发布；灰度看完成率和人工干预率
  5. 人工闸门：高风险动作挂 waiting_approval，人确认后继续
- 失败路径：仍会出错 -> 可重试的带幂等重试，不可重试的降级到规则或 fail-fast 标 failed
- 指标与验证：任务完成率、人工干预率、Badcase 率——目标是让干预率持续下降，不是追求 100% 自动化

**Prompt 管不住的事，一律交给 Runtime**

```text
❌ Prompt："不要重复扣款"          ✅ Runtime：Idempotency Key
❌ Prompt："不要执行危险命令"      ✅ Runtime：Permission + Sandbox
❌ Prompt："不要无限循环"          ✅ Runtime：MAX_STEPS + Timeout
❌ Prompt："只操作当前用户的数据"  ✅ Runtime：租户过滤 + 参数校验
```

- 判断标准很简单：**这条约束如果被违反，能不能回滚？** 不能回滚的，必须由程序在执行前拦截
- 不是否定 Prompt 的作用：Prompt 负责"让模型倾向于做对的事"，Runtime 负责"做错也伤不到系统"

**面试版回答**

> 怎么把不确定的 Agent 改造成确定的系统，我的理解是：确定性不靠等模型变强，靠收窄模型的决策空间，把它从"任意发挥"变成"有限选项里选"。
>
> 具体五层手段：第一，输入输出结构化，关键决策给枚举选项，输出过 Schema 校验；第二，关键路径 Workflow 化，像审批、资金、数据变更这些步骤不交给模型，模型只在固定节点做受限选择；第三，工具结果校验，非法结果不进上下文，防止错误沿链路传播；第四，评测门禁，上线前跑评测集，灰度里看完成率和干预率；第五，人工闸门，高风险动作挂起等确认。
>
> 即便这样还是会出错，所以失败路径要配好：可重试的带幂等重试，不可重试的降级到规则或直接 fail-fast。目标不是追求百分之百自动化，而是让人工干预率和 Badcase 率持续下降。
