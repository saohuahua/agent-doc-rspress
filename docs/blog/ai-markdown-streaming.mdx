# AI Markdown 流式渲染架构深度剖析：从 markstream-vue 源码到 unified/remark 复杂组件演进

在大模型（LLM）产品（如 ChatGPT、Claude、DeepSeek 等）普及的今天，前端 Markdown 渲染已经从传统的“一次性全量解析”彻底演变成了**高频、低延迟的流式渲染（Streaming Rendering）**。

在实际工程落地中，前端团队往往面临两大核心诉求：
1. **极致的流式性能与体验**：如何在每秒几十上百 Token 的推送下，做到 60 FPS 无卡顿、无语法破相、无闪烁？
2. **高度的产品化复用与扩展能力**：如何支持自定义 UI 规则、插槽（Slots）替换、业务埋点注入以及主题定制，把一个单纯的 Markdown 渲染器打造成一个“可交互的组件容器（Artifact Container）”？

本文将深度剖析开源方案 **[markstream-vue](https://github.com/Simon-He95/markstream-vue)** 的核心源码实现，并结合基于 **`unified` + `remark`** 构筑的通用 AST 组件化架构，做一次系统的工程拆解与对比。

---

## 1. 流式场景下的工程瓶颈：为什么常规方案会失效？

LLM 依靠 SSE (Server-Sent Events) 逐字吐出 Token，这导致前端每接收到一个微小字符更新，就需要重新绘制界面。

如果采用常规的全量解析方式，性能开销会随文本长度成二次方增长：

在字符数 <math><mi>N</mi></math> 达到几千字时，<math><mi>O</mi><mo>(</mo><msup><mi>N</mi><mn>2</mn></msup><mo>)</mo></math> 的开销会导致：
* **解析器性能崩溃**：主线程 CPU 飙升到 100%，引发页面掉帧。
* **DOM 树整盘重建**：未闭合的语法块（如代码块 ` ``` `、数学公式 `$ \frac{a}{b} `）导致 DOM 树结构剧烈跳变。
* **计算密集型组件反复高亮**：Shiki 语法高亮或 KaTeX 公式解析在每个 Token 到来时被重复执行，造成资源巨大浪费。

## 2. [markstream-vue](https://github.com/Simon-He95/markstream-vue) 核心源码与实现原理拆解

[markstream-vue](https://github.com/Simon-He95/markstream-vue) 是专门针对 Vue 3 / Nuxt 生态打造的高性能流式 Markdown 渲染库。它的核心解法可以归纳为三点：**块级增量状态机、语法自动补全修复、以及 Vue 3 响应式的细粒度控制**。

### 核心 1： Block-Level 增量分块状态机（Incremental Block Tokenizer）

`markstream-vue` 放弃了在每次更新时对整个 Markdown 字符串重新做 AST Parser 扫描，而是维护了一个**流式块切分状态机**。

1. **行与块的缓存（Block Freezing）**：
   解析器从上至下扫描输入流。凡是遇到了确定的块分割线（如双换行 `\n\n`、闭合的代码块 ```` ``` ```` 等），该 Block 就会被标记为 `finished: true`。

2. **状态切片**：
   文档被切分为一个数组：
   <div className="blog-formula">
     <math display="block"><mtext>Doc</mtext><mo>=</mo><mo>[</mo><msub><mtext>Block</mtext><mn>1</mn></msub><mo>(</mo><mtext>Finished</mtext><mo>)</mo><mo>,</mo><msub><mtext>Block</mtext><mn>2</mn></msub><mo>(</mo><mtext>Finished</mtext><mo>)</mo><mo>,</mo><mo>…</mo><mo>,</mo><msub><mtext>Block</mtext><mi>K</mi></msub><mo>(</mo><mtext>Streaming</mtext><mo>)</mo><mo>]</mo></math>
   </div>

   解析引擎**只对最后的 <math><msub><mtext>Block</mtext><mi>K</mi></msub></math> 重新执行正则 tokenize 与解析**，前面已闭合的块彻底脱离解析计算 loop。

```
[ SSE Token 持续流入 ]
          │
          ▼
   [ Stream Tokenizer 状态机 ]
          │
   ┌──────┴────────────────────────┐
   ▼                               ▼
历史已闭合 Block (Finished)      当前处于流式的 Block (Streaming)
   │                               │
   ├─► 状态冻结                     ├─► 投机补全 (Auto-Closure)
   ├─► 跳过 AST 重解析             ├─► 动态解析 & 渲染 VNode
   └─► Vue `v-memo` 节点锁定       └─► 增量 Patch 到视图末尾
```

### 核心 2： Speculative Repair（未闭合语法的投机补全）

对于正在吐出的 <math><msub><mtext>Block</mtext><mi>K</mi></msub></math>，`markstream-vue` 在将文本投递给 AST 生成逻辑前，会先经过一层预修补引擎：

* **代码块检测**：如果发现当前 Block 开头有 ```` ```typescript ```` 但结尾没有 ```` ``` ````，补全器会在内存缓冲区末尾强行追加 `\n``` `。
* **LaTeX 公式检测**：如果匹配到未闭合的单/双美角符 `$`，自动追加临时的 `$`。
* **列表与粗体**：补全未闭合的 `**` 或空列表子项。

> **效果**：送给渲染层的 AST 节点**永远是结构完整的合法节点**，消除了代码框、公式容器在渲染过程中因语法破相导致的样式抖动与排版坍塌。

### 核心 3： Vue 3 响应式极致榨干（Shallow Reactive & VNode Node Locking）

在 Vue 3 落地流式渲染时，最忌讳的是使用深度响应式 `ref()` 包装大体量的 AST 结构，这会导致 Vue 追踪内部每一个微小的节点对象变化。

`markstream-vue` 在框架适配上做到了：
1. **`shallowRef` 级数据更新**：只对 Blocks 数组做浅层响应式，防止深层 AST 属性变动触发无谓的依赖收集。
2. **`v-memo` 块级锁定**：在渲染模版层，将 Block 的唯一哈希或状态作为 `v-memo="[block.id, block.finished]"` 的 Key。一旦 `block.finished` 变成 `true`， Vue 虚拟 DOM Diff 算法将直接跳过该子树的比对，使渲染 Diff 耗时降为接近 <math><mi>O</mi><mo>(</mo><mn>1</mn><mo>)</mo></math>。
3. **延迟计算重型组件**：对于 Shiki/Prism 的高亮处理，在 Block 处于流式中仅以纯文本 `<pre><code>` 渲染；当 Block 状态收敛为 `finished` 时，才触发重构高亮，彻底剥离高频渲染时的 CPU 损耗。

## 3. 基于 `unified` + `remark` 的可扩展架构分析（实习项目实践）

在企业级 AI 交互（如 Copilot、Agent 工作流）中，纯粹的文本渲染是不够的。我们往往需要将 Markdown 变成一个**插件化组件引擎**。

基于 [unified](https://github.com/unifiedjs/unified) + [remark](https://github.com/remarkjs/remark) 方案的设计思想，就是利用 AST 的可塑性，将 Markdown 转化为一棵带有业务语义的 DOM/VNode 树。

```
[ Raw LLM Output Text ]
          │
          ▼
   [ remark-parse ] ──► 生成标准 mdast (Markdown AST)
          │
          ▼
 [ Unified Plugin Pipeline ] ──► 注入自定义 AST Transformer 规则 (自定义语法/节点)
          │
          ▼
  [ AST Node Walker ] ──► 遍历 AST，匹配 Node 类型与 Custom Renderers
          │
          ├── 命中 code 节点  ──► 替换为 Custom Vue/React CodeBlock (支持跑代码/复制)
          ├── 命中 artifact  ──► 替换为 业务 Artifact 容器 (UI 挂载)
          └── 命中普通节点    ──► 映射为 标准 HTML 元素 (带 Theme & Telemetry 标记)
          │
          ▼
   [ Dynamic VNodes ] ──► 最终渲染视图
```

### 核心 1： 管道化 AST 转换与自定义规则注入（Custom Rule Transformer）

`unified` 的核心价值在于其**管道（Pipeline）与生态**：

```javascript
import { unified } from 'unified';
import remarkParse from 'remark-parse';
import remarkGfm from 'remark-gfm';

// 自定义插件：将特殊的 [artifact: id] 语法扩展为自定义 AST 节点
function customArtifactPlugin() {
  return (tree) => {
    // 遍历 AST (mdast)，搜索特征节点并重构为 custom-artifact 类型 Node
  };
}

const processor = unified()
  .use(remarkParse)
  .use(remarkGfm)
  .use(customArtifactPlugin);
```

通过这一管道，可以在解析阶段将 AI 输出中特定格式的文本（如代码块、卡片声明、工具调用等）直接识别为自定义的 AST 节点。

### 核心 2： 递归 AST 到 VNode 映射器与 Slot/Custom Component 替换

拿到 AST 之后，引擎不通过传统的 HTML 字符串中转（即不走 `dangerouslySetInnerHTML`），而是利用 AST Walker **逐节点构建框架原生的 VNode (Vue `h()` 或 React `React.createElement()`)**：

* **自定义组件映射**：
  当 Walker 遇到类型为 `code` 的 AST 节点时，不直接输出 `<pre><code>`，而是渲染为一个包含“复制代码”、“一键运行”、“显示代码行号”的复杂前端组件。
* **Slot（插槽）透传机制**：
  外部可以通过组件 Props 或 Slots 传入具体 AST 节点的渲染实现：
  ```jsx
  <MarkdownRenderer
    components={{
      code: CustomCodeBlock,
      table: CustomDataTable,
      link: TelemetryLink
    }}
  />
  ```

### 核心 3： 主题样式、上下文与全局埋点 (Telemetry & Context Injection)

由于控制了每一个 AST Node 转换为 VNode 的全过程，我们能够在构造 VNode 时**无缝塞入业务切面代码**：

1. **自动曝光与点击埋点**：
   在渲染 `link` 或 `button` 节点时，自动读取 Node 的属性，绑定 `onClick` 事件，向日志服务上报包含上下文（如 `message_id`、`node_type`）的埋点数据。
2. **主题样式注入 (Theme Injection)**：
   将主题 Class 或 CSS Variables 结合 CSS Modules，通过 VNode 属性透传至层级极深的节点中，确保黑暗模式/明亮模式以及品牌主题样式的动态切换。

## 4. 方案架构对比：`markstream-vue` VS `unified + remark`

| 对比维度 | [markstream-vue](https://github.com/Simon-He95/markstream-vue) | `unified` + `remark` 体系方案 |
| :--- | :--- | :--- |
| **设计核心目标** | **流式渲染性能优先** | **生态扩展与 UI 组件化优先** |
| **解析方式** | 增量式 Block 分块状态机解析 | 全量/增量 Pipeline AST 转换 |
| **流式防闪烁能力** | 原生深度支持（自动投机闭合语法） | 需依赖外部预处理库（如 `remend`） |
| **框架耦合度** | 深度绑定 Vue 3 (利用响应式与 `v-memo`) | 框架无关（同套 AST 可切 React/Vue VNode） |
| **自定义组件插槽** | 提供常用 Slot 扩展，但偏向渲染标准 MD | **极强** (可将任意 AST 节点映射为复杂交互组件) |
| **埋点与主题控制** | 依赖外层 CSS 与常规事件委托 | 节点级细粒度 VNode 属性与 Handler 注入 |
| **典型适用场景** | 侧重长文本输出、极高帧率要求的 AI 对话界面 | ToB 复杂 Agent 工作流、卡片式交互、企业级 Copilot |

## 5. 生产级最佳实践：如何构建兼具“流式性能”与“高扩展性”的 Markdown 引擎？

在现代企业级 AI 架构中，最理想的方案其实是将两者的优势进行**组合集成**：

```
                    ┌──────────────────────────────────────────────┐
                    │  1. Incoming Token Stream (via SSE/WebSocket) │
                    └──────────────────────┬───────────────────────┘
                                           │
                                           ▼
                    ┌──────────────────────────────────────────────┐
                    │  2. Speculative Repair Engine (remend/补全器) │
                    │    - 纠正未闭合代码块、LaTeX 公式与 HTML 标签    │
                    └──────────────────────┬───────────────────────┘
                                           │
                                           ▼
                    ┌──────────────────────────────────────────────┐
                    │  3. Incremental Block Splitter (块分割器)     │
                    │    - 区分 Finished Blocks 与 Active Block     │
                    └──────────────────────┬───────────────────────┘
                                           │
                   ┌───────────────────────┴───────────────────────┐
                   ▼                                               ▼
   ┌───────────────────────────────┐               ┌───────────────────────────────┐
   │ Finished Blocks (历史已闭合块) │               │ Active Block (最末尾流式块)   │
   ├───────────────────────────────┤               ├───────────────────────────────┤
   │ • 结果进入 VNode Cache 缓存    │               │ • 投递至 unified AST 管道      │
   │ • 锁定高亮与代码块重绘         │               │ • 匹配自定义插件与插槽         │
   │ • 挂载埋点与主题 VNode         │               │ • 动态生成实时 VNode          │
   └───────────────┬───────────────┘               └───────────────┬───────────────┘
                   │                                               │
                   └───────────────────────┬───────────────────────┘
                                           │
                                           ▼
                    ┌──────────────────────────────────────────────┐
                    │  4. Native VNode Tree Output (React / Vue)   │
                    └──────────────────────────────────────────────┘
```

### 总结三条落地黄金法则：

1. **切勿直接把原始字符串传给 `unified` 执行全量重算**：必须在 `unified` 管道上层挂载 **Incremental Block Splitter**，把历史已经闭合的 `mdast` 节点及其对应的 VNode 冻结在缓存中。
2. **利用 AST Walker 直接输出组件树**：抛弃任何字符串拼接 HTML 的模式，通过递归 AST 生成框架原生 VNode。这是实现 Props 自定义规则、Slot 注入以及全链路埋点的关键。
3. **分级重型组件渲染**：对 Mermaid、Shiki、KaTeX 等重度渲染逻辑实施“双态策略”——**流式中用轻量占位符（Skeleton/Plain Text），闭合后触发 Web Worker 计算异步渲染**。

通过这套架构设计，既能享受 [markstream-vue](https://github.com/Simon-He95/markstream-vue) 带来的极致流畅体验，又能保留 `unified` 生态无与伦比的企业级扩展能力。
