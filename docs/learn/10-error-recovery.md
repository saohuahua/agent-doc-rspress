# 错误恢复与重试分类

第 02 篇的最小循环里没有一行错误处理——`llm.chat()` 要是 429 了、超时了、返回半条消息就断了，循环会怎么样？答案很尴尬：直接崩掉。

这篇文章讲清楚 Agent 的错误恢复：**失败分几类、哪些值得重试、哪些重试反而有害、以及一个错误发生时程序要做的完整分流。**

## 1. 最小循环里隐藏的假设

回看第 02 篇的骨架，它其实默认了三件事永远成立：

```typescript
while (true) {
  // 假设 1：这次调用一定成功
  const response = await llm.chat(messages, { tools });

  // 假设 2：要么文本要么工具调用，没有第三种结果
  if (response.type === 'text') return response.text;

  // 假设 3：工具一定执行成功
  const result = await tool.execute(response.toolCall.arguments);
  ...
}
```

生产环境中这三个假设每天都会破：

| 失败点 | 例子 | 谁的问题 |
|---|---|---|
| LLM 调用失败 | 429 限流、500/503 服务过载、网络超时、连接被重置 | 外部服务 |
| LLM 返回异常 | 输出被 Token 上限截断、返回不合法内容 | 模型行为 |
| 工具执行失败 | 文件不存在、命令报错（第 03 篇讲过） | 环境状态 |

第 03 篇已经解决了第三行——工具失败变成错误消息回填，模型自己调整。这篇文章解决前两行：**模型调用这一层失败后，循环该怎么继续。**

## 2. 第一步永远是分类，不是重试

遇到错误就重试，是最危险的本能反应。正确的顺序是先问：**这个错误再试一次，结果会不一样吗？**

```
                    错误发生
                       │
                       ▼
            ┌──────────────────────┐
            │ 重试会改变结果吗？      │
            └──────────────────────┘
                       │
        ┌──────────────┼─────────────────┐
        ▼              ▼                 ▼
    瞬时错误         持久错误           结构性错误
   （再试一次        （再试一万次        （重试解决不了，
     结果可能不同）    也一样）            要换策略）
        │              │                 │
        ▼              ▼                 ▼
    指数退避重试     快速失败，          换办法处理：
    429 / 5xx /     报告给用户          溢出→压缩上下文
    网络抖动         配额用完            截断→标记工具失败
                                       死循环→中止
```

三类错误的判定和应对：

| 类型 | 判定标准 | 例子 | 应对 |
|---|---|---|---|
| **瞬时错误** | 等一会儿再试，大概率成功 | 429 限流、503 过载、超时、连接重置 | 指数退避重试 |
| **持久错误** | 重试多少次结果都一样 | 401 认证失败、配额耗尽、余额不足 | 快速失败，报告用户 |
| **结构性错误** | 不是"这次调用"的问题，是状态的问题 | 上下文溢出、输出截断、模型打转 | 换策略，不是换时机 |

同一个 429 也可能属于不同类——配额刚好卡线时的 429 是瞬时的（等一分钟就恢复），但"本月配额已用完"的 429 是持久的。**分类看语义，不只看状态码。**

## 3. 指数退避：瞬时错误怎么重试

对瞬时错误，重试要有节制——立刻重试只会撞上同一个限流窗口：

```typescript
// 带指数退避的重试
// 第 1 次重试等 2s，第 2 次等 4s，第 3 次等 8s……
async function retryWithBackoff(fn, maxRetries = 3, baseDelayMs = 2000) {
  for (let attempt = 0; ; attempt++) {
    const result = await fn();

    if (result.ok) return result;          // 成功，直接返回
    if (!isTransient(result.error)) return result;  // 持久错误，不重试
    if (attempt >= maxRetries) return result;       // 预算用完，放弃

    const delay = baseDelayMs * 2 ** attempt;  // 2s → 4s → 8s
    await sleep(delay);
  }
}
```

三个必须有的设计点：

- **指数退避**：每次等待时间翻倍。给服务端恢复的时间越来越多，也让连续重试的总次数有限。
- **重试预算**：`maxRetries` 封顶。无限重试等于把瞬时故障放大成永久挂起。
- **可中止**：退避等待期间用户按了 Ctrl+C，应该立即放弃而不是睡完再退——重试逻辑也要尊重第 06 篇的中止信号。

## 4. 结构性错误：换策略而不是换时机

这类错误最有意思，因为每一种都对应一个前面讲过的机制：

**上下文溢出** —— 第 04 篇的窗口限制真的撞上了。重试没有任何意义（同样的消息列表还会溢出），正确的做法是**先压缩再重试**：

```
上下文溢出错误
  │
  ├─ 1. 摘掉最后一条失败的 assistant 消息
  ├─ 2. 触发压缩（第 08 篇的 Compaction）
  └─ 3. 用压缩后的上下文重新发起这一轮
```

**输出截断**（stopReason: length）—— 第 05 篇讲过：截断的 JSON 参数不完整，不应该尝试执行。正确做法是把这批工具调用**全部标记失败**回填给模型，让它重新发起调用。

**模型打转** —— 连续多轮重复同一个工具调用、或反复更新计划却毫无进展（第 09 篇埋的伏笔）。程序应该检测重复模式，达到阈值后中止，把控制权交还用户。

:::warning 一条红线

**有副作用的操作不能靠重试兜底。** 工具执行失败后盲目重试，可能造成重复副作用——`npm publish` 重试一次就是发了两个版本（第 08 篇的重放安全问题的另一面）。重试只适用于**读操作和幂等操作**；写操作失败后，应该先核对状态再决定下一步。

:::

## 5. 错误分流在循环里的位置

把所有处理加回最小循环，错误分流发生在**两轮之间**：

```
while (true) {
  ① 调 LLM（重试逻辑包裹在这里：瞬时错误→退避重试）
       │
       ▼
  ② 检查返回结果
       ├─ 正常文本/工具调用 → 继续走主流程
       ├─ 溢出 → 摘掉失败消息 → 压缩 → 重新发起本轮
       ├─ 截断 → 全部工具调用标记失败 → 回填错误 → 继续
       └─ 持久错误 → 退出循环 → 报告用户
       │
       ▼
  ③ 执行工具（单个工具失败不进这里，直接回填错误消息）
       │
       ▼
  ④ 回填结果 → 回到 ①
}
```

注意分层的含义：**循环层的重试是"重新发起一轮调用"，工具层的失败是"回填一条错误消息"**——两条恢复路径互不干扰。前者处理"和模型说话失败"，后者处理"模型说的话执行失败"。

## 6. 对照 Pi 源码

Pi 的错误恢复分了三层，每一层的职责都很干净：

| 本篇概念 | Pi 中的实现 | 先看什么 |
|---|---|---|
| 错误分类（瞬时 vs 持久） | `isRetryableAssistantError()`——用两组正则区分可重试和不可重试错误 | `packages/ai/src/utils/retry.ts:223` |
| 重试预算与指数退避 | `retryAssistantCall()`——`baseDelayMs * 2^(attempt-1)`，带中止支持 | `packages/ai/src/utils/retry.ts:163` |
| 持久错误识别 | `NON_RETRYABLE_PROVIDER_LIMIT_ERROR_PATTERN`——配额/账单类错误快速失败 | `packages/ai/src/utils/retry.ts:10` |
| 溢出判定 | `isContextOverflow()`——匹配各厂商的溢出报错文案，甚至识别"静默溢出" | `packages/ai/src/utils/overflow.ts:134` |
| 溢出→压缩→重试的分流 | `_checkCompaction()`——溢出后摘掉失败消息、压缩、重试一次 | `packages/coding-agent/src/core/agent-session.ts:2134` |
| 重试决策入口 | `_handlePostAgentRun()`——每轮结束后统一分流：重试 or 压缩 or 结束 | `packages/coding-agent/src/core/agent-session.ts:1100` |
| 重试上限配置 | `retry.maxRetries` 默认 3，`baseDelayMs` 默认 2000 | `packages/coding-agent/src/core/agent-session.ts:707` |

几个值得注意的细节：

- **分类是正则匹配错误文案，不是只看状态码。** 因为不同厂商的报错格式五花八门，Pi 维护了两份模式表：`RETRYABLE_PROVIDER_ERROR_PATTERN`（overloaded / 429 / 5xx / 网络类文案）和 `NON_RETRYABLE_PROVIDER_LIMIT_ERROR_PATTERN`（配额耗尽 / 账单类文案）。这正是第 2 节"分类看语义"的真实工程形态——同一份语义，要为每家 Provider 各写一份"翻译"。
- **溢出优先于重试。** `_isRetryableError()`（`agent-session.ts:2825`）的第一行就是：如果是溢出错误，直接返回 false，交给压缩去处理——重试和压缩两条路径不会打架。
- **溢出恢复只重试一次。** `_overflowRecoveryAttempted` 标记保证"压缩→重试"最多发生一轮，防止在压缩救不回来时无限循环。
- **截断处理在循环层**：第 05 篇提到的 `failToolCallsFromTruncatedMessage()`（`packages/agent/src/agent-loop.ts:379`）就是第 4 节"全部标记失败"的生产实现。
