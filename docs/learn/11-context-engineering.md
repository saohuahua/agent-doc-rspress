# 上下文工程

第 04 篇讲了上下文窗口的"容量"问题：Token 有限、消息会涨、需要压缩。但还有一个更根本的问题一直没正面回答：**每一轮请求，模型到底应该看到什么？**

这篇文章讲清楚系统提示的真实构成、项目规则怎么注入、以及"装得下"和"用得上"的区别。

## 1. 上下文不只是消息历史

一次 Agent 请求的完整上下文，远不止对话消息：

```
一次请求的完整上下文
┌─────────────────────────────────────────────────────────┐
│ ① 系统提示（system prompt）                              │
│    身份 + 工具说明 + 行为准则 + 项目规则 + 技能索引        │
├─────────────────────────────────────────────────────────┤
│ ② 工具定义（tools 参数）                                  │
│    每个工具的 name + description + parameters schema      │
├─────────────────────────────────────────────────────────┤
│ ③ 消息历史（messages）                                    │
│    user / assistant / tool 交替，含工具结果               │
└─────────────────────────────────────────────────────────┘
```

第 04 篇只详细讲了 ③。但 ① 和 ② 是每轮**固定重复**发送的，而且它们决定了模型对"我是谁、能干什么、这个项目有什么规矩"的理解。上下文工程（Context Engineering）研究的就是这整块的选材与编排：**从不断变化的信息里，挑出能让模型产生期望行为的最小高信号集合。**

## 2. 系统提示是拼装出来的

一个常见误解：系统提示是开发者手写的一段固定文本。真实的 Coding Agent 不是——**它是运行时生成的产物**，由多个来源动态拼装：

```typescript
// 简化后的系统提示拼装过程
function buildSystemPrompt(options) {
  let prompt = '';

  // ① 身份与工具说明：哪几个工具被启用，就写哪几个的说明
  //    工具列表是动态的——没启用 bash 的构建里，提示里也不会提 bash
  prompt += `You are an expert coding assistant...\n\nAvailable tools:\n${toolsList}\n`;

  // ② 行为准则：根据启用的工具动态生成
  //    没有专用搜索工具时，才提示"用 bash 的 ls/rg/find"
  //    有专用工具时，这条就消失了——避免教模型用笨办法
  prompt += `Guidelines:\n${guidelines}\n`;

  // ③ 项目规则：从项目目录读到的指令文件，原样嵌入
  for (const file of contextFiles) {
    prompt += `<project_instructions path="${file.path}">\n${file.content}\n</project_instructions>\n`;
  }

  // ④ 技能索引：只放 name + description，不放正文
  prompt += formatSkillsForPrompt(skills);

  // ⑤ 环境信息：当前工作目录
  prompt += `Current working directory: ${cwd}`;
  return prompt;
}
```

五个来源各自的性质完全不同：

| 部分 | 内容 | 来源 | 变化频率 |
|---|---|---|---|
| 身份 | "你是一个编码助手" | 代码内置 | 几乎不变 |
| 工具说明 | 每个工具的一行用法 | 由启用的工具决定 | 按构建/配置变化 |
| 行为准则 | "回答简洁""标明文件路径" | 代码内置 + 根据工具集动态增删 | 几乎不变 |
| 项目规则 | 项目约定、风格要求 | 项目目录下的指令文件 | 每个项目不同 |
| 技能索引 | 技能 name + description + 路径 | 技能目录扫描 | 按安装情况变化 |
| 环境信息 | 当前目录、平台 | 运行时 | 每次启动 |

注意 ③ 和 ④ 的共同点：**系统提示里放的只是"目录"，不是"正文"**。项目规则的正文用户可以自己看；技能的正文躺在文件里，模型判断任务匹配时才用 read 工具去读。这和第 03 篇"模型看到工具签名、看不到 execute 实现"是同一个设计原则——**上下文里只放索引和入口，需要时再加载**。

## 3. 项目规则：AGENTS.md

第 2 节的 ③ 是 Coding Agent 生态里事实标准化的机制：在项目目录下放一个约定文件（Pi 找的是 `AGENTS.md`，也兼容 `CLAUDE.md`），写上这个项目的规矩：

```markdown
<!-- AGENTS.md 的典型内容 -->
# 项目约定

- 组件用函数式写法，不用 class 组件
- 提交信息用 conventional commits 格式
- 测试文件放 __tests__ 目录，跑测试用 pnpm test
- 改动 src/core 前必须先跑 pnpm typecheck
```

Agent 启动时自动把它读进系统提示，模型就"出生在这个项目的规矩里"。几个值得注意的细节：

- **它是逐级查找的**。从当前目录一路向上找各级目录的指令文件，都拼进提示——monorepo 里根目录放全局规矩，子目录放各自的规矩，离得越近的越具体。
- **它是不可信输入**。第 07 篇的教训在这里同样成立：`AGENTS.md` 是项目仓库里的文件，clone 一个恶意仓库时，它里面的指令会进你的 Agent 上下文。这就是 Pi 设置**项目信任机制**（第一次打开项目先问你是否信任）的原因之一。
- **它不是 system prompt 的替代**。身份、行为准则这些"产品级"内容仍然在代码里，`AGENTS.md` 只负责"项目级"内容——分层清晰，互不污染。

## 4. "装得下"不等于"用得上"

第 04 篇的压缩篇让你以为上下文管理就是"别超窗口"。但真实情况更微妙——**窗口装得下的内容，模型也未必能稳定利用**：

- **相关性**：塞了 20 个文件的内容，模型可能被无关代码带偏。噪声不只是浪费 Token，还会稀释注意力（第 09 篇讲的"目标被挤出"就是同一现象）。
- **位置**：模型对上下文开头和结尾的内容最敏感，中间大段内容容易被"略读"。关键指令放哪、工具结果放哪，是有讲究的。
- **重复**：同一个信息以三种说法出现三次，不会加强记忆，反而增加干扰。

所以上下文工程的完整心法是三层递进：

| 层次 | 问题 | 手段 |
|---|---|---|
| 装得下 | 总量不超过窗口 | 截断、压缩（第 04/08 篇） |
| 看得见 | 关键信息在注意力范围内 | 索引代替正文、按需加载、及时压缩 |
| 用得上 | 信息是高信号的 | 精选项目规则、工具结果截断、去掉重复 |

**按需加载**是第三层最核心的手段：技能正文、大文件内容、搜索结果，都不该一股脑塞进上下文，而是"先给模型一个目录，让它自己决定什么时候读什么"。

## 5. 为什么稳定内容要放在前面

还有一层纯工程的原因，与钱有关：

```
无缓存的计费方式：
  每轮请求都按 全量输入 Token 计费
  第 1 轮 1000 tokens → 第 10 轮还是每次付 8000+ tokens 的钱

有 prompt cache 的计费方式：
  请求前缀（不变的头部）命中缓存 → 按缓存价计费（便宜数倍）
  只有新增的后缀按原价计费
```

模型 API 的 prompt cache 按**前缀匹配**工作：请求开头的部分如果和上次请求完全一致，就能命中缓存。这直接推出一条编排规则：

**变动频率越低的内容，放得越靠前。**

```
稳定（每轮都一样）          ← 系统提示、工具定义
    │
    ▼
半稳定（随会话增长）        ← 早期的消息历史
    │
    ▼
易变（每轮都变）            ← 最新几条消息、新的工具结果
```

第 04 篇"每次都把完整消息列表传过去"的设计，在这里得到了回报：消息列表只追加不修改，前缀天然稳定，每一轮都能命中大部分缓存。反过来说，**把高频变动的内容插进上下文中部，等于每次都把缓存作废**——既慢又贵。Pi 的压缩流程甚至专门为一次性摘要请求关闭了缓存写入，因为那种请求几乎不可能被复用，写缓存白花钱。

:::info 一句话总结

Prompt cache 优化的是成本和延迟，不扩大窗口，也不是记忆。它影响的是"同样的内容放在哪个位置"这个纯编排决策。

:::

两个值得注意的细节：

- Pi 的系统提示整体非常克制（只有 169 行代码生成），没有长篇的行为条款。对比某些产品动辄几千 token 的系统提示，这是"高信号"原则的激进版本——但也意味着更多行为引导被交给了模型自身。
- Pi 专门做了**缓存浪费检测**：`CacheMiss` 统计每轮有多少 Token 没命中缓存、多花了多少钱、距上次请求隔了多久（超过 5 分钟的空闲是缓存过期的常见原因）。上下文编排好不好，最终是可以被量化验证的。
