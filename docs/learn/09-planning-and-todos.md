# 规划与任务分解

前面几篇的 Agent 都是一次性接一个小任务：查天气、读文件、改一处代码。但如果任务是"把这个模块从回调风格重构成 async/await"，涉及 8 个文件的改动——**模型做到第 3 步时，还记得第 4 步该做什么吗？**

这篇文章讲清楚长任务中的规划问题：为什么模型会"走哪算哪"、Todo 列表怎么解决它、以及计划本身也会过时怎么办。

## 1. 问题：注意力会被稀释

给 Agent 一个复杂任务："把所有 Python 文件改成 snake_case 命名，然后跑测试，修好失败的。"

```
任务开始
  │
  ├─ 改了 3 个文件
  ├─ 跑测试，2 个失败
  ├─ 开始修失败 ────────────┐
  │                        │
  │   修着修着，模型忘了     │  ← 最初的目标被挤出注意力
  │   最初的目标是           │     工具结果不断填满上下文
  │   "全部改成 snake_case"  │
  │                        │
  └─ 最后只改了一半文件      │
     测试也没全跑            │
                            ▼
                 系统提示的影响力被稀释
```

这不是模型"笨"，而是结构性的：**对话越长，工具结果占据的上下文越多，任务目标的信号就被稀释了**。一个 10 步的重构，做到 1-3 步就开始即兴发挥，因为 4-10 步已经被挤出模型的注意力。

第 04 篇讲过上下文窗口是有限的，压缩会丢细节。规划要解决的是更早的问题：**在窗口还没满的时候，模型就已经不盯着目标了。**

## 2. 解决方案：把计划写进上下文

核心思路很朴素：**让模型在动手前先列一个清单，并且这个清单一直留在上下文里。**

```typescript
// 一个不做任何"实际工作"的工具
// 它不能读文件、不能跑命令，唯一的作用是让模型理清思路、更新状态
const todoWrite: Tool = {
  name: 'todo_write',
  description: '维护当前任务的待办列表。开始复杂任务前先列出步骤；每完成一步就更新状态。',
  parameters: {
    type: 'object',
    properties: {
      todos: {
        type: 'array',
        items: {
          type: 'object',
          properties: {
            content: { type: 'string' },                          // 要做什么
            status: { type: 'string', enum: ['pending', 'in_progress', 'completed'] },
          },
          required: ['content', 'status'],
        },
      },
    },
    required: ['todos'],
  },
  // 执行函数只做一件事：把列表存起来，显示给用户看
  async execute(args) {
    currentTodos = args.todos; // 存在程序内存里，渲染到终端
    return renderTodos(currentTodos);
  },
};
```

有了这个工具后，同一个任务的执行过程变成：

| 轮次 | 模型的动作 |
|---|---|
| 1 | `todo_write`：列出"改文件 ×8 → 跑测试 → 修失败 → 再跑"四步 |
| 2-9 | 逐个改文件，每改一个就更新列表状态 |
| 10 | 跑测试，2 个失败 |
| 11 | 修失败——**但列表还在上下文里，模型知道后面还有 4 个文件没改** |
| 12 | 修完、再跑测试、把列表全部标成 completed，才总结收尾 |

清单起了两个作用：

- **给模型**：每一轮请求都带着完整消息列表，清单作为消息的一部分反复出现。模型"看得见"自己还有哪几步没做——目标不再依赖它记住，而是摆在那里。
- **给用户**：进度从"不知道 Agent 在干嘛"变成"第 3 步，共 6 步"。这也是第 05 篇流式输出之外，另一个重要的可见性手段。

:::tip 关键认识

Todo 工具本身不做任何工作。它的全部价值在于**把"计划"变成上下文里持久存在的结构化数据**，对抗注意力稀释。

:::

## 3. 什么时候该列计划

不是所有任务都需要。清单本身占 Token，简单任务列计划是浪费。常见的判断标准：

| 任务特征 | 该列计划吗 | 原因 |
|---|---|---|
| 查个天气、读一个文件 | ✗ | 一步完成，清单是纯开销 |
| 改一个函数 + 跑测试 | ✗ | 2-3 步，模型装得下 |
| 多文件重构、跨模块改动 | ✓ | 步骤多，容易漏项 |
| 边做边才能确定步骤的任务 | ✓ | 先列已知部分，边做边补充 |
| 用户明确要求"先给个方案" | ✓ | 计划本身就是交付物 |

最后一种值得单独说：**plan mode**。很多 Coding Agent 提供"先出计划、用户批准后再动手"的模式——计划列出来给用户看，用户确认或修改后，Agent 才开始执行。这把"规划"从模型的自说自话，变成了一个人机对齐的检查点。

## 4. 计划也会过时

列了计划不等于一劳永逸。执行中发现的问题可能推翻原计划：

```
计划：改 a.ts → 改 b.ts → 跑测试
  │
  ├─ 改 b.ts 时发现它依赖 c.ts 里的接口
  │  ← 计划里没有 c.ts！
  │
  ▼
模型的正确行为：
  1. 用 todo_write 更新列表（插入"改 c.ts"）
  2. 继续执行新计划
```

所以 `todo_write` 不是"开始时调用一次"的工具，而是**贯穿全程的状态更新工具**。衡量一个 Agent 会不会规划，看的不是它列不列计划，而是**计划变了之后它改不改清单**——只列不改的清单比没有清单更糟，因为它会持续给模型错误的目标状态。

## 5. Reminder：模型忘了更新怎么办

还有一个现实问题：模型可能列了计划，然后十几轮都没有更新它。一个常见的补强手段是 **reminder 机制**——程序在循环里计数，连续 N 轮没看到模型调用 `todo_write`，就往上下文里注入一条提醒：

```typescript
// 在 Agent Loop 的工具结果回填处检查
let roundsSinceLastTodo = 0;

// 每轮执行完工具后调用
function checkTodoReminder(toolName: string | undefined): string | null {
  if (toolName === 'todo_write') {
    roundsSinceLastTodo = 0;  // 模型更新了清单，计数归零
    return null;
  }
  roundsSinceLastTodo++;
  // 连续 10 轮没更新，且还有未完成的事项 → 注入提醒
  if (roundsSinceLastTodo >= 10 && currentTodos.some(t => t.status !== 'completed')) {
    roundsSinceLastTodo = 0;
    return '提醒：当前任务还有未完成的待办事项，请检查并更新你的任务列表。';
  }
  return null;
}
```

这本质上是第 06 篇 Steering 机制的变体——只不过注入的不是用户消息，而是**程序根据运行状态自动生成的提醒**。防线可以再加一层：如果连续多轮模型反复调用同一个工具、或反复更新清单却毫无进展，程序应该检测这种"打转"并中止（这也是错误恢复篇的话题）。

## 6. 对照 Pi 源码

Pi 没有内置 todo 工具——这是 Pi 的一个真实取舍，不是疏漏：

| 本篇概念 | Pi 中的情况 | 先看什么 |
|---|---|---|
| todo_write 工具 | **没有内置实现**（`packages/coding-agent/src/core/tools/` 下不存在） | 工具目录 `packages/coding-agent/src/core/tools/` |
| 任务的可见性 | 靠 TUI 实时渲染流式事件和工具调用，而不是任务清单 | `packages/tui/` |
| 代码层面的规划 | 依赖系统提示引导（见下）+ 模型自身能力 | `packages/coding-agent/src/core/system-prompt.ts:128` |
| 计划作为交付物 | 项目里常见做法是让模型先把方案写进 markdown 文件，用户改完再让它执行 | —— |
| 长任务防走偏 | 不用清单，而是靠**会话分支**：走偏了就回分叉点重来 | `packages/agent/src/harness/session/session.ts:102` |

Pi 的系统提示（`buildSystemPrompt()`，`packages/coding-agent/src/core/system-prompt.ts:128`）非常克制——只有工具说明、几条行为准则和当前目录，没有"先列计划再动手"这类策略指令。Pi 的作者把规划看作模型侧的能力（弱模型列了也守不住），而不是框架侧的机制。

这个取舍不是唯一答案。Claude Code 内置了 TodoWrite 工具和 nag 提醒机制；Pi 选择了更瘦的骨架。**两种做法都对，取决于他们对目标模型能力的判断**——这本身就是很好的面试讨论材料：框架应该替模型补短，还是只服务足够强的模型？
