#消息、角色与上下文窗口

前面几篇一直在往 messages 数组里塞东西。这篇文章讲清楚这个数组的完整结构——四种角色、内容块的组合方式、以及为什么消息越来越长会成为一个必须解决的问题。

#1. 全景图

一次完整的 Agent 交互中，消息列表的增长过程：

消息列表增长过程 ═══════════════════════════════════════════════════════════ 初始状态（1 条） ┌─────────────────────────────────────────────────────┐ │ [0] system: "你是一个编码助手，可以读写文件。" │ │ [1] user: "帮我看看 src/index.ts 有什么问题" │ └─────────────────────────────────────────────────────┘ 第 1 轮后（+2 条 = 4 条） ┌─────────────────────────────────────────────────────┐ │ [0] system: "你是一个编码助手..." │ │ [1] user: "帮我看看 src/index.ts..." │ │ [2] assistant: [text + toolCall(read_file)] │ │ [3] tool: "const app = express();\n..."（500行） │ └─────────────────────────────────────────────────────┘ 第 2 轮后（+2 条 = 6 条） ┌─────────────────────────────────────────────────────┐ │ [0] system │ │ [1] user │ │ [2] assistant (toolCall) │ │ [3] tool (500 行代码) ← 占了大量 Token │ │ [4] assistant (toolCall: edit_file) │ │ [5] tool ("修改成功") │ └─────────────────────────────────────────────────────┘ 第 3 轮后（+2 条 = 8 条） ┌─────────────────────────────────────────────────────┐ │ [0] system │ │ [1] user │ │ [2] assistant │ │ [3] tool (500 行) │ │ [4] assistant │ │ [5] tool │ │ [6] assistant (toolCall: run_test) │ │ [7] tool ("3 tests passed, 1 failed:\n...") │ └─────────────────────────────────────────────────────┘

每次调 LLM 时，完整的消息列表都会被传过去。消息越长，消耗的 Token 越多。

#2. 四种角色

每条消息都有一个 role，决定了模型怎么理解它：

// system：系统指令，定义模型的身份和能力范围
// 通常只有一条，放在消息列表的最前面
{ role: 'system', content: '你是一个编码助手，可以读写文件和运行命令。' }

// user：用户的输入，每次用户提问或补充信息时产生
{ role: 'user', content: '帮我看看 src/index.ts 有什么问题' }

// assistant：模型的回复
// content 是一个数组，可以同时包含文本和工具调用
{ role: 'assistant', content: [
  { type: 'text', text: '让我先读一下这个文件。' },     // 文本部分
  { type: 'toolCall', id: 'call_1', name: 'read_file',      // 工具调用部分
    arguments: { path: 'src/index.ts' } },
]}

// tool：程序执行工具后返回的结果
// toolCallId 用于和上面的 toolCall 配对，确保多个工具结果不会混淆
{ role: 'tool', toolCallId: 'call_1', content: 'const app = express();\n...' }

四种角色的分工：

角色谁产生的内容是什么什么时候出现
system程序总体指令，定义模型的身份和能力对话开始，通常只有一条
user用户用户的提问或指令每次用户输入
assistant模型模型的回复，可包含文本和工具调用每次模型回复
tool程序工具执行结果每次工具执行完

#顺序规则

消息的角色必须按一定规则排列，否则 LLM API 会拒绝请求：

正确的顺序： system → user → assistant → tool → assistant → tool → assistant(text) 不合法的顺序： user → user（不能连续两个 user） assistant → assistant（不能连续两个 assistant） tool → user（tool 后面必须跟 assistant）
顺序口诀

user 和 assistant 交替出现，tool 紧跟在包含 toolCall 的 assistant 之后。

#3. 内容不只是文本

上一篇讲工具时提到过，一条 assistant 消息可以同时包含文本和多个工具调用。它的 content 是一个内容块数组：

┌──────────────────────────────────────────────────────────┐ │ 一条 assistant 消息的 content │ │ │ │ ┌─────────────────────────────────────────────────────┐ │ │ │ [0] { type: "text", text: "让我读一下这两个文件。" } │ │ │ ├─────────────────────────────────────────────────────┤ │ │ │ [1] { type: "toolCall", id: "call_1", │ │ │ │ name: "read_file", │ │ │ │ arguments: { path: "src/a.ts" } } │ │ │ ├─────────────────────────────────────────────────────┤ │ │ │ [2] { type: "toolCall", id: "call_2", │ │ │ │ name: "read_file", │ │ │ │ arguments: { path: "src/b.ts" } } │ │ │ └─────────────────────────────────────────────────────┘ │ └──────────────────────────────────────────────────────────┘

内容块的类型：

类型说明出现在哪个角色
text纯文本user, assistant
toolCall工具调用请求assistant
toolResult工具执行结果tool
image图片（部分模型支持）user
thinking模型的思考过程（部分模型支持）assistant

#4. 上下文窗口与 Token

模型有一个上下文窗口（context window）——它一次能处理的最大文本量，用 Token 衡量。

#什么是 Token？

Token 不是字符，也不是单词。它是模型把文本切分成的最小单元：

英文：Hello world → ["Hello", " world"] = 2 tokens 中文：北京今天 → ["北京", "今天"] ≈ 2-4 tokens 代码：const x=1 → ["const", " x", "=", "1"] = 4 tokens
Token 估算

1 个 Token ≈ 3-4 个英文字符 ≈ 1-2 个中文字符。

#各模型的上下文窗口

模型上下文窗口大约能装多少
小窗口模型4K - 8K tokens一个中等大小的文件
中等模型32K - 64K tokens几个文件 + 对话历史
大窗口模型128K - 200K tokens十几个文件 + 长对话

一个 500 行的代码文件大约 2000-4000 tokens。读 3 个文件、做几轮修改，很容易就超过 8K。即使是 128K 的大窗口，一个复杂的调试任务也可能用完。

#5. 消息增长的速度

来看一个实际的例子——修复一个 bug 的过程中，消息列表消耗的 Token：

┌─────────────────────────────────────────────────────────┐ │ Token 消耗增长 │ │ │ │ 轮次 操作 新增 Token 累计 Token │ │ ───── ────────────── ────────── ─────────── │ │ 0 system prompt ~500 500 │ │ 1 user 提问 ~50 550 │ │ 2 read_file(a.ts) ~3000 3550 ← 文件大 │ │ 3 read_file(b.ts) ~2000 5550 │ │ 4 edit_file ~200 5750 │ │ 5 run_test ~1000 6750 ← 输出长 │ │ 6 edit_file ~200 6950 │ │ 7 run_test ~500 7450 │ │ 8 assistant 总结 ~300 7750 │ │ │ │ 8 轮就用了 ~7750 tokens │ │ 一个 8K 窗口已经快满了 │ └─────────────────────────────────────────────────────────┘

工具结果（尤其是文件内容和测试输出）是最占 Token 的部分。

#6. 超了怎么办？

如果消息总量超过上下文窗口，有几种处理方式：

方法做法优点缺点
截断丢弃最早的消息简单模型忘记之前做了什么
压缩用模型把早期消息总结为摘要保留关键信息需要额外 LLM 调用，摘要可能丢细节
选择性保留保留 system + 最近几轮 + 关键结果平衡需要判断什么是"关键"

这就是上下文压缩（Compaction）存在的原因。简单说：

压缩前 压缩后 ┌────────────────────────┐ ┌────────────────────────┐ │ system │ │ system │ │ user (轮1) │ │ 摘要："用户让我修复 │ │ assistant (轮1) │ │ login.ts 的 bug， │ │ tool (轮1) │ ──→ │ 我读了文件并修改了 │ │ user (轮2) │ │ 第 15 行..." │ │ assistant (轮2) │ │ user (轮5 - 最近) │ │ ... │ │ assistant (轮5) │ │ user (轮5) │ │ tool (轮5) │ │ assistant (轮5) │ └────────────────────────┘ │ tool (轮5) │ └────────────────────────┘ ~8000 tokens ~3000 tokens

当前这一篇不展开压缩的实现——只需要知道"消息会增长、窗口有限、需要压缩"这个事实。第 08 篇会再讲持久化和恢复时的处理。

#7. 对照 Pi 源码

在 Pi 中，上面这些概念都有对应的实现：

本篇概念Pi 中的实现先看什么
四种角色Message 类型（system / user / assistant / toolResult）packages/ai/src/types.ts
Agent 内部消息AgentMessage（比 Message 多了元数据和时间戳）packages/agent/src/types.ts
上下文Context（systemPrompt + messages + tools）packages/ai/src/types.ts
Token 计算calculateContextTokens()packages/coding-agent/src/core/agent-session.ts
上下文压缩compact()packages/coding-agent/src/core/compaction/compaction.ts:859
工具结果截断truncate.ts（防止单个工具结果太长）packages/coding-agent/src/core/tools/truncate.ts

Pi 还做了一件事：工具结果截断。如果一个文件有 5000 行，Pi 不会把全部内容放回上下文，而是截断到合理大小，避免一个工具结果就占满窗口。
