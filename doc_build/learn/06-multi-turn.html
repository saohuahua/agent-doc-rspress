#多轮交互与用户插队

前面几篇的 Agent Loop 里，用户只在开始时提一个问题，然后安静等结果。但真实场景中，Agent 可能要跑好几轮才能完成任务，用户随时可能想补充信息、修改方向、甚至中止操作。

这篇文章讲清楚 Agent 如何处理这些"中途到达的消息"——Steering 和 Follow-up 两种机制，以及它们如何影响循环结构。

#1. 问题场景

一个真实的使用场景：

用户："帮我重构 src/utils.ts" │ ▼ ┌─────────────────────────────────────────────────────────┐ │ Agent 正在工作... │ │ │ │ 第 1 轮 read_file("src/utils.ts") → 读到 500 行 │ │ 第 2 轮 read_file("src/utils.test.ts") → 读到测试 │ │ 第 3 轮 Agent 正在分析代码... │ │ │ │ ┌─────────────────────────────────────────────────────┐ │ │ │ 用户这时候打字： │ │ │ │ │ │ │ │ "等等，先别动 calculateTax 函数，那个不用改" │ │ │ │ │ │ │ │ 这条消息怎么处理？ │ │ │ │ ✗ 丢弃？ → 用户的重要信息丢失 │ │ │ │ ✗ 立即中断？ → 当前工作白费 │ │ │ │ ✓ 排队注入？ → 在合适的时机让模型看到 │ │ │ └─────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────┘

#2. 两种插队方式

Agent 提供两种处理中途消息的策略：

┌────────────────────────────────────────────────────────┐ │ Steering（转向） │ │ │ │ 时机：当前工具执行完 → 下一次调 LLM 之前 │ │ 效果：模型在当前任务中立即看到这条消息 │ │ 类比：开车时副驾说"前面路口左转" │ │ │ │ 例子："等等，先看 src 目录" │ │ "不要改测试文件" │ │ "用 lodash 代替手写实现" │ ├────────────────────────────────────────────────────────┤ │ Follow-up（后续） │ │ │ │ 时机：当前整个任务完成之后 │ │ 效果：作为一个新问题排队等待 │ │ 类比：吃完饭后说"再来一份甜点" │ │ │ │ 例子："做完这个再帮我看看 login.ts" │ │ "重构完了之后跑一下完整测试" │ │ "然后帮我写个 README" │ └────────────────────────────────────────────────────────┘

对比：

维度Steering（转向）Follow-up（后续）
什么时候注入当前工具执行完、下一次调 LLM 前当前任务完全结束后
影响范围当前任务的后续步骤作为新任务
类比开车时修正方向到站后再出发
适合的场景补充信息、修正方向、限制范围新的独立任务

#3. 循环结构的变化

第 02 篇的最小循环只有一层 while。加上 Steering 和 Follow-up 后，变成了双层循环：

┌─────────────────────────────────────────────────────────┐ │ 外层循环（Follow-up） │ │ │ │ while (true) { │ │ ┌─────────────────────────────────────────────────┐ │ │ │ 内层循环（Tool Call + Steering） │ │ │ │ │ │ │ │ while (hasMoreToolCalls || hasPendingMessages) { │ │ │ │ │ │ │ │ ① 注入 pending messages（Steering 消息） │ │ │ │ ② 调 LLM，流式接收回复 │ │ │ │ ③ 检查 stopReason │ │ │ │ ④ 有 toolCall → 执行工具 → 继续内层循环 │ │ │ │ ⑤ 没有 toolCall → 退出内层循环 │ │ │ │ │ │ │ │ 检查是否有新的 Steering 消息 │ │ │ │ } │ │ │ └─────────────────────────────────────────────────┘ │ │ │ │ 检查是否有 Follow-up 消息 │ │ → 有 → 设为 pending → 继续外层循环 │ │ → 没有 → 退出，Agent 完成 │ │ } │ └─────────────────────────────────────────────────────────┘

简单说：

  • 内层循环处理工具调用和 Steering
  • 外层循环处理 Follow-up

#4. 一次完整的交互过程

用一个例子看看两种消息是怎么注入的：

═══ 初始输入 ═══ 用户："帮我重构 src/utils.ts" → 进入内层循环 ═══ 内层循环 第 1 轮 ═══ ① 检查 pending messages → 没有 ② 调 LLM → assistant: toolCall(read_file, "src/utils.ts") ④ 执行工具 → 返回文件内容 ──────────────────────────────────────── 这时候用户打字："不要改 calculateTax" ← Steering 消息入队 ──────────────────────────────────────── ═══ 内层循环 第 2 轮 ═══ ① 检查 pending messages → 有！注入 "不要改 calculateTax" ② 调 LLM（模型看到了文件内容 + 用户的补充指示） → assistant: toolCall(edit_file, ...) ← 跳过了 calculateTax ④ 执行工具 → 修改成功 ═══ 内层循环 第 3 轮 ═══ ② 调 LLM → assistant: text "已完成重构，保留了 calculateTax..." ⑤ 没有 toolCall → 退出内层循环 ──────────────────────────────────────── 之前用户还打过："做完了跑一下测试" ← Follow-up 消息 ──────────────────────────────────────── ═══ 外层循环检查 ═══ 检查 Follow-up → 有！"做完了跑一下测试" 设为 pending → 继续外层循环 ═══ 内层循环（新一轮）第 1 轮 ═══ ① 注入 "做完了跑一下测试" ② 调 LLM → toolCall(run_test, "npm test") ...

#5. 队列模式

当有多条 Steering 消息排队时，程序需要决定一次注入多少条：

模式行为什么时候用
all一次注入所有排队的消息多条消息是同一个意图的补充
one-at-a-time每次只注入最早的一条每条消息可能导致不同方向

#6. 中止（Abort）

除了补充信息，用户还可能想完全中止当前操作（比如按 Ctrl+C）：

Agent 正在第 5 轮工具调用... │ │ 用户按 Ctrl+C │ ▼ ┌─────────────────────────────────────────────────────────┐ │ 中止处理 │ │ │ │ 1. 设置 AbortSignal │ │ 2. 等待当前正在执行的工具完成（不能中途切断文件写入） │ │ 3. 不再发起新的 LLM 调用 │ │ 4. stopReason 变为 "aborted" │ │ 5. 退出循环 │ └─────────────────────────────────────────────────────────┘
WARNING

中止不是立即停止。如果工具正在写文件，突然切断可能留下半写的文件。通常会等当前工具执行完，但不再开始新的工具调用。
