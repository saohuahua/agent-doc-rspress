#使用记录

这个板块和其他板块的性质完全不同：

其他板块可以靠读源码写出来，这个板块只能靠真的用。

#1. 为什么必须即刻开始

面试问题证据矩阵（交接文档 §12）里有两个问题，读一万行源码也答不了：

#面试问题唯一证据来源
3你的 AI Coding 过程为什么跑这么久，问题在哪本人使用记录 + 会话文件
11这个方案给你的任务带来了怎样的效率提升本人实测数据

这两个问题的共同点是：必须有 before/after 的真实数字。事后补写只能编，而编造效率提升是明令禁止的（§19）。

所以规则是：用一次记一次，哪怕只有三行。

#2. 记什么

每条记录必须包含这五项，缺项就写「未测」，不许留空也不许猜：

项说明
任务一句话说清做了什么，而不是「让它改代码」
环境Pi 版本、模型、thinking level、启用的工具
过程花了多久、几轮、触发了什么（压缩 / 重试 / 中止）
结果可用 / 部分可用 / 不可用，返工几次
结论下次要改什么

模板见 记录模板。

#3. 怎么拿到客观数字

不要凭感觉写「感觉挺快的」。三个可靠来源：

① 交互模式底栏与 /session

底栏实时显示 token / 缓存用量、花费、上下文占用；/session 给出会话文件、消息数、token 和成本。

② JSON 模式导出事件流

pi --mode json "任务描述" > run.jsonl 2>run.err
统计工具调用次数
jq -c 'select(.type == "tool_execution_start") | .toolName' run.jsonl | sort | uniq -c
看是否触发了压缩或重试
jq -c 'select(.type | test("compaction|retry"))' run.jsonl

用法见 JSON 模式。

③ 会话 JSONL 事后复盘

会话是 append-only 的树，模型切换、压缩、分支摘要都是显式条目。所以「这次为什么慢/为什么贵」可以事后查出来，不依赖当时的记忆。

格式见 会话文件格式。

想回答「为什么跑这么久」，先知道有哪些已知的耗时源

这些都是可查证的，不是猜测：

耗时源怎么确认
Agent 级自动重试默认 3 次，指数退避 2s/4s/8s（retry.baseDelayMs）；事件里有 auto_retry_start
Provider 要求的长延迟超过 retry.provider.maxRetryDelayMs（默认 60s）会直接失败并报错
上下文压缩每次压缩是一次额外的 LLM 调用，且不写 prompt 缓存
Split turn 压缩单个超长 turn 会生成两份摘要再合并
Prompt 缓存未命中开 showCacheMissNotices 后会在对话里提示

对应机制见 上下文压缩 和 设置 §7 重试。

#5. 诚实标注规则

沿用交接文档 §12 的强度规则，在这个板块尤其严格：

  • 没实际跑过的，标 未验证
  • 跑过但没测量的，标 未测量，不要写「大约快了一半」
  • 失败的记录必须保留——踩坑记录比成功记录更有说服力
  • 单次样本不能称为「提升了 X%」，只能写「单次观察」
