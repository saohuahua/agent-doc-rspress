下次开始新章节前先把 CLI 升到与源码同版本。

#从这组数字里能读出什么

① 4 条用户消息驱动 129 轮助手回合。 平均一条指令换来 32 轮自主工作。这是 Coding Agent 与普通 Chat 最直观的差距，也是回答面试问题 #1 时可以直接引用的实测比例。

② input 258，cacheRead 2378 万。 差了五个数量级。说明几乎全部上下文都命中了 prompt 缓存，真正当作新 input 计费的只有 258 token。这解释了长会话为什么没有想象中那么贵，也说明"token 总量"这个指标单独看没有意义——必须区分 input / cacheRead / cacheWrite。

③ 整场 0 次压缩。 2 小时、143 次工具调用、写了 5600 行，居然一次都没触发压缩。结合 ② 可以推断上下文始终没超过 contextWindow - reserveTokens（默认预留 16384）。 → 这意味着我还没有观察到压缩的真实行为，上下文压缩 那一页目前完全是读文档写的，属于未实跑验证。

④ 143 次工具调用里 bash 占 74 次。 一半以上是 shell。其中很大一部分是 grep/ls 这类查找——因为 grep、find、ls 三个内置只读工具默认没启用，模型只能用 bash 绕。 → 下次试试把 defaultTools 加上 grep/find/ls，看 bash 占比是否下降、是否更快。这是一个具体可做的对照实验。

⑤ 4 次工具报错，没有中断整体任务。 对应 Learn 03 讲的"错误回填给模型，模型自己决定下一步"——实测确实如此。

⑥ 中途换了 1 次模型、5 次 thinking level。 这两个动作在会话文件里是显式条目（model_change、thinking_level_change），所以事后可复盘。如果某段输出质量突然变差，可以定位到是哪次切换之后。

坑 2：自定义 provider 拿不到成本

成本统计显示 $0.0000，不是免费，是没有价格表。

models.json 里自建的 provider 不带定价信息，所以底栏和会话里的 cost 恒为 0。

直接后果：面试问题 #11「效率提升」如果想用"省了多少钱"来答，在当前配置下拿不到数据。要么改用官方 provider 跑对照实验，要么只用时间和 token 作为指标。这一条必须在写 interview/ 之前解决。

符号交接文档实际定义

streamAssistantResponse193281

agentLoop:31、getFollowUpMessages:263、prepareNextTurn:232、beforeToolCall:619 是对的。

#5. 尚未验证 / 尚未测量

明确列出来，避免以后误以为做过：

  • ❌ 官方 provider 的真实 Smoke 未跑（当前只用自建网关，且拿不到成本）
  • ❌ 压缩行为未实测（0 次触发）
  • ❌ 分支 / /tree / /fork 未实测（0 次分支摘要）
  • ❌ 自动重试未观测到（本次会话无 auto_retry 事件）
  • ❌ 效率对照实验未做（没有"手写 vs Pi"的同任务对比）
  • ❌ CLI 未升级到 v0.84.3
  • ⚠️ 本次数据只有一个样本，任何百分比结论都不成立

#6. 下一条记录要做的事

按优先级：

  1. 把 CLI 升到 v0.84.3，消除版本漂移
